131. **`evalSettings` is constructed at static-init time with a literal `LookupPathHooks` table that hard-wires it to `settings.readOnlyMode`.** The global in `libcmd/common-eval-args.cc` is initialised with a hard-coded `LookupPathHooks` table that calls `parseFlakeRef`, `fetchToStore`, and `state.allowPath`; it also takes `&settings.readOnlyMode` (from `libstore/include/nix/store/globals.hh`) by reference, hard-wiring two globals together. The `LookupPathHooks` registry should live on `EvalState` (added imperatively in `initNix` or by the embedder), and `EvalSettings::readOnlyMode` should query the active `Store`/`StoreConfig` rather than alias another global.
    - ../verified/15-libflake-libmain.md, ../verified/16-libcmd.md
    - **Validation:** VALID. `LookupPathHooks` is a `std::map<std::string, fun<LookupPathHook>>` member of `EvalSettings`; the `EvalSettings` constructor takes both `readOnlyMode` and `lookupPathHooks` as arguments — so the wiring is structural (cannot be constructed without both). Move to `EvalState::registerLookupPathHook(scheme, fun)` called from `initNix` or embedder setup. Compounds with #133. Effort: small.

132. **Cross-library settings globals are constructed in libcmd, not in the libraries that own the types.** `libcmd/common-eval-args.cc` defines `fetchSettings` (libfetchers), `evalSettings` (libexpr), `flakeSettings` (libflake), and `compatibilitySettings` (libcmd) as namespace-scope globals with their own `GlobalConfig::Register` lines. The owning libraries declare these as `extern`, but the storage and the registration both live in libcmd, forcing every libstore-only consumer to pull in libcmd just to link against the globals. Each library should own its own singleton (or, better, none at all — pass via context).
    - ../verified/16-libcmd.md
    - **Validation:** VALID. All four `extern` declarations live in `libcmd/include/nix/cmd/common-eval-args.hh`, **not** in their owning libraries' headers. Each owning header carries a `@todo Get rid of global settings variables` comment. Two paths: (a) each library owns its own singleton (mechanical, preserves global model) — trivial; (b) full DI via constructor injection — large/structural. **Pitfall:** `evalSettings` initialiser captures `settings.readOnlyMode` (#138) and registers a flake lookup hook (#131); moving requires resolving those entanglements first. Effort: trivial (decomposition only) / large (full DI).

133. **`flake::Settings::configureEvalSettings` is plugin registration smuggled into a `configure*` method.** The method in `libflake/settings.cc` (called from `nix/main.cc`) imperatively appends three primops to `evalSettings.extraPrimOps` — that is, a method on a settings type imperatively pushes entries into another settings type's vector. The right shape is an `EvalState::registerPrimOp(PrimOp)` call at process init, with libflake providing a `flake::registerPrimOps(EvalState &)` free function — no settings type required.
    - ../verified/15-libflake-libmain.md
    - **Validation:** VALID. The method takes a non-const `EvalSettings &` and pushes into the public `extraPrimOps` field — its name is misleading (configures nothing about settings). **Pitfall:** `primops::getFlake` captures `flake::Settings` by reference into the primop's function closure; moving the `flake::Settings` to per-EvalState requires the closure to capture from there too. With #131 done, `EvalSettings` ctor reduces to nothing extra. Effort: small.

134. **`Settings` privately inherits from four sibling settings groups via `: public virtual Config` only to namespace fields.** `Settings` in `libstore/include/nix/store/globals.hh` is a virtual-base diamond of `LocalSettings`, `LogFileSettings`, `WorkerSettings`, `NarInfoDiskCacheSettings`, exposed via `getLocalSettings()` / `getLogFileSettings()` / `getWorkerSettings()` / `getNarInfoDiskCacheSettings()` accessors that all just `return *this`. The inheritance has no behavioural purpose — it is purely a way to namespace fields and inherit `addSetting` registration through `Config`. The header even apologises for it ("we expose them from `settings` with `settings.getLocalSettings()` for now ... we would much prefer if you use [`localStore.config->getLocalSettings()`]"). Composition (a `Settings` that *holds* the four sub-configs and registers them via `addSetting` forwarding) would be both clearer and would let the per-store version of `LocalSettings` actually decouple.
    - ../verified/07-libstore-local.md
    - **Validation:** VALID. **Zero `dynamic_cast<LocalSettings*>` sites anywhere in the tree** — every consumer goes through `getLocalSettings()` etc. So the composition refactor is unblocked at the consumer side; only #136's constructor self-registration blocks it on the implementation side. **Pitfall:** external code (Hydra-like consumers) using `settings.someLocalField` directly — ABI breaks on the type but field syntax is preserved if accessors stay. Effort: medium (gated by #136; structural otherwise).

135. **`LocalSettings` multiply-inherits `GCSettings` and `AutoAllocateUidSettings` only for grouping in docs.** `GCSettings` and `AutoAllocateUidSettings` (`libstore/include/nix/store/local-settings.hh`) both `: public virtual Config` and contribute their own `Setting<T>{this, ...}` definitions; `LocalSettings` then multiply-inherits both. There's no polymorphism, no overrides, no methods — they're just struct namespaces. A flat `LocalSettings` with `gc_*`/`autoAlloc_*` field-name prefixes would be simpler. The same critique applies to `LogFileSettings` and `NarInfoDiskCacheSettings` in `globals.hh`.
    - ../verified/07-libstore-local.md
    - **Validation:** VALID. **Pitfall:** `getAutoAllocateUidSettings()` returns `nullptr` when `autoAllocateUids` is off, used by callers as a presence check; flattening would require those callers to read `autoAllocateUids` directly. Two options: (a) flatten — drop `GCSettings` and `AutoAllocateUidSettings`, inline their `Setting<T>` members into `LocalSettings` directly with `gc-`/`auto-allocate-` name prefixes (settings already have these prefixes in their `name` parameter); (b) composition (gated on #136). (a) is trivial after consumers stop calling `getGCSettings()`. Compounds with #134. Effort: small.

136. **`Setting<T>{this, ...}` constructor sneakily registers itself with `*this` config via `options->addSetting(this)`.** Each `Setting` member's constructor (`libutil/include/nix/util/configuration.hh`) writes a pointer to itself into the parent `Config::_settings` map. This makes `Setting<T>` non-trivially-relocatable, forbids copying or moving a `Config`, and forces the canonical heavy `Setting<T>{this, default, name, R"(doc)", aliases, xpFeature}` constructor invocation on every line. A two-phase approach — `Setting<T>` is a plain member, then a `void registerSettings()` method or a constexpr table iterates them at the end of `Config`'s constructor — would let settings be tabulated in a single static array per config (compounds with #19 and #21).
    - ../verified/03-libutil-runtime.md
    - **Validation:** VALID. **Keystone refactor.** Makes both `Setting<T>` and `Config` non-relocatable, non-movable, non-copyable: any moved-from `Config` has stale pointers in `_settings`. The specialisation `Setting<AbsolutePath>` does the same; `DeprecatedWarnSetting`/`PluginFilesSetting` do `options->addSetting(this)` manually. **Pitfall:** every existing `Setting` site (several hundred) gives `(this, default, name, doc, aliases, doc-default, xpFeature)` — flipping to a static descriptor list requires rewriting all of them or providing a `static constexpr` member-pointer-keyed view. Cross-cuts unblock #134, #135, #137, #149 (and likely #19/#21). Effort: large to structural.

137. **`GlobalConfig::Register` instances are scattered across 13 TUs (16 production register sites) and rely on link-order static-init.** Every settings struct gets a file-scope `static GlobalConfig::Register r…(&config);` instance. The production sites: `globals.cc`, `filetransfer.cc`, `archive.cc`, `fs-sink.cc`, `logging.cc`, `config-global.cc` (`rSettings` for `experimentalFeatureSettings`), four sites in `common-eval-args.cc` (`rFetchSettings`, `rEvalSettings`, `rFlakeSettings`, `rCompatibilitySettings`), `plugin.cc`, `develop.cc`, `nix-env.cc`, `unix/daemon.cc`, `upgrade-nix.cc`. Consolidating into an explicit `registerBuiltinConfigs()` call inside `initLibStore()`/`initLibUtil()`/`initNix()` (similar to how `initLibStore` already calls `loadConfFile(globalConfig)`) would make startup deterministic and let the order be documented.
    - ../verified/03-libutil-runtime.md, ../verified/15-libflake-libmain.md
    - **Validation:** PARTIALLY VALID. **Correction:** the production count is **15** sites, not 16 — the original "16 production" included one test-only site in `libutil-tests/nix_api_util.cc`. SIOF analysis: `configRegistrations()` is a Meyers singleton (function-local `static`), so the deque itself is SIOF-safe within one TU; the actual SIOF risk is link-order between TUs determining push order. **Pitfall:** `experimentalFeatureSettings` is registered before `loadConfFile` because `loadConfFile` consults the registry; ordering inside the explicit init function must respect that. Effort: small (after #136); medium (without #136).

138. **`settings.readOnlyMode` is plumbed into `EvalSettings` via a `bool *` reference field.** `EvalSettings::readOnlyMode` is a raw `bool *` aliasing `settings.readOnlyMode` (`libexpr/include/nix/expr/eval-settings.hh`, set up in `libcmd/common-eval-args.cc`); the comment says `FIXME: This really shouldn't be public. Compounds with #131. Effort: medium.

139. **`drvHashes` is a process-wide concurrent memo table outliving any `Store`.** `DrvHashes drvHashes;` in `libstore/derivations.cc` is a `boost::unordered::concurrent_flat_map<StorePath, DrvHashModulo>` keyed by store path but globally shared across stores. `pathDerivationModulo(Store & store, ...)` reads the cache without checking whether the cached entry came from a different store with a different `storeDir` — a latent correctness bug as well as a state-leakage problem. Move the memo onto `Store` (next to other per-store caches) so two stores with different `storeDir`s cannot poison each other.
    - ../verified/06-libstore-derivations.md
    - **Validation:** VALID. The header already carries `// FIXME: global, though at least thread-safe.` The cache is also written from `libexpr/primops.cc` (`builtins.derivation` evaluation) at `drvHashes.insert_or_assign`. **Pitfall:** the `libexpr` writer in `builtins.derivation` populates an entry from a derivation just constructed in-memory, *before* any `Store` write — that drv may be materialised later in a different store via `state.store` vs `state.buildStore`. **Per-EvalState (rather than per-Store) may be the more honest scope.** Effort: medium.

149. **`Config::_settings` map values are non-owning `AbstractSetting *` pointers tied to the parent `Setting` member's lifetime.** `Config::_settings` (`libutil/configuration.cc`) is a `map<name, {isAlias, AbstractSetting *}>`; the pointer must outlive the map, which is enforced only by both being members of the same `Config`.     - ../verified/03-libutil-runtime.md
    - **Validation:** VALID. Compounds with #136. **Mechanism:** the `created = 123;` debug field on `AbstractSetting` is a sentinel-style integrity check (catches use-after-free of a moved-from setting). Switch `Config::_settings` to value storage — `std::map<name, std::variant<Setting<bool>, ...>>` or a type-erased `std::map<name, std::unique_ptr<AbstractSetting>>` where the `Config` owns settings outright and `Setting<T>` "members" become non-owning views. **Pitfall:** the public API (`Setting<T>::operator T()`, `set`, `get`) is exercised everywhere via field syntax (`settings.foo.get()`); any storage rework must preserve that surface. Effort: structural.
