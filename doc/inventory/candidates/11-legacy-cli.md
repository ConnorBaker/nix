They differ only in that `nix-env`'s carries a `Globals&` argument while `nix-store` uses a file-scope `static std::shared_ptr<Store> store`. Both also duplicate the "set `op` from flag, throw if set twice" loop. A shared `LegacySubcommandTable<Ctx>` helper would consolidate both.

Four hand-roll an inline `{ {"name", []() { return make_ref<...>(); } }, ... }` factory list instead: `CmdRegistry` (`registry.cc`, 5 children), `CmdProfile` (`profile.cc`, 8 children), `CmdKey` (`sigs.cc`, 2 children), `CmdHash` (`hash.cc`, 7 children — `to-base16/32/64/sri` factories carry a `HashFormat` argument). Three of the four inline-style ones (`CmdRegistry`, `CmdProfile`, `CmdKey`) could trivially switch to `getCommandsFor` plus `registerCommand2` per child; `CmdHash` is the only one whose factories pass non-trivial constructor arguments and would need a more general "registry-with-args" mechanism.
    - ../verified/17-nix-modern-1.md, ../verified/18-nix-modern-2-legacy.md

Effort: small (three of four) / medium (`CmdHash`).

222. **`--max-freed` parses as `int64_t` then clamps via `std::max(..., 0)` before assigning to `uint64_t`.** Both `nix-store --gc --max-freed N` (`nix/nix-store/nix-store.cc::opGC`) and `nix-collect-garbage --max-freed N` (`nix/nix-collect-garbage/nix-collect-garbage.cc::main_nix_collect_garbage`) parse the argument with `getIntArg<int64_t>(...)` and assign `options.maxFreed = std::max(getIntArg<int64_t>(...), (int64_t) 0)`. `GCOptions::maxFreed` (in `libstore/include/nix/store/gc-store.hh`) is `uint64_t`, defaulting to `uint64_t`'s maximum (the "no limit" sentinel). The clamp's only effect is on *negative* inputs: `--max-freed -1` parses to `-1` (`string2Int<int64_t>` does not reject the leading `-` for a signed type), then `std::max(-1, 0)` yields `0`, which `gc.cc`'s WholeStore handler treats as "free nothing" (a near-no-op collection, the strictest cap) — not "disable the cap". Values above `INT64_MAX` do *not* reach the clamp: `boost::lexical_cast<int64_t>` rejects out-of-range input by throwing (it does not wrap), so over-range already errored at parse on master. Parse as `uint64_t` directly via `getIntArg<uint64_t>(...)` and drop the `std::max` clamp — negatives then error at parse, and the full `uint64_t` range above `INT64_MAX` becomes honourable. Fix is one-line at each of the two call sites. (Corrected per the 2026-05 audit, finding F002: the prior body's "overflow to negative -> clamp -> silently disables" mechanism was wrong on every step.)
    - ../verified/18-nix-modern-2-legacy.md
    - **Validation:** VALID. Pre-existing oddity surfaced by Pass-B reuse review of #128's `getIntArg` parameter cleanup. Both call sites are mechanical edits; `getIntArg<uint64_t>` works fine because `string2IntWithUnitPrefix<uint64_t>` accepts only non-negative values (rejects the leading `-`). Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libmain` (both call sites switched to `getIntArg<uint64_t>(...)` with the `std::max` clamp dropped; user-visible behaviour change for negative or out-of-range values: previously `--max-freed -1` clamped to `0` (a no-op collection), now it errors at parse time, and `--max-freed N` above `int64_t::max()` is now honoured up to `uint64_t::max()`. **Audit correction (F002):** the rl-next entry `max-freed-clamp.md` and this Branch note formerly described the old `-1` behaviour as "silently disabled the cap" and advised users to "drop the flag entirely instead" — both wrong: old `-1` was a no-op GC (strictest cap), and dropping the flag performs an *unbounded* GC. The rl-next prose was rewritten; the underlying code change is correct and unaffected. **Coverage gap (Pass-4 review):** the negative-value error path has no functional-test coverage — the existing `--max-freed` tests use positive values only. A regression that re-introduced the clamp behaviour would not be caught.).

231. **`nix-env --priority` open-codes the `getArg`+`string2Int` pattern that `getIntArg<N>` was meant to encapsulate.** [LOW] After libmain #223 turned `getIntArg<N>` into a one-line wrapper around `getArg(opt, i, end)` + `string2IntWithUnitPrefix<N>(...)`, exactly one in-tree CLI-arg-parse site still hand-rolls the same advance + end-check + parse: `src/nix/nix-env/nix-env.cc::opInstall` (the `--priority` arm). It does manual end-check, throws `UsageError("'%1%' requires an argument", arg)`, then `priority = string2Int<int>(*i++)` followed by another `UsageError` if the parse returned `nullopt`. It cannot use `getIntArg` directly: `getIntArg` calls `string2IntWithUnitPrefix<N>` (which accepts `K`/`M`/`G` suffixes that don't make sense for a profile priority) and throws on bad input, whereas `opInstall` wants `string2Int` (no unit prefix) with explicit `nullopt`-handling. **Do NOT use `getArg(arg, i, opFlags.end())` here (F001):** `getArg` pre-increments the iterator (`++i` first), but `opInstall`'s loop already advanced past the flag via `auto arg = *i++`, so the iterator points *at the value* on arm entry — `getArg` would skip the value and throw "requires an argument" on every invocation. The correct helper is the file-local `needArg(i, opFlags, arg)`, which has *no* leading increment (matching the `*i++` loop idiom) and is already used at sibling sites; the fix is `priority = string2Int<int>(needArg(i, opFlags, arg))`. Pre-existing oddity surfaced by libmain reviewer in the holistic-review pass; the `getArg` mis-recommendation and the original `opSetFlag` misnomer were corrected by the 2026-05 audit.
    - ../verified/18-nix-modern-2-legacy.md
    - **Validation:** VALID. The fix is mechanical at the single call site. **Post-Batch-G adversarial review:** the original framing also offered "optionally accompanied by a sibling `getIntArgNoUnit<N>` template if a second similar caller appears" — that framing has been **dropped** because it is exactly the speculative-public-API-with-no-second-caller pattern that drove the libutil #163 revert. Ship the conservative form (inline `getArg` substitution at the one site); a `getIntArgNoUnit<N>` template can be re-considered only when an actual second caller materialises. **See also:** #128 (the original `allowUnit` parameter deletion), #223 (the wrapper refactor that surfaced this), libutil #163 revert (the speculative-API anti-pattern). Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/nix-cli` (replaced the inline end-check + iterator advance + `UsageError` throw in `opInstall`'s `--priority` arm with a single helper call; kept the `string2Int<int>(...)` parse + `nullopt`-check unchanged. **Audit correction (F001):** the first landing (`ffb5ea72b`) used `getArg(arg, i, opFlags.end())`, which was a *regression* — `getArg` pre-increments, but `opInstall`'s `auto arg = *i++` loop had already advanced past the flag, so the value was skipped and every `nix-env -i --priority N pkg` threw "'--priority' requires an argument" (test-covered by `tests/functional/user-envs-test-case.sh`). The 2026-05 audit fixed it to `needArg(i, opFlags, arg)` — the file-local helper with no leading increment, matching the `*i++` loop idiom and already used at sibling sites — restoring master semantics and the identical diagnostic. 236. **`CmdHash` is the only `getCommandsFor`-eligible `NixMultiCommand` that can't migrate without a registry-with-args mechanism.** [LOW] #93 migrated `CmdRegistry`/`CmdProfile`/`CmdKey` to the `getCommandsFor` pattern but explicitly deferred `CmdHash`. Two paths: (a) split `CmdHash` into a per-format subclass family (`CmdHashBase16`, `CmdHashBase32`, …), each registered via `NIX_REGISTER_COMMAND`, with the `HashFormat` passed via a virtual; (b) extend the registry to support `getCommandsForWithArgs<Args...>(name, factoryArgs)` so the per-format `HashFormat` argument flows through registration. (a) is the cheaper substitution and matches the existing CLI shape; (b) is the more general mechanism and would also unlock any future "registry-with-runtime-args" caller. **See also:** #93 (the parent migration that deferred this), #24 (`registerCommand<...>` boilerplate), #93's Branch line for the explicit deferral. Effort: small under (a); medium under (b).
    - ../verified/18-nix-modern-2-legacy.md
