# Dispatch tables and schemas (plus other pass-2 candidates)

Candidates N26, N27, N30-N38, N40, N42-N44. Cluster G is **the catalog's
broadest cross-cutting pattern**: every subsystem has a dispatch table
that's hand-coded, with at least one parallel hand-coded table elsewhere
that should agree. The architectural direction is "schema as data, not
code", with `boost::describe` (U10) as the canonical implementation
choice. This cluster compounds across A1-A6 (architectural debt themes):
a dispatch-table is settings (A5), protocols (A6), value types (A1), or
fingerprints (A7) depending on what's being dispatched.

This section also collects pass-2's other production-code candidates
(N27, N31, N33, N34, N42, N43) that didn't fit the C-API or
test-infrastructure clusters.

N26. **Three parallel typed-attribute extractors with no shared backend abstraction.** Three separate typed-attribute helper families exist for three "key/value bag" backends: `nix::fetchers::Attrs` (`libfetchers/attrs.cc`, helpers `getStrAttr`/`getBoolAttr`/`getIntAttr`/`maybeGetStrAttr`/`maybeGetBoolAttr`/`maybeGetIntAttr`/`getHashAttr`); `StringMap` + `StructuredAttrs` (`libstore/derivation-options.cc`, helpers `getStringAttr`/`getBoolAttr`/`getStringSetAttr` plus private static fns); `nlohmann::json` (`libutil/json-utils.hh`, helpers `getString`/`getInteger<T>`/`getObject`/`getArray`/`getStringList`/`getStringMap`/`getStringSet`/`valueAt`/`optionalValueAt`). Each family has a "required" version that throws on missing, an "optional" version returning `std::optional<T>`, a typed coercion (`getIntAttr` does `string2Int`, `getInteger<T>` validates the JSON number), a diagnostic that mentions key + expected type + surrounding context. The pattern is the same; the backends differ. `derivation-options.cc::getStringAttr` hand-rolls `env.find(name)` plus a `parsed->find(name)` fallback — exactly the kind of "the same operation in two places" the catalog targets.
- **Validation:** VALID. A `TypedAttrSource<Backend>` concept (or class template) requiring `Backend::find(name)` and `Backend::iter()`, parameterised on the value type and providing the required+optional+throwing-with-diagnostic shape. Each of the three backends becomes a `TypedAttrSource<Attrs>`, `TypedAttrSource<MergedSlot<StringMap, StructuredAttrs>>`, `TypedAttrSource<json>` instance. The typed coercion (`string2Int`, `string2Float`, `parseHashAlgo`, etc.) becomes a `Coerce<T>` family of free functions that the backend-side just dispatches into. **Compounds with N11 (the iterate-attrset plumbing — N26 is the inner typed coercion layer underneath). Supersedes the catalog's implicit duplication observation in #114.** Effort: medium.

N27. **The `*Impl : *` factory pattern is 13+ instances of one shape.** Header/impl split where header carries `struct Foo { virtual ~Foo() = 0; ... };` and `.cc` carries `struct FooImpl : Foo { ... };` plus `ref<Foo> makeFoo(args)` factory returning `make_ref<FooImpl>(...)`. Independent grep finds ~13 such pairs: `MountedSourceAccessorImpl`, `NarAccessorImpl`, `InterruptCallbackImpl`, `AllowListSourceAccessorImpl`, `InputCacheImpl`, `CacheImpl` (libfetchers), `GitRepoImpl`, `GitFileSystemObjectSinkImpl`, `DummyStoreImpl`, `NarInfoDiskCacheImpl`, `AwsCredentialProviderImpl`, `DerivationBuilderImpl`, plus `CachingSourceAccessor`. In *most* of these cases the abstract base has a single implementation. The "abstract base + Impl" layer is purely a compilation-firewall device (and a way to express "factory returns ref-counted, member type is opaque to callers"). It is not polymorphism — `make*` always returns the one `*Impl`. A more direct shape would be free-function-over-opaque-handle.
- **Validation:** VALID. **Coding rule:** when an abstract base has exactly one `Impl` subclass and no plans for a second, prefer the opaque-handle + free-function shape over the abstract-base + Impl shape. For sites where polymorphism is genuine (multiple Impls per base — e.g. `SourceAccessor`, `Store`, `Sink`), the existing shape is fine. **Compounds with N7 (the SourceAccessor factories overlap this for the SourceAccessor subset), N10 (Connection types).** Effort: medium (rule + inventory) / large (migrate the single-Impl bases to opaque-handle).

N30. **The `MixJSON` / `bool json` / per-command if-else dispatch recurs in ~25 sites.** `MixJSON` (libmain) declares `bool json = false`. Each modern `nix` subcommand inheriting `MixJSON` then has its `run()` body branch on `if (json) { ... emit JSON ... } else { ... emit text ... }`. Independent grep finds ~25 sites with `if (json) {` over the modern CLI: `src/nix/eval.cc`, `path-info.cc`, `develop.cc`, `flake.cc` (10+ separate sites), `prefetch.cc`, `search.cc`, `profile.cc`, `ls.cc`, `build.cc`, `log.cc`, `config.cc`, `why-depends.cc`, `store/info.cc`, `derivation/show.cc`. Each command (1) declares its own JSON-encoder lambda or inline JSON construction, (2) branches on `json` and emits text *or* JSON, (3) calls `printJSON(j)` (from `MixPrintJSON`) for the JSON branch. The duplication is the *bifurcated output formatter*. Each command hand-rolls "format-as-text" and "format-as-JSON" twice. The catalog notes #92 (cat/ls) and #94 (BuiltPath/SingleBuiltPath) but doesn't name the wider issue.
- **Validation:** VALID. An `OutputFormat<T>` trait — given a `T`, declares both `to_json(T)` and `to_text(T)` — would let `MixJSON::run` dispatch in one place. The 25 commands collapse onto one decision: `if (json) printJSON(toJson(result)); else logger->cout("%s", toText(result));`. **Compounds with #73 (json-vs-text dual output paths in commands), #92 (cat/ls cmd duplication); extends the catalog's coverage of `nix` CLI duplication. See also:** Cluster G, U10. Effort: medium.

N31. **The 7 `*-cache` SQLite caches all encode versions in filenames; orphaned caches are never cleaned up.** N13 names the SQLite-cache base shape but doesn't articulate the *filename-versioning* pattern's safety hazard. Each SQLite cache encodes its schema version in the filename, *not* in `PRAGMA user_version`: Eval cache (`eval-cache-v6/<fp>.sqlite`), Binary cache (`binary-cache-v8.sqlite`), Fetcher cache (`fetcher-cache-v4.sqlite`), Tarball cache (`tarball-cache-v2/`), Local store schema (`<store>/var/nix/db/schema` integer file), GC roots (no version), Build hook log (no version). The bumping protocol on schema change is "create a new directory with the new version suffix; old directory is orphaned". This means **old caches stay on disk forever — there is no cleanup**. The right shape is a single `~/.cache/nix/` cleanup pass that knows all the cache schema versions; today there is no such pass.
- **Validation:** VALID. A single `CacheRegistry` enumerating all SQLite caches with their schema version + path constructor. Plus a `nix store gc-caches` (or extend `nix store gc`) that walks the registry and deletes caches where the on-disk version is older than the current. This is part of the broader N13 candidate but is independent enough to warrant its own candidate — the "old caches never cleaned up" hazard is a separate latent bug from the "no shared base" abstraction. **Compounds with N13; supersedes #168 (which notes the magic numbers; this names the underlying mechanism). See also:** A5, Cluster D. Effort: small (registry + comment) / medium (also write the gc-caches pass).

N32. **Three+ parallel typed (parse, show) symmetric pairs without convention.** The codebase has many `parseX` / `showX` (or `printX`) function pairs that go enum/struct-to-string and back, with no shared API style: `HashAlgorithm` (`parseHashAlgo`/`printHashAlgo`), `HashFormat` (`parseHashFormat`/`printHashFormat`), `CompressionAlgo` (`parseCompressionAlgo`/`showCompressionAlgo`), `ExperimentalFeature` (`parseExperimentalFeature`/`showExperimentalFeature`), `SandboxMode` (`BaseSetting<SandboxMode>::parse`/`to_string`), `ContentAddressMethod` (`parse`/`render`), `BuildResult::Status` (table → `buildResultStatusTable`), `LogFormat` (`parseLogFormat`/none), `Verbosity` (settings/`showVerbosity`?). The split is: *some* use `parse*`/`print*` (libutil-data); *some* use `parse*`/`show*` (libutil-runtime); *some* use member functions; *some* use `BaseSetting<T>::parse`/`to_string`. The catalog has #97 (`parseHashFormat`/`parseHashAlgo` parser) but doesn't name the *parse-show pair* pattern as duplication.
- **Validation:** VALID. A `nix::Stringly<T>` concept + uniform `parse<T>(string_view)` / `to_string(T)` family, possibly implemented via `boost::describe` / `boost::pfr` descriptor tables (so the table is the source of truth; the parse and show are derived). C++23's `std::format` integration makes this even cleaner: every `Stringly<T>` is automatically formattable. **Extends #97; compounds with N15 (versioned formats also need parse/show), N26 (typed extractors share the `Coerce<T>` need). See also:** Cluster G, U10. Effort: medium.

N33. **The 16 friend declarations in `eval.hh` are AST/EvalState coupling and concrete evidence the decomposition is overdue.** Independent grep verifies `eval.hh` has 16 `friend` declarations. Of these: 11 are `friend struct Expr*` AST node lines (`ExprVar` ×2 — one duplicate, plus `ExprAttrs`, `ExprLet`, `ExprOpUpdate`, `ExprOpConcatLists`, `ExprString`, `ExprInt`, `ExprFloat`, `ExprPath`, `ExprSelect`); 3 are `friend void prim_*` primops (`prim_getAttr`, `prim_match`, `prim_split`); 2 are `friend struct Value`/`friend class ListBuilder` (11+3+2 = 16). The pattern indicates that `EvalState` has private state that the AST nodes and primops must read/write directly. This is the "context object too big" smell of N19 at the *member-access* level: the AST → EvalState coupling is via 11 friend lines (10 distinct names), each spelling one piece of internal data the AST needs to touch. (Counts corrected from "10 lines / 9 distinct" per the 2026-05 audit, F013.)
- **Validation:** VALID. The right factoring is `EvalContext` / `EvalMemory` / `PrimOpHelpers` collaborators (#169, #210, #217 each names one slice). The friend list shrinks to 0 because the needed access becomes public (or via collaborator references). **Compounds with #169, #210, #217, N19. See also:** A1. Effort: structural (multi-PR; same as N19 / #210 in scope).

N34. **The `*Cache` clearing protocols use four+ different invalidation idioms.** The codebase has several cache-invalidation protocols, each rolled differently: `EvalCache` (libexpr) — schema-version-in-filename + read-mostly + `try { ... } catch (SQLiteError &) { disable; }` per-operation; `Cache` (libfetchers) — same shape but *different* doSQLite protocol (silent-disable on error vs. throw); `NarInfoDiskCache` — `LastPurge` row + per-cache TTL; `EvalState::importResolutionCache` — purely in-memory `concurrent_flat_map`, no invalidation; `drvHashes` global — purely in-memory, no invalidation; `GitArchiveCache` — TTL-driven (settings `tarball-ttl`, "if older than 24h refetch"). Six caches; six invalidation protocols. There is no shared `Cache<K, V, InvalidationPolicy>` template. The `try-catch-disable` half is covered by N13; the *invalidation-policy* half is not.
- **Validation:** VALID. A `CachePolicy<TTL=never, Schema=v0>` policy template plus an `InvalidationStrategy` enum (`OneShot`, `TTL`, `OnError`, `OnSchemaChange`) could replace the six protocols with one shape where the one differing axis is named explicitly. **Compounds with N13's `SqliteCache<Schema>` template; N34 adds the invalidation axis. See also:** #71 (TTL+present-bit shape), Cluster D. Effort: medium.

N35. **The 7-9 X-macros for "list of names" share the X-macro discipline gap.** The codebase has multiple X-macros that emit "list of names" boilerplate, each implemented inconsistently: `NIX_VALUE_STORAGE_FOR_EACH_FIELD` (`value.hh`) — drives the Value layout discrimination, recurs in 4-5 expansions; `NIX_FOR_EACH_COMPRESSION_ALGO` (`compression-algo.hh`) — drives the algo enum + parser + JSON serialiser; `NIX_FOR_EACH_LA_ALGO` (`compression.cc`, file-private) — drives libarchive algo dispatch; `JSON_IMPL` / `JSON_IMPL_INNER` (`json-impls.hh`); `NIX_DECLARE_CONFIG_SERIALISER(T)` (`configuration.hh`). Each is hand-rolled; each has its own discipline (some are `#define X(...) __VA_ARGS__`, others are `#define X(MACRO) MACRO(name, ...)`). The choice of style is inconsistent. With `boost::describe` (U10), each list becomes `BOOST_DESCRIBE_STRUCT(...)` and every consumer derives from the descriptor.
- **Validation:** VALID. Standardise the X-macro shape (always `X(MACRO)` form), document where each is used, then incrementally migrate to `boost::describe` once U10 lands. **Compounds with N22 (parallel observation that "macros emitting struct declarations" exist in equal number); depends on U10 (boost.describe) for the migration target. See also:** #43, #9. Effort: medium (X-macro discipline cleanup) / large (full boost.describe migration).

N36. **The 14 `make*Sink` factories have no common Sink-construction trait.** Independent grep finds these `make*Sink`-shaped factories in libutil/libstore: `makeCompressionSink(algo, sink)`, `makeDecompressionSink(algo, source)`, `makeFileSink(path)` (implicit), `makeStringSink()` (`StringSink` struct, no factory), `makeMemorySink()`, `makeTeeSink(a, b)` (implicit), `makeNullSink()`, `makeLengthSink(inner)`, `makeRefScanSink(refs)`, `makeRewritingSink(rewrites, inner)`, `makeHashModuloSink(...)` (composes Rewriting + Hash), `makeHashSink(algo)`, `makeFdSink(fd)`, the Brotli + Xz + Zstd compression-sink families. Some are factory functions; some are exposed as `SubclassSink<...>` constructors. There is no convention for "how to construct a Sink". N6 names the *side-channel observer* pattern but the construction question is orthogonal.
- **Validation:** VALID. A `SinkSpec` variant for the common cases (Compression, Hash, RefScan, Tee, Length, Null, String); a `makeSink(SinkSpec)` factory. **Compounds with N6, #38 (Sink/Source hierarchy). See also:** Cluster G. Effort: small (variant + factory) / medium (migrate sink construction sites).

N37. **Three+ "magic file headers" share no shape.** The codebase has multiple magic-byte headers used to identify on-wire / on-disk formats: `narVersionMagic1 = "nix-archive-1"` (string-magic, NAR), `exportMagic = NIXE` (4-byte tag, `nix-store --export`), `xz`/`bzip2`/`gzip`/`zstd`/`brotli` magic bytes (used by `getCompressionMethod` to dispatch by file suffix), `git tree`/`git blob` magic (`blob ...\0` prefix), `pack:` prefix (protocol version negotiation), the `0x01000000` magic in length-prefixed proto helper. Six magic markers; six implementations. No `MagicHeader<Tag>` shared trait. N15 names the *version* aspect; the magic-marker aspect is adjacent.
- **Validation:** VALID. A `MagicHeader<...>` trait — given a tag, provides serialise/parse with consistent error message. **Compounds with N15 (versioned formats — magic markers without version are a parallel observation). See also:** Cluster G. Effort: small.

N38. **The 9+ `extern template` instantiation lists are duplicated between header and .cc.** Several headers carry `extern template` declarations to opt out of implicit instantiation for compile-time savings. Each implementation file then `template ... ;`-instantiates the same list: `src/libutil/include/nix/util/strings.hh` (4 instantiations of `concatStringsSep` for `std::list`/`StringSet`/`std::vector`/`small_vector`); `src/libstore/include/nix/store/length-prefixed-protocol-helper.hh` (similar pattern for `vector<T>`/`set<T>`/`tuple<...>`/`map<K,V>`); the `BaseSetting<T>::parse` family in `configuration.hh`; the `WorkerProto::Serialise<T>` / `ServeProto::Serialise<T>` template specialisations in `worker-protocol-impl.hh`. Each header declares a list; each .cc echoes the same list; drift between the two halves is silently a build error or (worse) silent implicit instantiation.
- **Validation:** VALID. An `EXTERN_TEMPLATE_LIST(T, ...)` macro in each of the affected headers, paired with `INSTANTIATE_TEMPLATE_LIST(T, ...)` in the corresponding .cc. Or — more aggressive — a `boost::describe`-backed list that both halves derive from (also what N35 / U10 unblocks). **Compounds with #1, #3 (proto specialisation), N35. See also:** U10. Effort: small (macro) / medium (full migration).

N40. **Per-`InputScheme` URL-query handling is the same loop four times — and a latent drift hazard between URL parser and `allowedAttrs`.** A refinement of N12. Independent grep of the `InputScheme` URL-parser bodies confirms 4 schemes do nearly identical URL-query iteration: `path.cc::PathInputScheme::inputFromURL` (validates against `{rev, narHash, revCount, lastModified}`), `git.cc::GitInputScheme::inputFromURL` (validates against `{rev, ref, ...}`), `mercurial.cc::MercurialInputScheme::inputFromURL` (validates against `{rev, ...}`), `github.cc::GitHubInputScheme::inputFromURL` (and `GitLab`, `SourceHut` siblings). Each loop has a hardcoded allow-list, hand-spelled per scheme. The allow-list is *also* expressed in `allowedAttrs()` — but as a `std::map<string, AttributeInfo>` rather than as a set. **The same allow-list is encoded twice per scheme** (URL parser allow-list + `allowedAttrs` map), with no compile-time check that the two agree. This is the *latent bug hiding inside duplication* the catalog targets.
- **Validation:** VALID. As N12 names, the `attribute_schema<Scheme>` descriptor would unify the URL-parser allow-list with the `allowedAttrs` map. This candidate names the latent-bug payoff explicitly; N12 names the cleanup direction. **Sibling of N12; refines the latent-bug claim. See also:** Cluster G. Effort: medium (depends on N12 / boost.describe migration).

N42. **The "atomic ID counter" pattern recurs five times.** Five separate places have a `static std::atomic<T> counter{0}` (or similar) used to mint unique IDs: `src/libutil/source-accessor.cc::nextNumber{0}` — process-global `SourceAccessor` ID counter (used by `operator==`/`<=>`); `src/libutil/logging.cc::nextId{0}` — process-global activity ID counter; `src/libutil/file-system.cc::counter` — random-seeded for unique tempfile names; `src/libstore/local-binary-cache-store.cc::counter{0}` — for a retry/backoff loop counter; `src/libstore/unix/build/linux-derivation-builder.cc::counter{0}` — for unique sub-uid allocation. Plus the implicit `Counter::inner` in libexpr (a different shape — per-instance counter, not ID minting). There is no shared `IdGenerator<T>` or `mintId()` helper. Each site re-rolls the same idiom (`counter.fetch_add(1, std::memory_order_relaxed)`) — sometimes with `relaxed`, sometimes without specifying memory order.
- **Validation:** VALID. An `IdGenerator<T = uint64_t>` class template providing `next()` with documented `memory_order` discipline. Or a free function `mintId<Tag>()` that emits a distinct counter per `Tag` template parameter. **Compounds with N21 (the broader counter pattern). See also:** R8. Effort: small.

N43. **Six+ subsystems own their own `std::thread` member with hand-rolled lifecycle — `std::jthread` migration target.** Each subsystem that owns a worker thread declares the thread + a flag + an interrupt mechanism + a join-on-destruct sequence inline. There is no shared `WorkerThread` helper. Subsystems: `progress-bar` (`std::thread updateThread`, join in stop()); `Pid` (libutil) (`std::thread killThread`, join in dtor); `MonitorFD` (unix) (`std::thread thread`, join in dtor); `curlFileTransfer` (`std::thread workerThread`, join + condvar + flag); `gc.cc::serverThread` (join + listener); `PathSubstitutionGoal::thr` (join + state machine); `DerivationBuilderImpl::daemonThread` (join after kill). Six+ instances of the same shape. C++20 has `std::jthread` which provides this exact lifecycle (interrupt + join-on-destruct via `std::stop_token`); the codebase has chosen not to use it. This is "hand-rolled abstractions where stdlib already has it" — the `std::jthread` exclusion is undocumented; each site rolled its own.
- **Validation:** VALID. Migrate to `std::jthread` where the "kill via stop_token" semantics suit (most sites). For the curl transfer thread (which has a complex ready/wait/dispatch cycle), a `WorkerThread` wrapper around `std::jthread` exposing `notify()` + stop-token may be cleaner. **Compounds with N8 (the async-idiom axis is parallel to the thread-management axis), R10. See also:** A2. Effort: medium.

N44. **The `BaseSetting<T>::trait` specialisation pattern is ad-hoc and three-layered.** `BaseSetting<T>` (libutil-runtime) is the per-T specialisation site for setting parsing/serialisation. The specialisation pattern has *three* shapes: (1) `parse`/`to_string`/`appendOrSet` — defined per `T` outside the class body; used by `BaseSetting<SandboxMode>` (`globals.cc`), `BaseSetting<PathsInChroot>` (`globals.cc`), `BaseSetting<StoreReference>` (`store-reference.cc`), `BaseSetting<CompressionAlgo>` (`compression-settings.cc`), `BaseSetting<std::optional<CompressionAlgo>>` (same). (2) `trait` static-member — when a setting overrides `appendable` (i.e. supports `+=`), `BaseSetting<T>::trait::appendable = true` is declared explicitly. Currently `BaseSetting<PathsInChroot>::trait` does so; #56 names the placement question. (3) `NIX_DECLARE_CONFIG_SERIALISER(T)` macro — declares the `parse`/`to_string` *signatures* in a header so consumers can rely on them being there. These three layers don't compose cleanly: nothing forces all three to land together. #56 is the latent-bug example (the `trait` specialisation lived in a .cc and was missed by some TUs).
- **Validation:** VALID. A `SettingTrait<T>` concept-constrained class template that bundles `parse` + `to_string` + `appendable` + `default_value` would collapse the three layers. **Compounds with N4 (the X-macro setting struct definition) — every per-T specialisation could be co-located with the setting declaration. See also:** #19, #43, #56, #136. Effort: medium.
