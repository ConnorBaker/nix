96. **Three sibling base-N encoders with parallel-but-not-shared APIs.** `nix::base16`, `nix::base64` (namespaces with free functions in `base-n.{hh,cc}`) and `nix::BaseNix32` (a struct with static methods in `base-nix-32.{hh,cc}`) each expose `encode(std::span<const std::byte>)`, `decode(std::string_view)`, `encodedLength(size_t)`, but the shape is structural-only — the alphabet tables (`base16Chars`, `base64Chars`, `BaseNix32::characters`) and inverse tables (`base64DecodeChars` constexpr lambda; `BaseNix32::reverseMap` static member; base16 hand-coded `parseHexDigit`) are independently constructed, and one is a namespace, one a struct. The closest factoring is the `decltype(base16::decode) *` function-pointer trick used inside `Hash::parseLowLevel`. A shared `BaseN<Alphabet>` template (or a namespace-of-namespaces with conforming names) would unify all three.
    - ../verified/02-libutil-data.md
    - **Validation:** VALID. **Caveat:** touches a hot path (hash parsing) and a load-bearing function pointer (`decltype(base16::decode) *` is used in `Hash::parseLowLevel`/`baseExplicit`/`parseAnyHelper`); needs careful benchmarking. Encode/decode logic is shaped by alphabet bit-width (4/5/6) and Nix32's reversed-byte order, so a single template needs strategy parameters. Effort: medium.

97. **`parseHashFormat`/`parseHashAlgo` use the Opt-plus-throwing-wrapper idiom; `parseCompressionAlgo` does not.** In `hash.cc`, `parseHashFormatOpt`/`parseHashAlgoOpt` return `std::optional<…>` via if-chains, and `parseHashFormat`/`parseHashAlgo` are four-line wrappers that re-throw `UsageError`. By contrast, `parseCompressionAlgo` in `compression-algo.cc` is a single throwing function built from the `NIX_FOR_EACH_COMPRESSION_ALGO` X-macro plus a `Suggestions::bestMatches` lookup. Three near-identical "named-enum parser" implementations with no common helper; consolidating on a `parseEnumOpt<E>(string_view) -> optional<E>` plus a generic throwing wrapper (with optional suggestions) would eliminate the divergence.
    - ../verified/02-libutil-data.md
    - **Validation:** VALID. `magic_enum` (header-only) is **not** in tree; introducing it would cover this cleanly. Effort: small.

98. **`dropEmptyInitThenConcatStringsSep` is `[[deprecated]]` but still load-bearing.** The header declares it `[[deprecated("Consider removing the empty string dropping behavior. If acceptable, use concatStringsSep instead.")]]`, yet `strings.cc` still has explicit `template` instantiations for `std::list<std::string>`, `StringSet`, and `std::vector<std::string>`. The function differs from `concatStringsSep`/`basicConcatStringsSep` only in its `if (s.size() != 0) s += sep;` test, which suppresses the separator before the first non-empty element. The TODO comment in `strings-inline.hh` explicitly flags that the contract is not enforced. Either remove the function or assert `!i.empty()`; the deprecation has been silently ignored.
    - ../verified/02-libutil-data.md
    - **Validation:** VALID. Five callers remain: `libflake/config.cc` (with `// FIXME: evil`), `nix/profile.cc`, `libstore-tests/references.cc`, `libexpr/eval-cache.cc`, `libexpr/attr-path.cc`. **Semantic:** body differs from `concatStringsSep` only by `if (s.size() != 0) s += sep;` — so an empty after the first non-empty would still produce a separator (NOT naive "drop all empties"); the in-body assertion to enforce non-emptiness is commented out. `attr-path.cc` and `eval-cache.cc` join `Symbol`/value lists where empties shouldn't occur (safe to switch); the flake-config and `profile.cc` cases need verification. Migrate, then delete the function and the three explicit instantiations. Effort: small.

99. **Brotli compression and decompression sinks share an identical `finish()` shape.** In `compression.cc`, `BrotliCompressionSink::finish()` and `BrotliDecompressionSink::finish()` both consist of `flush(); writeInternal({});` — the empty `writeInternal` call is the codec's "drain" idiom. `NoneSink::finish()` is just `flush()`; `ArchiveCompressionSink::finish()` is `flush(); check(archive_write_close(archive));`; `ZstdMultiFrameCompressionSink::finish()` is `flush(); if (!inbuf.empty() || !emittedAnyFrame) emitFrame();`. The `flush()`-then-trailer pattern is uniform; the Brotli pair specifically could share a `ChunkedCompressionSink::finish()` that calls a virtual `drainTrailer()`.
    - ../verified/01-libutil-io.md
    - **Validation:** VALID — but marginal. Two call sites with identical `flush(); writeInternal({});` bodies. **Caveat:** the `writeInternal({})` "drain" semantics is Brotli-specific — the helper must live on the `ChunkedCompressionSink` subclass, not on the top `CompressionSink`. The other three sinks don't subclass `ChunkedCompressionSink` and won't share. Honest "small win" rather than a debt entry; keep but accept the marginality. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libutil` (`flush(); writeInternal({});` lifted onto `ChunkedCompressionSink::finish()`; both Brotli overrides removed)

A `forEachConfiguredSigner(callback)` helper would let both sites become a single line; this would also be the natural place to honour the FIXME comment about caching keys in memory.
    - ../verified/05-libstore-core.md
    - **Validation:** VALID. Both sites carry the identical `// FIXME: keep secret keys in memory.` comment. The FIXME would be addressed by lifting `SecretKey`/`LocalSigner` construction into a cached vector built lazily once per `Store` instance. **Scope choice:** if the refactor stops at `forEachConfiguredSigner` it is trivial; if it includes the cache-keys-in-memory work the body bumps to small. The catalog should pick one scope and own the effort label — recommended scope is the helper extraction only (`forEachConfiguredSigner`), with the cache-keys work as a separate follow-up. Effort: small.
    - **Branch:** `vibe-coding/cleanup/libstore` (helper-only scope: `forEachConfiguredSigner` extracted as a templated helper `template<class Callback> static void forEachConfiguredSigner(const Callback & callback)` so the per-call lambda is captured inline rather than through `std::function`/`fun<>` type-erasure indirection; both `signPathInfo` and `signRealisation` reduce to one-line lambda dispatches. The cache-keys-in-memory follow-up is intentionally *not* included; the FIXME comment remains as a separate future task.).

101. **`copyPaths`/`copyClosure` `RealisedPath::Set` overloads are thin wrappers over their `StorePathSet` siblings.** In `store-api.cc`, the `RealisedPath::Set` `copyPaths` partitions into a `StorePathSet` plus `std::vector<const Realisation *>` via a `std::visit`, calls the `StorePathSet` overload, then loops `dstStore.registerDrvOutput(*r, checkSigs)` (with a `MissingExperimentalFeature{Xp::CaDerivations}` catch). The `RealisedPath::Set` `copyClosure` extracts a `StorePathSet closure0`, runs `srcStore.computeFSClosure(closure0, closure1)`, re-merges via `closure.insert({std::move(path)})`, and forwards. The only `Realisation`-specific work is `registerDrvOutput`; an adapter that splits a `RealisedPath::Set` into `(StorePathSet, std::vector<Realisation>)` and lets the StorePath-side functions take a "post-copy hook" would collapse both pairs.
    - ../verified/05-libstore-core.md
    - **Validation:** VALID. Effort: small.

102. **Unkeyed/keyed type pairs replicate the fingerprint-sign-verify protocol with key-type substitution.** `UnkeyedValidPathInfo` + `ValidPathInfo : virtual UnkeyedValidPathInfo` (adding `path`); `UnkeyedRealisation` + `Realisation : UnkeyedRealisation` (adding `id`); `UnkeyedNarInfo : virtual UnkeyedValidPathInfo` + `NarInfo : ValidPathInfo, UnkeyedNarInfo`. `UnkeyedRealisation::fingerprint(DrvOutput)`/`sign(DrvOutput,Signer)`/`checkSignature(DrvOutput,…)`/`checkSignatures(DrvOutput,…)` mirror `ValidPathInfo::fingerprint(StoreDirConfig)`/`sign(Store,Signer)`/`checkSignature(StoreDirConfig,…)`/`checkSignatures(StoreDirConfig,…)`. The realisation form passes the key explicitly because `UnkeyedRealisation` doesn't carry one; the path-info form gets the key from `path`. A `Keyed<Body, Key>` template (or CRTP) plus a `Signable` mixin parametrised on `Body::fingerprint(Key)` would replace the diamond inheritance and the per-pair sign/verify boilerplate.
    - ../verified/05-libstore-core.md
    - **Validation:** VALID. **Mechanism correction:** `fingerprint`/sign methods actually live on `ValidPathInfo : virtual UnkeyedValidPathInfo`, not on the unkeyed half (the unkeyed half just holds data); `realisation.hh` puts them on `UnkeyedRealisation` because there's no embedded key (`DrvOutput key` is passed explicitly). `nar-info.hh` is a genuine virtual diamond (`UnkeyedNarInfo : virtual UnkeyedValidPathInfo`, `NarInfo : ValidPathInfo, UnkeyedNarInfo`). The diamond is harder to flatten — mixin route is invasive; CRTP feasible. **Caveat:** touches the public ABI of a widely-included header. **See also:** N5 (`Signable<Body>` CRTP/mixin lifting `fingerprint`/`sign`/`checkSignature`/`checkSignatures` onto any type that provides `Body::fingerprint() -> string` — the four-method protocol is the deeper duplication this candidate's diamond-flattening sits orthogonal to), N2 (the underlying `<algo>:<base-encoded>` fingerprint formatter), Cluster B (variant-shaped types). Effort: medium-large.

103. **Scan-and-rewrite sinks form an ad-hoc pipeline.** `RefScanSink` (in `references.{cc,hh}`) does substring matching for hash-part references; `PathRefScanSink : public RefScanSink` (in `path-references.{cc,hh}`) adds a `backMap<std::string, StorePath>` to translate hash hits back to `StorePath`s. `RewritingSink` does string substitution and tracks match positions; `HashModuloSink` composes `HashSink` + `RewritingSink` (rewriting the modulus to zero bytes before hashing) and additionally hashes the match positions to prevent self-reference collisions. `make-content-addressed.cc` then uses both: a `HashModuloSink` to compute `narModuloHash`, then a fresh `RewritingSink rsink2` to produce the rewritten NAR. The "scan + rewrite" pipeline is a recurring shape (see also #45 in the FSO walker) but there's no `ScanRewriteSink` abstraction.
    - ../verified/05-libstore-core.md
    - **Validation:** VALID. **Caveat:** the `make-content-addressed.cc` two-pass cost is structural (must hash before rewrite) and not eliminable. Less ambitious than a unified `ScanRewriteSink`: factor the `tail`-buffered scanning loop into a reusable mixin separate from result-collection. Effort: medium.

104. **No shared "renderable store object" abstraction.** `StoreDirConfig::printStorePath` formats `<storeDir>/<base>` via `(storeDir + "/").append(path.to_string())`; `parseStorePath` reverses it. `StorePath::to_string()` returns the base only; `DrvOutput::to_string()` returns `drvPath.to_string() + "^" + outputName`, while `DrvOutput::render(store)` prepends `store.printStorePath(drvPath)`. `DerivedPath::to_string(store)` and `SingleDerivedPath::to_string(store)` dispatch over `raw()` via `std::visit`, with `to_string_legacy(store)` doing the same with `!` instead of `^`. `StorePathWithOutputs::to_string(store)` and `DerivedPath::Opaque::to_string(store)` each redo the `store.printStorePath(...)` prefix step. Each type's `parse(store, …)` is a corresponding ad-hoc inverse. A `Renderable<T>` concept (`render(store)` / `parse(store, sv)`) plus a generic store-prefix wrapper would consolidate the `<storeDir>/<base>(<suffix>)` formatting.
    - ../verified/05-libstore-core.md, ../verified/06-libstore-derivations.md
    - **Validation:** PARTIALLY VALID. The `to_string` vs `render` vs `to_string_legacy` split reflects three real concerns (storeless, full prefix, `^` vs `!` separator for backwards compat with old CLI) — the legacy `^`/`!` split is a compat tax that cannot be erased. A `StorePrefixed<T>` wrapper holding `(StoreDirConfig &, T)` with `operator<<` plus a `std::formatter<StorePrefixed<T>>` specialisation eliminates manual concatenation for the new-form case only. Effort: medium.

221. **`BaseSetting<container<T>>::parse`/`to_string`/`appendOrSet` is hand-rolled across six specialisations.** `src/libutil/configuration.cc` carries five near-identical specialisation triples for `BaseSetting<std::set<std::filesystem::path>>`, `BaseSetting<std::list<std::filesystem::path>>`, `BaseSetting<StringSet>`, `BaseSetting<Strings>`, and `BaseSetting<std::set<ExperimentalFeature>>`; `src/libstore/globals.cc` adds a sixth pair for `BaseSetting<std::vector<StoreReference>>` and `BaseSetting<std::set<StoreReference>>` (the `StoreReference` half of #85, already deduplicated within libstore via two file-static templates). The `parse` body is uniformly "tokenize on whitespace, push each parsed element onto an empty container"; `to_string` is uniformly "iterate, render each element with the per-T formatter, join with single spaces"; `appendOrSet` differs structurally between vectors (end-extend) and sets (merge-insert). Lifting the `parse`/`to_string` halves into a libutil header with the per-element parser/formatter passed in (matching the shape #85 introduced in libstore) would deduplicate ~5 specialisations alongside the libstore pair, leaving only the genuinely-divergent `appendOrSet` bodies inline.
    - ../verified/03-libutil-runtime.md
    - **Validation:** VALID. The `parse`/`to_string` shape is identical across all six specialisations and matches the existing #85 templates verbatim modulo the per-element parser. **Pitfall:** `BaseSetting<std::set<ExperimentalFeature>>` parses each token via `parseExperimentalFeature`, which can return `std::nullopt` for unknown feature names *and* warns on each unknown name — its body is irreducibly per-T and stays inline. **Scope:** the library-shaped helper covers the libstore `StoreReference` pair (already deduplicated under #85 within libstore) and any future `BaseSetting<C<T>>` whose token parser returns a single `T`; the existing libutil specialisations for `Strings` / `StringSet` are already one-liners over `tokenizeString<C>` with nothing left to factor, and `list<path>` / `set<path>` only save 1 line each. **See also:** #85 (the libstore pair which seeded the templates), #21 (`Setting<T>` collection serialisation), Cluster D (settings-tied configuration). Effort: small (lift the `StoreReference` pair into a libutil header so future external `BaseSetting<C<T>>` specialisations can reuse it).
    - **Branch:** `vibe-coding/cleanup/libstore` (lifted `parseSettingTokens<C, Parser>` and `renderSettingTokens<C, Render>` from `globals.cc` into shipped `configuration.hh`; the libstore `BaseSetting<vector<StoreReference>>`/`BaseSetting<set<StoreReference>>` specialisations now call the libutil helpers. Existing libutil specialisations were inspected during implementation — `Strings` and `StringSet` are already one-liners over `tokenizeString<C>` with nothing to factor; `list<path>` and `set<path>` save one line each and were left inline as the gain didn't justify the call-site noise; `set<ExperimentalFeature>` has irreducible per-T `parseExperimentalFeature`+warn semantics and stays inline. Net win: future external `BaseSetting<C<T>>` specialisations have a public hook.)

218. **`Hash::dummy` and `StorePath::dummy` are overloaded as both "uninitialised placeholder" and "wire-marker for missing".** The two sentinels — `Hash::dummy` (in `libutil/hash.cc`) and `StorePath::dummy` (in `libstore/path.cc`) — serve two structurally different purposes with one type. **Placeholder-then-overwrite sites** (the value is constructed with `dummy`, then mutated to a real value before any read): `local-store.cc::queryPathInfoInternal` (`auto narHash = Hash::dummy;`), `derivation-trampoline-goal.cc` (`auto drvPath = StorePath::dummy;`), `make-content-addressed.cc` (constructs `ContentAddress` with `Hash::dummy` placeholder), `unix/build/derivation-builder.cc` (`Hash::dummy` slot in `ValidPathInfo` constructor before `narHash` is computed), `nar-info.cc::NarInfo` constructor (carries two `// FIXME: hack` comments adjacent to `UnkeyedValidPathInfo(store, Hash::dummy)` and `ValidPathInfo(StorePath::dummy, ...)`). **Wire-marker sites** (the value is genuinely `dummy` on the wire and decoded back to `dummy` on the other side): `worker-protocol.cc` and `serve-protocol.cc` use `Hash::dummy.to_string(HashFormat::Base16, true)` to mint a wire-format placeholder for `DrvOutput::id`'s missing-hash case, and `legacy-ssh-store.cc` does `if (info.narHash == Hash::dummy)` to detect the no-hash case across the wire. Plus a third class: tests use `Hash::dummy` as a known-canonical hash value. **The pattern is a name-collision smell.** The right factoring is `std::optional<Hash>` / `std::optional<StorePath>` for the placeholder-then-overwrite sites, and a separately-named sentinel (e.g. `Hash::wireUnsetMarker` or a wire-protocol-specific encoding) for the wire-marker sites. The codebase is already signalling discomfort via two `// FIXME: hack` tags in `nar-info.cc`.
    - **Validation:** VALID. **Verified inventory** via `grep -rn "Hash::dummy\|StorePath::dummy" src/ --include="*.cc" --include="*.hh" --include="*.h"`: 16 sites across `src/`, broken into placeholder-then-overwrite (6 sites including the FIXME-tagged `nar-info.cc` constructor), wire-marker (3 sites in `worker-protocol.cc`, `serve-protocol.cc`, `legacy-ssh-store.cc`), test fixture (3 sites in `register-valid-paths-bench.cc` and `serve-protocol.cc`), legitimate constant (`nix-store.cc` for `--add-fixed`), and the two definitions (`hash.cc`, `path.cc`). C1 named the placeholder-then-overwrite half; the wire-marker half is a separate but related observation. **Cross-class:** also "Latent bugs hiding inside duplication" — a wire-format change that touches `Hash::dummy.to_string(...)` while a placeholder-then-overwrite path forgets to overwrite would cause silent confusion between the two roles. **See also:** C1 for the pattern surface; #54 for an adjacent uninitialised-bool latent bug; #102 (`Keyed`/`Signable` mixin) shares the `nar-info.cc` constructor as a touchpoint. Effort: small (pattern is small per-site; aggregated it's medium because the wire-marker rename touches the protocol header).

224. **`NarIndexer::createMember` computes path depth via `for (auto _ : path) (void) _; ++level;`.** In `libutil/nar-listing.cc`, the helper that's called per NAR entry by `parseDump` advances a `std::stack<NarListing*>` to track the current parent. The depth `level` is computed by iterating `path` and incrementing — which works because `CanonPath` is segment-iterable, but the idiomatic spelling is whatever `CanonPath` exposes for "number of segments". `CanonPath` does not currently expose a depth/segment-count accessor; either add one (e.g. `size_t numSegments() const`) and use it here, or rewrite the loop as `std::ranges::distance(path)` once `path` exposes its iterator pair as a forward range. Pre-existing oddity surfaced by Pass-B reuse review of #37. The cosmetic improvement is a one-line edit; the cleaner fix (a `CanonPath::numSegments` accessor) is also one-line in `canon-path.hh`.
    - ../verified/01-libutil-io.md
    - **Validation:** VALID. The current shape works; the asymmetry is purely stylistic. The cleaner factor — adding a `CanonPath::numSegments()` accessor — would also serve any future caller asking the same question without re-iterating. **See also:** #37 (the NAR-walk extraction that surfaced this). Effort: trivial.
