A single template `forceTyped<ValueType T>(...)` plus a small per-`ValueType` traits map (already implicitly present in `showType`) would replace all sixteen bodies. Compounds with #65 (primop arg-validation duplication), which sits one layer above this.

212. **`EvalState`'s constructor performs eight independent initialisation phases inline, with no `init*` decomposition.** [MEDIUM] The body of `EvalState::EvalState` does, in order: (1) construct `storeFS` as a `MountedSourceAccessor` over the configured store with a long inline TODO about union-vs-mounted semantics; (2) construct `rootFS` via a same-ctor lambda that branches on `pureEval`/`restrictEval` to choose accessors and applies `AllowListSourceAccessor` with a per-call diagnostic; (3) construct `corepkgsFS`/`internalFS` and immediately `addFile` `derivation-internal.nix` and `imported-drv-to-derivation.nix` from generated headers; (4) bump the process stack size via a `std::call_once` flag (`stackSizeBumped`) for `std::regex` reasons; (5) read `NIX_COUNT_CALLS`; (6) build `lookupPath` from arguments, `EvalSettings::nixPath`, and `EvalSettings::getDefaultNixPath`; (7) install `fetchurl.nix` into `corepkgsFS`; (8) call `createBaseEnv` (which itself spans ~300 lines in `primops.cc` and registers every primop and constant), then optionally register a `FunctionCallTrace` and a `SampleStackProfiler`. Splitting these into named phases (`initStoreFs()`, `initRootFs()`, `initInternalFs()`, `initLookupPath()`, `initBaseEnv()`, `initProfilers()`) — each safe to call independently from the C API or from tests — would let embedders reuse pieces (e.g. swap the source-accessor stack without paying for `createBaseEnv`) and would document the hidden ordering between the phases. The `stackSizeBumped` `call_once` is a process-global side effect of constructing an `EvalState` and arguably belongs in `initLibExpr`, not the per-instance constructor.

    - **Validation:** VALID. Effort: medium.

213. **`Value::vEmptyList`/`vNull`/`vTrue`/`vFalse` are documented "not singletons" — yet `getBool` and `ExprList::maybeThunk` hand out their addresses.** [DESIGN] The four canonical instances in `value.hh` carry the comment `This is _not_ a singleton. Pointer equality is _not_ sufficient.`, but `EvalState::getBool(bool b) { return b ? &Value::vTrue : &Value::vFalse; }` (in `eval.cc`) and `ExprList::maybeThunk` (returning `&Value::vEmptyList` for empty lists) both hand out their addresses, and `prim_tryEval`, `prim_match`, and `prim_split` (`primops.cc`) embed `&Value::vNull`/`&Value::vTrue`/`&Value::vFalse` into result attrsets directly. Meanwhile the eval cache and the C API may construct fresh copies — so equality semantics are split between "this address" (handed out by `getBool`) and "any value-equal Boolean/null/empty-list" (constructed elsewhere). Either rename to drop the singleton implication, or make them genuinely canonical (immutable, pointer-comparable, with all consumers — including the eval cache — required to reference rather than copy).
    - ../verified/11-libexpr-eval.md
    - **Validation:** VALID. Effort: medium.

214. **`forceValue`'s inline hot path and the three `noinline` slow paths replicate the `mkFailed` recovery dance.** [MEDIUM] `forceValue` (in `eval-inline.hh`) is `gnu::always_inline` and contains the thunk/app/failed dispatch with three `try/catch` arms calling `handleEvalExceptionForThunk`, `handleEvalExceptionForApp`, and `handleEvalFailed` (all `gnu::noinline` in `eval.cc`). The first two `handleEvalExceptionFor*` bodies are nearly identical: re-`std::current_exception`, `try { rethrow } catch (RecoverableEvalError &) { recovery = allocValue(); } catch (...) {}`, then `if (recovery) recovery->mk*(...); v.mkFailed(e, recovery);` — they differ only in how `recovery` is populated (a fresh thunk pointing at `(env, expr)` vs a copy of `savedApp`). Factoring a `mkFailedFromCurrentException(v, recoveryFactory)` helper in `eval.cc` would consolidate the two slow paths and document the invariant that `recoveryValue` is set iff the in-flight exception is `RecoverableEvalError`. The inline-vs-noinline split itself is load-bearing for the hot path, so the noinline boundary should remain — only the bodies should consolidate.
    - ../verified/11-libexpr-eval.md
    - **Validation:** VALID. Effort: small.

215. **`EvalErrorBuilder<T>` heap-allocates and `delete this`-deletes itself across two TUs.** [DESIGN] `EvalState::error<T>(args...)` (in `eval.hh`) does `return *new EvalErrorBuilder<T>(*this, args...);` returning a reference to the heap-allocated builder; the `[[nodiscard, gnu::noinline]]` chain methods (`atPos`, `withTrace`, `withFrame`, `withSuggestions`, `addTrace`, `setIsFromExpr`, `withExitStatus`, `withFrameTrace`) each return `*this` and are out-of-line in `eval-error.cc`; the chain must terminate in `debugThrow()` which `auto error = std::move(this->error); delete this; throw std::move(error);`. The dance exists so that the typed `T` (e.g. `TypeError`) is constructed once at the start of the chain and only thrown if the user calls `debugThrow()` — but the same effect can be had with a stack-allocated builder whose destructor either swallows (when `debugThrow` ran) or throws (when the user forgot — caught by `[[nodiscard]]` already). The current `[[nodiscard]]` plus `delete this` combination is fragile.
    - ../verified/11-libexpr-eval.md
    - **Validation:** **INVALID.** The alleged fragility doesn't hold. `[[nodiscard]]` already enforces the chain-must-end-in-`debugThrow` contract at compile time, and a destructor-throwing alternative would be strictly worse — UB risk under nested throw (destructor called during stack unwind), harder reasoning about early-exit paths. Keep as-is.

216. **`Value`'s bit-packed and generic storage layouts are not pinned by `static_assert`; the `sizeof(Env) <= 16` invariant is asserted in the wrong scope.** [HIGH] `value.hh` declares `inline constexpr bool useBitPackedValueStorage = (ptrSize == 8) && (__STDCPP_DEFAULT_NEW_ALIGNMENT__ >= 16);` and provides two `ValueStorage<ptrSize>` specialisations — the bit-packed `alignas(16)` one and the generic discriminator-plus-union fallback. The bit-packed path uses `__m128i`/`MOVAPS` on x86_64-with-SSE2 and falls back to a `std::array<uint64_t, 2>` elsewhere (Apple Silicon has `__STDCPP_DEFAULT_NEW_ALIGNMENT__ == 16` — so it gets the bit-packed layout but not the SSE2 atomic load/store). There is no `static_assert(sizeof(Value) == 16)` in either layout, no `static_assert(alignof(Value) == 16)`, and no test that round-trips every `InternalType` through `setStorage`/`getStorage` on both layouts. Separately, `eval.cc` puts `static_assert(sizeof(Env) <= 16, "environment must be <= 16 bytes");` at line-of-execution scope inside `EvalState::EvalState`, so the assertion is invisible to any TU that allocates an `Env` via `EvalMemory::allocEnv` from an inline header. Both invariants belong at namespace scope next to the `Value`/`Env` declarations.
    - ../verified/11-libexpr-eval.md
    - **Validation:** VALID. Confirmed no namespace-scope `static_assert(sizeof(Value) == 16)` and no `static_assert(alignof(Value) == 16)`. The `static_assert(sizeof(Env) <= 16)` is at line-of-execution scope inside `EvalState::EvalState`'s body. Effort: small (asserts) + medium (round-trip test).
