150. **`Worker`'s six per-goal-kind weak-pointer maps duplicate `initGoalIfNeeded` plumbing.** [HIGH] `Worker` carries six caches keyed by goal-specific identity: `derivationTrampolineGoals` (a `DerivedPathMap<map<OutputsSpec, weak_ptr<...>>>`), `derivationGoals` (`map<StorePath, map<OutputName, weak_ptr<...>>>`), `derivationResolutionGoals`, `derivationBuildingGoals`, `substitutionGoals`, and `drvOutputSubstitutionGoals` (each `map<Key, weak_ptr<...>>`). The single template `Worker::initGoalIfNeeded(weak_ptr<G> &, Args &&...)` is the same for all six, but the `make*Goal` accessors and the `removeGoal` clean-up branches re-derive the key shape per goal kind. A `WeakGoalCache<G, Key>` collaborator owning the map plus a `getOrInit(key, factory)` and `remove(key)` member would collapse six near-identical sites into one type and let the `derivationGoals` two-level nesting be a `WeakGoalCache<DerivationGoal, pair<StorePath, OutputName>>` rather than hand-rolled.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. **See also:** N14 (the 12+2 worker counters share fate; the per-goal `MaintainCount` members are part of this candidate's surface), N19 (Worker is one of the "fat types" — six per-goal-kind weak-pointer maps + 14 progress counters + Waker self-pipe + scheduling queue + `dynamic_pointer_cast` chain). Effort: medium. **Keystone for #151, #170.**

151. **`Worker::removeGoal` is a six-arm `dynamic_pointer_cast` chain — the wrong tool for this dispatch.** [HIGH] `Worker::removeGoal(GoalPtr)` does `dynamic_pointer_cast<DerivationTrampolineGoal>` then `<DerivationGoal>` then `<DerivationResolutionGoal>` then `<DerivationBuildingGoal>` then `<PathSubstitutionGoal>` then `<DrvOutputSubstitutionGoal>`, falling through to `unreachable()`. Each arm reaches into the matching weak-pointer map and erases by a goal-kind-specific key. The map already knows what kind of goal it holds, so a `removeFromCache(self)` virtual on `Goal` (or a `WeakGoalCache<G, Key>::remove(self)` invoked from a single virtual hook) eliminates RTTI dispatch and fuses with #150. Compounds with the `friend struct RestrictedStore` style downcasts elsewhere in the build tree.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. With #150's `WeakGoalCache` in place, the `friend class Worker;` declarations on `DerivationBuildingGoal`, `DerivationResolutionGoal`, `DrvOutputSubstitutionGoal` (which exist because `Worker::removeGoal` reads private key fields like `drvBuildingGoal->drvPath`/`subGoal->id`) become unnecessary. (`DerivationGoal`, `DerivationTrampolineGoal`, `PathSubstitutionGoal` already expose key fields publicly — that's a per-class accident, not a design.) `removeGoal` is called from `Goal::amDone` via `worker.removeGoal(shared_from_this())` while the goal still holds a strong self-reference; `removeFromCache` reads only `const` key fields, so this is safe. Effort: small.

152. **`Worker::Waker` cross-thread wakeup hand-rolls a self-pipe / IOCP that `Sync<queue>` could express directly.** [DESIGN] `Worker::Waker` carries a `Sync<queue<WeakGoalPtr>> wakeupQueue_` plus, on POSIX, a `unix::SelfPipe wakeupPipe` and on Windows the `Worker::ioport`. `Waker::enqueue` pushes onto the queue and either `wakeupPipe.notify()` or `PostQueuedCompletionStatus()`s; `wakeAll` drains the queue holding the lock. The pipe / completion-port exists solely so the main `waitForInput` `poll()` returns when an external thread enqueues; a `condition_variable_any` pair on the same `Sync` lock combined with timed waits in the main loop would replace both platform shims, and the duplication between the `#ifndef _WIN32` self-pipe arm and the IOCP arm in `worker.{hh,cc}` would vanish.
    - ../verified/10-libstore-build.md
    - **Validation:** PARTIALLY VALID. **A `condition_variable_any` cannot replace the self-pipe** because the Worker main loop is `poll()`-ing real child fds in `MuxablePipePollState::poll`, not waiting on a CV. The achievable refactor is unifying the platform notifier (`eventfd`/self-pipe/IOCP) behind one `MuxableNotifier` seam. Effort: medium.

153. **`DerivationBuilderImpl` inherits from `DerivationBuilderParams` instead of holding it.** [HIGH] `class DerivationBuilderImpl : public DerivationBuilder, public DerivationBuilderParams` (in `unix/build/derivation-builder.cc`) baked the `params` move into a base subobject so member-init can read `drv` (used to compute the cached `derivationType{drv.type()}`). The pattern means every reference to `drvPath`, `drv`, `drvOptions`, `inputPaths`, `initialOutputs`, `buildMode`, `defaultPathsInChroot`, `systemFeatures`, `desugaredEnv`, `buildResult` inside the class body is an inherited-member access — the params have leaked into the class's public/protected name lookup. Holding `DerivationBuilderParams params;` as a member, with a constructor-init `derivationType(params.drv.type())`, removes the inheritance, narrows the surface, and makes `params` swappable for testing. The accompanying `// FIXME: rename this to UnixDerivationBuilder or something like that.` comment immediately above the class declaration is a cosmetic rename hint; the inheritance smell is the real refactor.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. Effort: small.
    - **Branch:** `vibe-coding/cleanup/libstore` (replaced `class DerivationBuilderImpl : public DerivationBuilder, public DerivationBuilderParams` with composition: `DerivationBuilderParams params;` as a protected member, ctor takes `DerivationBuilderParams params` by value and stores it via `params{std::move(params)}`, `derivationType{this->params.drv.type()}` resolves member-name lookup. Six subclass ctors (`ChrootDerivationBuilder`, `DarwinDerivationBuilder`, `ExternalDerivationBuilder`, `FreeBSDDerivationBuilder`, `LinuxDerivationBuilder`, `ChrootLinuxDerivationBuilder`) updated. `freebsd-derivation-builder.cc` accesses none of the renamed fields and is unchanged. `chroot-derivation-builder.cc::prepareSandbox` declared a local `BuildChrootParams params{...}` that would shadow the class member; renamed to `chrootParams`. About 100 member-name accesses rewritten from bare `drv`/`drvPath`/etc to `params.drv`/`params.drvPath`/etc. **Subtle:** the JSON wire-key emitted to external builders by `external-derivation-builder.cc::startChild` is `"inputPaths"` (a documented protocol key), not `"params.inputPaths"`; the key spelling is preserved verbatim despite the C++ field rename, since it appears in a string literal that an over-broad rename would otherwise corrupt silently.)

154. **`DerivationBuilderImpl::registerOutputs` is a 590-line monolith with five nested lambdas.** [HIGH] `registerOutputs()` runs from the start of construction of `referenceablePaths` through the final `signRealisation`/`registerDrvOutput` loop, inlining `finish`, `rewriteOutput`, `rewriteRefs`, `newInfoFromCA`, and `moveOutputToTempDir` as captures. Each is a ~30-60-line operation that touches member state (`outputRewrites`, `inodesSeen`, `actualPath`, `localSettings`) and then is invoked from one or two sites in the loop body. Extracting them to private member functions (or a small `OutputRegistration` helper holding the ephemeral state — `inodesSeen`, `outputRewrites`, the `outputReferencesIfUnregistered` map, the `outputStats` map) would reduce the function to its real responsibilities: topo-sort, rewrite-and-canonicalise, register. The current shape obscures that the per-output body is itself a state machine over `InputAddressed` / `CAFixed` / `CAFloating` / `Deferred` / `Impure`.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. Effort: medium.

155. **`startChild` / `runChild` / `setUser` / `prepareSandbox` strategy hooks are unevenly overridden — a hint they should be a strategy object, not a virtual diamond.** [DESIGN] In the platform-derived classes, `prepareSandbox` is overridden in all of `chroot`/`linux`/`freebsd`/`darwin`; `startChild` only in `linux`/`freebsd`/`external`; `setUser` only in `linux`/`darwin`; `enterChroot` only in `chroot`/`linux`/`freebsd`; `setBuildTmpDir`/`tmpDirInSandbox`/`needsHashRewrite` only in `chroot` and `external`; `killSandbox` in `linux`/`darwin`; `cleanupBuild` in `chroot`/`freebsd`. No subclass overrides all of them; many overrides are no-op-defaults inherited from `DerivationBuilderImpl`. The shape — many fine-grained virtuals each polymorphic across a different subset — fits the strategy/policy pattern (a `SandboxPolicy`, `UserPolicy`, `ChildLaunchPolicy` composed at construction time) far better than a diamond inheritance with one chroot mixin and per-OS leaves. Compounds with #28, #34.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. The override matrix factors cleanly into three policies — `SandboxPolicy` (prepareSandbox/enterChroot/cleanupBuild/needsHashRewrite/setBuildTmpDir/tmpDirInSandbox/killSandbox), `UserPolicy` (getBuildUser/prepareUser/setUser), `ChildLaunchPolicy` (startChild/execBuilder/addDependencyImpl). `ChrootLinuxDerivationBuilder`'s namespace state (`usingUserNamespace`, `userNamespaceSync`, `sandboxMountNamespace`) lives on the policy, not on the builder. Compounds with #28, #34, #153. Effort: structural.

156. **`DerivationTrampolineGoal::haveDerivation` and `DerivationGoal::haveDerivation` and `DerivationBuildingGoal::gaveUpOnSubstitution` all share a "fetch drv → fan out per-output → await waitees → check `nrFailed`" skeleton.** [MEDIUM] `DerivationTrampolineGoal::haveDerivation` resolves `OutputsSpec::All` to `drv.outputs` keys, builds a `Goals concreteDrvGoals` of `makeDerivationGoal` per output, `co_await await(Goals(concreteDrvGoals))`, then merges `builtOutputs`. `DerivationGoal::haveDerivation` does substitute-then-build with a similar `Goals waitees` then `co_await await(std::move(waitees))` then `if (nrFailed != 0)` failure path. `DerivationBuildingGoal::gaveUpOnSubstitution` walks `drv->inputSrcs`, builds substitution waitees, `co_await await(...)`, then `if (nrFailed != 0) doneFailure(...)`. The "build a `Goals waitees`, await, branch on `nrFailed`, build a per-failure `HintFmt`" shape is the canonical fan-out idiom and could be a `Goal::awaitAll(Goals, dependencyFailureHint)` helper that merges with `Goal::await` to standardise the dependency-failure message.
    - ../verified/10-libstore-build.md
    - **Validation:** PARTIALLY VALID. **Only two sites genuinely share the idiom**: `DerivationBuildingGoal::gaveUpOnSubstitution` and `DerivationResolutionGoal::resolveDerivation`. `DerivationTrampolineGoal::haveDerivation` does **not** want to fail on `nrFailed` — it merges children's `buildResult` and tail-calls `amDone(g->exitCode)`. `DerivationGoal::haveDerivation`'s first fan-out is substitution (where failure is expected and reset), not dependency-failure. So this is a 2-site dedup, not a generalised idiom. Effort: small.

158. **`HookInstance` constructor inlines the build-hook protocol's setup-frame transmission with no protocol-version negotiation.** [DESIGN] After `fork`/`exec`ing the hook program, `HookInstance::HookInstance` writes the global config to the hook in a hand-coded loop: `for (auto & setting : settings) sink << 1 << setting.first << setting.second.value; sink << 0;`. The first response is parsed line-by-line in `DerivationBuildingGoal::tryBuildHook` looking for `decline` / `decline-permanently` / `postpone` / `accept`; build-side framing in `buildWithHook` then sends `try` / inputPaths / missingOutputs as raw `CommonProto` writes, and parses the hook's stderr for `# `-prefixed reply lines and `@nix { ... }` JSON log frames inline in the coroutine. There is no protocol version exchanged — the hook protocol is a frozen `1`/`0` framing convention split across three files (`hook-instance.cc`, `derivation-building-goal.cc::tryBuildHook`, `derivation-building-goal.cc::buildWithHook`). A `BuildHookProtocol` codec class colocated with `HookInstance` would centralise the framing and make versioning possible.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. Effort: medium.

159. **`Goal::ChildEvents` is an over-modelled queue; a `std::queue<ChildEvent>` plus an `optional<TimedOut>` short-circuit would express the same invariant.** [MEDIUM] The private `ChildEvents` class in `goal.hh` carries three fields — `std::queue<ChildOutput> childOutputs`, `std::optional<ChildEOF> childEOF`, `std::unique_ptr<TimedOut> childTimeout` — with three `pushChildEvent` overloads, a `hasChildEvent()` predicate, and a `popChildEvent()` that returns the variant. The asymmetry exists because timeouts flush the queue (`childOutputs = {}; childEOF.reset(); childTimeout = make_unique<TimedOut>(...)`) and EOF asserts uniqueness (`assert(!childEOF)`). A `std::queue<ChildEvent>` plus a single boolean "timed-out, ignore further pushes" flag would preserve the invariants with one container and three trivial pushers. The `unique_ptr<TimedOut>` (sole owner, never null when set) is gratuitous — `optional<TimedOut>` (or moving the `TimedOut` directly into the variant) suffices.
    - ../verified/10-libstore-build.md
    - **Validation:** VALID. **Caveat:** a literal `std::queue<ChildEvent>` alone changes timing semantics — today `popChildEvent` always returns outputs before EOF before timeout, regardless of arrival order. The candidate's `bool timedOut` shape works only because `pushChildEvent(TimedOut)` clears the queue first. Preserve that. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libstore` (`std::queue<ChildEvent>` plus `bool timedOut`; pop order preserved by FIFO insertion semantics; the old `assert(!childEOF)` defensive check was dropped after walking producers — `Goal::handleEOF` is called once per fd EOF and only one fd is watched per goal in the existing call paths)

160. **The `Goal::Co` coroutine machinery (~600 lines of header) is structurally a stackless task that `boost::asio::awaitable` already provides.** [DESIGN] `goal.hh` defines `Goal::Co` plus `promise_type` plus three custom awaiters (`InitialSuspend`, `SuspendAwaiter`, `ChildEventAwaiter`) plus a `final_awaiter` plus the `await_transform` overloads for `Suspend`/`WaitForChildEvent`/`AsyncCallback<T>`. The hardest awaiter to replace is `final_awaiter`: it tail-calls the next coroutine via `goal->top_co = std::move(c); return goal->top_co->handle;`, implementing the `co_return some_other_coroutine()` continuation-passing optimisation noted in the file's `@todo Allocate explicitly on stack since HALO thing doesn't really work`. `std::generator` (C++23) is the wrong shape. `boost::asio::awaitable<T>` plus `asio::experimental::channel` for child events would replace `Co`/`ChildEventAwaiter`/`SuspendAwaiter` directly; only the tail-call optimisation in `final_awaiter` is genuinely custom.
    - ../verified/10-libstore-build.md
    - **Validation:** PARTIALLY VALID. **`final_awaiter` is genuinely custom and not replaceable.** The tail-call optimisation `top_co = std::move(c); return top_co->handle;` is an O(1)-frame tail-call. `boost::asio::awaitable<T>` does **not** natively support `co_return another_awaitable();` — it requires `co_await another_awaitable();`, which is correct but leaves O(depth) frames live. The header's own `@todo` confirms HALO doesn't cover this. The "600-line" claim is overstated (~350 LoC across header+cc). **Hybrid migration only:** keep the bespoke `final_awaiter`; replace `SuspendAwaiter` and `ChildEventAwaiter` with asio primitives. `Goal::Co` is custom because `std::task<T>` was never standardised (C++23 shipped `std::generator`, not `task`; C++26 working draft does not include `task` either). **Hybrid-migration hazard:** any partial migration to `asio::awaitable<T>` for sub-operations breaks the homogeneity of the coroutine machinery. `Goal::Co` uses `co_await` to suspend on a custom `Suspend` token; if that becomes `co_await asio::post` or similar, the `final_awaiter`'s view of "what is the parent continuation" changes — asio's awaiter chain is independent of `promise_type::continuation`. The hybrid migration requires verifying that asio's `experimental::channel` or equivalent doesn't capture the parent continuation in a way that conflicts with `final_awaiter`'s `top_co` swap. A migration step that replaces `SuspendAwaiter` while keeping `final_awaiter` must confirm via test that the same number of frames are alive at the same call depth (equivalent stack depth in micro-benchmark). **See also:** N8 (three async idioms — `Callback<T>` from #22, `awaitable<T>`, and `Goal::Co`; pick one), E3 (Goal::Co property test asserting O(1) frame depth before any partial migration). Effort: structural.

219. **The post-build hook consumer in `runPostBuildHookCo` silently drops `TimedOut` events.** [MEDIUM] `derivation-building-goal.cc::runPostBuildHookCo` (and pre-extraction, the inline post-build-hook loops in `buildWithHook` and `buildLocally`) consumes `co_await WaitForChildEvent{}` in a `while (true)` loop that branches only on `ChildOutput` and `ChildEOF`. A `TimedOut` event delivered to the goal during the post-build hook phase falls through both branches and the loop spins. This is a pre-existing latent bug — present in both inline copies before the #157 extraction and preserved verbatim in the extracted helper. Not in scope for #157's pure dedup; surfaces here because the post-build hook can run for many seconds and the goal's overall timeout machinery (`pushChildEvent(TimedOut)`) still fires during the hook. The fix is to add a `if (auto * timeout = std::get_if<std::unique_ptr<TimedOut>>(&event)) { hookState->complete(); worker.childTerminated(this); co_return doneFailure(std::move(**timeout)); }` arm, matching the timeout-handling pattern in `buildLocally`'s build phase.
    - ../verified/10-libstore-build.md
    - **Validation:** PARTIALLY VALID — surfaced by post-#157 review. The "silently drops" framing is correct for a `co_await` that returns a TimedOut: the consumer's `if (output)` and `if (eof)` arms both fail, so the loop iterates again awaiting the next event. Whether this is reachable in practice depends on whether `Worker::wakeUp` fires `pushChildEvent(TimedOut)` for the child registered by `runPostBuildHook` (via `worker.childStarted(shared_from_this(), {hookState->out->readSide.get()}, false, false)`) — needs verification of `Worker`'s timeout-tracking against the post-build-hook child. If the post-build hook is not subject to the build timeout, this is dead-code defence; if it is, the loop spin is reachable on hook-induced timeouts. Effort: trivial (add the timeout arm) once reachability is confirmed.
