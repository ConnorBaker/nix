105. **`MakeBinOp`/`MakeBinOpMembers` macros expand to six near-identical AST node classes.** `MakeBinOpMembers(name, s)` synthesises `pos`/`e1`/`e2`, two constructors, `show` (always wrapping `e1 s e2` in parens), `bindVars` (`e1->bindVars; e2->bindVars`), an `eval` declaration, and `getPos`. `MakeBinOp(name, s)` wraps it in `struct name : Expr { ... }`. Used six times for `ExprOpEq`, `ExprOpNEq`, `ExprOpAnd`, `ExprOpOr`, `ExprOpImpl`, `ExprOpConcatLists`, plus a partial reuse where `ExprOpUpdate` opens its struct manually and embeds `MakeBinOpMembers(ExprOpUpdate, "//")` so it can override `evalForUpdate` alongside the generated members. A CRTP base `BinOp<Derived>` with a `static constexpr std::string_view symbol` would replace the macros and let `ExprOpUpdate` inherit instead of carving out a manual special case.
    - ../verified/12-libexpr-parse.md
    - **Validation:** VALID. Plain CRTP — no template trickery beyond `static constexpr std::string_view symbol = Derived::symbol;`. Eliminates both `MakeBinOp` and `MakeBinOpMembers` macros. Effort: small.
    - **Branch:** `vibe-coding/cleanup/libexpr` (`template<class Derived> struct BinOp : Expr` carries `pos`/`e1`/`e2`, the two constructors, `show` (using `Derived::symbol`), `bindVars`, and `getPos`. Each derived `Expr*` declares its own `eval` override one-liner so the out-of-line definitions in eval.cc remain `void ExprOpEq::eval(...)`-style. `ExprOpUpdate` is no longer a special case — it inherits from `BinOp<ExprOpUpdate>` like the others and adds its private `eval(EvalState &, Value &, Value &, Value &)` helper plus its `evalForUpdate` override directly.)

106. **`parseExprFromBuf` and `parseReplBindingsFromBuf` duplicate the entire scanner/parser skeleton.** Both construct identical `LexerState`/`ParserState`, call `yylex_init_extra`, install a `Finally` for `yylex_destroy`, run `yy_scan_buffer`, instantiate `Parser`, and call `parser.parse()`. The repl variant adds exactly two things: a `setReplBindingsMode(scanner)` call between `yy_scan_buffer` and the `Parser` construction, and a `dynamic_cast<ExprAttrs *>(state.result)` plus two `assert`s on the way out. The two start-rule alternatives in the grammar (`expr` vs `REPL_BINDINGS binds1`) already encode the mode difference; a single `parseFromBuf<T>(text, ..., bool replMode)` template returning `T *` would consolidate the bodies.
    - ../verified/12-libexpr-parse.md
    - **Validation:** VALID. Single `template<bool replMode>` helper, or runtime-bool parameter, returning `Expr *` with the repl variant doing the cast at the public entry point. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libexpr` (static `parseFromBuf(..., bool replMode)` driver; both public entry points are wrappers; the `dynamic_cast<ExprAttrs *>` and asserts moved to the repl wrapper)

107. **`Printer::shouldPrettyPrintAttrs` and `shouldPrettyPrintList` are byte-for-byte equivalent modulo the element accessor.** Both check `!options.shouldPrettyPrint() || empty`, return `true` when `size > 1`, fetch the single element (`v[0].second` for attrs, `list[0]` for lists), guard a null pointer, call `state.forceValue(*item, item->determinePos(noPos))`, and return `itemType == nList || nAttrs || nThunk`. The only meaningful difference is that the attrs version dereferences `v[0].second` (the `Value *` half of an `AttrPair`) while the list version uses `list[0]` directly. A small `shouldPrettyPrintSingleton(state, Value *)` helper (or a templated `shouldPrettyPrint<Container>(c, extractValue)`) would dedupe the body and leave each public method as a one-line dispatch.
    - ../verified/12-libexpr-parse.md
    - **Validation:** VALID — but borderline. Two methods with a single accessor difference; smallest possible "duplicated code" cluster. Keep but accept it is borderline. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libexpr` (private `shouldPrettyPrintNonEmpty(size_t, Value *)` helper)

108. **`LazyPosAccessors` and `LazyFetcherAttr` re-implement the same internal-primop-plus-pre-applied-thunk machinery.** Both build an unregistered `PrimOp` whose `impl` decodes a forced argument, then construct a `Value` for the primop (`mkPrimOp`) and a `Value` carrying the deferred state (an integer-encoded `PosIdx` in `LazyPosAccessors::operator()`, an `ExternalValueBase` subclass in `emitLazyAttrThunk`), and finally splice them together with `dest.mkApp(vPrimOp, vState)`. `LazyPosAccessors` is a static-instance struct holding `primop_lineOfPos`/`primop_columnOfPos` plus pre-built `lineOfPos`/`columnOfPos` `Value`s; `emitLazyAttrThunk` builds a function-local `static PrimOp forcePrimOp` and allocates fresh `Value`s on each call. A generic `mkLazyValueThunk(state, primFn, stateValue)` helper (templated on the state encoding) would unify both at the cost of one extra `Value` allocation in the int-encoded case.
    - ../verified/12-libexpr-parse.md, ../verified/14-libfetchers.md
    - **Validation:** PARTIALLY VALID. The state encodings genuinely differ (int packed into `Value::Int` vs heap-allocated `ExternalValueBase`), and the pre-allocation pattern is asymmetric (one is a static-instance struct, the other allocates per-call — wasteful, could be unified with the pre-built shape). A `mkLazyValueThunk(state, PrimOp & primop, Value * stateValue)` helper unifies the splice step. Pre-allocating the primop `Value` for `__forceLazyFetcherAttr` (the way `LazyPosAccessors` does) is an independent win. Effort: small.

109. **`printIdentifier` re-implements `isVarName`'s character-class predicate by hand.** `isVarName(s)` (file-local in `print.cc`) checks `empty`, `isReservedKeyword`, the leading-char rejection `(c >= '0' && c <= '9') || c == '-' || c == '\''`, and the per-char predicate `[a-zA-Z0-9_-']`. `printIdentifier` (public) repeats the same first-char predicate (allowing `[a-zA-Z_]`) and the same per-char predicate inline before falling back to `printLiteralString`. `printAttributeName` then dispatches via `isVarName`. The two checks accept the same set of identifiers (modulo whether `_` is a permitted leading char in both cases). Factoring `isVarName` into a public helper and having `printIdentifier` call it would make the identifier classification a single source of truth.
    - ../verified/12-libexpr-parse.md
    - **Validation:** VALID. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libexpr` (promoted `isVarName` to a public helper and restructured its first-char gate to mirror the lexer's `ID = [a-zA-Z_][a-zA-Z0-9_'-]*` form directly; the predicate's accepted set is unchanged because the old `isVarName`'s per-char loop already rejected non-`[a-zA-Z0-9_'-]` bytes from the first position)

110. **Four parallel "value already seen" sets across renderers.** `Printer` (`print.cc`) uses `std::optional<ValuesSeen>` where `ValuesSeen = std::set<const void *>`, inserting `v.attrs()` for attrsets and `&v` for non-empty lists. `printAmbiguous` (`print-ambiguous.cc`) takes a caller-owned `std::set<const void *> *` with the same insertion rules. `getDerivation`/`getDerivations` (`get-drvs.cc`) use `Done = std::set<const Bindings *>` and insert `v.attrs()` (only for derivations, to dedupe `rec { x = drv; y = x; }`). `printValueAsXML` (`value-to-xml.cc`) uses `StringSet drvsSeen` keyed on the textual `drvPath` of derivations and only special-cases derivations. The first three track Bindings/Value identity; only XML keys on the drvPath string. A `SeenSet<Key>` abstraction (or a `dedupe(seen, key)` mixin) would unify the first three; XML's drvPath-based variant could live alongside as a separate specialisation.
    - ../verified/12-libexpr-parse.md
    - **Validation:** VALID. Compounds with #36. The first three (`Printer::seen`, `printAmbiguous::seen`, `getDerivations::done`) are uniformly `std::set<const void *>` keyed on `Bindings *` / `Value *` and unify trivially under a `using SeenSet = std::set<const void *>;` plus a `dedupe(SeenSet &, const void *)` helper. The XML drvPath-based variant has different semantics (string identity, not pointer) and stays separate. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libexpr` (`SeenSet` alias and `dedupe()` helper in `print.hh`; six sites updated, including `EvalState::forceValueDeep` migrated in a follow-up commit. `getDerivations::done` widened from `std::set<const Bindings *>` to `std::set<const void *>` — only `v.attrs()` is ever inserted, so behaviour is unchanged)

111. **`prim_match` and `prim_split` share the entire regex-fetch / forceString / regex_error scaffold.** Both open with `state.forceStringNoCtx(*args[0], pos, "while evaluating the first argument passed to builtins.<name>")`, call `state.regexCache->get(re)`, then `state.forceString(*args[1], context, pos, "while evaluating the second argument passed to builtins.<name>")`, and wrap the body in `try { ... } catch (std::regex_error & e)` that branches on `error_space` to throw "memory limit exceeded by regular expression" vs "invalid regular expression". The post-match assembly differs (single `regex_match` yielding capture list vs `cregex_iterator` yielding interleaved suffix/match list); both use the file-local `mkString(state, csub_match)` helper. A `withRegex(state, args, primopName, body)` helper that yields `(regex, str)` and centralises the catch block would shrink both functions.
    - ../verified/13-libexpr-primops.md
    - **Validation:** PARTIALLY VALID. Only the open/close scaffold actually deduplicates; the bodies are structurally distinct. Effort: small.

112. **`prim_ceil` and `prim_floor` cite `https://github.com/NixOS/nix/issues/12899` four times across two byte-for-byte-twin primops.** Each primop has two diagnostic blocks that reference issue 12899: one for the "NixInt rounded to -int_min on cast to NixFloat" undefined-behavior path and one for the "NixInt argument was rounded to a different NixInt" precision-loss path. The two primops differ only by `ceil(value)` vs `floor(value)`, so the four occurrences are really one diagnostic copy-pasted. Already partly covered by candidate #68 (which notes ceil/floor are byte-for-byte twins); the four-times-cited issue link is a more specific symptom that a `requireExactNixIntRoundtrip(state, pos, in, out)` helper plus a single `BUG_12899_URL` constant would fix.
    - ../verified/13-libexpr-primops.md
    - **Validation:** VALID. Compounds with #68. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libexpr` (`constexpr std::string_view bug12899Url`; passed to `error<EvalError>` as a `%1%` boost-format argument. Initial implementation used a `#define` BUG_12899_URL because the URL was concatenated into format strings via adjacent-string-literal syntax; post-cleanup review converted to a `string_view` since boost::format accepts it identically.)

113. **Trusted-`nixConfig` whitelist in `ConfigFile::apply` duplicates the `commitLockFileSummary` alias list.** `nix::flake::ConfigFile::apply` (in `libflake/config.cc`) hardcodes a local `StringSet whitelist{"bash-prompt", "bash-prompt-prefix", "bash-prompt-suffix", "flake-registry", "commit-lock-file-summary", "commit-lockfile-summary"}`, but the last two entries are precisely the canonical name and the alias of `flake::Settings::commitLockFileSummary` declared in `libflake/include/nix/flake/settings.hh`. Adding a new flake setting that should bypass the prompt requires editing both files; the bash-prompt entries are not declared in `flake::Settings` at all, so the whitelist is the only place that records them. Promoting "no-prompt" to a flag on the setting declaration plus iteration over `flake::Settings` (including aliases) would replace the literal list.
    - ../verified/15-libflake-libmain.md
    - **Validation:** VALID. **Note:** the `bash-prompt*` entries genuinely have no source-of-truth elsewhere in the tree — any "promote no-prompt to a flag" refactor must declare them as `flake::Settings` entries first, then add the flag. Effort: small.

114. **`getStringAttr`/`getBoolAttr`/`getStringSetAttr` in `derivation-options.cc` share one shape three times.** Each file-static helper (in `libstore/derivation-options.cc`) takes `(StringMap & env, StructuredAttrs * parsed, name)`, looks up `parsed->structuredAttrs[name]` first (calling `getString`/`getBoolean`/`getStringSet` with an `addTrace` wrapper), and falls back to `env[name]` with a per-helper coercion (`*i`, `*i == "1"`, `tokenizeString<StringSet>(*i)`). The three differ only in the JSON converter and the env-string parser. A single template `getAttr<T>(env, parsed, name, jsonGet, envParse)` (or two type-class-style overloads of `attrCoerce`) would dedupe all three.
    - ../verified/06-libstore-derivations.md
    - **Validation:** VALID. A function template `template<class T> std::optional<T> getAttr(const StringMap &, const StructuredAttrs *, const std::string &, T(*jsonGet)(const json &), T(*envParse)(const std::string &))` works directly. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libstore` (file-static `getAttr<T>` template in `derivation-options.cc`; the three call sites pass per-type `jsonGet`/`envParse` callbacks. Replaces `getStringAttr`/`getBoolAttr`/`getStringSetAttr` directly.)

115. **Generation-deletion helpers in `profiles.cc` share the `lockProfile + findGenerations` prologue.** `deleteGenerations`, `deleteGenerationsGreaterThan`, `deleteOldGenerations`, `deleteGenerationsOlderThan`, and `switchGeneration` (in `libstore/profiles.cc`) all open with `PathLocks lock; lockProfile(lock, profile); auto [gens, curGen] = findGenerations(profile);`, then walk `gens` with a per-function predicate to invoke `deleteGeneration2` (or `switchLink`). A `forEachGenerationToDelete(profile, predicate, dryRun)` driver parametrised on the predicate would consolidate four of the five (the `switchGeneration` shape is slightly different because it picks one target rather than a set).
    - ../verified/05-libstore-core.md
    - **Validation:** VALID. `forEachGenerationToDelete(profile, predicate, dryRun)` driver consolidates the four delete entry points; `switchGeneration` is structurally different (picks one target via `switchLink`) and remains. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libstore` (extracted only the `lockProfile + findGenerations` prelude into `withLockedProfileGenerations(profile, body)`; per-call iteration logic stays in each caller's lambda because `deleteGenerationsGreaterThan`/`deleteGenerationsOlderThan` use stateful reverse iteration with cumulative counters that don't fit a strict predicate-driven driver. Originally proposed as `forEachGenerationToDelete`, but the function does not iterate — renamed during post-cleanup review.)

116. **`Os` and non-`Os` halves of the environment-variables API are mostly thin wrappers on Unix.** `libutil/include/nix/util/environment-variables.hh` declares parallel pairs (`getEnv`/`getEnvOs`, `getEnvNonEmpty`/`getEnvOsNonEmpty`, `setEnv`/`setEnvOs`, `unsetenv`/`unsetEnvOs`, `clearEnv`, `replaceEnv`). On Unix (`libutil/unix/environment-variables.cc`) every `Os` overload is a one-line forwarder to its narrow twin (`OsString == std::string`); the cross-file `getEnvNonEmpty` and `getEnvOsNonEmpty` in `libutil/environment-variables.cc` are byte-identical bodies parametrised only on the underlying lookup function. On Windows (`libutil/windows/environment-variables.cc`) the two halves are genuinely distinct (`SetEnvironmentVariableA` vs `SetEnvironmentVariableW`). Picking a single `OsString`-based public API plus thin `std::string` overloads would halve the surface on Unix without losing the Windows split.
    - ../verified/03-libutil-runtime.md, ../verified/04-libutil-misc.md
    - **Validation:** VALID. ABI-visible API rename; well-defined surface. On Unix the forwarder is free; on Windows it does the conversion that's already happening in the narrow `getEnv()`/`setEnv()`. Effort: small.

117. **`narMaxDepth` is enforced in two places with two error messages.** `libutil/archive.cc` defines `static constexpr size_t narMaxDepth = 64;` and checks the bound twice: `SourceAccessor::dumpPath` raises `Error("path '%s' exceeds maximum NAR directory depth of %d", ...)` while the reader `parse` raises `badArchive("NAR directory nesting exceeds maximum depth of %d", ...)`. The two callers intentionally differ in wording (write-side names a path, read-side names the format), but the bound and the depth counter are shared. A `checkNarDepth(depth, [pathFn])` helper or a class invariant on a depth counter would consolidate the constant and the comparison.
    - ../verified/01-libutil-io.md
    - **Validation:** VALID. Wording differences are deliberate (write-side knows the path; read-side has only the wire stream), so a single helper should accept a callback or a tag — only the constant and comparison consolidate. Effort: trivial.
    - **Branch:** `vibe-coding/cleanup/libutil` (two file-static helpers — `checkNarDepthWrite(depth, accessor, path)` and `checkNarDepthRead(depth)` — share the constant; exception types differ deliberately (`Error` vs `SerialisationError`), so a single helper would lose that)

118. **Mercurial dirty-workdir handling in `mercurial.cc::fetchToStore` parallels Git's `getAccessorFromWorkdir` but factors no shared helper.** Both honour `settings.allowDirty`/`settings.warnDirty`, but the two implementations diverge on the result type: in `libfetchers/git.cc::getAccessorFromWorkdir`, the result is a `SourceAccessor` (built via `repo->getAccessor(workdirInfo, ...)` plus `makeNotAllowedError`/`makeMountedSourceAccessor` for submodules), and the workdir is recorded via `dirtyRev`/`dirtyShortRev` attrs. In `libfetchers/mercurial.cc::fetchToStore`, the dirty branch shells out to `hg status --clean --modified --added --no-status --print0` to gather tracked files into a `StringSet`, builds a custom `PathFilter` that lower-bounds against that set for directories, and copies the working tree into the store via `store.addToStore`. There is no shared "tracked-files filter" abstraction; the Mercurial side materialises into the store eagerly while the Git side delegates to the existing accessor stack. A common pre-`addToStore` filter helper plus a uniform `dirty*` attribute scheme would centralise the warn/allow check and the per-VCS path filter.
    - ../verified/14-libfetchers.md
    - **Validation:** VALID. Effort: medium.

    - **Branch:** `vibe-coding/cleanup/libstore` (added `BaseSetting<T>::overrideIfSet`; only the four `makeRequest` sites changed — `init`'s `setDefault` is a different shape and stays out)

120. **`getConcurrent` is shared, but the surrounding insert-on-miss pattern is hand-rolled at every site.** `getConcurrent(map, key)` (in `libutil/include/nix/util/util.hh`) wraps `boost::concurrent_flat_map::cvisit` to return `std::optional<mapped_type>`; it is used in `libutil/posix-source-accessor.cc::WindowsSourceAccessor::cachedLstat`, `libutil/mounted-source-accessor.cc::MountedSourceAccessorImpl::getMount`, three sites in `libutil/caching-source-accessor.cc::CachingSourceAccessor` (`maybeLstat`, `lstat`, `readLink`), `libstore/dummy-store.cc`, and five sites in `libexpr/eval.cc` (`importResolutionCache`, `fileEvalCache`, `srcToStore`, `resolvedPaths`, `lookupPathResolved`). The lookup half is shared via `getConcurrent`; the insert-on-miss half (`if (auto res = getConcurrent(...)) return *res; auto v = compute(); cache.emplace(...); return v;`) is hand-rolled at each site. A `getOrInsertConcurrent(map, key, compute)` helper would replace ~10 nearly identical bodies.
    - ../verified/01-libutil-io.md, ../verified/05-libstore-core.md, ../verified/11-libexpr-eval.md
    - **Validation:** VALID. **Note:** `eval.cc::evalFile` already uses `try_emplace_and_cvisit` directly, so a helper would also unify with that pattern. **See also:** N1 (the broader concurrent-insert-on-miss vs Sync<map> rubric — pass 2 splits N1 into N1a (insert-on-miss caches) and N1b (registries with ordered iteration); this candidate is squarely under N1a). Cross-references with #139 (`drvHashes`), Cluster A (concurrent state and globals). Effort: small.
