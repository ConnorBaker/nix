# B1 — investigate #134/#135 → #144 demotion

## Source-level structure

This section records the actual diamond as it stands in the tree (no
line numbers — names only).

### Inheritance graph

`Settings` (declared in `nix/store/globals.hh`) inherits four bases
**privately**:

```
class Settings : public virtual Config,
                 private LocalSettings,
                 private LogFileSettings,
                 private WorkerSettings,
                 private NarInfoDiskCacheSettings
```

Each of `LocalSettings`, `LogFileSettings`, `WorkerSettings`,
`NarInfoDiskCacheSettings`, and `GCSettings`/`AutoAllocateUidSettings`
itself derives `: public virtual Config` (where `Config` lives in
`nix/util/configuration.hh`). So the diamond is:

```
                 Config (virtual)
                 ^
                 |
   +------+------+------+--------------+
   |      |      |      |              |
LocalSettings  LogFileSettings  WorkerSettings  NarInfoDiskCacheSettings
   ^
   |
   +--- public GCSettings (also `: public virtual Config`)
   +--- public AutoAllocateUidSettings (also `: public virtual Config`)

   Settings : virtual Config, private {Local,LogFile,Worker,NarInfoDiskCache}Settings
```

`LocalSettings` itself is a *secondary* diamond:

```
struct LocalSettings : public virtual Config,
                       public GCSettings,
                       public AutoAllocateUidSettings
```

### Accessors

Every accessor on `Settings` is `return *this`:

- `Settings::getLocalSettings()` (mut + const)
- `Settings::getLogFileSettings()` (mut + const)
- `Settings::getWorkerSettings()` (mut + const)
- `Settings::getNarInfoDiskCacheSettings()` (mut + const)
- `LocalSettings::getGCSettings()` (mut + const)
- `LocalSettings::getAutoAllocateUidSettings()` const — **distinct shape**:
  returns `const AutoAllocateUidSettings *`, returning `this` when
  `autoAllocateUids` is true and `nullptr` when false. Used by
  `unix/user-lock.cc::createBuildUser` to gate auto-allocate behaviour.

`LocalBuildStoreConfig::getLocalSettings()` (in `local-store.cc`) is
**not** a slice of the diamond; it's a forwarder declared on a
`StoreConfig`-shaped type that simply does `return settings.getLocalSettings();`.
The header comment is explicit: "For now, this just grabs the global
local settings, but by having this method we get ready for these being
per-store settings instead." This is the migration affordance the
candidate text alludes to ("`localStore.config->getLocalSettings()` is
the long-term API").

### Constructor self-registration

`Settings()` body in `globals.cc` runs after the four sibling bases'
constructors have already run (each base's `Setting<T>{this, …}` member
ctors have called `Config::addSetting(this)` on the *Settings* object,
because virtual-base `Config` is shared and `this` is the most-derived
`Config`). That is exactly how the four sibling structs all register
their settings into the same `Settings::_settings` map without anyone
writing `addSetting` explicitly.

If `Settings` were composed-not-inherited, those `Setting<T>` members
would register against a *different* `Config` instance (the held
sub-config), not against `Settings`. Aggregating them on `Settings`
would require a forwarding `addSetting` or — cleaner — a two-phase
`registerSettings()` post-construction step, i.e. exactly what #136
proposes.

### `GlobalConfig::Register`

`globals.cc` carries `static GlobalConfig::Register rSettings(&settings);`.
This pushes the **whole `Settings` aggregator** (including all four
sub-config namespaces' settings, since they're virtual-base-fused into
`Settings::_settings`) into `globalConfig`. `globalConfig.set(key,value)`
and `globalConfig.getSettings(map)` then route uniformly through that
single registration regardless of which sub-namespace owns the field.

Likewise on `LocalSettings`/`GCSettings`/`AutoAllocateUidSettings`: the
GC and auto-uid `Setting<T>` members register onto the most-derived
`LocalSettings` (or, when `LocalSettings` is itself a base of `Settings`,
onto `Settings` — that's the diamond's load-bearing trick).

## Per-candidate dependency analysis

### #134 — Settings virtual-base diamond → composition

**Concrete proposal:** replace the
`Settings : virtual Config, private LocalSettings, …` diamond with
`Settings : Config { LocalSettings local; LogFileSettings logFile;
WorkerSettings worker; NarInfoDiskCacheSettings narInfoDiskCache; … };`
plus accessors that return references to the held sub-configs, plus a
mechanism for those sub-configs' `Setting<T>` members to register
themselves into `Settings::_settings` so that `globalConfig.set("keep-log",
…)` continues to find `keepLog`.

**Prerequisite:** **#136 is load-bearing.** Today, when
`LocalSettings::buildCores{this, …}` runs in the `Settings` ctor, `this`
is the most-derived `Settings` (because of the virtual base) and so the
`Setting<T>::Setting` ctor's `options->addSetting(this)` reaches the same
map regardless of which sub-class wrote the line. Composition breaks
that: a held `LocalSettings local;` member's settings register onto
`local._settings`, **not** onto `Settings::_settings`. To preserve the
single-aggregated-map property without #136, `Settings` would need to
either:

1. forward `addSetting` from each held sub-config back onto itself
   (requires the ability to introspect the sub-config's settings after
   construction — exactly #136's `registerSettings()`), or
2. expose four separate `globalConfig::Register` lines (one per held
   sub-config), turning today's single `rSettings` registration into
   four. That's a behavioural change that touches `nix.conf` parsing
   semantics.

So #134's clean form requires #136 first. Without #136, #134 either
multiplies registrations (#137 territory) or rebuilds an
`addSetting`-forwarding facility ad hoc — which is just #136 with a
different name.

**Does #144 subsume #134?** Partially. #144's "collapse the small ones"
quick win (fold `LogFileSettings` and `NarInfoDiskCacheSettings` into
`Settings` directly — they have no diamond presence outside `Settings`)
**does** shrink the diamond from 4 sibling bases to 2 (`LocalSettings`
and `WorkerSettings` are the only ones left after the small ones go
away). But it does not eliminate the diamond. `LocalSettings` and
`WorkerSettings` still need to live somewhere; either as composed
members of `Settings` (which is #134) or as sibling globals that
`Settings` does not inherit from (which would change the
`settings.getLocalSettings()` accessor's meaning from "this-Settings-as-a-LocalSettings"
to "the-other-LocalSettings-global", a much larger break).

**Does #136 alone subsume #134?** No. #136 makes composition *possible*
without changing which `Settings` instance owns the registry. But the
diamond-vs-composition choice is a separate design call once #136 has
removed the constructor-side blocker. A consumer of "the long-term
API" `localStore.config->getLocalSettings()` cannot decouple from the
global `Settings` until composition (or full per-store settings, #144's
"structural" half) lands.

**Verdict:** #134 has independent technical content that survives both
#136 and #144 individually. The **clean form** of #134 *requires* #136;
the **incremental form** (do #144's small-collapse first, then narrow
the diamond to LocalSettings-vs-Settings) reduces #134's surface area
but doesn't dissolve it.

### #135 — `LocalSettings`/`GCSettings`/`AutoAllocateUidSettings` flattening

**Concrete proposal:** drop `GCSettings` and `AutoAllocateUidSettings`
as separate classes; inline their `Setting<T>` members directly into
`LocalSettings`, prefixing the field names with `gc_*`/`autoAlloc_*`
to mirror the existing setting-name prefixes (`gc-reserved-space`,
`auto-allocate-uids`, etc.).

**Prerequisite analysis:**

- `getGCSettings()` returns `*this` — semantically *no* call site
  expects `GCSettings` to be a distinct type once flattening lands; all
  consumers use the per-field accessors (`gcSettings.minFree`,
  `gcSettings.keepOutputs`, …). The `LocalSettings`-as-`GCSettings`
  upcast slice is purely formal: zero `dynamic_cast<GCSettings *>` in
  the tree, the subset relation is never used. Removing the inheritance
  edge does not require #136 by itself — the consumer-side migration is
  mechanical.
- `getAutoAllocateUidSettings()` returns `nullptr` when
  `autoAllocateUids` is off. Its **one** caller
  (`unix/user-lock.cc::createBuildUser`) tests the pointer for null and
  reads `startId`/`uidCount` only when non-null. Flattening means the
  caller reads `autoAllocateUids` directly to gate, then reads the now-
  inlined `startId`/`uidCount`. A trivial 4-line edit.
- The `Setting<T>` members of `GCSettings` and `AutoAllocateUidSettings`
  currently register through the virtual-base trick onto the most-
  derived `LocalSettings` (or `Settings`). Inlining puts them directly
  on `LocalSettings`; the registration target does not change because
  `Setting<T>::Setting`'s `options->addSetting(this)` still reaches the
  same most-derived `Config`. **#136 is *not* load-bearing for #135.**
  The flattening can land without #136.

**Does #144 subsume #135?** #144's "collapse the small ones" mentions
`LogFileSettings` / `NarInfoDiskCacheSettings` / `WorkerSettings`
explicitly, but does not name `GCSettings` / `AutoAllocateUidSettings`
in the candidate body. The deeper-pattern theme N4 (X-macro driver) and
the catalog's "collapse small" framing both point at the same shape, so
#135 is morally a #144 quick-win. But the catalog text itself does not
list `GCSettings`/`AutoAllocateUidSettings` among the targets of #144 —
they're called out only in #135.

**Does #136 subsume #135?** No. #136 unblocks structural changes; it
does not propose flattening `GCSettings` into `LocalSettings`.

**Verdict:** #135 is logically identical in shape to #144's "collapse
the small ones" quick win, applied to the LocalSettings tree rather
than the Settings tree. **It does not require #136**, contrary to the
catalog's keystone-block claim ("#136 is the unblocker for #134, #135,
#137, #144, #149"). The catalog's chain is overstated for #135.

### #144 — per-subsystem ownership of the 19+ `Config`-derived globals

**Concrete proposal:** two paths, named in the body:

1. *Quick incremental wins:* collapse `LogFileSettings`,
   `NarInfoDiskCacheSettings` into `Settings` directly (eliminate them
   as separate types — they're pure namespacing); collapse
   `CompatibilitySettings` into `MixEvalArgs`/`EvalSettings`. Effort:
   medium.
2. *Structural full form:* dissolve the global `Settings`/`EvalSettings`/etc.
   instances entirely; have each owning subsystem (`Store::config`,
   `EvalState::config`, …) hold its own settings object. The
   `globalConfig` aggregator continues to work via per-subsystem
   registration. Effort: structural.

**Prerequisite analysis:**

- The quick-win collapse of `LogFileSettings`/`NarInfoDiskCacheSettings`
  into `Settings` does **not** require #136. Both classes have one
  caller pattern (`settings.getLogFileSettings()` and
  `settings.getNarInfoDiskCacheSettings()`) and pure field membership;
  inlining them is mechanical.
- The structural form *does* depend on #136 — moving settings off the
  global `Settings` and onto e.g. `Store::config` requires that
  `Setting<T>{this, …}` register against the per-store `Config`
  instance, which must outlive the `Setting<T>` members. That works
  today (since `Store::config` is a `StoreConfig` and `StoreConfig` is
  itself a `Config`), but per-store settings means *moving* a
  `Setting<T>` from one `Config` to another — and `Setting<T>` is
  non-movable because of the back-pointer in `Config::_settings`. So
  the structural form needs #136.

So #144's quick-win path is independent of #136; #144's structural path
requires #136.

**Does #134 subsume #144?** No. #144 is a much wider claim (19+ struct
collapse / per-subsystem ownership). #134 is local to the Settings
diamond.

## Decision: keep cross-referenced (status quo), but tighten the dependency annotations

I disagree with the consolidator's *rationale* but agree with the
*outcome*.

The consolidator's stated reason for keeping #134/#135 separate from
#144 was that "the dependency on #136 is the load-bearing fact" — i.e.,
collapsing into #144 would obscure that each requires #136. The source
review above shows the reasoning is asymmetric:

- **#134** does require #136 for its clean form. Keystone dependency
  is real.
- **#135** does *not* require #136. The catalog header's claim "#136
  is the unblocker for #134, **#135**, #137, #144, #149" is wrong about
  #135. #135 can land alone today.
- **#144 quick-win** does not require #136 either; only #144's
  structural form does.

So the load-bearing-keystone argument is true for #134 but **false for
#135**. By that argument's own logic, #135 should be demoted into #144
(both are quick-win collapses of small/diamond-only classes; both are
independent of #136), while #134 stays separate.

But there are three orthogonal reasons to keep all three separate
that the consolidator did not name:

1. **Different effort classes.** #134 is "medium gated by #136". #135
   is "small, today". #144's quick-win is "medium" (touching multiple
   structs). #144's structural form is "structural". A demoted
   sub-bullet inside #144 cannot carry an effort-class — readers
   choosing what to pick up next lose the ability to filter by effort.
2. **Different blast radii.** #134 changes the *type* of `Settings`
   (composition vs inheritance), which is a hard ABI break for any
   C++ consumer that derived from `LocalSettings` directly (none in
   our tree, but the candidate text flags Hydra-class consumers). #135
   only changes *which class declares each `Setting<T>`*, with no
   inheritance-shape change visible from outside `LocalSettings`. #144
   structural ranges from "trivial collapse" (LogFile/NarInfoDiskCache)
   to "rebuild every subsystem's config ownership". These are not
   substitutable.
3. **Sequencing.** Pass-2 itself (in `03-…`) recommends doing #144's
   quick-win **first** so #134 becomes a smaller exercise. That
   sequencing only makes sense when both candidates exist independently
   — if #134 were a sub-bullet of #144, the "do quick-wins first, then
   shrink #134" recipe loses its addressing.

**Decision: keep cross-referenced, but fix the keystone block to
reflect #135's independence from #136.**

This is a **hybrid in spirit** of the original three options: status
quo on the structure, but the "keystone-on-#136" annotation is
factually wrong for #135 and should be removed.

If the user wants a stronger structural change instead, the second-best
option is **demote #135 into #144's quick-win bullets** (since they
*are* the same shape of change applied to different sub-trees) and
**keep #134 separate** (its #136 dependency is real and load-bearing).
That's the *partial demotion* the brief listed as a hybrid. I'd
endorse that as a reasonable alternative — but not as my primary
recommendation, because #135's "drop the inheritance, inline the
fields" shape is structurally tighter than #144's "collapse the small
ones into Settings" (which keeps `LocalSettings` as a sibling of
`Settings` rather than absorbing it). Listing #135 as a sub-bullet of
#144 would conflate the two operations.

## Open questions

1. **`Settings` constructor body assigns to inherited Setting members
   directly (`buildUsersGroup = …`, `allowSymlinkedStore = …`,
   `sandboxPaths = {…}`).** These are `LocalSettings::buildUsersGroup`,
   `LocalSettings::allowSymlinkedStore`, `LocalSettings::sandboxPaths`
   in fact — accessed *as if* they were members of `Settings` via the
   private inheritance. If #134's composition refactor lands, these
   in-ctor assignments must be rewritten as e.g.
   `local.buildUsersGroup = …`. That's mechanical, but it widens the
   #134 patch by ~6 lines in `globals.cc`. Worth noting in #134's body
   (it's not in the candidate validation today).

2. **`getDiffHook()` and `findExternalDerivationBuilderIfSupported`
   are member functions on `LocalSettings`.** They're not just field
   bundles — they have non-trivial bodies. #135's flattening (move
   GC/AutoAllocateUid `Setting<T>` members into `LocalSettings`)
   doesn't disturb them; #134's composition refactor (hold a
   `LocalSettings local;` on `Settings`) doesn't either, since they're
   members of `LocalSettings` itself. No additional concern, but worth
   confirming that the candidate text doesn't accidentally propose
   replacing `LocalSettings` with a POD aggregate — it shouldn't, but
   the body's "field-name prefixes would be simpler" framing reads
   ambiguously.

3. **The `LocalBuildStoreConfig::getLocalSettings()` forwarder.** This
   is the migration affordance to per-store settings. It currently
   returns `settings.getLocalSettings()` (the global). If #144's
   structural form lands, this returns the per-store `LocalSettings`
   instead. #134's composition refactor leaves the forwarder's
   signature unchanged but changes the underlying object's identity
   (held member rather than `*this`). The interaction between #134 and
   #144 at this site deserves an explicit note — the forwarder is a
   #144 hook today, but a #134 patch that doesn't update it would
   leave the comment ("by having this method we get ready for these
   being per-store settings instead") stale.

4. **N4 (X-macro `*Settings` driver) interacts with all three.** N4
   would generate the struct + `Setting<T>` members + `globalConfig`
   registration from a single declarative table. If N4 lands first,
   both #134's diamond and #135's flattening become trivial table-edit
   operations rather than full refactors. If N4 lands after, #134/#135
   leave the per-struct hand-written form unchanged. The catalog's
   header already cross-references N4; no body edit needed, but
   sequencing-wise, **landing N4 first would dissolve #135 entirely**
   (a flatness/inheritance choice becomes a generator option). That's
   a stronger argument for keeping #135 separate today: it's the
   minimal landing target if N4 is deferred, and the trivial demote
   target if N4 lands.
