# B2 — investigate #65 + #211 merge

## Summary

**Decision: keep cross-referenced (status quo) — but tighten the cross-reference language to be explicit about layering and sequencing.** I disagree with pass 2's "merge into one structural candidate". I agree with the consolidator that the two candidates sit at distinct layers, but I think pass 1 / the consolidator under-stated *how distinct* the two are. The merge would conflate two refactors with non-overlapping API surfaces, non-overlapping risk profiles, and non-overlapping error-message-stability concerns. Sequencing matters (#211 should land first), but a merger destroys the option to ship #211 alone — which is the smaller, safer half.

## Source-level relationship

I read three representative `prim_*` bodies (`prim_ceil`, `prim_findFile`, `prim_genericClosure`, plus the type predicates `prim_isNull` … `prim_isPath`), the `force*` family in `src/libexpr/eval.cc`, and the inline forms in `src/libexpr/include/nix/expr/eval-inline.hh`.

### What each layer actually looks like

**Inner layer (#211, the `force*` family).** Two distinct shapes coexist:

- **Out-of-line shape (`eval.cc`).** `forceInt`, `forceFloat`, `forceBool`, `forceFunction`, `forceString` (single-overload), plus the `evalBool`/`evalAttrs` pair all use:

  ```
  try { forceValue(v, pos); if (v.type() != T) error<TypeError>(...).atPos(pos).debugThrow(); return v.<accessor>(); }
  catch (Error & e) { e.addTrace(positions[pos], errorCtx); throw; }
  ```

  That is **7 bodies** (forceInt, forceFloat, forceBool, forceFunction, forceString-single, evalBool, evalAttrs). The `forceString(NixStringContext&, ...)` overload and `forceStringNoCtx` *delegate* to `forceString(...)` — they don't duplicate the try/catch. So the actual try/catch/`addTrace` shape recurs **7 times**, not 10 and not 16.

- **Inline shape (`eval-inline.hh`).** `forceAttrs` and `forceList` are `[[gnu::always_inline]]`. Both use `withTrace(pos, errorCtx)` on the `EvalErrorBuilder<TypeError>` *instead* of a try/catch + `addTrace`. They are not part of the same duplication cluster.

  ```
  forceValue(v, pos);
  if (v.type() != nAttrs) error<TypeError>(...).withTrace(pos, errorCtx).debugThrow();
  ```

  This is materially different machinery: the trace is added at error-construction time rather than at exception-rethrow time. `withTrace` only fires if the type-check itself fails, while the out-of-line shape's `addTrace` fires for *any* exception escaping `forceValue` (including thunk-evaluation failures). Pass 1's catalog body lumped these together and the validation paragraph downgraded to "10 force* overloads"; the actual structural duplication is **7 try/catch wrappers + 2 inline `withTrace` checks** that are *not* the same pattern.

So the catalog body's "16 → 10 → ~7 pattern duplications" recount is correct for the try/catch shape only. The corrected corrected count of bodies that fit the same structural template is 7; `forceAttrs`/`forceList` are a different (better) shape; `forceString-with-context`/`forceStringNoCtx` are delegations.

**Outer layer (#65, primop-prologue boilerplate).** Each `prim_*` body opens with one or more `state.forceX(*args[N], pos, "while evaluating the [first|second|...] argument passed to builtins.<name>")` calls. Counts in `src/libexpr/primops.cc` + `src/libexpr/primops/*.cc` + `src/libflake/flake-primops.cc`:

| Helper            | Call sites |
| ----------------- | ---------- |
| `forceValue`      | 51         |
| `forceStringNoCtx`| 46         |
| `forceList`       | 29         |
| `forceAttrs`      | 25         |
| `forceInt`        | 16         |
| `forceString`     | 13         |
| `forceFunction`   | 13         |
| `forceBool`       | 12         |
| `forceFloat`      | 10         |
| **Total**         | **215**    |

Of those, **79** call sites use the verbatim `"while evaluating the [first|second|third|...] argument passed to builtins.<name>"` template (counted by `grep -rh "while evaluating the .* argument passed to builtins\."`). The remaining ~135 sites use richer messages — e.g. `"while evaluating the 'startSet' attribute passed as argument to builtins.genericClosure"`, `"while evaluating an element of the list passed to builtins.findFile"`, `"while evaluating the values of the second argument passed to builtins.removeAttrs"`. Those non-positional contexts are *not* mechanically derivable from `(primop_name, arg_index)`.

### Three representative primops walked

1. **`prim_ceil`** (single-arg numeric).
   - Body: `state.forceFloat(*args[0], args[0]->determinePos(pos), "while evaluating the first argument passed to builtins.ceil")`.
   - The error-context message is the canonical template; the position is `determinePos(pos)`, not `pos` itself (a subtle exception). #65 abstraction would need to expose the determinePos vs. pos choice as a parameter — both `prim_ceil` and `prim_floor` use `determinePos`, while most primops use `pos` directly.

2. **`prim_findFile`** (mixed: forceList outer, forceAttrs per-element, forceStringNoCtx inner).
   - Three different error contexts, only two of which fit the canonical template (`"first argument"`, `"second argument"`); the inner ones are `"while evaluating an element of the list passed to builtins.findFile"` and `"while evaluating the 'prefix' attribute of an element of the list passed to builtins.findFile"`.
   - A `validateArg(state, n, "findFile", nList)` helper would only deduplicate the outer two; the inner contexts are bespoke.

3. **`prim_genericClosure`** (the awkward case).
   - Outer: `forceAttrs(*args[0], noPos, "while evaluating the first argument passed to builtins.genericClosure")` — fits the template, but uses `noPos` instead of `pos`.
   - Inner: `state.forceAttrs(*e, noPos, "")` wrapped in *its own* try/catch that adds `"in genericClosure element %s"` via `addTrace`. The empty `errorCtx` is load-bearing — the primop wants to add a richer trace (with the element value printed) than `forceAttrs` would synthesise. A `validateArg` helper would actively *get in the way* here.

### Verdict on the layering claim

The consolidator's "outer / inner" framing is right: #65 sits in primop bodies; #211 sits in `EvalState` member functions. But the relationship is asymmetric:

- **#65 uses #211's API** — every `prim_*` site that calls `state.forceInt(...)` consumes the result of #211's body. Refactoring #65 doesn't require touching #211's API, *as long as #211 keeps the same `(Value&, PosIdx, string_view)` signature*.
- **#211 is invisible to #65's call sites** — if #211 is rewritten as `forceTyped<nInt>(...)` internally but exposes the same `forceInt(Value&, PosIdx, string_view)` wrapper, #65's call sites need no change.
- **#65's abstraction *might* want to bypass #211's outer wrapper.** A `validateArg<int>(state, n, "ceil")` could in principle call `forceValue` directly and synthesise its own trace, skipping `forceInt`'s try/catch entirely. That's a design choice for #65, not a forcing function.

## Independent-landing analysis

### Can #211 land without touching #65's call sites?

**Yes, cleanly.** #211 is a refactor of `EvalState::forceInt`, `forceFloat`, `forceBool`, `forceFunction`, `forceString` (and possibly `evalBool`/`evalAttrs`) into a single template:

```cpp
template <ValueType T> auto forceTyped(Value & v, PosIdx pos, std::string_view errorCtx) {
    try {
        forceValue(v, pos);
        if (v.type() != T) error<TypeError>(...).atPos(pos).debugThrow();
        return v.<accessor for T>();
    } catch (Error & e) {
        e.addTrace(positions[pos], errorCtx);
        throw;
    }
}
```

The 7 existing wrappers become one-liners delegating to `forceTyped`. Public API is preserved. All 215 call sites in primops continue to work without modification. End state: 7 bodies → 1 template + 7 thin shims (or eventually inline aliases). N20 (the table-driven `nValueType` dispatch) is the natural place to keep the per-`ValueType` traits (accessor, diagnostic noun, expected-type tag).

The two inline shapes (`forceAttrs`/`forceList`) are a separate question: they *could* be folded into the same `forceTyped<T>` template, but they currently use the better `withTrace` pattern (no exception interception). A merge into `forceTyped` would actually *regress* their error trace semantics. Better to leave them alone or refactor only the trace-shape if the team picks one direction (see `addTrace` vs. `withTrace` semantic question — out of scope here, possibly a separate candidate).

### Can #65 land without changing the `force*` API?

**Yes, but with a caveat.** A `validateArg(state, n, "ceil", v)` helper that returns the type-checked value can be written entirely in terms of the existing `force*` API:

```cpp
NixFloat validateFloatArg(EvalState & s, size_t n, const char * primopName, Value ** args, PosIdx pos) {
    return s.forceFloat(*args[n], args[n]->determinePos(pos),
        synthesiseArgMsg(n, primopName));  // "while evaluating the [first|second|...] argument passed to builtins.<primopName>"
}
```

The `synthesiseArgMsg(n, primopName)` is a `constexpr`/runtime helper that returns the canonical message. It saves ~79 hand-written strings (the canonical-template subset), each ~70-100 bytes — call it ~6KB of binary string-table reduction. The remaining ~135 non-canonical contexts stay inline because they're not derivable from `(primop_name, arg_index)`.

**Caveat: this helper does NOT subsume the entire arg-validation prologue.** Cases like `prim_ceil` (uses `determinePos(pos)` not `pos`) and `prim_genericClosure` (empty `errorCtx`, custom outer trace) would need a knob or remain inline. The realistic reach of #65 is "the ~79 canonical-template sites", not "every `prim_*`'s opening".

### Are there primops that bypass `force*` and would be migrated as part of #65 but not #211?

**Yes — the type-predicate primops.** `prim_isNull`, `prim_isFunction`, `prim_isInt`, `prim_isFloat`, `prim_isString`, `prim_isBool`, `prim_isPath`, `prim_isAttrs`, `prim_isList` all use `state.forceValue(*args[0], pos)` and then a manual `args[0]->type() == nX` comparison. They are *outside* #211's scope (they don't go through the `force*` wrappers) but *inside* #65's scope (they are part of the primop-prologue boilerplate, and #66 — the type-predicate-table-driven candidate — addresses them directly). #66 already exists and is the right home for the type predicates; #65 should cross-reference it.

There's also `prim_dirOf` (`forceValue` + manual `nPath` test) and the various `prim_*` that call `forceValue` and dispatch on type for genuinely heterogeneous behaviour (`prim_seq`, `prim_deepSeq`, `prim_trace`, `prim_addErrorContext`). Those are *not* arg-validation; they're "force, but then do something polymorphic". #65's helper does not apply.

## Merged-landing analysis

### Common abstraction?

The pass-2 proposal hints at "primop type-checking machinery" as a unified candidate. Looking at it concretely:

- A merged abstraction would be something like `validateArg<T>(state, n, primop_name, args, pos)` that *both* (a) generates the canonical "while evaluating the Nth argument..." trace context *and* (b) enforces the type *and* (c) returns the typed accessor. That helper would internally call `forceValue` directly, skipping the existing `force*` wrappers entirely.
- If the merged candidate goes that route, then **#211's `forceTyped<T>` template becomes redundant** for the primop-arg path (the 215 sites). It still serves the non-primop path: `evalBool`, `evalAttrs`, plus the ~30 non-primop callers of `forceX` (in `eval.cc`'s `Expr::eval` machinery, `attr-path.cc`, `print.cc`, `flake.cc`, etc.). So #211 remains worthwhile *outside* the primop-arg-validation context.
- Equivalently, the merged candidate could keep #211's `forceTyped<T>` as the underlying primitive and have `validateArg<T>` call into it. Then the merge is just "two refactors that share an inner helper" — which is exactly the "compounds" relationship the catalog already records.

### End-state cleanness

If we merge into one structural candidate ("primop type-checking machinery"):
- One PR that touches `EvalState`'s `force*` API, the 215 primop-arg call sites, and probably the `evalBool`/`evalAttrs` pair.
- ~15-20 file diff (primops.cc plus the per-fetcher primops files in `src/libexpr/primops/`, plus eval.cc, plus eval-inline.hh, plus flake-primops.cc).
- Massive churn in error message text: every primop-arg trace has to be byte-for-byte audited against the test suite expectations. The lang-test golden files (`tests/functional/lang/eval-okay-*.exp`, `tests/unit/libexpr/error_traces.cc`) are sensitive to this. Pass 2's expanded "daemon-client error-text preservation" concern (logged for #125) applies here too: error-trace text is observed by the C-API and by tooling that parses Nix's error output.

If we keep them independent (and let them land in sequence):
- #211 first: small, contained, internal-only refactor of `EvalState::forceInt` etc. Public API preserved. Zero risk to error-message text. ~50-line diff in `eval.cc`.
- #65 second: introduces `validateArg<T>` and the canonical-message synthesiser; migrates ~79 canonical sites; leaves ~135 bespoke-message sites alone. Larger diff but *all in primops.cc / primops/*.cc / flake-primops.cc*; no eval.cc changes.

**The independent end state is *better*** because it preserves the property that error-message text is migrated in one identifiable PR (#65), making the lang-test diff reviewable as a single concern. Merging conflates #211's "internal refactor, no observable change" with #65's "migrate ~79 string literals to a canonical synthesiser" — and the second concern is the only one with observable risk.

### Structural cost vs. cleaner end state

The merged PR would be ~10-12 weeks of effort for one engineer (estimate based on the file count, the test-golden-file blast radius, and the review back-and-forth on error-message wording). The split version is:
- #211: ~1 week (mechanical, no test churn beyond unit tests).
- #65: ~4-6 weeks (driven mostly by the test-golden-file audit and the per-primop bespoke-message judgment calls).

The split is shorter end-to-end *and* lets #211 ship while #65's error-message debate is still in flight.

## Sequencing

If kept separate:

1. **#211 lands first.** It's purely internal (no public API change, no error-message-text change), so no observable impact. After it lands, the `force*` family is one template + thin shims. *Note: the inline `forceAttrs`/`forceList` should NOT be folded into the new template — they're a different (and arguably better) trace-shape. Document that explicitly in #211's body.*

2. **#65 lands second.** The `validateArg<T>` helper sits *above* #211's `forceTyped<T>` and adds the canonical-message synthesiser. It migrates only the canonical-template sites (~79). Bespoke-message sites stay inline. Type-predicate primops are out of scope for #65; they belong to #66 (which lands independently).

3. **Partial #211 first?** A partial #211 — e.g. extract just the try/catch shell as a free function `withErrorTrace(pos, errorCtx, lambda)` and leave the type-check inline in each `forceX` — is possible but doesn't buy anything that the full template doesn't. Not recommended.

4. **Could #65 land before #211?** Technically yes, since #65 only reads #211's API. But there's no benefit: the canonical-message synthesiser is independent of how `forceX` is implemented internally. Order is set by risk profile, not by dependency.

## Decision

**Keep cross-referenced. Do not merge.**

Rationale:
1. **Different risk profiles.** #211 is internal-only; #65 is observable-text-changing. Merging exports #211's safety into a higher-risk PR.
2. **Different abstraction scopes.** #211's template lives on `EvalState`. #65's `validateArg<T>` lives in primops-land. They share the "type-check after force" idea but the abstractions live in different modules and serve different consumers.
3. **#211 is reusable outside #65's scope.** The non-primop callers of `forceInt`/`forceBool`/etc. (in `Expr::eval`, `attr-path.cc`, `print.cc`, `flake.cc`) all benefit from #211's consolidation. #65 doesn't touch them. A merge would suggest these callers also need #65-style migration, which they don't.
4. **#65's reach is smaller than the catalog body suggests.** The catalog says "Same shape ~hundreds of times" — actual count of canonical-template sites is **79**, with ~135 sites using bespoke contexts that #65 cannot mechanically migrate. The "structural" framing oversells the consolidation; the medium effort label was correct.
5. **The "compounds with" cross-reference is the right tool** — it acknowledges the layering without forcing co-shipping.

I disagree with pass 2's recommendation. The pass-2 framing ("two views of one refactor") is rhetorically clean but factually wrong: #211 would still be valuable even if #65 never lands (because of the non-primop callers), and #65 would still be valuable even if #211 never lands (because the canonical-message synthesiser is orthogonal to how `forceX` is implemented internally).

## Open questions

1. **Is the canonical "while evaluating the Nth argument..." string text part of any external contract?** If C-API consumers, error-formatting tools, or test frameworks parse this string, then even #65's helper needs to reproduce the exact byte sequence. I haven't audited the C-API for trace-string consumers. (If E4's daemon-client error-text matrix exists for `#125`, the same audit applies here.)

2. **Should `evalBool`/`evalAttrs` be included in #211's scope?** They share the try/catch/`addTrace` shape but operate on `(Env, Expr*)` not `(Value)`. #211's body says "plus the inline `forceAttrs`, `forceList`, `evalBool`, `evalAttrs`". The inline ones are different-shape (see above). The `evalBool`/`evalAttrs` pair is genuinely the same shape as `forceInt` etc. but the lambda body differs (`e->eval(*this, env, v)` instead of `forceValue(v, pos)`). A `forceTyped<T>` template parameterised over the "produce a Value" step (force vs. eval) could subsume both. Worth deciding at design time.

3. **Does `prim_ceil`'s use of `determinePos(pos)` (instead of `pos`) generalise?** A grep across primops.cc would tell us how many sites use `determinePos` vs. plain `pos`. If it's only `prim_ceil` and `prim_floor`, hardcode it as a knob in the helper; if it's broader, the helper needs to expose the position computation.

4. **What's the right home for the canonical-message synthesiser?** Free function in primops.cc, member function on `EvalState`, or `constexpr` table keyed by `(primop_name, arg_index)`? If `constexpr`, what's the upper bound on argument count (currently 3 in `replaceStrings`/`split`/`compareVersions`)? — small detail, decide at #65 design time.

5. **Should the type-predicate primops migrate to #66's table-driven approach as part of #65's scope, or strictly under #66?** I'd argue strictly under #66 — they bypass `force*` entirely and the duplication shape is "table of `(primop_name, ValueType)` pairs", which is a different abstraction from `validateArg<T>`. But the catalog should make the boundary explicit.
