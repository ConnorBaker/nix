## ROOT CAUSE (2026-06-02) — context-dependent producer trace hash; CONFIRMED

**Threshold (scale, NOT pathological input — settled):** stable ≤~53K traces
under BOTH the first-8000 and last-8000 package slices (different packages, same
~53K count); thrashes only on the full 10,839 pkgs / ~66K traces. So it is the
trace COUNT crossing ~53–66K, not a specific package.

**Failure mode (decoded from a thrashed cache):** a hot pass has verify.failed=
17,375 → misses=4,556, and recovery FAILS for ALL 4,556 (recovery=4,556,
recovery.failures=4,556). NO §14 empty-trace signature (smallest values_blob
bucket is 20–100B; every trace is current-pointed; History = 1 version/attr_path).
So this is NOT the §14 empty-trace defect Fix 1a closed — it is a distinct,
deeper flaw.

**Mechanism (code-confirmed):** the producer trace's deps are
`innerDeps = snapshotEpochRange(epochStart, epochEnd)` (primops.cc:1690) — a slice
of the GLOBAL `replayStore.epochLog_`, which grows via BOTH fresh recording AND
`replayMemoizedDeps` replay (context.hh:334). So a producer's hash is a function
of the global epoch-log STATE when `derivationStrict` runs — NOT a pure
content-address of the derivation's inputs. Cold (nothing memoized) vs warm
(other traces already materialized → different replay state) capture different
innerDeps for the same derivation.

**Smoking gun (direct DB diff, cold vs first warm pass, full workload):** of
66,208 shared attr_paths, 8,149 recorded a DIFFERENT trace_hash cold→warm —
**503 of them PRODUCERS** (same `__ca:<drvHash>`, different hash ⇒ different
innerDeps ⇒ context-dependent) + 7,646 consumers (the cascade from stale edges).
(Caveat: "producer" classified by values_blob<100B; a few small-scalar consumers
may be miscounted — but producers changing at all is the confirmation.)

**Why scale-dependent:** at ≤53K traces the materialize/re-eval interleaving is
reproducible enough that ~all producer hashes match cold↔warm (cache serves
clean); at ~66K the interleaving varies, a fraction (~1.5%) of producers capture
different innerDeps, and re-recording them perturbs the shared epoch log further
→ a DIFFERENT set destabilizes next pass → chaotic oscillation that never settles
(hot×10 never converged).

**Fixable vs inherent:** this is the documented "§3b does not isolate the
producer's own input-reads from ambient eval context" problem. Making innerDeps
context-independent is the aggressive sub-scope isolation that was TRIED AND
REVERTED as unsound (it under-records ambient deps the consumer needs). So it is
the RFC-scale "partition producer input-reads from ambient" problem — a DESIGN
flaw, not a small bug. Fix 1a fixed a different (empty-trace) symptom at 8-pkg
scale; this context-dependence is unaddressed and breaks warm caching at scale.

**Confidence:** mechanism code-confirmed; producer-hash instability directly
measured (the 503); scale-not-input settled. NOT isolated: WHICH specific
eval-order/replay difference makes those particular ~1.5% of producers
context-dependent (deeper still). n=1 per phase.

## TIER-0 CEILING (2026-06-03) — async-recording potential, measured

> **SUPERSEDED IN PART — see `cold-tax-decomposition-2026-06-03.md`.** Profiling the
> always-on tax (per the user's "profile the tax first") found the "~25s movable
> record" below is a misread: `recT`=28.97s is mostly GC-STALL wall, not record
> cpu (real record cpu ≈5–6s). The DOMINANT cold cost is GC mark amplification
> (+30.9s) from eval-trace's `traceable_allocator` value-keyed maps, which Tier-0
> does not touch. Read the decomposition doc before acting on the numbers below.

python3Packages cold, byte-identical output across all three:
- `--no-eval-trace` (true baseline): **18.7s** wall / 15.2s cpu / record 0s.
- eval-trace ON (no-§3b): **66.7s** wall / 55.9s cpu / **record.timeUs = 28.8s**.
- ⇒ eval-trace cold overhead = **48s**, of which **~29s is recording** (serialized
  on the eval thread by `syncAwait`), and ~19s is dep-capture + always-on tax.

**Tier-0 ceiling:** moving the ~29s record off the critical path → cold
~66.7s → **~38s (43% cut)**; cannot reach no-trace (18.7s) — ~19s of
dep-capture/tax is outside Tier-0's scope.

**Feasibility (confirmed):** `DataPathPool` (interning-pools.hh:24) is a resizing
`std::vector<DataPathNode> nodes` + map; `internChild` does `nodes.push_back`
(reallocates) while `collectPath` reads `nodes[cur]`. So a naive fire-and-forget
(worker `collectPath` racing eval-thread `internChild`) is UB. The vocab's
`paths` (attr-vocab-store.hh) is ALSO a resizing `std::vector<PathEntry>`
(single-writer). So a SOUND async record needs **eager-resolve**: do ALL
pool/vocab-reading resolution on the eval thread, hand self-contained material to
a worker for BLAKE3+serialize+store, copy the deps, defer the traceId wiring,
barrier at session end.

### CORRECTION — perf-measured record split (the naive ceiling above was wrong)

The "~29s movable, ceiling ~38s" above ASSUMED the whole record is movable. It is
not — `resolveDepKeyMaterial` (the pool read) must stay sync on the eval thread.
But the worry that resolve *dominates* (H-cold-1's comment calls pool resolution
"the dominant cold-record cost") is REFUTED at this point in the code: that was
the OLD 3×-resolve shape. Post-H-cold-1 (resolve 1×), `perf record` of a cold
python3Packages eval (557MB dwarf, comm=nix self-time, excluding parallel GC
markers) measures:

| record component        | self-time | async-movable?                 |
|-------------------------|-----------|--------------------------------|
| BLAKE3 (3× feeds)       | **13.2%** | ✅ owned/stable data           |
| sqlite / storage        | 5.3%      | ✅ store mutex                 |
| zstd / serialize        | 2.0%      | ✅ raw IDs/digests            |
| **resolve + collectPath** | **2.6%** | ❌ SYNC — single-writer pool   |
| sortAndDedup            | 2.9%      | ✅ pool-free                  |
| eval + GC               | ~78%      | (the no-trace baseline)        |

Counter cross-check (same run): recT=28.97s = hashUs 16.35s (resolve+BLAKE3 fused)
+ serializeKeys 1.03s + serializeValues 1.06s + storage/other ~9.5s. The 13.2:2.6
BLAKE3:resolve self-time ratio splits hashUs into **resolve ≈2.7s (SYNC)** +
**BLAKE3+framing ≈13.6s (movable)**.

**Corrected Tier-0 ceiling:** movable = BLAKE3 13.6s + serialize 2.1s + storage
9.5s ≈ **25s**; sync residual = resolve 2.7s (+ sortAndDedup, pool-free so also
movable). cold 66.7 → **~42s** (eval-bound; the ~19s gap to no-trace's 18.7s is
the always-on dep-CAPTURE tax, a separate H3-style lever, NOT Tier-0).

**Why the seam is SOUND (key finding):** the dominant cost (3× BLAKE3) reads only
the pre-resolved `ResolvedDepKeyMaterial` — owned `path`/`encodedBlob` vectors
(the collectPath output) + `string_view`s into the append-only, thread-safe
`StringInternTable`. serialize reads raw IDs/digests; storage is store-mutex.
NONE touch the single-writer `DataPathPool.nodes` or `vocab.paths` — those are
read ONLY in resolve (eval thread). So eager-resolve isolates the unsafe access
to the eval thread and the movable 25s is genuinely race-free on a worker.

**3× BLAKE3 is inherent, not reducible:** traceHash (TraceHashV2, contributing
deps + value), fullHash (FullTraceHashV1, all deps + value, UNIQUE storage key),
keySetHash (DepKeySetHashV1, all keys, NO value, dep-key-set dedup) have distinct
domains ⇒ divergent BLAKE3 states from field 0 ⇒ no compression sharing. So the
dominant cost can only be HIDDEN (Tier-0 async), not eliminated, without a schema
change that drops the keyset dedup.

**Implementation approaches (both sound; byte-identical is the bar):**
1. *Eager-resolve* — build `vector<ResolvedDepKeyMaterial>` (+ a resolved
   trace-context form, since vocab.paths is single-writer) on the eval thread; a
   feed3 variant indexes the pre-resolved material on the worker. Reuses H-cold-1
   machinery; RISK = reimplementing trace-context `feedPath` framing
   byte-identically.
2. *Buffer-the-preimage* — run the existing feed3 into 3 byte buffers (a
   `CanonicalHashBuilder` sink-to-buffer mode) on the eval thread; `blake3(buffer)`
   on the worker. Byte-identical BY CONSTRUCTION (same preimage), no framing
   reimplementation; RISK = a sink refactor of a hot-path class + 3×~MB buffers
   per record. Testable: assert `blake3(captured) == sync hash`.

Status: measured + designed, NOT yet implemented. The realized win depends on
overlap (eval per-attr > record per-attr ⇒ record fully hides) and a free core
(many idle; only the eval thread + GC markers are busy).
