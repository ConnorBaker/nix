# Derivation: from the specification to the implementation

This document is the implementation as it stands, derived from `01-specification.md`. Section 0 states the architecture and the correctness argument; section 1 gives each component as an equation in one unknown — the operation to write — with the check that would show it wrong (how each check is run is `05-validation.md`'s; the local store's locks, invariants and sink order are `08-store-model.md`'s); section 2 the risks a maintainer relies on; section 4 the defects of master this work found. Section numbers are stable because the code cites them. Locators are `file:line` in master at the branch's merge base unless stated; line numbers drift.

## 0. The architecture and the correctness argument

### 0.1 The architecture

The meaning is `01-specification.md`'s: a source and a store object are content-addressed trees; the store is a Merkle DAG of trees with reference edges; a tree has one address, its object hash — the git identifier of its root under SHA-256 — from which the store path is formed with the object's name and references, and the NAR is its serialisation, whose hash is computed by one walk when an old form asks for it and never stored (`01` sections 2.4 and 9.11).

The Store interface, the protocols, the database and the language changed as `01` section 9.11 says: path info carries `objectHash` where it carried `narHash`, the database column and schema, the fingerprint, the worker and serve protocols, the `.narinfo`, the path-info JSON, the lock file and the language's hash attributes changed with it (1.9); the store path's form and the string-context variants did not (`01` section 6). Deferral lives in the evaluator. `EvalState` holds a `WriteBuffer` (`src/libexpr/write-buffer.{hh,cc}`): a map from `StorePath` to pending bytes, references and the text hash, holding the outstanding writes of objects whose bytes evaluation already has — derivations and `toFile` texts — because their paths are functions of their content and are therefore known before the write (1.1). Sources are not deferred: the reference hashes and copies a filesystem source in one walk, and a pending source would need two (1.5). Mounted flake inputs use master's own accessor-based deferral, `mountInput` hashing without copying and `ensureLazyPathCopied` copying on dereference (1.5).

Outstanding text writes are discharged at the escape boundary (`01` section 3), by two rules. A door — an operation through which text leaves the evaluator — writes the whole buffer, references before referrers, in one `addMultipleToStore`, with temp roots taken at enqueue, whatever the text's own provenance says; a dereference — a name about to be read or handed to a reader — writes the buffer when the object named is pending and nothing otherwise. The string context also identifies mounted inputs: `derivationStrict` and `toFile` realise their opaque references before handing a text to the buffer, and `emit` copies the inputs its text names (`ensureLazyPathsCopied`) (1.2). Output sinks take a `RealisedString`, which only a flushing accessor of `EvalState` can construct. A bare `StorePath` obtained from a value is therefore valid by construction, and the Builder, GC roots and every command inherit that without knowing it.

Names come from one homomorphism inside the accessors — `subtree`, `filter`, `union`, `graft`, each with its derived naming rule (`01` sections 7 and 8): the vanilla git leaf names every subtree by its object with its mode, the fixed-set filter by the inner name and its prefix-closed admitted set, the evaluation root’s explicit input grafts by their fetched accessor names, and its unmounted fallback union by its contributing child names, declining a merged directory when one contributor is unnamed; one persistent memo, tree name to object hash (method and recursive name-decoding policy in the key, `sourcePathToHash`), serves git inputs and tarballs alike (1.3, 1.4; `01` section 9.9).

**The escape guard, as the semantics forces it (`01` section 3).** (C2) holds by construction exactly when the only ways of separating a string's text from its provenance are the exits that discharge the obligation first. The exits are two, told apart by the conditions: `realise` writes every pending object — whatever the string's own provenance says, so that a context-free text naming a pending path cannot escape either — and yields the bytes; `emit` does the same and also copies the mounted inputs the provenance names, and is used exactly where the reference copies them, the commands' outputs, because copying at a diagnostic would write what the reference does not (C1). Both yield a `RealisedString`, the only type the evaluator's printers and the commands' output statements accept. Exclusivity is the representation: a string value's bytes are private to `Value`, and the payload beneath them private to `Value` alone, readable only by the friends named beside them — the evaluator, the symbol table, the parser's literal, the tests — so outside the evaluator text is reached through the doors and nothing else, and inside it through `EvalState`'s accessors, which return bytes and provenance together, or refuse a provenance, for results that stay inside. A `StorePath` is obtainable from a value only through a flushing coercion, and a path about to be read is written first when it names a pending object. The text exits are therefore the sites the compiler refuses once the bytes are hidden, not a list kept by hand; the dereferences inside the evaluator that parse a store path from accessor bytes, and the builtins that drop a string's provenance, still flush by hand and are the enumerated rows of the table in 1.2, swept by the builtin test. What the compiler cannot scope is the accessors themselves, since C++ has no access control at the scope of a library: a check script holds them to `src/libexpr` and `src/libflake`, and what the kernel does with the bytes is reviewed. The libexpr accessor API changes, and so — by `01` section 9.11, not by this guard — do the Store interface's path info, the protocols, the database and the language's hash attributes (1.9); the store path's form and the context variants do not, so the guard is within the charter of `01` section 6 as it now reads.

### 0.2 The correctness argument, and what checks it

**The argument.** ⟦store with buffer⟧ = ⟦store⟧ + Δ, where Δ is what the reference would already have written (1.1). (C1): every object in the buffer is in Δ, and the flush is total and runs at every escape and at the end of the command, so the final store is the reference's up to the renaming the address induces (`01` section 3: every source's path, and everything built from one, is renamed; the objects are the same) — deferral reorders and batches writes and never omits one. (C2): a pending name can leave the evaluator only through a door or a dereference; a door writes everything before it emits, a dereference writes before it reads whatever it reads if that is pending, so no name escapes before its object exists. Naming soundness: equal name implies equal NAR, by the rules of `01` section 8 applied inside the combinators. The remainder — that each path is what master computes, that repair, garbage collection and the trust bit agree — is that each operation computes exactly what the corresponding master operation computes (1.1, 1.7).

**What checks it.** The differential harness runs master's functional suite under the reference and under the implementation and compares the resulting stores object by object, in local mode and through the daemon, under the renaming views (`05-validation.md` section 3). The sweep runs every builtin on a pending text, a pending derivation path and an attribute set naming them, against eager evaluation (1.2; `src/libexpr-tests/write-buffer.cc`). The (C2) observer dereferences every printed path from a second process (`05-validation.md` section 3), and a byte-level check fails any printer that emits a pending name. Naming soundness is a rapidcheck property over random terms and over real git trees (1.3, 1.4). The serialisation round trip is checked byte-exact over real store objects and directly for `.git` and the name domain (`01` section 2.7).

**What is not proved, in the built implementation.** The text exits are derived, not enumerated: the compiler confines a value's bytes to `Value`'s friends, and the check script confines `EvalState`'s accessors to the kernel, `src/libexpr` and `src/libflake` (0.1, 1.2). Inside the kernel the accessors return bytes, so a new primop could still hand them to a process-level sink without a door; review holds that, C++ having no access control at the scope of a library. The dereferences inside the kernel that parse a store path from accessor bytes (`storePath`, `fetchTree`'s attributes; the table of 1.2) remain an enumerated set, swept by the builtin test. The context-free case — a pending path's text arriving without provenance — is closed at the doors by their total write and at the reads by `writePendingBeforeRead`, pinned by `aContextFreeLiteralNamingAPendingPathCannotEscape` and `aContextFreeLiteralNamingAPendingPathCanBeRead` (`src/libexpr-tests/write-buffer.cc`); it still reaches two exits that are not doors, a diagnostic printed while the evaluator lives that names an attribute or a source literal (the repl's error print; a fatal error prints after the destructor's flush), and a path value built from a literal. The suite is bounded by the commands it contains; the sweep and the observer stand in where it does not reach.

## 1. Components as equations

### 1.1 The write buffer

**Meaning.** ⟦store with buffer⟧ = ⟦store⟧ + Δ, where Δ is the set of objects the reference implementation would already have written.

**Representation.** A member of `EvalState`, beside `store` and `storeFS`: a map from `StorePath` to a pending object, where a pending object is the bytes — a derivation's ATerm or a `toFile` text — its references, and the text hash computed to name it; the blob hash is computed only when a missing object is flushed, and sources are not pending (section 1.5). An already-valid object needs no pending write unless repair was requested: its temporary root protects its recorded closure. The remaining state is the set of references already temp-rooted, and the buffer's own footprint in bytes. The `ValidPathInfo` an eager write registers is not kept: it is built at the flush, by the call that named the path, so the description and the name are one equation. The bytes are held once, behind a `shared_ptr<const std::string>` the flush lends to the source it streams from and to the NAR-hash thunk the description carries — a thunk the store replaces, at the registration, by its own walk of the path, so that nothing the buffer held outlives the flush (section 2, *What the write retains*); and they are held at their own size, `addText` taking a `std::string_view` so that `unparse`'s 64 KiB reservation (`src/libstore/derivation/aterm.cc:798`) cannot be taken over with them. Both are memory, and both are measured: `05-validation.md` section 6.

**Operations, solved.**
- `addText(name, contents, references) -> StorePath`: compute the same text-addressed path as the eager write. A pending entry is reused and retains any repair request. Otherwise root the path, and return immediately if it is valid and repair was not requested; only an outstanding write retains bytes and roots references outside the pending set. The producers, `derivationStrict` and `toFile`, first realise their mounted opaque references, because this call may flush at the memory bound or return an already-valid path. Read-only evaluation keeps computing paths and writing nothing, as master does. The masked-hash memo seed at instantiation is unchanged.
- `flush()`: total. Order the pending set so that references precede referrers (a walk over pending references only, marking the entries themselves and carrying iterators, since at this size a second set of store paths is a copy of the buffer; references outside the set are already valid), build a `Store::PathsSource` of `(ValidPathInfo, Source)` pairs — each description built fresh by `ValidPathInfo::makeFromCA`, each source, a `NarOfString`, streaming the very bytes the entry holds as a NAR of a single file exactly as `dumpString` does and without a coroutine, a `sinkToSource`'s stack being a mapping made and unmade per object (`WriteBufferTest.theNarOfAStringIsDumpStrings`; `05-validation.md` section 6, the wall table) — and call `store->addMultipleToStore(...)` once with `NoCheckSigs`. The Store operations own path-info cache invalidation, including `RemoteStore` (section 2, *Client cache*). Empty buffer: return immediately, one branch.
- Trust bit: the daemon forces `ultimate = false` on bulk adds (`src/libstore/daemon.cc:553`); eager writes of derivations and sources already carry `false`, so the final state agrees. Built outputs are never in the buffer.
- Repair: `--repair` re-adds an existing derivation in master (`derivations.cc:128-129`). With the buffer, a repair request enqueues even if the path is valid and flushes with `Repair`. The differential test with `--repair` and the repair unit test are the check.

**Read-your-writes.** With a total flush there are exactly two in-process readers of a pending object that are not escapes: the masked-hash memo, seeded at instantiation so it never misses within a process, and the eval cache's getters, which are doors (section 1.2). Everything else that would read a pending object, `realiseContext`, `import`, `builtins.storePath`, `fetchTree`, the deep-dependency closure in `derivationStrict` (`primops.cc:1794-1810`), is a dereference and writes first what it is about to read. The builtin sweep of 1.2 holds this sentence to the code.

Two rules cover them (`01` section 10): a door writes the whole buffer, since a text's provenance may be incomplete; a dereference writes it when the object named is pending. A string that loses its provenance inside the evaluator (`unsafeDiscardStringContext`, `getContext`, `match`, `split`) is as safe as any other text under those two rules and needs no write of its own. Inside the evaluator text is reached through `forceString`, `forceStringNoCtx` and `coerceToString`, which return bytes with their provenance or refuse a provenance, for results that stay inside: comparison, symbols, the serialisers' accumulation, the eval cache's memo, the meta-attribute parsers, the flake primops. Outside it, through the doors only: `realise` — of a forced string, of rendered bytes, of a store path, and the forcing forms `realise(v, pos, errorCtx)` and `realiseNoCtx(v, pos, errorCtx)`, which are `forceString` and `forceStringNoCtx` followed by the total write — and `emit` and `coerceAndEmit` at the commands' outputs; `RealisedString` (`realised-string.hh`) is their result, and nothing else constructs one. "Realised" means written, not built; `realiseString`, which builds, writes totally first. `maintainers/check-string-kernel.sh`, run as a pre-commit hook, holds the accessors to `src/libexpr`, `src/libflake` and the tests — a boundary chosen, since C++ offers none finer; libflake's own code uses the doors and only its primops the accessors — and proves its three checks on each run by planting five violations in a scratch copy of the tree and requiring each to be reported (the textual matches it excludes are in `nix_api_external.cc`, the C API's callback table and the external-value interface, which use the accessor's name). The dereferences — `coerceToPath` and the resolved path, `coerceToStorePath`, the derived-path coercions, the fetchers' local inputs — all go through `writePendingBeforeRead`: written iff the object named is pending.

**Batching.** Every door writes totally, so a diagnostic in the middle of an evaluation — `builtins.trace`, `warn`, a printed value in the repl — splits the batch at that point: correct by (C2), and the cost of a diagnostic is the write of whatever is pending then. `nix-instantiate` prints each derivation path it obtained through `requireDrvPath`, which is `coerceToStorePath`, which flushes; so the command flushes once per top-level derivation, each flush carrying the derivations that evaluation created since the last one. That is the consequence of the decision that a bare `StorePath` obtained from a value is valid by construction; the alternative, coercion that does not flush, would move the obligation to every consumer of a `StorePath` in libstore, which the specification forbids. The bound that does hold: every flush writes at least one object, so a command makes at most as many bulk adds as master makes single adds, and exactly one when nothing escapes before the end.

**Residue, stated.** Outside the kernel, by construction on `Value` and by the check on `EvalState`; inside it, the accessors are public members, and review holds them. What the type does not reach: a store path named by its physical location in a diverted store, which `isInStore` does not recognise; the check script's textual limits, stated in its header; and the legacy `main`s' three end flushes (the teardown row above). Attribute names and source literals are context-free by construction and print through the same doors as everything else when they reach a diagnostic, since the repl's error prints and the printers realise the text they show, and a fatal error prints after the destructor's flush.

### 1.3 Mount and union alignment (libutil)

**Meaning.** `01-specification.md` sections 7, 8.2, and 8.4.

**Operations, solved.**
- `MountedSourceAccessor`: select the nearest explicit mount and retain its accessor, relative path and descendant bindings before invoking child callbacks. Directory shape follows from explicit descendants without inspecting the fallback; only listing and naming demand surviving directory contents. When needed, `resolveTree` checks only prefixes required by those descendants; an absent or nondirectory prefix discards the old fallback subtree. A selected mount with no nested bindings delegates directly, without source-ancestor probes. Strict ancestors of grafts answer as directories; their listing keeps surviving directory entries and replaces each mounted name, promoting names with deeper bindings to directories. An absent mounted root removes its old entry unless a deeper graft promotes it. Listing determines these directory shapes before querying any still-needed mounted root types. Reads below discarded fallback ancestry report absence, so a replaced symlink cannot leak its physical target. File/link reads at constructed directories are refused. `getKnownEntry` and `getPhysicalPath` decline altered subtrees. A composite fingerprint uses `graft-v2`, the surviving base name or an explicit empty base for discarded ancestry, and the descendant bindings' names; old partial-graft names cannot alias this meaning. `mount()` remains insert-only, and each operation owns the children it observed across callbacks.
- `UnionSourceAccessor`: the top-down definition of `01-specification.md` section 7.1. One function, `owner(p)`, gives the child whose node p denotes, or nothing when an earlier child's non-directory at an ancestor hides p; `readDirectory(p)` merges the directories of the owner and every later child that has one there; `readFile`, `readLink`, `maybeLstat` go to the owner. `getFingerprint(p)`: the three-case rule for a general union, with a merged directory named by the JSON of its parts' names or not at all. The evaluator’s unmounted fallback uses the same rule. A content-addressed input mount does not prove that an arbitrary raw host entry at the same logical pathname is the same complete tree; the former `ChildrenAgree` policy and its ancestor-hiding bypass remain removed. Cross-view tests compare the union’s names against both children, including private entries and every named/unnamed node-type pairing.
- `EvalState`: first build the original store view; in impure mode put the original host/store union at the root of an outer `MountedSourceAccessor`. Input mounts go into that outer graft map, then metadata/naming caching and pure/restricted admission wrap it. Thus an input owns its prefix without consulting host occupants. Its required ancestors become directories, including over host files or symlinks; displaced nondirectory ancestry contributes no sibling nodes. Elsewhere the fallback is unchanged. `mountInput` invalidates observations after publication and retains the first mount at a repeated point. This is the explicit semantic correction in `01` sections 3, 5 and 8.4: freshly reading an input and copying its opaque reference observe the same accessor. Existing import/search memos remain scoped to the evaluation epoch; mounts do not recompute previously evaluated or transitive values. It is not a claim that an arbitrary host occupant matches the input. Live worktree bytes and later address checks remain unchanged.

- `CmdShell`: after `Installable::toStorePaths(..., Realise::Outputs, ...)` discharges the selected outputs' materialisation obligations, interpret package metadata through the execution store's accessor. The evaluator may use a different store and its input grafts are not the execution namespace. This also corrects the reference's separate-evaluation-store failure, explicitly listed in `01` section 5.

**Checks.** A rapidcheck property over `MemorySourceAccessor` trees: for generated terms of the four operations with a content-naming leaf, equal names imply equal NARs at every path, and equal subtrees under a naming leaf imply equal names. Unit tests for the listing changes and the evaluator’s complete mount domain (`01` section 8.6): 180 node/location/admission combinations, twelve registration/physical-presence cases, thirty proper-ancestor kind/location/admission cases, and restricted/unrestricted fallback, symlink and nested-graft cases. The evaluation-epoch regression keeps cached imports and searches until explicit reset. The differential excludes only the explicit result/error corrections in `01` section 5; ambient-store imports at unmounted paths remain unchanged.

### 1.4 Names (libfetchers, libutil)

**Meaning.** The naming rules of `01-specification.md` section 8.2, with names withheld for attribute-dependent accessors.

**Operations, solved.**
- `GitSourceAccessor::getFingerprint(p)`: for an accessor with neither LFS smudging nor export-ignore, return the object identifier of the entry at p as the name and the root as the path: a tree identifier for directories, a blob identifier with its mode for files and symlinks, since the mode is part of the NAR (`src/libfetchers/git-utils.cc:874-1149` holds the entries; master has no override). Otherwise the input-level name, as on master. Submodule mounts are a graft above the leaf and get the graft rule from 1.3.
- `FilteringSourceAccessor::getFingerprint(p)`: when the accepted set is fixed at construction, the pair of the inner name at p and a canonical hash of the prefix-closed accepted set restricted to the paths below p (`01-specification.md` section 7.1); the set is computed once by the same top-down pruning walk `dumpPath` performs (`src/libutil/archive.cc:102-108`), so the accessor's tree and its NAR agree. Master's accessor forwards the unfiltered name (`src/libfetchers/filtering-source-accessor.cc:60-65`). For the allow list, whose set grows: pass the inner name through when p lies under an allowed prefix, since everything beneath is then admitted, and withhold a name otherwise.
- `fetchToStore2`: replace the `filter ? nullopt : getFingerprint` bypass (`src/libfetchers/fetch-to-store.cc:64-65`) by wrapping the source in a fixed-set filtering accessor built from the predicate, and pass no `PathFilter`. The store path is unchanged, because dumping the wrapped accessor without a filter produces the same NAR as dumping the unwrapped one with the filter: both are the pruning walk. The persistent memo keys the accessor's name with the method and, for Git/NAR, the directory-name decoding policy (`sourcePathToHash`) — and its Git value is the node’s entry `{hash, mode}`, from which the root object address is derived (`01` section 9.9); it becomes the subtree memo because the git leaf names subtrees.
- The in-process memo retains the pure naming result `(StorePath, Hash)` under the current view fingerprint, relative path, address method, logical store directory, output name and, for Git/NAR, the directory-name decoding policy. These are exactly the arguments that determine that result; the key owns neither the source nor a store connection. A hit avoids deriving the same address and rewriting the same memo entry. A dry-run entry or a completed copy in another store still establishes no presence in the requested store: every copy roots and checks that destination before returning, and walks when it is missing (section 1.5).

### 1.5 Sources in the buffer

**Meaning.** Δ contains every `builtins.path` and `filterSource` result, every `toFile`, every instantiated derivation, and a mounted flake input only when the reference would copy it.

**Sources stay eager.** Enqueueing `builtins.path`, `filterSource` and `copyPathToStore` results as pending sources, with the accessor as contents, is refuted on cost and empty on correctness:

- The reference copies a filesystem source in one walk: `copyPathToStore` (`src/libexpr/eval.cc:2700`) and `addPath` (`primops.cc`) call `fetchToStore(Copy)`, which for a path without a fingerprint, that is every path under the real filesystem, goes straight to `addToStore(name, path, ...)` and hashes while it copies. A pending source needs its store path at once, since the language returns it, so it must be hashed at enqueue; the copy at flush is then a second walk. Under no elision every source in Δ is written by the end of the command regardless, so deferral saves no write and costs a walk, or the memory to hold the NAR. The persistent memo does not help: it is keyed by fingerprint, which filesystem paths lack.
- The bulk add cannot take a source whose NAR size is unknown: `LocalStore::addToStore(info, source)` checks `narSize` as well as the object hash (and an asserted NAR hash, when the sender asserted one) (`src/libstore/local-store.cc`), and neither the memo (`sourcePathToHash` stores the hash alone) nor `computeStorePath` yields a size. Streaming a mounted input into the batch would need a third libstore API or a sizing walk.
- Mounted inputs are already deferred: hashed once at mount (`mountInput`, `paths.cc`), copied on demand at the doors that copy, and at the dereferences (`ensureLazyPathCopied`, called from `derivationStrict`, `toFile`, `realiseContext`'s callers, `exec`, `nix eval`, `nix-instantiate`, `installable-value.cc`, `app.cc`). The two text producers realise their mounted opaque references before enqueueing: a threshold flush must see valid references, and an already-valid referrer must still detect a mounted source whose contents have changed. `path`-type inputs are not even mounted: their fetcher names them by one walk and copies them, when the store lacks the tree, before evaluation sees them (`src/libfetchers/path.cc`, `PathInputScheme::getAccessor`; `01` section 10, *a `path:` input outside the store is named first*).
- Correctness gains nothing: an eager write satisfies (C1) and (C2) trivially, and the specification's "Δ made explicit" does not require Δ to pass through the buffer, only that the implementation be the reference with Δ accounted for. The buffer holds what deferral makes free, objects whose bytes are already in memory.

**The order of copy and emission in `nix eval`.** The reference prints a mounted input's path and copies the input afterwards (`src/nix/eval.cc`, `ensureLazyPathsCopied` after the output statements); once copied the input is in Δ for that command, so a reader of the output can hold the name before the object exists. This is the case the specification's ordering rule names (`01-specification.md` section 3). `nix eval` copies before it emits, in all four output modes: `--raw` and `--json` after producing their bytes and before writing them, `--write-to` per string before `writeFile`, and the default printer after rendering the value to a string and before writing it. `builtins.trace`, `builtins.warn` and the repl's `:p` are left as the reference has them: they never copy, so copying there would add an object to the store the reference does not add, and (C1) forbids it. The check is the (C2) observer with a git input large enough for the copy to take visible time, which distinguishes the two orders (`05-validation.md` section 3, the observer's mounted-input modes).

### 1.7 The store's object store (libstore, libfetchers)

**Meaning.** `01-specification.md` section 9.10: the local store keeps its objects' trees as git objects under SHA-256 — blobs, trees, the executable bit on the edge — and a store path is a view of its tree whose regular files are hard links to the canonical file for each (blob, mode) — which, for a regular file, is *a store path's own file*, a **holder**, the store keeping an index from (blob, mode) to it, and, for a symlink's target blob and a tree body, a file of the store's own naming under `.objects`. The roots are the column: which root a path has is the object hash in `ValidPaths.hash` (1.9). Unconditional: there is no setting (the `auto-optimise-store` of master is removed, `01` section 10), and the object store is what a local store is.

**Representation.** `GitObjectStore` (`git-object-store.cc`, `.hh`), over `<realStoreDir>/.objects/`: `blobs/<xx>/<id>` (0444), `blobs-x/<xx>/<id>` (0555, the twin made only on demand and never by a link across the bit), `trees/<xx>/<id>` (raw body), `tmp/`. No `roots/`. `<xx>` is the identifier's first byte in hexadecimal, git's own layout, 256 shards under each kind; every name is built by one function, `nameUnder`, and every enumeration by one other, `eachObjectFile`, which also yields a file lying flat in a kind's directory, where an earlier, unreleased build of this branch put it. The four directories are made when a writable store is opened (`createDirectories` in `LocalStore`'s constructor) and again at the start of the sweep and of the inode table (`08` K12); a shard is made by the first write into it, on the `ENOENT` its link gets, so a store's open costs four `mkdir`s and not 772. The other readers treat their absence as emptiness. Identifiers are SHA-256 in git's object format, computed by libutil's `merkle::blobId`/`merkle::treeId` over the framing, ungated, equal to libgit2's for the same bytes (checked). The copy from the store's own objects walks a directory's subdirectories on a bounded pool (fixed at the machine's width capped at eight; `08` K17), its own files on the walking thread; every read and hash stays on one thread, the source accessor serialising them. `blobs` and `blobs-x` hold the symlink-target blobs alone; a regular-file blob's file is a store path's own, and where it is, is the index below. Two operations put a regular file under the store's care, and they are the whole of optimisation: `link(id, mode, dirFd, name, where, size, repair, hold)` *before* a file is written, and `place`, *after* a file is written and canonicalised. A registered candidate is acquired by a hard link before its inode, device, size, type, mode and timestamp are checked against the row and canonical metadata; repair additionally hashes the acquired inode. `link` acquires under the new name, `place` under a temporary name and validates before renaming over the existing file. A rejected acquisition removes only that new link, conditionally forgets the observed row, and tries the next registered candidate; the donor's file is never removed. Missing candidates are misses; link or directory limits leave the destination unwritten or as written respectively. A completed file in the same ingestion is already under its destination's ownership and takes precedence over registered candidates. A miss in `place` makes the written file a holder with a pending row and no filesystem call; its result records the final inode and whether the file was entered. `enterWritten`, the form for a file written because `link` missed, is one `fstatat` and a pending row, and issues no `linkat` at all. Around them: `putBlob` (a symlink's target, from bytes), `putTree`, `putRootTree` (the synthetic tree of an executable or symlink root, through which its blob is reachable), `readTree`, `parseTreeBody`, `holderOrForget`, `blobInodes()` and `sweep`.

**The index, the ingestion, the stale rule.** The object store does not own the index: it reaches it through `GitObjectStore::Index`, three functions — `lookup`, `forget`, `inodes` — that the `LocalStore` owning the object store installs (`blobIndex`, `local-store.cc`); a bare `GitObjectStore` has none and misses every lookup, which is how the unit fixtures and a lower store behave. *The tables* are `Blobs(id, exec, ino, dev, ingestion, name, size)`, primary key `(id, exec, ingestion)` on the identifier’s **32 bytes**, avoiding the doubled key of hexadecimal; its `name` relative to the holder's store path, because a store path never moves; and `Ingestions(id, path, hold)` (`schema.sql`). `Blobs` stores that complete key directly, without a separate SQLite row identity; its ingestion index retains the same logical lookup. The named migration copies all seven columns transactionally, including currently invisible candidates; read-only opens use either layout without migration. The holder's path is named *through* `Ingestions` and not by a foreign key into `ValidPaths`, because a completed builder output can hand off its rows before bulk validity registration. *The ingestion.* `beginIngestion(hold, root)` starts a fresh per-path projection with `setRoot`; its candidate rows remain private in the hold until that path is complete. Workers record them in 256 lazy shards. Each row owns its identifier once; the pending index projects its active hash bytes and executable bit instead of storing a second encoded key. Tags and inactive bytes remain data in the first retained row, not part of pending identity. After all walking workers join, `takeRows` transfers the completed rows and retires their pending first-winner map; publication retries own those rows independently. A database identity is allocated at the completed-path boundary. There is no background writer or separate writer connection. Completion carries the whole eligible regular-file projection, including the empty set. Reusing a registered holder records this ingestion's own candidate from the acquired status: collecting the donor before publication cannot erase the recipient's witness. Each `(blob, mode)` keeps its first completed pending candidate; a worker that acquired another inode links that pending winner over its own file. `registerValidPaths` reserves SQLite’s writer before querying collisions, reconciles overlapping regular inodes before exposing candidates, and replaces every previous ingestion for that fully ingested path in the same transaction. `endIngestion` does this itself for already-valid repair and optimisation paths; for a new builder output it names an invisible completed projection, recovered at later bulk registration by one indexed `(path, hold)` lookup per output. Each completed builder output is handed off before the hold starts its next path; the latest ingestion for each `(path, hold)` is that completed projection. Raw metadata registration and `--load-db` provide no projection and retire none. Old failed named ingestions therefore cannot become visible merely because a later successful writer registers the same path, and repeated optimisation retains no ingestion history. Lookup joins `Blobs`, `Ingestions` and `ValidPaths`, enumerates candidates by signed `(device, inode, ingestion)` order, and conditionally forgets only an invalid observed candidate. A collision costs one physical no-follow alias walk under the writer reservation; a path without a collision has no extra filesystem pass. The helper never invokes the database, auxiliary namespace locking or temp-root registration. It pins donors, checks canonical metadata and hashes their bytes before relinking, returning the partial map of eligible own or winning representatives; refused sharing contributes no new canonical donor. *The stale rule* replaces the cascade a foreign key would have given: a persisted row whose ingestion has no path, or whose path is no longer valid, names no holder, and two things judge it — `holderOrForget`, which forgets the one row it met, and `LocalStore::sweepStaleBlobRows`, which removes every such row and its ingestion in two statements under the GC lock, keeping the rows of an ingestion still in flight, whose hold is still under `.objects/tmp`, exactly as the sweep keeps that ingestion's objects. It runs after the object sweep, because the object sweep is what removes a dead ingestion's hold — and it runs after it *unconditionally*: `LocalStore::sweepObjects` is not virtual and is the two halves in order, the overridable `sweepObjectStore()` and then `sweepStaleBlobRows()`, so a store that replaces the first (the local overlay store, with its upper layer) cannot lose the second (`gc.cc`; `08` §1.5, K13, K16).

**One hasher, one traversal, the visitors.** The hasher is libutil's `HashingVisitor` (`object-hash-sink.hh`), a `NodeVisitor<HashedNode>` over the one traversal `traverse` (`tree-traversal.hh`): a node's result is its entry and optional NAR size; a directory's encoded body stays local to hashing and publication, since its parent needs only that summary; an owned child name moves into the finite map after its visit, and a refused insertion changes neither the map nor its NAR-size summary; the algorithm is `merkle::hashAlgo` (SHA-256) and nothing else — the hasher has no algorithm parameter, and `checkIngestionAlgorithm` refuses any other algorithm at every creation entry. Two drivers deliver nodes to a visitor: `traverse` over an accessor — the depth bound first, then stat and `node(path, stat, descend)` before contents are read, the names unhacked as `dumpPath` unhacks them, the descent by the on-disk name — and `ObjectHashSink`, the push adapter from the sink protocol (`parseDump`) to the same visitor, which never calls `node` and must consume every child immediately; `objectHashOf(accessor, path, filter, visitor)` runs the first, `objectHashOfNar` the second. A deferred pull visit borrows the physical-name string from the listing or its validated remapping, and one directory context shared by all siblings. Both outlive every accepted visit; the child closure carries only those two references, while the push driver retains its immediate-delivery contract. Its stack borrows the callbacks owned by active directory calls, so recursive growth cannot relocate an executing callback or discard its state between siblings. `MemoVisitor` (`fetch-to-store.cc`; 1.6) derives from `HashingVisitor` and surrounds a node's synchronous descent with lookup and recording. The store's five derived visitors are in `optimise-store.cc` — `ObjectStoreVisitor`, which writes each symlink's target as a blob (`putBlob`) and each directory's body as a tree (`putTree`) from `hashDirectory`'s local pair of summary and encoding, regular files being the drivers' business; `LinkingVisitor`, the restore route; `MaterialisingVisitor` over it, the copy from the store's own objects (below); `EnterVisitor`, the on-disk route; `VerifyVisitor`, the verifier's. *A stream being restored:* `LocalStore::restoreThroughObjects` runs `parseDump` → `ObjectHashSink` → `LinkingVisitor`, whose scoped current frame borrows the `RestoreSink` each directory's callback handed back, seeded with the caller's, so a node is created on the innermost sink under `/name`; `directory` opens `createSubdirectory`'s scope and visits the children inside it, so `directoryDone` (canonicalisation) runs when the scope closes, before the tree is written; `symlink` creates the link, then hashes. A regular file goes to the hasher as its bytes arrive and is held in memory up to `restoreBufferLimit` (one mebibyte; `BufferThenStreamFile`); with the entry in hand the visitor decides: a blob the store holds is linked under the name (`GitObjectStore::link`, acquisition and validation as above) and never written — the restore sink's `regularFileCreated` does not fire for it; a blob the store lacks is written from its complete memory buffer through the fresh restore writer's unbuffered operation, then finished with the same canonicalising hooks and entered as the store's file (`GitObjectStore::enterWritten`: one `fstatat` and a pending row, no `linkat` on a miss). If another worker completed the same blob meanwhile, `place` resolves that pending winner before returning; link or directory limits leave the file as written. The entering runs on the walk's own thread: moving it to a thread of its own was built and measured slower, and `01` section 10 and `05` section 6 say by how much and why. A file the NAR announces above the limit (`preallocateContents` precedes the bytes), or that overflows without an announcement, is opened at once (`RestoreSink::beginRegularFile`, the two-phase regular file), streamed, finished and entered through `enterWritten`, which calls `place` because no earlier lookup occurred: a miss records the written file, a hit replaces it with the acquired holder. This write-then-link cost is paid on large files, where the write dominates it. *Why the decision is made before the write.* The question "does the store hold this blob?" needs the blob's identifier, a function of every byte, so it is answerable only when the last byte has been seen; a sink that writes bytes as they arrive has already written the file when the answer comes, and on a hit must undo the write — link the store's file to a temporary name and rename it over the file just written. Measured on APFS, that link and rename cost three and a half times the write they undo, and made a second fetch of a 4000-file tree differing in one file two and a half times slower than a sink that decides first [unverified: measured during the work; the run is not in the tree]; a composition of the two sinks through the generic tee, which writes every file first, was built and measured slower, and this is why. The root's synthetic tree is written after the walk (`putRootTree`). The three ingestions call it — `addToStore(info, source)` from a NAR, and both restores of `addToStoreFromDump`, which every `Store::addToStore` from an accessor reaches by serialising the accessor (`store-api.cc`) — each after its `autoGC()`, so the collection an add triggers cannot sweep the add's own objects (`LocalStoreAutoGCTest`), and register the root as the object hash and the size as `narSize`. *The copy from the store's own objects* (`01` §9.10, *One route*, the second route; `LocalStore::materialise`, `materialiseThroughObjects`, `MaterialisingVisitor`): `fetchToStore2`'s copy, under the git method into a local store for which `materialisesFromObjects()` holds — the one predicate, asked in one place — runs the pull driver over the source accessor with a `LinkingVisitor` beneath and a `node` continuation that can answer the root and each directory from the store: the producer's canonical entry or the naming's memo (`MemoVisitor::lookup`, passed as the `TreeNamer`) gives the node's entry, and when the store holds the tree body — read and verified against its identifier by `GitObjectStore::readVerifiedTree`, refused with a warning when it does not hash to its name — the subtree is made from the objects alone, `mkdirat` per directory, `GitObjectStore::link` per regular file (an ordinary registered hit costs one index lookup, one `linkat` and one `fstatat` of the acquired inode; a rejected candidate advances the lookup cursor; on a system that does not link the file, the holder's bytes are read and written plainly), the target read from its blob and checked for a symlink, the canonicalising hooks run on each directory and symlink as `RestoreSink` runs them, and the NAR size summed from the blob files' sizes and the names; a node the memo does not name, or a directory whose objects the store lacks or holds corrupt, is left to the driver, which lists it and hands its files to the `LinkingVisitor` as the one route would — linked when held, written when not — after whatever the failed materialisation made is removed. `MaterialisingVisitor::tryKnown`, called by `node`, first asks the source producer for a regular file's canonical SHA-256 entry. Under `NoRepair`, a matching entry lets it probe the holder before reading bytes; a miss streams the immutable bytes directly into the destination without buffering or hashing them again. Only producers that established canonical modes and rendering supply this fact (`getKnownEntry`), including the canonical SHA-256 tarball cache; an arbitrary Git object ID or input assertion does not. When that fact is absent, only roots and directories consult the naming memo, so the ordinary copy adds no SQLite lookup per unnamed regular child. Repair bypasses the producer-identity shortcut. A named directory may still be materialised from the store, with its tree bodies verified and acquired regular-file bytes hashed under repair; an unusable object falls back to the source. The on-disk names follow the NAR restorer's case hack on both paths (`CaseHackNames`, one rule shared with `parseDump`: from a tree body the entries are visited in the NAR's order, so a colliding name is numbered as the restorer numbers it). A copy that stages uses `addToStoreFromDump`'s publication steps — `autoGC()` before its first write, a locked temporary directory in the store, the destination temp-rooted, locked and checked valid again, then moved into place (`EXDEV` copied and entered by the one walk), fsynced under `fsync-store-paths` and registered with the root's object hash and the walk's NAR size. An unnamed regular root can establish validity before staging, as below. The deferred version-1 signature check of `addToStore(info, source)` has no analogue, as it has none in `addToStoreFromDump`. A speculative directory keeps its regular-file rows in `Hold::ownRows()` until the entire subtree succeeds. A failed attempt deletes only names it has not offered to sibling workers. On success, the parent ingestion claims each completed candidate; if an earlier parent candidate has another inode, the same physical alias walk used at publication reconciles every local alias. Only copied collision rows are rebased to the subtree; published rows retain names relative to the whole ingestion. Once any row is published, a merge error aborts the copy and its workers join before cleanup; it cannot return to source fallback. This merge precedes the copy's normal durability boundary. The memo is consulted and never written by this route, so that a first entry pays no upsert per file; the rows are the naming walk's (1.6). *A path already on disk:* `enterIntoObjects` — the walk `nix-store --optimise` (`optimiseStore`), the after-build `enterPath` and the flat-add and `EXDEV`-copy routes of `addToStoreFromDump` make, one walk per built output and per flat add, which hashes and enters in the same pass, under `--repair` entering with `Repair` so that a blob the store holds is re-hashed before a repaired output's file is linked to it — is `objectHashOf` over the written path with `EnterVisitor`: its `node` continuation treats `blobInodes()` as a hint, then requires a current holder whose inode, device, size and canonical metadata match the owned file; only then is the file not read, and its own candidate is recorded. The link count is irrelevant: a holder that no second path shares has one link (`08` K8); `regular` asks `placementOf(where)`, the one place the exceptions of `01` §9.10 law 3 are decided (a writable file is left as suspicious; a file this system does not link — `.app/Contents` on macOS, every file on Windows — is left as written), and otherwise makes the parent writable around `placeRegularFile`. `optimiseStore` migrates an older row before entering its path, by the walk `nix store migrate` makes (`walkOldRow`: the object hash and, on a tee of the same bytes, the NAR hash the row asserts, checked before `recordObjectHash` writes), skips a path found modified or missing with the verifier's message, and reports files entered, files linked and rows migrated. *The verifier:* `verifyObjects` is the same on-disk walk with `VerifyVisitor`, expecting every tree, the synthetic root tree and every symlink's blob as files under `.objects`, and, for every regular file `placementOf` says the store places, a **row**: `holderOrForget(entry.hash, executable, NoRepair)` must answer, and the file is reported missing when it does not. Law 4 for a regular-file blob is exactly that, and the difference is worth stating because it looks like a weaker check and is not one: the bytes are under the verifier's own hands — the file it is walking *is* a file with those bytes — so there is nothing else to check, and what the row adds is that the store *knows* the blob, which is what a later ingestion needs. A file whose row is missing is a file the store will write again; `--repair` re-enters the path, which writes the row. A store the verifier finds short of rows is not corrupt, only forgetful, and `nix-store --optimise` is the wholesale form of the same repair. The producer's canonical entry and the memo's entry have the same meaning but different evidence: the producer established the bytes and canonical rendering, while a memo row records a hashing walk under a stable name. Neither establishes that the destination store holds the object; materialisation checks that separately. There are no `git::` forwarders over the core; the fetchers call `merkle::` directly. The object store's files are fsynced under `fsync-store-paths`, as the paths' files are. On Windows the object store shares nothing: the `*at` calls the two operations rest on have no counterpart there, so every file is left as written and the verifier expects no blob (by inspection only, `01` section 13).

**One ordered scheduler.** Plain pull hashing, memoised hashing and materialising copies share `CopyPool`, created lazily at the first useful directory split. Parallel traversal requires `AllPaths` and an accessor that explicitly permits it; copying also requires permission for its hooks and namer. Each node's synchronous continuation owns its memo key, and only named cache facts share a mutex. Child results and failures are consumed in traversal order, and every accepted job joins before its directory scope expires. Default and caller-supplied hashing visitors and the NAR push driver remain sequential. `08` K17 states the finite permission domain and failure/lifetime rules.

**An unnamed regular root.** Its value is its executable bit and bytes, so the completed read already determines the Git address, including the synthetic tree for an executable root. `LocalStore::materialise` uses the same `readBufferedRegular` and `LinkingVisitor::placeRegular` as the restore visitor: the reader retains the observed bytes up to the existing one-mebibyte bound, and its writer opens lazily on a spill. When the complete root fits in memory, the destination is temp-rooted and checked before any `autoGC()`, ingestion hold or temporary directory. A valid destination under `NoRepair` discharges the copy; a missing destination is locked and checked uncached before staging and placing those same bytes. `Repair` still takes the materialisation path for a registered destination. A spill starts staging before the hash is complete and uses the same publication path afterwards. There is one source read and one hash pass in either case; size mismatch or read failure publishes nothing, and an open writer closes before its temporary directory is removed. Producer-known and explicitly named roots retain their existing reuse contracts. The change is confined to this Git-addressed, reference-free copy; Flat, Text, NAR and received-description routes retain their addressing and checks. Selecting this root case adds one root metadata query to the unchanged routes, not a query per child.

**The tarball cache.** Opened as a SHA-256 repository (`tarball-cache-v4`; `GitRepo::Options::oidType`, `git_repository_init_ext`; canonical-name provenance and root projection in `01` §9.10), so a tarball's tree identifier is the store's name for it and its blobs' identifiers the store's. Its packs' compression is the per-object decision of `01` section 10 (`packaging/patches/0004-pack-compression-heuristic.patch`, on top of the three patches of NixOS/nix PR 16427; `GitUtilsTest.packsStoreWhatWouldNotShrink`).

**Operations, solved.** A directory the naming names and the store holds: made from its tree body and blob files, nothing read from the source (the second route above). Hit under the limit: `link` acquires the holder under the new name, then checks the acquired inode against the candidate and canonical metadata; under repair it also hashes those acquired bytes. A rejected link is removed and its exact observed row forgotten before trying the next candidate, leaving the donor's file alone. A successful registered hit records an own pending witness and writes no bytes. Miss under the limit: written from memory, canonicalised by the restore sink's hooks, and entered as the blob's holder by a pending row — no `linkat` — or, should a holder have appeared meanwhile, replaced by it. Over the limit: written as received, then `place` as before, hit or miss. Concurrent entry of the same identifier: each ingestion retains its own candidate until publication, which reconciles distinct physical inodes and only then publishes the complete path projection. A failed ingestion cannot overwrite a successful holder, and a refused alias cannot become the canonical source for later successful files. At the filesystem's link limit or a full directory index (`EMLINK`, `ENOSPC`, the latter as the old pass tolerated) the file is left as it is; on macOS a file under `.app/Contents` is written and not placed. Collection: `GitObjectStore::sweep` in `collectGarbage` where `.links` was swept — the live roots read from the database as the object hashes of the valid paths (`forEachValidObjectHash`, `gc.cc`); trees unreachable from them, blob files with one link that no reachable tree names — the symlink-target blobs, `.objects` holding no other now — and temporary files older than an hour; then, after the file passes and because they are what removes a dead ingestion's hold, the stale index rows (`sweepStaleBlobRows`), a regular-file blob being owned by the path that holds it and collected with it; each tree body's identifier is verified as the sweep reads it, and a corrupt tree aborts the removal rather than let a wrong body decide what is reachable; no grace (`01` section 9.10); while any row is unmigrated no tree and no blob is removed and the collector says so — and the collector's walk of the store directory skips `.objects` and `.links`. `nix-store --optimise` walks every valid path, enters what an older Nix wrote plainly, links nothing on a store this Nix wrote and says so, and removes the legacy `.links` directory — as every whole-store collection does (`removeLegacyLinks`); neither is done on the local overlay store, whose merged store directory shows the lower store's (`08` K13). Daemon: unchanged, the NAR sink on receipt. `verifyStore --check-contents` hashes every blob file and every tree body against its identifier. The GitHub fetcher parses the tarball cache's tree hash as SHA-256 and treats a row of the SHA-1 cache as absent, as the tarball fetcher does.

**The check order.** `LocalStore::addToStore(info, source)` verifies a received path's content address before its object hash, its asserted NAR hash and its size; the address is what the name asserts, and for a git-addressed path it is the sink's root, so the check reads nothing. All checks remain; the order decides which mismatch is reported when several fail.

### 1.8 Garbage collection

Pre-existing references of a pending object are temp-rooted at enqueue against `EvalState::store` (`addTempRoot`; the daemon deduplicates per connection, `remote-store.cc:751-758`). ### 1.9 One address (libstore, libfetchers, libexpr, libflake, nix)

**Meaning.** `01-specification.md` section 9.11: a store object's content hash is the git entry of its root under SHA-256, total over store objects, with distinct content identified under the collision assumption of §2.4; the NAR is a serialisation; the flat hash is read through a shim and never written as a name.

**Representation.** The object hash is a `Hash`: `merkle::objectHash(TreeEntry root)` — the tree id of a directory, the blob id of a plain file, the tree id of `{"." ↦ entry}` for an executable or a symlink — replacing `rootHash`; `UnkeyedValidPathInfo::objectHash` where `narHash` is, `narSize` kept and computed by the same walk (`merkle::nar::{regular,symlink,root}`, from names and sizes; the property `MerkleHash.narSizeEqualsDumpPathLength`). A hasher core in libutil (`merkle-hash.hh`: blob id from size and chunks, tree id from entries, the `name + "/"` key; `merkle::insertEntry` refuses `.`, `..` and the reserved case-hack marker, so among canonical trees only the synthetic root wrapper admits a `.` entry, emitted by `syntheticRootTree`), ungated; over it `HashingVisitor` and its two drivers, `traverse` and the push adapter `ObjectHashSink` (a NAR stream or an accessor walk to a root entry and a NAR size, no disk), the store's `LinkingVisitor` (the restore route, deciding before the write; 1.7) and `EnterVisitor` (the on-disk walk, `enterIntoObjects`). `ValidPaths.hash` holds `git:sha256:<hex>` for an object hash and the old `sha256:<hex>` for an unmigrated NAR hash, told apart by prefix before parsing — the prefix test comes first because the old parser raises `UsageError` on an unknown algorithm, not the `BadHash` the read site catches; `nixSchemaVersion` 11. The object store's root record is the column: the sweep reads the object hashes of valid paths (`forEachValidObjectHash`) and treats each as a possible tree; there is no `roots/` directory, and no symlink-root special case. Fingerprint `"2;" + path + ";" + objectHash + ";" + refs`; `WorkerProto::featureObjectHash` (the same string slot on the wire, its meaning negotiated); a serve version; `NarInfo::objectHash` beside `narHash`; JSON version 4. Lock version 8 with `treeHash`; `Input::getTreeHash`; the GitHub fetcher's dormant `treeHash` made the SHA-256 SRI value; no `narHash` attribute on any input. The shim as one function in libfetchers, `narHashOf(settings, Store &, SourcePath tree, Hash treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the existing memoised NAR walk (`fetchToStore2` under `NixArchive`, dry run) with the `treeAddress` pair recorded — called through `assertNarHash` from `Input::getAccessor` (every fetch route, `mountInput`'s included), from `addPath` for a `sha256`, on `fetchTarball`'s route, and directly by `fetchTree` to build the language's lazy `narHash`; in libstore, `narHashOf(Store &, StorePath)` — a walk, `narFromPath` into a `HashSink`, no cache — for an old client on the wire (once per query) and for the path-info JSON formats 1 to 3. A version-1 signature is checked against an `assertedNarHash` when the description carries one, and otherwise through this walk when a caller binds it (`NarHashThunk`: `nix store verify`, `copy-sigs`, and `addToStore`'s tee for a description that asserts none).

**Operations, solved.** Registration computes the object hash where the NAR hash is computed today: the sink's root at the three ingestions, `enterIntoObjects` after a build (so every output has one, input-addressed or not), `objectHashOf` for `computeStorePath` (the one tree walker; the fetchers' memoised naming is `objectHashOf` with `MemoVisitor`, whose `node` answers from the memo or retains its key while `descend` computes the summary to record); the NAR hash is computed at registration only where an old sender asserted one — the receiving tee of a copy from an old peer or an old cache, at no cost — and is verified there and never stored. `mountInput` names by `fetchToStore2` alone; the second walk and the lazy attribute's pairing rule go; `narHash` on an input is the shim's lazy attribute. `addPath` and `fetchTarball` with a `sha256`: fetch, then verify by the shim, then record; with a `treeHash`: the fast path is `isValidPath` of the name it determines. Copy: the receiver verifies the object hash from its sink's root and, when the sender is old, the NAR hash from the tee. `verifyStore --check-contents`: the object hash against the root recomputed from the files, by way of the blob identifiers the object store checks already. `nix store migrate`: every unmigrated row filled by the verified walk (`walkOldRow`, `01` section 9.11 *The database*), then re-rendered.

**The column and the type.** Two facts fix the type. First, a path info describes a path in *some* store: for a path the local store holds the object hash is always known, but a substituter's description of a path (a `.narinfo` from an old cache, an old peer's reply) may carry only a NAR hash until the NAR itself arrives. Second, if the daemon kept speaking the old protocol while the column changed, every `QueryPathInfo` from a client would cost a walk to produce the NAR hash it must send; so the worker feature under which the object hash travels is part of the same change. Hence:

- `ObjectHash` (libutil, `object-hash.hh`): a strong type over `Hash` — `static ObjectHash of(const merkle::TreeEntry & root)`, `std::string render() const` giving `git:sha256:<base16>`, `static std::optional<ObjectHash> parse(std::string_view)` (nullopt for anything else, in particular an old `sha256:` row), `==`/`<=>`. A NAR `Hash` cannot be assigned to it by accident; the compiler enumerates the sites.
- `UnkeyedValidPathInfo`: `std::optional<ObjectHash> objectHash` — present for every info the local store returns or accepts for registration (`addValidPath` refuses one without), possibly absent for an info from a substituter or an old peer; `std::optional<Hash> assertedNarHash` — the NAR hash a sender asserted (an old peer on the wire, a `.narinfo`, `--load-db`, JSON before version 4), verified on the receiving tee and never stored; `narSize` as before. The field `narHash` is gone; every former reader is either an `objectHash` reader (content identity), an `assertedNarHash` verifier (receipt), or a call of the shim `narHashOf(store, path)` (a walk producing the NAR hash for an old form).
- The local database: `hash` column holds `objectHash.render()`; an old row's `sha256:` value is recognised at the one read site by `ObjectHash::parse` returning nullopt, and migrated in `queryPathInfoUncached` between two lock scopes, as `verifyStore` does its walk, and never in `queryPathInfoInternal`, which `addSignatures` calls inside a transaction — by `objectHashOf` over the path (`migratePathInfo`) — then written back unless the store is read-only; the migration takes no temp root: a path deleted mid-walk reads as invalid, and the row is left for the next query; `nixSchemaVersion` 11, stated as the deliberate exception to the additive-migration convention.
- Where the object hash is set: the three ingestions from the sink's root; `LocalStore::materialise` from the root the materialising walk computed (1.7, the second route), which is the memo's entry where the store held the tree and the hasher's where it was read; `addToStoreFromDump`'s flat and copy routes by `objectHashOf` over the written path; the builder's outputs by one walk, `enterPath`, where `hashPath(NixArchive)` ran on master, before the `--check` branch: it hashes and enters the object store in the same pass, so a built output and a flat add cost one walk where master's NAR hash and optimise pass cost two, under `--repair` entering with `Repair`; `--load-db`/`--register-validity` by a walk. Verification by recomputation: `verifyStore --check-contents`, `pathContentsGood`, `nix store verify`, `nix-store --verify-path` compare `objectHashOf` with the row; `nix-store --export` and `--import` compute the object hash of the stream with `ObjectHashSink` on the tee and compare or register.
- The forms in this step: fingerprint 2 (`2;<path>;<objectHash.render()>;<refs>`; a version-1 signature verified against `assertedNarHash` when present and otherwise against the NAR hash the caller's `NarHashThunk` supplies by one walk — `ValidPathInfo::checkSignature`, bound by `nix store verify`, `copy-sigs` and `addToStore`'s tee, so a version-1 signature on a locally held path keeps verifying once its row is migrated; `narSize` must be known). Signing produces both where both hashes are known — `ValidPathInfo::sign` signs the version-2 fingerprint and `signV1` the version-1 one (`1;<path>;<NAR hash>;<NAR size>;<refs>`); `nix store sign` calls `sign` only when the info carries an object hash and `signV1` whenever the NAR size is known, the NAR hash asserted by the info (a narinfo's `NarHash:`) or else computed by one walk (`narHashOf(store, path)`), so it works on a cache an older Nix wrote, whose infos have no object hash and get version 1 alone; the binary cache's upload signs both with the cache's keys, its NAR hash from the tee; `Store::signPathInfo`, signing at build under `secret-key-files`, signs version 2 only, no NAR hash existing there — because an old client verifies version 1 alone and counts only the signatures it can verify (master's `checkSignatures`), so a cache carrying version 2 alone was refused under `require-sigs`, and a build-signed path copied into a keyless cache still is until `nix store sign` runs on the cache (`01` section 9.11, *Signatures*). Since one key then has two signatures, `checkSignatures` counts distinct keys. A path an old client verifies is one the daemon can describe to it; a path info that arrives at `LocalStore::addToStore` with neither hash and no content address is refused (the daemon reaches it through the store), since nothing about it can be checked; `WorkerProto::featureObjectHash`, under which the path-info slot carries `objectHash.render()` and without which the daemon sends `narHashOf` and reads the client's string as `assertedNarHash`; a serve-protocol version likewise; `.narinfo` reads `ObjectHash:` into `objectHash` and `NarHash:` into `assertedNarHash`, and the upload writes both, its NAR hash from the tee it already has; path-info JSON version 4 with `objectHash` required and `narHash` optional, versions 1 to 3 written through the shim; `nix hash path --mode git` prints the object hash: for a bare executable or symlink the synthetic tree's id, where master printed the blob's (`01` section 9.11); `nix-store --dump-db` writes the rendering.
- The object store: the synthetic root tree written when entering; the sweep reads the live roots from the column (`forEachValidObjectHash`); there is no `roots/` directory and no root record beside the column: the migration walks the path.

**The fetchers' and the language's representation.** The fetchers and the language stop naming anything by the flat hash; every source is named by its tree hash; old assertions are verified by the shim.

- *No setting.* Every site names by the git method (`fetchToStore`'s default, `addPath`, `copyPathToStore`, `mountInput`, the `path` fetcher's copy and the Mercurial fetcher's dirty-checkout copy); the exceptions and the explicit methods are `01` section 9.9's.
- *`treeHash` on inputs.* `Input::getTreeHash()` reads the attribute `treeHash`, an SRI SHA-256 string, the git tree (object) hash of the input's root — the same value the store's `objectHash` renders, so `Input::computeStorePath` is `makeFixedOutputPathFromCA(name, {Git, SHA256, treeHash})`. - *The lock file, version 8.* A locked input's `locked` attributes carry `treeHash`; `narHash` is not written. Reading a version-7 lock: the node's `narHash` is an assertion; `mountInput`, after naming the tree, verifies it through the shim and then replaces it in the input's attributes by the `treeHash` it computed — the one mutation the copy in `checkLocks`'s final branch admits. - *The shim, one function in libfetchers:* `Hash narHashOf(const fetchers::Settings &, Store &, const SourcePath & tree, const Hash & treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the memoised NAR walk, recording the `treeAddress` pair (it keeps no memo of its own); and `void assertNarHash(settings, store, tree, treeHash, asserted, description)` throwing the existing `Error(102, "NAR hash mismatch in input '%s' ...")`. Called from `Input::getAccessor` (`fetchers.cc`, every fetch route — a version-7 lock, `fetchGit { narHash }`, `?narHash=` and `mountInput`'s inputs among them), from `addPath` (a `sha256` on `builtins.path`/`filterSource`), on `fetchTarball`'s route (`fetchTree.cc`), and by `fetchTree`'s `emitTreeAttrs` to build the language's lazy `narHash` thunk from the tree hash. No input ever carries a `narHash` attribute again, lazy or not (`attrsToJSON`/`attrsToQuery` force lazy attributes, so one on the input would be walked and written by every lock and URL).
- *The language.* `fetchTree` and `fetchGit` results carry `treeHash`; `narHash` is a lazy attribute `emitTreeAttrs` builds through the shim; `builtins.path { sha256 }`, `fetchTarball { sha256 }`, `fetchTree { narHash }` and `?narHash=` accept the NAR hash (shim) and `treeHash` (the cheap assertion); `nix flake prefetch` prints `treeHash` as `hash` (`01` section 9.9, *The language*).

## 2. Risks and open items

- **Destructor flush.** A flush can fail; a destructor cannot throw. Every command flushes explicitly and fails loudly (see the teardown row of 1.2); the destructor's flush is a fallback that logs. A library consumer that neither flushes nor lets the command end normally is the one case where an error could be swallowed; the explicit entry point is the remedy, and its absence is a documented limit, not a silent loss of data.
- **Least sure step.** Inside the kernel: the dereferences that parse a store path from accessor bytes, and the sinks a primop may write to, are held by review and the builtin sweep (every builtin against eager evaluation on pending inputs), not by the type (0.2). Outside it the door is the type and the check.
- **Round trips through a daemon.** An object absent from the pending set is rooted before its validity is checked, as in the eager write. A valid non-repair object retains no bytes or reference roots. A miss pays that validity query before the later bulk query, so an uncached remote miss adds one `IsValidPath` round trip relative to deferred checking alone. For an outstanding write, rooting each reference outside the pending set is also a round trip on its first use (`RemoteStore::addTempRoot` deduplicates per connection); the protocol has no bulk temp-root operation. The warm savings and cold cost require measurement (`09-performance.md`).
- **Client cache.** `RemoteStore::addToStore` from a stream and `RemoteStore::addMultipleToStore` did not invalidate the client's path-info cache while `addToStoreFromDump` did, so a cached negative answer survived a copy; a defect of master's remote store that any `copyPaths` caller could hit. Fixed in `RemoteStore`; the buffer relies on the store's own invalidation.
- **Repair through the batch add.** `Store::addMultipleToStore(PathsSource&&)` calls `addToStore` only for paths not already valid, so it ignores the repair flag for a valid-but-corrupt object (`src/libstore/store-api.cc`). The buffer cannot repair through its one batch; its flush falls back to a per-object `addToStore` whenever repair is asked, which honours it, exactly as an eager `writeDerivation(_, Repair)` would. Latent from the CLI, since no command sets `EvalState::repair` to `Repair`; `WriteBufferLocalStoreTest.repairRewritesAnObjectTheDatabaseStillCallsValid` pins it.
- **Reuse considered and not taken.** The pending set is a store in the specification's own sense, and the flush is `copyPaths` from it. `DummyStore` cannot yet hold a derivation (it refuses `.drv` names in `addToStoreFromDump` and synthesises reference-free info for them), so making the buffer a `DummyStore` and the flush a `copyPaths` needs a libstore change with its own tests first; the buffer stays a bespoke type until then; recorded as a decision.
- **Mounted references before enqueue.** Mounted inputs use master's accessor-based deferral; the buffer defers outstanding text writes. `derivationStrict` and `toFile` realise each mounted opaque reference before calling the buffer, as the reference implementation does before its eager write. This establishes reference validity before an automatic threshold flush and preserves the changed-source error even when the referrer is already valid. `flushPendingWrites` therefore needs no second reference walk. At command outputs `emit` writes the texts and copies the inputs the provenance names; dereferences copy what they read (`realisePath`), and hand-offs to a program or builder copy what they hand off (`exec`, `realiseString`, the installables, `nix run`'s app). A mounted input never used at one of these boundaries is not copied.
- **Memory.** Pending text accumulates between flushes: one top-level closure for the plain printer and `nix-instantiate`, which realise each string as they emit it; the whole serialised value for `nix eval --json` and `--raw`, whose serialisers are pure. What one pending object costs is its text once and a bounded constant besides — measured against the allocator's own accounting, 392 B while it waits and 1056 B at the moment the flush has built its batch on macOS, 383 and 1196 under glibc, against a stated bound of 1536 B (`WriteBufferTest.aPendingObjectCostsTheBoundBesidesItsText`; `05-validation.md` section 6). The buffer bounds the total by writing what it holds once that footprint reaches 32 MiB; there is no setting, the store's contents and every write count being the same at any threshold (`01` section 10). (C2) holds because those sinks emit nothing until after the final flush. A drain thread would overlap writes with evaluation and is deferred for simplicity.
- **What the write retains, beyond the buffer.** The description the buffer hands the store carries a NAR-hash thunk over the object's bytes (`01` section 9.11: the cost falls on the old peer), and `Store`'s path-info cache keeps the description of every object written, up to `path-info-cache-size` entries. The bytes of every `.drv` an evaluation wrote therefore stayed resident for the life of the process. What is registered now carries the store's own walk of the path instead, which answers the same hash and holds nothing (`LocalStore::addToStore`; `LocalStoreObjectsTest.theRegisteredDescriptionsNarHashIsTheWalkAndNotTheSendersClosure`). Measured on the builder, `nix-instantiate` over 64000 derivations, which holds one object pending at a time so that what is measured is what the write retains: 239.5 MB against 263.6 with the sender's thunk registered and 226.9 for the reference — 24 MB of the 37 MB gap, about 375 bytes per object, in two rounds of the per-term ablation (`05-validation.md` section 6). The remaining 13 MB, about 200 bytes per object, is neither the thunk nor the buffer and is not addressed. An earlier reading of this item concluded from a `path-info-cache-size` of one, on macOS at N=4000, that the cache held nothing of it; the ablation that removes the thunk and leaves the cache alone says otherwise, and is the discriminating measurement.
- **Trust bit.** Equal for everything the buffer holds: derivations and texts carry `ultimate = false` when written eagerly and through the bulk add alike. If the buffer ever holds a built output, which it must not, the bit would differ.
- **Out-of-tree consumers.** `Value::string_view()` is private: an out-of-tree consumer that read `Value` strings directly now goes through `realise`/`emit`, which write first, or through the accessors; a libexpr API change, which the specification does not freeze (`01` section 6).
- **`--eval-store`.** Unchanged: the buffer drains into `EvalState::store`, where master writes.

## 4. Defects of master found by this work

Fixed on the branch and pinned: the ATerm reader promoted `char` to `int`, so a byte 0xFF in a derivation read as `EOF` (`DerivationAtermTest.aByteEqualToEofRoundTrips`); a platform string containing `"` or `\\` was written verbatim and could not be read back (`DerivationAtermTest.platformOutsideTheFormatIsRefused`); the store-directory field of a `.drv` was written verbatim off Windows and unreadable when the directory holds `"` or `\\` — the escape flag's default is the platform, not the directory's characters — and the writer now refuses such a directory under the verbatim mode (`DerivationAtermTest.storeDirOutsideTheVerbatimFormIsRefused`, `WindowsStoreDirTest.unsupportedIsRefusedAtTheWriter`); `nix-prefetch-url --attr` had an inverted condition (`tests/functional/prefetch-url-attr.sh`); `RemoteStore::addToStore` from a stream and `addMultipleToStore` did not invalidate the client's path-info cache while `addToStoreFromDump` did (fixed in `src/libstore/remote-store.cc`; the buffer relies on it and patches nothing). Found and not fixed, master's: `builtins.fetchGit`'s default `exportIgnore = true` makes libgit2 look the attribute up for every file on every copy whether or not the repository declares it. Fixed here: master's `export-ignore` lookup for a *commit* passes `GIT_ATTR_CHECK_INCLUDE_COMMIT | GIT_ATTR_CHECK_NO_SYSTEM`, whose low bits are `GIT_ATTR_CHECK_FILE_THEN_INDEX` (0), so libgit2 reads the working directory's `.gitattributes` and then the index's entry before the commit's blob — an uncommitted file in a checkout decided what a fetch of a committed revision from it exported, and the same revision fetched from a bare clone exported something else (`GitUtilsTest.committedRevIgnoresTheWorkdirsUncommittedGitattributes`).
