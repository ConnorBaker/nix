# Derivation: from the specification to the implementation

This document is the implementation as it stands, derived from `01-specification.md`. Section 0 states the architecture and the correctness argument; section 1 gives each component as an equation in one unknown — the operation to write — with the check that would show it wrong (how each check is run is `05-validation.md`'s; the local store's locks, invariants and sink order are `08-store-model.md`'s); section 2 the risks a maintainer relies on; section 4 the defects of master this work found. Section numbers are stable because the code cites them. Locators are `file:line` in master at the branch's merge base unless stated; line numbers drift.

## 0. The architecture and the correctness argument

### 0.1 The architecture

Sources and store objects retain the content-addressed tree model in `01-specification.md`: the object hash names the logical tree, references form the store DAG, and old-wire NAR hashes are serialization obligations. Naming, acquisition history, source-copy history and content memos retain their separate meanings. This evaluator change does not replace those domains with a single cache or freeze a live mounted accessor.

Text publication is eager. `derivationStrict` calls `Store::writeDerivation`; `toFile` calls `Store::addTextToStore`. Both share the latter's destination naming, temporary root, validity/repair decision, reference protection and existing flat/Text ingestion route. Derivation serialization prepares its bytes and references once. No evaluator write buffer, pending-text map, destructor flush, threshold, alternate eager mode, or retained text-hash closure remains.

Mounted inputs still have a separate materialization obligation. The text producers verify their mounted references before publication, including on an already-valid referrer. Command output code renders bytes and gathers context, copies the mounted inputs at the same semantic boundaries as before, then delivers bytes. Diagnostics and ordinary string getters do not acquire that copy effect. `realiseContext` and `realiseString` still perform genuine build/rewrite/copy work; they are not text-buffer fences.

### 0.2 The correctness argument, and what checks it

A successful text producer has already published exactly the object it returns, unless evaluation is read-only. Therefore dropping context, reading a literal path, printing an error, or returning through C cannot reveal an outstanding text write. No-elision follows from keeping each producer's write, including objects whose value is subsequently discarded. Failure still reports the producer/backend error and leaves a reference-closed store; C1′ does not specify which partial objects survive.

Before a backend may collect garbage, the shared publisher roots the destination and, on a write or repair, its actual references. An already-valid non-repair destination protects its recorded closure and avoids another upload. The evaluator also roots actual context inputs before mounted copies or closure traversal can collect, and roots existing paths admitted by `storePath`/`appendContext` before a later nested producer can collect them. `appendContext` roots each parsed writable key before availability validation and arbitrary flag evaluation, even when validation fails or the flags select no context. These process-lifetime roots are excluded from C1/C1′ comparisons. This protects its existing all-key validation; it does not root unselected source-filter candidates. Read-only text evaluation names without publishing or rooting.

`src/libexpr-tests/text-store.cc` checks actual local-store objects, literal reads, printer byte sinks, both text writers, repair, read-only behavior, GC during publication and nested evaluation, complete successful object sets, failure closure and retry. Its builtin sweep compares producer expressions with already-materialized equivalent context literals over callable builtin names outside its exclusion set, three selected input shapes and arities one through each primitive's remaining declared arity (at least two); ordinary lambdas retain the one/two-argument probes because their curried arity can depend on evaluation. It does not enumerate all possible inputs; errors are compared by class, status and root message, excluding expression-specific rendered traces. C tests cover returned values, error text and builder lifetime. Existing functional escape/observer tests remain behavioral checks of mounted copy ordering. These are test obligations until the integrated build runs; prior buffered measurements and test records in `05-validation.md` and `09-performance.md` are historical evidence, not validation of this replacement.

## 1. Components as equations

### 1.1 Eager text publication

`addTextToStore(name, contents, references, repair)` computes the existing Text address, roots that destination, and returns it when valid without repair. Otherwise it roots the actual references and calls the existing `addToStoreFromDump(Flat, Text, SHA256, ...)`. It preserves current object-hash ingestion, the old-daemon compatibility route, backend error propagation and the ordinary `ultimate = false` metadata. `writeDerivation` serializes once and supplies its input base paths as references; output paths are not references.

This is a shared store operation, not a store decorator or a second representation of pending objects. It holds bytes only for the synchronous producer call. There is no end-of-command publication step. `--eval-store` continues selecting `EvalState::store`. A valid referrer does not excuse checking a current mounted source's name; changed-source error 102 remains observable before that fast path.

### 1.2 Values, output boundaries and C ownership

Ordinary `Value` string reads return ordinary bytes; forcing/coercion continues validating type and context. Printers accumulate context while rendering. `nix eval` and `nix-instantiate` copy mounted inputs before output, including raw, JSON, XML, ordinary and file-output forms as applicable. Program and builder handoffs retain their actual realization calls. Trace, warnings, REPL inspection and C string/path getters remain non-copying observations.

`RealisedString`, `FinishedEvaluation`, `execvpAfterEvaluation`, manual pending-read fences and the `check-string-kernel.sh` hook are removed. A prior flush event is not a durable proof about future evaluation, and eager text publication removes the obligation those branch-internal wrappers represented. Before an exec, command code explicitly persists evaluation caches by clearing their owners; it does not construct a proof token.

The existing C boundary still translates exceptions and separates evaluation from returned-handle allocation. The two-phase returned-handle boundary allocates its handle after evaluation succeeds, and no flush follows that allocation. `nix_value` retains its allocation arena pointer rather than an evaluator solely for byte access. The built C evaluator owns its settings, fetch settings and state, plus the builder-owned read-only flag those settings may reference; freeing the builder cannot dangle that flag. Temporary callback wrappers borrow the active evaluator. Expression/position arena ownership and source-cache invalidation are unchanged.

### 1.3 Mount and union alignment (libutil)

**Meaning.** `01-specification.md` sections 7, 8.2, and 8.4.

**Operations, solved.**
- `MountedSourceAccessor`: select the nearest explicit mount and retain its accessor, relative path and descendant bindings before invoking child callbacks. Directory shape follows from explicit descendants without inspecting the fallback; only listing and naming demand surviving directory contents. When needed, `resolveTree` checks only prefixes required by those descendants; an absent or nondirectory prefix discards the old fallback subtree. A selected mount with no nested bindings delegates directly, without source-ancestor probes. Strict ancestors of grafts answer as directories; their listing keeps surviving directory entries and replaces each mounted name, promoting names with deeper bindings to directories. An absent mounted root removes its old entry unless a deeper graft promotes it. Listing determines these directory shapes before querying any still-needed mounted root types. Reads below discarded fallback ancestry report absence, so a replaced symlink cannot leak its physical target. File/link reads at constructed directories are refused. `getKnownEntry` and `getPhysicalPath` decline altered subtrees. A composite fingerprint uses `graft-v2`, the surviving base name or an explicit empty base for discarded ancestry, and the descendant bindings' names; old partial-graft names cannot alias this meaning. `mount()` remains insert-only, and each operation owns the children it observed across callbacks.
- `UnionSourceAccessor`: the top-down definition of `01-specification.md` section 7.1. One function, `owner(p)`, gives the child whose node p denotes, or nothing when an earlier child's non-directory at an ancestor hides p; `readDirectory(p)` merges the directories of the owner and every later child that has one there; `readFile`, `readLink`, `maybeLstat` go to the owner. `getPhysicalPath` follows that owner and declines a directory merged from multiple contributors. `getFingerprint(p)`: the three-case rule for a general union, with a merged directory named by the JSON of its parts' names or not at all. The evaluator’s unmounted fallback uses the same rule. A content-addressed input mount does not prove that an arbitrary raw host entry at the same logical pathname is the same complete tree; the former `ChildrenAgree` policy and its ancestor-hiding bypass remain removed. Cross-view tests compare the union’s names against both children, including private entries and every named/unnamed node-type pairing.
- `EvalState`: first build the original store view; in impure mode put the original host/store union at the root of an outer `MountedSourceAccessor`. Input mounts go into that outer graft map, then metadata/naming caching and pure/restricted admission wrap it. Thus an input owns its prefix without consulting host occupants. Its required ancestors become directories, including over host files or symlinks; displaced nondirectory ancestry contributes no sibling nodes. Elsewhere the fallback is unchanged. `mountInput` invalidates observations after publication and retains the first mount at a repeated point. This is the explicit semantic correction in `01` sections 3, 5 and 8.4: freshly reading an input and copying its opaque reference observe the same accessor. Existing import/search memos remain scoped to the evaluation epoch; mounts do not recompute previously evaluated or transitive values. It is not a claim that an arbitrary host occupant matches the input. Live worktree bytes and later address checks remain unchanged.

- `CmdShell`: after `Installable::toStorePaths(..., Realise::Outputs, ...)` discharges the selected outputs' materialisation obligations, interpret package metadata through the execution store's accessor. The evaluator may use a different store and its input grafts are not the execution namespace. This also corrects the reference's separate-evaluation-store failure, explicitly listed in `01` section 5.

**Checks.** A rapidcheck property over `MemorySourceAccessor` trees: for generated terms of the four operations with a content-naming leaf, equal names imply equal NARs at every path, and equal subtrees under a naming leaf imply equal names. Unit tests for the listing changes and the evaluator’s complete mount domain (`01` section 8.6): 180 node/location/admission combinations, twelve registration/physical-presence cases, thirty proper-ancestor kind/location/admission cases, and restricted/unrestricted fallback, symlink and nested-graft cases. The evaluation-epoch regression keeps cached imports and searches until explicit reset. The differential excludes only the explicit result/error corrections in `01` section 5; ambient-store imports at unmounted paths remain unchanged.

### 1.4 Names (libfetchers, libutil)

**Meaning.** The naming rules of `01-specification.md` section 8.2, with names withheld for attribute-dependent accessors.

**Operations, solved.**
- `GitSourceAccessor::getFingerprint(p)`: for a raw accessor without LFS smudging and outside an active export-ignore wrapper, return the object identifier of the entry at p as the name and the root as the path: a tree identifier for directories, a blob identifier with its mode for files and symlinks, since the mode is part of the NAR (`src/libfetchers/git-utils.cc:874-1149` holds the entries; master has no override). LFS views may use only an explicitly supplied sound outer name, and production attribute-dependent views decline revision-derived names. Export-ignore is handled by the constructor-owned wrapper decision in 1.6. Submodule mounts are a graft above the leaf and get the graft rule from 1.3.
- `FilteringSourceAccessor::getFingerprint(p)`: when the accepted set is fixed at construction, the pair of the inner name at p and a canonical hash of the prefix-closed accepted set restricted to the paths below p (`01-specification.md` section 7.1); the requested subtree is selected with an ordered range of that immutable set; the set is computed once by the same top-down pruning walk `dumpPath` performs (`src/libutil/archive.cc:102-108`), so the accessor's tree and its NAR agree. Master's accessor forwards the unfiltered name (`src/libfetchers/filtering-source-accessor.cc:60-65`). For the allow list, whose set grows: pass the inner name through when p lies under an allowed prefix, since everything beneath is then admitted, and withhold a name otherwise. The same whole-subtree admission proof gates physical directory paths; arbitrary and fixed-set filters conservatively decline those paths, while admitted leaves may retain theirs.
- `fetchToStore2`: replace the `filter ? nullopt : getFingerprint` bypass (`src/libfetchers/fetch-to-store.cc:64-65`) by wrapping the source in a fixed-set filtering accessor built from the predicate, and pass no `PathFilter`. The store path is unchanged, because dumping the wrapped accessor without a filter produces the same NAR as dumping the unwrapped one with the filter: both are the pruning walk. The persistent memo keys the accessor's name with the method and, for Git/NAR, the directory-name decoding policy (`sourcePathToHash`) — and its Git value is the node’s entry `{hash, mode}`, from which the root object address is derived (`01` section 9.9); it becomes the subtree memo because the git leaf names subtrees.
- The in-process memo retains the pure naming result `(StorePath, Hash)` under the current view fingerprint, relative path, address method, logical store directory, output name and, for Git/NAR, the directory-name decoding policy. These are exactly the arguments that determine that result; the key owns neither the source nor a store connection. A hit avoids deriving the same address and rewriting the same memo entry. A dry-run entry or a completed copy in another store still establishes no presence in the requested store: every copy roots and checks that destination before returning, and walks when it is missing (section 1.5).

**Checks.** The soundness property from 1.3 extended with a git-like leaf. Cost tests (subtree shared across two revisions hashed once; filtered source cached across processes; N same-content names copied once) using the existing `hashing '` and `copying '` activity lines (`fetch-to-store.cc:97-102`). The differential run, expecting no behavioural change.

### 1.5 Source publication and mounted inputs

Filesystem sources stay eager: naming and copying share the existing walk. Deferring such a source would require another walk or retaining its serialization, without permission to omit the final object. Mounted inputs retain accessor-based deferred copying because their acquisition protocol already separates naming from materialization. `path:` inputs retain their registered-copy semantics; Git's live tracked accessor does not become an immutable snapshot.

The two text producers copy mounted opaque references before publishing, and check them even when the referrer is already valid. Command output copies its context before delivering rendered bytes. Diagnostics do not copy merely because they display a mounted name. The retained functional observer distinguishes these orders and checks that an unused mount is not copied. No text buffer or `emit` wrapper participates in this source protocol.

### 1.7 The store's object store (libstore, libfetchers)

**Meaning.** `01-specification.md` section 9.10: the local store keeps its objects' trees as git objects under SHA-256 — blobs, trees, the executable bit on the edge — and a store path is a view of its tree whose regular files are hard links to the canonical file for each (blob, mode) — which, for a regular file, is *a store path's own file*, a **holder**, the store keeping an index from (blob, mode) to it, and, for a symlink target and a tree body, owned metadata under the same ingestion lifetime. The roots are the column: which root a path has is the object hash in `ValidPaths.hash` (1.9). Unconditional: there is no setting (master’s `auto-optimise-store` is accepted as an ignored compatibility setting, `01` section 10), and the object store is what a local store is.

**Representation.** `GitObjectStore::Hold` owns a typed pending relation of regular rows and auxiliary values. `Auxiliary{entry,body}` admits Directory/Symlink with full SHA-256 identifiers; its string owns the canonical tree body or symlink target. `Projection{regular,auxiliary}` is transferred after workers join, reserving both vectors before extracting values. `LocalStore` publishes it into `Blobs` and `AuxValues` under one `Ingestions` owner (`schema.sql`). AuxValues stores a body in contiguous 1 MiB BLOB chunks, including one empty BLOB for an empty body; malformed sequences and wrong framed hashes cannot become hits. `readAuxiliary` copies one candidate from one statement snapshot and releases the database state before ordinary hashing or callbacks. The shared borrowed-body parser checks canonical mode spelling, ordering and sink admission without framing copies or a re-encoding pass. A bare object store or old read-only database without this provider misses normally. `.objects/tmp` retains ingestion leases and regular coalescing pins; loose auxiliary files are neither produced nor read as another backend.

Regular files retain the same operations. `link` acquires a registered holder before checking its inode, device, size, kind, mode and timestamp, with hashing under repair. `place` acquires under a temporary name before replacing a written file. A rejection removes only the acquired link, conditionally forgets the observed row and advances the candidate cursor, never deleting a valid donor. A completed file in the same ingestion takes precedence. A miss records the destination as a holder; `enterWritten` performs its existing stat and pending-row operation. Link/refusal exceptions remain unchanged. `putRootTree` now stages the same synthetic encoded Directory body instead of publishing a file.

**The index, ingestion and stale rule.** The LocalStore-owned `Index` supplies regular lookup/forget/inodes and optional auxiliary acquisition. Regular lookup joins `Blobs`, `Ingestions` and `ValidPaths`, preserving signed `(device,inode,ingestion)` ordering, conditional forgetting and first usable holder selection. Each recipient records its own witness, and completed publication reconciles colliding physical aliases under the existing SQLite writer reservation. Its filesystem-only collision helper calls neither a provider nor temp-root registration; rejected sharing supplies no new canonical donor. Metadata-only registration does not replace a projection.

`beginIngestion` starts a private per-path projection. `endIngestion` publishes a completed builder output and both value classes, then retains its path/id completion value as the shared hold advances to the next output; registration consumes those values without an SQL identity-recovery query. Direct registration publishes the projection with validity and a NULL hold marker in the same transaction. The vectors remain owned across rollback/retry. Each source add owns a fresh `Hold`; a speculative directory attempt shares its parent’s memoised lease acquisition while keeping its own projection. `endIngestion` forces the lease before taking the database lock, and physical coalescing forces it only for temporary links. Private staging alone needs no lease directory. Auxiliary reads can use a committed completed output before validity because they verify independent body bytes; regular donor reads still require validity. Successful materialisation stages every consumed body into the recipient, while failed private attempts stage nothing globally. NoRows suppresses regular insertion only, not auxiliary publication. The common stale rule deletes an ingestion whose path is absent/invalid only after its lease is gone; both regular and auxiliary rows cascade. `LocalStore::sweepObjects` remains nonvirtual: bounded overridable legacy/dead-lease cleanup first, then SQL stale cleanup that an overlay override cannot omit (`08` K13/K16).

**One hasher, one traversal, the visitors.** The hasher is libutil's `HashingVisitor` (`object-hash-sink.hh`), a `NodeVisitor<HashedNode>` over the one traversal `traverse` (`tree-traversal.hh`): a node's result is its entry and optional NAR size; a directory's encoded body stays local to hashing and publication, since its parent needs only that summary; the child callback supplies a borrowed name, which the fold copies into an owned key after the visit and then moves into the finite map, and a refused insertion changes neither the map nor its NAR-size summary; the algorithm is `merkle::hashAlgo` (SHA-256) and nothing else — the hasher has no algorithm parameter, and `checkIngestionAlgorithm` refuses any other algorithm at every creation entry. Two drivers deliver nodes to a visitor: `traverse` over an accessor — the depth bound first, then stat and `node(accessor, from, path, stat, descend)` before contents are read, the names unhacked as `dumpPath` unhacks them, the descent by the on-disk name — and `ObjectHashSink`, the push adapter from the sink protocol (`parseDump`) to the same visitor, which never calls `node` and must consume every child immediately; `objectHashOf(accessor, path, filter, visitor)` runs the first, `objectHashOfNar` the second. A deferred pull visit borrows the physical-name string from the listing or its validated remapping, and one directory context shared by all siblings. Both outlive every accepted visit; the child closure carries only those two references, while the push driver retains its immediate-delivery contract. Its stack borrows the callbacks owned by active directory calls, so recursive growth cannot relocate an executing callback or discard its state between siblings. `MemoVisitor` (`fetch-to-store.cc`; 1.6) derives from `HashingVisitor` and surrounds a node's synchronous descent with lookup and recording. The store's visitors are in `optimise-store.cc` — `ObjectStoreVisitor`, which stages each symlink's entry and owned target or directory's entry and owned body through `addAuxiliary`, the latter from `hashDirectory`'s local pair of summary and encoding, regular files being the drivers' business; `LinkingVisitor`, the restore route; `MaterialisingVisitor` over it, with `ObjectAccessor` and `CachedVisitor` using the common traversal for cached subtrees (below); `EnterVisitor`, the on-disk route; `VerifyVisitor`, the verifier's. *A tree being restored:* `LocalStore::restoreThroughObjects` calls a filesystem-node producer once, synchronously, through `ObjectHashSink` → `LinkingVisitor`. NAR callers supply `parseDump`; a buffered Flat caller supplies one regular-file node directly, so those bytes are hashed and placed without a synthetic NAR or a physical-path rehash. Addressing, reference filtering and validity checks stay with the caller. The visitor’s scoped current frame borrows the `RestoreSink` each directory's callback handed back, seeded with the caller's, so a node is created on the innermost sink under `/name`; `directory` opens `createSubdirectory`'s scope and visits the children inside it, so `directoryDone` (canonicalisation) runs when the scope closes, before the tree body is staged; `symlink` creates the link, then hashes. A regular file goes to the hasher as its bytes arrive and is held in memory up to `restoreBufferLimit` (one mebibyte; `BufferThenStreamFile`); with the entry in hand the visitor decides: a blob the store holds is linked under the name (`GitObjectStore::link`, acquisition and validation as above) and never written — the restore sink's `regularFileCreated` does not fire for it; a blob the store lacks is written from its complete memory buffer through the fresh restore writer's unbuffered operation, then finished with the same canonicalising hooks and entered as the store's file (`GitObjectStore::enterWritten`: one `fstatat` and a pending row, no `linkat` on a miss). If another worker completed the same blob meanwhile, `place` resolves that pending winner before returning; link or directory limits leave the file as written. The entering runs on the walk's own thread: moving it to a thread of its own was built and measured slower, and `01` section 10 and `05` section 6 say by how much and why. A file the producer announces above the limit (`preallocateContents` precedes the bytes), or that overflows without an announcement, is opened at once (`RestoreSink::beginRegularFile`, the two-phase regular file), streamed, finished and entered through `enterWritten`, which calls `place` because no earlier lookup occurred: a miss records the written file, a hit replaces it with the acquired holder. This write-then-link cost is paid on large files, where the write dominates it. *Why the decision is made before the write.* The question "does the store hold this blob?" needs the blob's identifier, a function of every byte, so it is answerable only when the last byte has been seen; a sink that writes bytes as they arrive has already written the file when the answer comes, and on a hit must undo the write — link the store's file to a temporary name and rename it over the file just written. Historical write-then-link experiments are retained in `05`; they do not measure the SQL auxiliary representation. The root's synthetic tree is staged after the walk (`putRootTree`). The three ingestions call it — `addToStore(info, source)` from a NAR, and both restores of `addToStoreFromDump`, which the generic accessor-add route reaches by serialising the accessor; `Store::addToStore(SourcePath, ...)` instead selects local Git materialisation when its capabilities permit (`store-api.cc`) — each after its `autoGC()`, so an add does not trigger its own synchronous collection inside the write/publication window (`LocalStoreAutoGCTest`), and register the root as the object hash and the size as `narSize`. *The copy from the store's own objects* (`01` §9.10, *One route*, the second route; `LocalStore::materialise`, `materialiseThroughObjects`, `MaterialisingVisitor`): `fetchToStore2`'s copy, under the git method into a local store for which `materialisesFromObjects()` holds — selected by `Store::addToStore` and checked again by `LocalStore::materialise` — runs the pull driver over the source accessor with a `LinkingVisitor` beneath and a `node` continuation that can answer the root and each directory from the store: the producer's canonical entry or the naming's memo (`MemoVisitor::lookup`, passed as the `TreeNamer`) gives the node's entry, and when the store holds the tree body — read and verified against its identifier by `GitObjectStore::readAuxiliary`, which refuses unusable incarnations, then canonically parsed by `parseTreeBody` — `ObjectAccessor` and `CachedVisitor` feed the common traversal at the original logical path and depth; the subtree is made from the objects alone, `mkdirat` per directory, `GitObjectStore::link` per regular file (an ordinary registered hit costs one index lookup, one `linkat` and one `fstatat` of the acquired inode; a node the memo does not name, or a directory whose objects the store lacks or holds corrupt, is left to the driver, which lists it and hands its files to the `LinkingVisitor` as the one route would — linked when held, written when not — after whatever the failed materialisation made is removed. `MaterialisingVisitor::tryKnown`, called by `node`, first asks the source producer for a regular file's canonical SHA-256 entry. Under `NoRepair`, a matching entry lets it probe the holder before reading bytes; a miss streams the immutable bytes directly into the destination without buffering or hashing them again. Only producers that established canonical modes and rendering supply this fact (`getKnownEntry`), including the canonical SHA-256 tarball cache; an arbitrary Git object ID or input assertion does not. When that fact is absent, only roots and directories consult the naming memo, so the ordinary copy adds no SQLite lookup per unnamed regular child. Repair bypasses the producer-identity shortcut. A named directory may still be materialised from the store, with its tree bodies verified and acquired regular-file bytes hashed under repair; an unusable object falls back to the source. The on-disk names follow the NAR restorer's case hack on both paths (`CaseHackNames`, one rule shared with `parseDump`: from a tree body the entries are visited in the NAR's order, so a colliding name is numbered as the restorer numbers it). A copy that stages shares `addToStorePrepared` and `moveIntoStore` with `addToStoreFromDump` — `autoGC()` before its first write, a locked temporary directory in the store, the destination temp-rooted, locked and checked valid again, then moved into place (`EXDEV` copied and entered by the one walk), fsynced under `fsync-store-paths` and registered with the root's object hash and the walk's NAR size. An unnamed regular root can establish validity before staging, as below. The deferred version-1 signature check of `addToStore(info, source)` has no analogue, as it has none in `addToStoreFromDump`. A speculative directory keeps its regular-file rows and all consumed auxiliary bodies in `Hold::ownRows()` until the entire subtree succeeds. A failed attempt deletes only names it has not offered to sibling workers. On success, the parent ingestion claims every auxiliary body and completed regular candidate; if an earlier parent candidate has another inode, the same physical alias walk used at publication reconciles every local alias. Only copied collision rows are rebased to the subtree; published rows retain names relative to the whole ingestion. Once any row is published, a merge error aborts the copy and its workers join before cleanup; it cannot return to source fallback. This merge precedes the copy's normal durability boundary. The memo is consulted and never written by this route, so that a first entry pays no upsert per file; the rows are the naming walk's (1.6). *A path already on disk:* `enterIntoObjects` — the walk `nix-store --optimise` (`optimiseStore`), the after-build `enterPath` and the flat-add and `EXDEV`-copy routes of `addToStoreFromDump` make, one walk per built output and per flat add, which hashes and enters in the same pass, under `--repair` entering with `Repair` so that a blob the store holds is re-hashed before a repaired output's file is linked to it — is `objectHashOf` over the written path with `EnterVisitor`: its `node` continuation treats `blobInodes()` as a hint, then requires a current holder whose inode, device, size and canonical metadata match the owned file; only then is the file not read, and its own candidate is recorded. The link count is irrelevant: a holder that no second path shares has one link (`08` K8); `regular` asks `placementOf(where)`, the one place the exceptions of `01` §9.10 law 3 are decided (a writable file is left as suspicious; a file this system does not link — `.app/Contents` on macOS, every file on Windows — is left as written), and otherwise makes the parent writable around `placeRegularFile`. `optimiseStore` migrates an older row before entering its path, by the walk `nix store migrate` makes (`walkOldRow`: the object hash and, on a tee of the same bytes, the NAR hash the row asserts, checked before `recordObjectHash` writes), skips a path found modified or missing with the verifier's message, and reports files entered, files linked and rows migrated. *The verifier:* `verifyObjects` is the same on-disk walk with `VerifyVisitor`, expecting every tree, synthetic root and symlink target through the auxiliary provider when available, and, for every regular file `placementOf` says the store places, a **row**: `holderOrForget(entry.hash, executable, NoRepair)` must answer, and the file is reported missing when it does not. Law 4 for a regular-file blob is exactly that, and the difference is worth stating because it looks like a weaker check and is not one: the bytes are under the verifier's own hands — the file it is walking *is* a file with those bytes — so there is nothing else to check, and what the row adds is that the store *knows* the blob, which is what a later ingestion needs. A file whose row is missing is a file the store will write again; `--repair` re-enters the path, which writes the row. A store the verifier finds short of rows is not corrupt, only forgetful, and `nix-store --optimise` is the wholesale form of the same repair. The producer's canonical entry and the memo's entry have the same meaning but different evidence: the producer established the bytes and canonical rendering, while a memo row records a hashing walk under a stable name. Neither establishes that the destination store holds the object; materialisation checks that separately. There are no `git::` forwarders over the core; the fetchers call `merkle::` directly. Auxiliary SQL values use the existing metadata transaction durability policy; the physical path retains its `fsync-store-paths` boundary. On Windows regular files remain as written and the verifier expects no regular-holder witness; auxiliary SQL acquisition and verification remain available. No Windows build or run has checked this integration (`01` section 13).

**One ordered scheduler.** `HashingVisitor::orderedChildren` owns child collection, admission and ordered consumption; `hashDirectory` only folds summaries. Plain pull hashing, memoised hashing and materialising copies share `CopyPool`, created lazily at the first useful directory split. Parallel traversal requires `AllPaths` and an accessor that explicitly permits it; copying also requires permission for its hooks and namer. Each node's synchronous continuation owns its memo key, and only named cache facts share a mutex. With more than one worker, groups with more than one child and a directory hint join before their ordered fold; other groups read/fold inline even with an existing pool, preserving first-child failure selection and joining accepted jobs before scopes expire. Default and caller-supplied hashing visitors and the NAR push driver remain sequential; `Children::canDefer` keeps borrowed push callbacks immediate. `08` K17 states the finite permission domain and failure/lifetime rules.

**An unnamed regular root.** Its value is its executable bit and bytes, so the completed read already determines the Git address, including the synthetic tree for an executable root. `LocalStore::materialise` uses the same `readBufferedRegular` and `LinkingVisitor::placeRegular` as the restore visitor: the reader retains the observed bytes up to the existing one-mebibyte bound, and its writer opens lazily on a spill. When the complete root fits in memory, the destination is temp-rooted and checked before any `autoGC()`, ingestion hold or temporary directory. A valid destination under `NoRepair` discharges the copy; a missing destination is locked and checked uncached before staging and placing those same bytes. `Repair` still takes the materialisation path for a registered destination. A spill starts staging before the hash is complete and uses the same publication path afterwards. There is one source read and one hash pass in either case; size mismatch or read failure publishes nothing, and an open writer closes before its temporary directory is removed. Producer-known and explicitly named roots retain their existing reuse contracts. The change is confined to this Git-addressed, reference-free copy; Flat, Text, NAR and received-description routes retain their addressing and checks. Selecting this root case adds one root metadata query to the unchanged routes, not a query per child.

**The tarball cache.** Opened as a SHA-256 repository (`tarball-cache-v4`; `GitRepo::Options::oidType`, `git_repository_init_ext`; canonical-name provenance and root projection in `01` §9.10), so a tarball's tree identifier is the store's name for it and its blobs' identifiers the store's. Its packs' compression is the per-object decision of `01` section 10 (`packaging/patches/0004-pack-compression-heuristic.patch`, on top of the three patches of NixOS/nix PR 16427; `GitUtilsTest.packsStoreWhatWouldNotShrink`).

**Operations.** A named subtree can be made from verified metadata and regular holders without reading its source. A regular hit under the limit links and records the recipient's witness; a miss writes its buffer once. Large files stream before placement. Missing/corrupt auxiliary candidates are skipped; if none works, the existing private subtree attempt falls back. Regular aliases are reconciled before the parent projection becomes visible. SQL verification checks every auxiliary incarnation, including unreachable cache copies; repair transactionally rechecks the exact bad copy before deletion and reports outside the state lock. Physical path hashing and ordinary regular repair remain independent.

Whole-store GC removes dead leases and bounded retired cache leaves without reading a graph, then deletes stale SQL projections. Missing/unmigrated roots do not block this ownership-based cleanup. `nix-store --optimise` walks valid paths and rebuilds complete projections while preserving regular sharing; ordinary stores remove legacy `.links`. Overlays mutate upper SQL and upper legacy files only, and retain their existing disabled materialisation/merged-verification/`.links` routes. Daemon transfer still receives a NAR. Auxiliary rows follow SQLite metadata durability, while `fsync-store-paths` retains the physical path boundary. Fresh rewritten-NAR output restoration uses canonicalising hooks; initial builder security checks, the Windows fallback and the later final metadata walk remain. Cached directories rebuild, serialize and hash their summaries after parsing, and cached symlinks hash their verified bytes again. No new syscall, CPU or RSS benefit follows from these source changes.

**The check order.** `LocalStore::addToStore(info, source)` verifies a received path's content address before its object hash, its asserted NAR hash and its size; the address is what the name asserts, and for a git-addressed path it is the sink's root, so the check reads nothing. All checks remain; the order decides which mismatch is reported when several fail.

**Checks.** Keep the external identifier/round-trip, all-root-mode and route-independence oracles; `restoreThroughObjects`, the unchanged-file/write-count tests, regular mode/inode/refusal/repair cases and the materialisation properties remain behavioral checks. In particular, an edited source with a held nested subtree must read none of that subtree (`FetchToStoreLocalTest.copyIsMadeFromTheObjectStoreWhereTheMemoNamesWhatItHolds`), and losing a donor after successful reuse must preserve the recipient's witnesses and bodies. Existing missing/corrupt-child, private-attempt rollback, builder multioutput, live/dead lease and creation-window checks must be adapted without weakening their visible outcomes. SQL fixtures must independently cover empty/exact/partial chunks, malformed encodings, alternate incarnations, signed identities, retry, old read-only stores and conditional repair. Legacy cleanup needs no-follow, bounded-depth and upper-only authority checks; real mounts must retain lower inventory/hashes, merged visibility and no whiteouts. File-per-body, per-body fsync and mark-graph counter assertions describe the retired representation and are not evidence for the replacement. Executed results belong in `09-performance.md`; historical controls remain in `05-validation.md`.


### 1.8 Garbage collection

`Store::addTextToStore` protects actual references before backend publication can invoke GC, including with an older daemon. The already-valid destination fast path roots the referrer and relies on its recorded closure. The evaluator roots actual context base paths before mounted copies or deep traversal, and newly admitted existing context paths before another nested eager write. Read-only evaluation introduces no publication roots. `TextStoreTest.publicationRootsExistingReferencesBeforeBackendCollection`, `anAlreadyValidReferrerRootsItsClosureWithoutUploading`, `admittedReferencesSurviveNestedEagerWrites` and `validatedContextKeysSurviveArbitraryFlagEvaluation` exercise these distinct cases with real collection and an unreferenced control object.

### 1.9 One address (libstore, libfetchers, libexpr, libflake, nix)

**Meaning.** `01-specification.md` section 9.11: a store object's content hash is the git entry of its root under SHA-256, total over store objects, with distinct content identified under the collision assumption of §2.4; the NAR is a serialisation; the flat hash is read through a shim and never written as a name.

**Representation.** The object hash is a `Hash`: `merkle::objectHash(TreeEntry root)` — the tree id of a directory, the blob id of a plain file, the tree id of `{"." ↦ entry}` for an executable or a symlink — replacing `rootHash`; `UnkeyedValidPathInfo::objectHash` where `narHash` is, `narSize` kept and computed by the same walk (`merkle::nar::{regular,symlink,root}`, from names and sizes; the property `MerkleHash.narSizeEqualsDumpPathLength`). A hasher core in libutil (`merkle-hash.hh`: blob id from size and chunks, tree id from entries, the `name + "/"` key; `merkle::insertEntry` refuses `.`, `..` and the reserved case-hack marker, so among canonical trees only the synthetic root wrapper admits a `.` entry, emitted by `syntheticRootTree`), ungated; over it `HashingVisitor` and its two drivers, `traverse` and the push adapter `ObjectHashSink` (a NAR stream or an accessor walk to a root entry and a NAR size, no disk), the store's `LinkingVisitor` (the restore route, deciding before the write; 1.7) and `EnterVisitor` (the on-disk walk, `enterIntoObjects`). `ValidPaths.hash` holds `git:sha256:<hex>` for an object hash and the old `sha256:<hex>` for an unmigrated NAR hash, told apart by prefix before parsing — the prefix test comes first because the old parser raises `UsageError` on an unknown algorithm, not the `BadHash` the read site catches; `nixSchemaVersion` 11. The object store's root identity is the column; there is no `roots/` directory or second root record. Auxiliary lifetime follows ingestion ownership rather than interpreting valid hashes as a reachability graph. Fingerprint `"2;" + path + ";" + objectHash + ";" + refs`; `WorkerProto::featureObjectHash` (the same string slot on the wire, its meaning negotiated); a serve version; `NarInfo::objectHash` beside `narHash`; JSON version 4. Lock version 8 with `treeHash`; `Input::getTreeHash`; the GitHub fetcher's dormant `treeHash` made the SHA-256 SRI value; no `narHash` attribute on any input. The shim as one function in libfetchers, `narHashOf(settings, Store &, SourcePath tree, Hash treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the existing memoised NAR walk (`fetchToStore2` under `NixArchive`, dry run) with the `treeAddress` pair recorded — called through `assertNarHash` from `Input::getAccessor` (every fetch route, `mountInput`'s included), from `addPath` for a `sha256`, on `fetchTarball`'s route, and directly by `fetchTree` to build the language's lazy `narHash`; in libstore, `narHashOf(Store &, StorePath)` — a walk, `narFromPath` into a `HashSink`, no cache — for an old client on the wire (once per query) and for the path-info JSON formats 1 to 3. A version-1 signature is checked against an `assertedNarHash` when the description carries one, and otherwise through this walk when a caller binds it (`NarHashThunk`: `nix store verify`, `copy-sigs`, and `addToStore`'s tee for a description that asserts none).

**Operations, solved.** Registration computes the object hash where the NAR hash is computed today: the sink's root at the three ingestions, `enterIntoObjects` after a build (so every output has one, input-addressed or not), `objectHashOf` for `computeStorePath` (the one tree walker; the fetchers' memoised naming is `objectHashOf` with `MemoVisitor`, whose `node` answers from the memo or retains its key while `descend` computes the summary to record); the NAR hash is computed at registration only where an old sender asserted one — the receiving tee of a copy from an old peer or an old cache, without an extra source read — and is verified there and never stored. `mountInput` names by `fetchToStore2` alone; the second walk and the lazy attribute's pairing rule go; `narHash` on an input is the shim's lazy attribute. `addPath` and `fetchTarball` with a `sha256`: fetch, then verify by the shim, then record; with a `treeHash`: the fast path is `isValidPath` of the name it determines. Copy: the receiver verifies the object hash from its sink's root and, when the sender is old, the NAR hash from the tee. `verifyStore --check-contents`: the object hash against the root recomputed from the files, by way of the blob identifiers the object store checks already. `nix store migrate`: every unmigrated row filled by the verified walk (`walkOldRow`, `01` section 9.11 *The database*), then re-rendered.

**The column and the type.** Two facts fix the type. First, a path info describes a path in *some* store: for a newly registered or successfully migrated local path the object hash is known, while an old row that cannot be migrated may still be returned with only its NAR assertion, but a substituter's description of a path (a `.narinfo` from an old cache, an old peer's reply) may carry only a NAR hash until the NAR itself arrives. Second, if the daemon kept speaking the old protocol while the column changed, every `QueryPathInfo` from a client would cost a walk to produce the NAR hash it must send; so the worker feature under which the object hash travels is part of the same change. Hence:

- `ObjectHash` (libutil, `object-hash.hh`): a strong type over `Hash` — `static ObjectHash of(const merkle::TreeEntry & root)`, `std::string render() const` giving `git:sha256:<base16>`, `static std::optional<ObjectHash> parse(std::string_view)` (nullopt for anything else, in particular an old `sha256:` row), `==`/`<=>`. A NAR `Hash` cannot be assigned to it by accident; the compiler enumerates the sites.
- `UnkeyedValidPathInfo`: `std::optional<ObjectHash> objectHash` — required for new local registration (`addValidPath` refuses one without), possibly absent for an unmigrated legacy row or an info from a substituter or an old peer; `std::optional<Hash> assertedNarHash` — the NAR hash a sender asserted (an old peer on the wire, a `.narinfo`, `--load-db`, JSON before version 4), verified on the receiving tee and never stored; `narSize` as before. Legacy NAR computation is passed to the transfer operation, not retained in this description; batch callbacks distinguish original `Source` objects even when destination names coincide. The field `narHash` is gone; every former reader is either an `objectHash` reader (content identity), an `assertedNarHash` verifier (receipt), or a call of the shim `narHashOf(store, path)` (a walk producing the NAR hash for an old form).
- The local database: `hash` column holds `objectHash.render()`; an old row's `sha256:` value is recognised at the one read site by `ObjectHash::parse` returning nullopt, and migrated in `queryPathInfoUncached` between two lock scopes, as `verifyStore` does its walk, and never in `queryPathInfoInternal`, which `addSignatures` calls inside a transaction — by `objectHashOf` over the path (`migratePathInfo`) — then written back unless the store is read-only; the migration takes no temp root: a path deleted mid-walk reads as invalid, and the row is left for the next query; `nixSchemaVersion` 11, stated as the deliberate exception to the additive-migration convention.
- Where the object hash is set: the three ingestions from the sink's root; `LocalStore::materialise` from the root the materialising walk computed (1.7, the second route), which is the memo's entry where the store held the tree and the hasher's where it was read; `addToStoreFromDump`'s flat and copy routes by `objectHashOf` over the written path; the builder's outputs by one walk, `enterPath`, where `hashPath(NixArchive)` ran on master, before the `--check` branch: it hashes and enters the object store in the same pass, so a built output and a flat add cost one walk where master's NAR hash and optimise pass cost two, under `--repair` entering with `Repair`; `--load-db`/`--register-validity` by a walk. Verification by recomputation: `verifyStore --check-contents`, `pathContentsGood`, `nix store verify`, `nix-store --verify-path` compare `objectHashOf` with the row; `nix-store --export` and `--import` compute the object hash of the stream with `ObjectHashSink` on the tee and compare or register.
- The forms in this step: fingerprint 2 (`2;<path>;<objectHash.render()>;<refs>`; a version-1 signature verified against `assertedNarHash` when present and otherwise against the NAR hash the caller's `NarHashThunk` supplies by one walk — `ValidPathInfo::checkSignature`, bound by `nix store verify`, `copy-sigs` and `addToStore`'s tee, so a version-1 signature on a locally held path keeps verifying once its row is migrated; `narSize` must be known). Signing produces both where both hashes are known — `ValidPathInfo::sign` signs the version-2 fingerprint and `signV1` the version-1 one (`1;<path>;<NAR hash>;<NAR size>;<refs>`); `nix store sign` calls `sign` only when the info carries an object hash and `signV1` whenever the NAR size is known, the NAR hash asserted by the info (a narinfo's `NarHash:`) or else computed by one walk (`narHashOf(store, path)`), so it works on a cache an older Nix wrote, whose infos have no object hash and get version 1 alone; the binary cache's upload signs both with the cache's keys, its NAR hash from the tee; `Store::signPathInfo`, signing at build under `secret-key-files`, signs version 2 only, no NAR hash existing there — because an old client verifies version 1 alone and counts only the signatures it can verify (master's `checkSignatures`), so a cache carrying version 2 alone was refused under `require-sigs`, and a build-signed path copied into a keyless cache still is until `nix store sign` runs on the cache (`01` section 9.11, *Signatures*). Since one key then has two signatures, `checkSignatures` counts distinct keys. A path an old client verifies is one the daemon can describe to it; a path info that arrives at `LocalStore::addToStore` with neither hash and no content address is refused (the daemon reaches it through the store), since nothing about it can be checked; `WorkerProto::featureObjectHash`, under which the path-info slot carries `objectHash.render()` and without which the daemon sends `narHashOf` and reads the client's string as `assertedNarHash`; a serve-protocol version likewise; `.narinfo` reads `ObjectHash:` into `objectHash` and `NarHash:` into `assertedNarHash`, and the upload writes both, its NAR hash from the tee it already has; path-info JSON version 4 with `objectHash` required and `narHash` optional, versions 1 to 3 written through the shim; `nix hash path --mode git` prints the object hash: for a bare executable or symlink the synthetic tree's id, where master printed the blob's (`01` section 9.11); `nix-store --dump-db` writes the rendering.
- The object store: the same synthetic root body is staged when entering; SQL metadata belongs to its ingestion. The column remains the path's root identity, with no `roots/` directory or separate root record. Hash migration walks physical contents but does not publish an auxiliary projection.

**The fetchers' and the language's representation.** The fetchers and the language stop naming anything by the flat hash; every source is named by its tree hash; old assertions are verified by the shim.

- *No setting.* Every site names by the git method (`fetchToStore`'s default, `addPath`, `copyPathToStore`, `mountInput`, the `path` fetcher's copy and the Mercurial fetcher's dirty-checkout copy); the exceptions and the explicit methods are `01` section 9.9's.
- *`treeHash` on inputs.* `Input::getTreeHash()` reads the attribute `treeHash`, an SRI SHA-256 string, the git tree (object) hash of the input's root — the same value the store's `objectHash` renders, so `Input::computeStorePath` is `makeFixedOutputPathFromCA(name, {Git, SHA256, treeHash})`. Every scheme that allowed `narHash` allows `treeHash` (put it beside `narHash` in each `allowedAttrs`); `isLocked` accepts either; the URL query `treeHash=` is parsed and emitted where `narHash=` is. The GitHub fetcher's dormant `treeHash` (SHA-1 hex behind `#if 0`) becomes this value: the tarball cache is SHA-256, so `TarballInfo::treeHash` is it; a 40-hex value is refused. A fetch's result carries `treeHash` and never `narHash`: `Input::fetchToStore` sets it from the path info's `objectHash`; `mountInput` sets it from the dry-run tree hash; the tarball and file fetchers set it from the cache's tree hash and from the object hash of the flat file.
- *The lock file, version 8.* A locked input's `locked` attributes carry `treeHash`; `narHash` is not written. Reading a version-7 lock: the node's `narHash` is an assertion; `mountInput`, after naming the tree, verifies it through the shim and then replaces it in the input's attributes by the `treeHash` it computed — the one mutation the copy in `checkLocks`'s final branch admits. But `nix flake lock` keeps an unchanged node without fetching it, so a version-7 lock whose inputs are all unchanged is not rewritten, and forcing a rewrite would fetch every input only to name it; the rule is therefore that a node gains `treeHash` when it is next fetched, that a lock is written as version 8 whenever it is written at all, and that a version-8 lock may still carry a node's `narHash` alone — every reader accepts either, and the old-lockfiles test keeps its comparison. `lockfile.cc` reads 5 to 8 and writes 8; `flake.cc` erases `treeHash` where it erased `narHash` after `applySelfAttrs`.
- *The shim, one function in libfetchers:* `Hash narHashOf(const fetchers::Settings &, Store &, const SourcePath & tree, const Hash & treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the memoised NAR walk, recording the `treeAddress` pair (it keeps no memo of its own); and `void assertNarHash(settings, store, tree, treeHash, asserted, description)` throwing the existing `Error(102, "NAR hash mismatch in input '%s' ...")`. Called from `Input::getAccessor` (`fetchers.cc`, every fetch route — a version-7 lock, `fetchGit { narHash }`, `?narHash=` and `mountInput`'s inputs among them), from `addPath` (a `sha256` on `builtins.path`/`filterSource`), on `fetchTarball`'s route (`fetchTree.cc`), and by `fetchTree`'s `emitTreeAttrs` to build the language's lazy `narHash` thunk from the tree hash. The `treeAddress` memo is read only by the shim's fast paths: a `sha256`/`narHash` assertion that names a tree already present finds it through the memo, else fetches and verifies. No input ever carries a `narHash` attribute again, lazy or not (`attrsToJSON`/`attrsToQuery` force lazy attributes, so one on the input would be walked and written by every lock and URL).
- *The language.* `fetchTree` and `fetchGit` results carry `treeHash`; `narHash` is a lazy attribute `emitTreeAttrs` builds through the shim; `builtins.path { sha256 }`, `fetchTarball { sha256 }`, `fetchTree { narHash }` and `?narHash=` accept the NAR hash (shim) and `treeHash` (the cheap assertion); `nix flake prefetch` prints `treeHash` as `hash` (`01` section 9.9, *The language*).

**Checks.** Totality and root-kind separation on generated trees (not a proof of collision freedom) (`libutil-tests/merkle-hash.cc`, `object-hash.cc`); the case-hack discriminator (`01` section 9.11: a NAR with `Foo` and `foo` through the sink and re-hashed from disk, equal, on macOS; `libutil-tests/object-hash-sink.cc`, `LocalStoreObjectsTest.caseHackSuffixIsNotHashed`); every form's round trip (`libstore-tests/object-hash-*.cc`); the shim's entry points each with a negative control (a wrong old assertion refused: `source-addressing.sh` for `builtins.path { sha256 }`, `filterSource`, `treeHash`, `fetchTarball { sha256 }` and a planted wrong hash in a version-7 lock; `fetchGit.sh` for `fetchGit { narHash }`); the old-peer interop through the reference binary, gated on `NIX_REFERENCE_BIN` (`tests/functional/object-hash.sh`, both directions and both feature states); the cost law measured on Linux (`05-validation.md` section 6: a tarball fetched twice, the second differing in one file; the copy of an edited tree) — no read-counting discriminator exists.

## 2. Risks and open items

- **Integrated validation remains required.** Source review and recast tests do not establish runtime equivalence or performance. Earlier buffer ablations remain historical; this change makes no new CPU, RSS or wall-time claim.
- **Remote errors and cost.** Eager publication exposes the existing producer/backend error directly. Rooting and validity checks can require daemon round trips. A valid destination avoids upload; absent or repaired text follows the existing compatibility route. No retry in a C exception handler or destructor can replace the first error.
- **Partial failure.** No-elision fixes complete successful object sets; C1′ allows different reference-closed partial sets on failure. Tests must not turn the previous flush schedule into a semantic requirement.
- **Mounted source history.** Eager text writes do not freeze mounts. Copying must still reject a changed name, and output must still wait for its required mounted copies. Source-copy history and content-memo eligibility remain separate.
- **Repair.** The shared synchronous producer passes repair through the existing dump operation even for a database-valid object with missing bytes. It does not use the bulk-add fast path that skips already-valid entries.
- **Metadata ownership.** Text bytes are not retained in path-info metadata. An old-wire hash computation is scoped to the transfer that needs it; modern metadata caching must not retain a producer's payload.
- **Consumer compatibility.** Branch-internal flush/token APIs are removed. Ordinary value string access returns bytes, while build and mount realization remain explicit where needed. C allocation arenas and evaluator settings must outlive their respective users.
- **Client cache.** The earlier fixes to remote path-info cache invalidation remain necessary for all writers, independently of text buffering.

## 4. Defects of master found by this work

Fixed on the branch and pinned: the ATerm reader promoted `char` to `int`, so a byte 0xFF in a derivation read as `EOF` (`DerivationAtermTest.aByteEqualToEofRoundTrips`); a platform string containing `"` or `\\` was written verbatim and could not be read back (`DerivationAtermTest.platformOutsideTheFormatIsRefused`); the store-directory field of a `.drv` was written verbatim off Windows and unreadable when the directory holds `"` or `\\` — the escape flag's default is the platform, not the directory's characters — and the writer now refuses such a directory under the verbatim mode (`DerivationAtermTest.storeDirOutsideTheVerbatimFormIsRefused`, `WindowsStoreDirTest.unsupportedIsRefusedAtTheWriter`); `nix-prefetch-url --attr` had an inverted condition (`tests/functional/prefetch-url-attr.sh`); `RemoteStore::addToStore` from a stream and `addMultipleToStore` did not invalidate the client's path-info cache while `addToStoreFromDump` did (fixed in `src/libstore/remote-store.cc`; ordinary store producers rely on it). Found and not fixed, master's: `builtins.fetchGit`'s default `exportIgnore = true` makes libgit2 look the attribute up for every file on every copy whether or not the repository declares it. Fixed here: master's `export-ignore` lookup for a *commit* passes `GIT_ATTR_CHECK_INCLUDE_COMMIT | GIT_ATTR_CHECK_NO_SYSTEM`, whose low bits are `GIT_ATTR_CHECK_FILE_THEN_INDEX` (0), so libgit2 reads the working directory's `.gitattributes` and then the index's entry before the commit's blob — an uncommitted file in a checkout decided what a fetch of a committed revision from it exported, and the same revision fetched from a bare clone exported something else (`GitUtilsTest.committedRevIgnoresTheWorkdirsUncommittedGitattributes`).
