# Derivation: from the specification to the implementation

This document is the implementation as it stands, derived from `01-specification.md`. Section 0 states the architecture and the correctness argument; section 1 gives each component as an equation in one unknown — the operation to write — with the check that would show it wrong (how each check is run is `05-validation.md`'s; the local store's locks, invariants and sink order are `08-store-model.md`'s); section 2 the risks a maintainer relies on; section 4 the defects of master this work found. Section numbers are stable because the code cites them. Locators are `file:line` in master at the branch's merge base unless stated; line numbers drift.

## 0. The architecture and the correctness argument

### 0.1 The architecture

The meaning is `01-specification.md`'s: a source and a store object are content-addressed trees; the store is a Merkle DAG of trees with reference edges; a tree has one address, its object hash — the git identifier of its root under SHA-256 — from which the store path is formed with the object's name and references, and the NAR is its serialisation, whose hash is computed by one walk when an old form asks for it and never stored (`01` sections 2.4 and 9.11).

The Store interface, the protocols, the database and the language changed as `01` section 9.11 says: path info carries `objectHash` where it carried `narHash`, the database column and schema, the fingerprint, the worker and serve protocols, the `.narinfo`, the path-info JSON, the lock file and the language's hash attributes changed with it (1.9); the store path's form and the string-context variants did not (`01` section 6). Deferral lives in the evaluator. `EvalState` holds a `WriteBuffer` (`src/libexpr/write-buffer.{hh,cc}`): a map from `StorePath` to a pending object's `ValidPathInfo` and bytes, holding exactly the objects whose bytes evaluation already has — derivations and `toFile` texts — because their paths are functions of their content and are therefore known before the write (1.1). Sources are not deferred: the reference hashes and copies a filesystem source in one walk, and a pending source would need two (1.5). Mounted flake inputs use master's own accessor-based deferral, `mountInput` hashing without copying and `ensureLazyPathCopied` copying on dereference (1.5).

Materialisation happens at the escape boundary (`01` section 3), by two rules. A door — an operation through which text leaves the evaluator — writes the whole buffer, references before referrers, in one `addMultipleToStore`, with temp roots taken at enqueue, whatever the text's own provenance says; a dereference — a name about to be read or handed to a reader — writes the buffer when the object named is pending and nothing otherwise. The string context carries provenance for the one purpose the buffer cannot serve, `emit`'s copying of the mounted inputs a text names (`ensureLazyPathsCopied`) (1.2). Output sinks take a `RealisedString`, which only a flushing accessor of `EvalState` can construct. A bare `StorePath` obtained from a value is therefore valid by construction, and the Builder, GC roots and every command inherit that without knowing it.

Names come from one homomorphism inside the accessors — `subtree`, `filter`, `union`, `graft`, each with its derived naming rule (`01` sections 7 and 8): the vanilla git leaf names every subtree by its object with its mode, the fixed-set filter by the inner name and its prefix-closed admitted set, the evaluation root's union by either child under the coherence precondition; one persistent memo, tree name to object hash (the method in the key, `sourcePathToHash`), serves git inputs and tarballs alike (1.3, 1.4; `01` section 9.9).

**The escape guard, as the semantics forces it (`01` section 3).** (C2) holds by construction exactly when the only ways of separating a string's text from its provenance are the exits that discharge the obligation first. The exits are two, told apart by the conditions: `realise` writes every pending object — whatever the string's own provenance says, so that a context-free text naming a pending path cannot escape either — and yields the bytes; `emit` does the same and also copies the mounted inputs the provenance names, and is used exactly where the reference copies them, the commands' outputs, because copying at a diagnostic would write what the reference does not (C1). Both yield a `RealisedString`, the only type the evaluator's printers and the commands' output statements accept. Exclusivity is the representation: a string value's bytes are private to `Value`, and the payload beneath them private to `Value` alone, readable only by the friends named beside them — the evaluator, the symbol table, the parser's literal, the tests — so outside the evaluator text is reached through the doors and nothing else, and inside it through `EvalState`'s accessors, which return bytes and provenance together, or refuse a provenance, for results that stay inside. A `StorePath` is obtainable from a value only through a flushing coercion, and a path about to be read is written first when it names a pending object. The text exits are therefore the sites the compiler refuses once the bytes are hidden, not a list kept by hand; the dereferences inside the evaluator that parse a store path from accessor bytes, and the builtins that drop a string's provenance, still flush by hand and are the enumerated rows of the table in 1.2, swept by the builtin test. What the compiler cannot scope is the accessors themselves, since C++ has no access control at the scope of a library: a check script holds them to `src/libexpr` and `src/libflake`, and what the kernel does with the bytes is reviewed. The libexpr accessor API changes, and so — by `01` section 9.11, not by this guard — do the Store interface's path info, the protocols, the database and the language's hash attributes (1.9); the store path's form and the context variants do not, so the guard is within the charter of `01` section 6 as it now reads.

### 0.2 The correctness argument, and what checks it

**The argument.** ⟦store with buffer⟧ = ⟦store⟧ + Δ, where Δ is what the reference would already have written (1.1). (C1): every object in the buffer is in Δ, and the flush is total and runs at every escape and at the end of the command, so the final store is the reference's up to the renaming the address induces (`01` section 3: every source's path, and everything built from one, is renamed; the objects are the same) — deferral reorders and batches writes and never omits one. (C2): a pending name can leave the evaluator only through a door or a dereference; a door writes everything before it emits, a dereference writes before it reads whatever it reads if that is pending, so no name escapes before its object exists. Naming soundness: equal name implies equal NAR, by the rules of `01` section 8 applied inside the combinators. The remainder — that each path is what master computes, that repair, garbage collection and the trust bit agree — is that each operation computes exactly what the corresponding master operation computes (1.1, 1.7).

**What checks it.** The differential harness runs master's functional suite under the reference and under the implementation and compares the resulting stores object by object, in local mode and through the daemon, under the renaming views (`05-validation.md` section 3). The sweep runs every builtin on a pending text, a pending derivation path and an attribute set naming them, against eager evaluation (1.2; `src/libexpr-tests/write-buffer.cc`). The (C2) observer dereferences every printed path from a second process (`05-validation.md` section 3), and a byte-level check fails any printer that emits a pending name. Naming soundness is a rapidcheck property over random terms and over real git trees (1.3, 1.4). The bijection is checked byte-exact over real store objects and directly for `.git` and the name domain (`01` section 2.7).

**What is not proved, in the built implementation.** The text exits are derived, not enumerated: the compiler confines a value's bytes to `Value`'s friends, and the check script confines `EvalState`'s accessors to the kernel, `src/libexpr` and `src/libflake` (0.1, 1.2). Inside the kernel the accessors return bytes, so a new primop could still hand them to a process-level sink without a door; review holds that, C++ having no access control at the scope of a library. The dereferences inside the kernel that parse a store path from accessor bytes (`storePath`, `fetchTree`'s attributes; the table of 1.2) remain an enumerated set, swept by the builtin test. The context-free case — a pending path's text arriving without provenance — is closed at the doors by their total write and at the reads by `writePendingBeforeRead`, pinned by `aContextFreeLiteralNamingAPendingPathCannotEscape` and `aContextFreeLiteralNamingAPendingPathCanBeRead` (`src/libexpr-tests/write-buffer.cc`); it still reaches two exits that are not doors, a diagnostic printed while the evaluator lives that names an attribute or a source literal (the repl's error print; a fatal error prints after the destructor's flush), and a path value built from a literal. The suite is bounded by the commands it contains; the sweep and the observer stand in where it does not reach.

## 1. Components as equations

### 1.1 The write buffer

**Meaning.** ⟦store with buffer⟧ = ⟦store⟧ + Δ, where Δ is the set of objects the reference implementation would already have written.

**Representation.** A member of `EvalState`, beside `store` and `storeFS`: a map from `StorePath` to a pending object, where a pending object is a `ValidPathInfo` plus its bytes — a derivation's ATerm or a `toFile` text; sources are not pending (section 1.5). Plus the set of paths already temp-rooted.

**Operations, solved.**
- `addText(name, contents, references) -> StorePath`: compute exactly what `Store::writeDerivation` computes (`src/libstore/derivations.cc:92-116`, `infoForDerivation`) and what `toFile` computes (`src/libexpr/primops.cc:2783-2799`), insert, temp-root each reference that is not itself pending, return the path. Replaces `state.store->writeDerivation(drv, state.repair)` at `primops.cc:1919-1920`; read-only mode keeps computing the path and writing nothing, as master does. The masked-hash memo seed at `primops.cc:1928-1931` is unchanged.
- `flush()`: total. Order the pending set so that references precede referrers (`topoSort` over pending references only; references outside the set are already valid), build a `Store::PathsSource` of `(ValidPathInfo, Source)` pairs, streaming each text as a NAR of a single file exactly as `dumpString` does, and call `store->addMultipleToStore(...)` once with `NoCheckSigs`. Then `invalidatePathInfoCacheFor` each flushed path, since master's `RemoteStore` does not (`src/libstore/remote-store.cc:436, 814`). Empty buffer: return immediately, one branch.
- Trust bit: the daemon forces `ultimate = false` on bulk adds (`src/libstore/daemon.cc:553`); eager writes of derivations and sources already carry `false`, so the final state agrees. Built outputs are never in the buffer.
- Repair: `--repair` re-adds an existing derivation in master (`derivations.cc:128-129`). With the buffer, a repair request enqueues even if the path is valid and flushes with `Repair`. The differential test with `--repair` and the repair unit test are the check.

**Read-your-writes.** With a total flush there are exactly two in-process readers of a pending object that are not escapes: the masked-hash memo, seeded at instantiation so it never misses within a process, and the eval cache's getters, which are doors (section 1.2). Everything else that would read a pending object, `realiseContext`, `import`, `builtins.storePath`, `fetchTree`, the deep-dependency closure in `derivationStrict` (`primops.cc:1794-1810`), is a dereference and writes first what it is about to read. The builtin sweep of 1.2 holds this sentence to the code.

A string that loses its provenance inside the evaluator (`unsafeDiscardStringContext`, `getContext`, `match`, `split`) is as safe as any other text under those two rules and needs no write of its own. The dereferences — `coerceToPath` and the resolved path, `coerceToStorePath`, the derived-path coercions, the fetchers' local inputs — all go through `writePendingBeforeRead`: written iff the object named is pending.

**Batching.** Every door writes totally, so a diagnostic in the middle of an evaluation — `builtins.trace`, `warn`, a printed value in the repl — splits the batch at that point: correct by (C2), and the cost of a diagnostic is the write of whatever is pending then. `nix-instantiate` prints each derivation path it obtained through `requireDrvPath`, which is `coerceToStorePath`, which flushes; so the command flushes once per top-level derivation, each flush carrying the derivations that evaluation created since the last one. That is the consequence of the decision that a bare `StorePath` obtained from a value is valid by construction; the alternative, coercion that does not flush, would move the obligation to every consumer of a `StorePath` in libstore, which the specification forbids. The bound that does hold: every flush writes at least one object, so a command makes at most as many bulk adds as master makes single adds, and exactly one when nothing escapes before the end.

**Residue, stated.** Outside the kernel, by construction on `Value` and by the check on `EvalState`; inside it, the accessors are public members, and review holds them. What the type does not reach: a store path named by its physical location in a diverted store, which `isInStore` does not recognise; the check script's textual limits, stated in its header; and the legacy `main`s' three end flushes (the teardown row above). Attribute names and source literals are context-free by construction and print through the same doors as everything else when they reach a diagnostic, since the repl's error prints and the printers realise the text they show, and a fatal error prints after the destructor's flush.

### 1.3 Mount and union alignment (libutil)

**Meaning.** `01-specification.md` sections 7, 8.2, and 8.4.

**Operations, solved.**
- `MountedSourceAccessorImpl::readDirectory(p)`: the resolved accessor's listing, plus one entry per mount point directly below p, typed by the mount's root, and one synthesised directory entry for the first component of every deeper mount point; an entry the resolved tree already has is kept. `maybeLstat(p)`: the resolved accessor's answer, else a synthesised directory if some mount lies strictly below p. `mount()` stays insert-only. `getFingerprint(p)`: below a mount point or away from all of them, the resolved accessor's name; above one, the JSON of the resolved name at p and every mount point below p with its root name, or nothing if any part is unnamed.
- `UnionSourceAccessor`: the top-down definition of `01-specification.md` section 7.1. One function, `owner(p)`, gives the child whose node p denotes, or nothing when an earlier child's non-directory at an ancestor hides p; `readDirectory(p)` merges the directories of the owner and every later child that has one there; `readFile`, `readLink`, `maybeLstat` go to the owner. `getFingerprint(p)`: the three-case rule for a general union, with a merged directory named by the JSON of its parts' names or not at all. The evaluation root passes `UnionCoherence::ChildrenAgree` (`src/libexpr/eval.cc`), which keeps master's first-child-with-a-name rule; the precondition, that the on-disk store is a valid content-addressed store, is the specification's own assumption.

**Checks.** A rapidcheck property over `MemorySourceAccessor` trees: for generated terms of the four operations with a content-naming leaf, equal names imply equal NARs at every path, and equal subtrees under a naming leaf imply equal names. Unit tests for the two listing changes. The differential run of the functional suite, expecting one exclusion: impure `readDir` of the store directory.

### 1.4 Names (libfetchers, libutil)

**Meaning.** The naming rules of `01-specification.md` section 8.2, with names withheld for attribute-dependent accessors.

**Operations, solved.**

Otherwise the input-level name, as on master. Submodule mounts are a graft above the leaf and get the graft rule from 1.3.
- `FilteringSourceAccessor::getFingerprint(p)`: when the accepted set is fixed at construction, the pair of the inner name at p and a canonical hash of the prefix-closed accepted set restricted to the paths below p (`01-specification.md` section 7.1); the set is computed once by the same top-down pruning walk `dumpPath` performs (`src/libutil/archive.cc:102-108`), so the accessor's tree and its NAR agree. Master's accessor forwards the unfiltered name (`src/libfetchers/filtering-source-accessor.cc:60-65`). For the allow list, whose set grows: pass the inner name through when p lies under an allowed prefix, since everything beneath is then admitted, and withhold a name otherwise.
- `fetchToStore2`: replace the `filter ? nullopt : getFingerprint` bypass (`src/libfetchers/fetch-to-store.cc:64-65`) by wrapping the source in a fixed-set filtering accessor built from the predicate, and pass no `PathFilter`. The store path is unchanged, because dumping the wrapped accessor without a filter produces the same NAR as dumping the unwrapped one with the filter: both are the pruning walk. The persistent memo keeps its key form — the accessor's name with the method (`sourcePathToHash`) — and its value under the git method is the object hash, the store's own address (`01` section 9.9); it becomes the subtree memo because the git leaf names subtrees.

**Checks.** The soundness property from 1.3 extended with a git-like leaf. Cost tests (subtree shared across two revisions hashed once; filtered source cached across processes; N same-content names copied once) using the existing `hashing '` and `copying '` activity lines (`fetch-to-store.cc:97-102`). The differential run, expecting no behavioural change.

### 1.5 Sources in the buffer

**Meaning.** Δ contains every `builtins.path` and `filterSource` result, every `toFile`, every instantiated derivation, and a mounted flake input only when the reference would copy it.

**Sources stay eager.** Enqueueing `builtins.path`, `filterSource` and `copyPathToStore` results as pending sources, with the accessor as contents, is refuted on cost and empty on correctness:

- The reference copies a filesystem source in one walk: `copyPathToStore` (`src/libexpr/eval.cc:2700`) and `addPath` (`primops.cc`) call `fetchToStore(Copy)`, which for a path without a fingerprint, that is every path under the real filesystem, goes straight to `addToStore(name, path, ...)` and hashes while it copies. A pending source needs its store path at once, since the language returns it, so it must be hashed at enqueue; the copy at flush is then a second walk. Under no elision every source in Δ is written by the end of the command regardless, so deferral saves no write and costs a walk, or the memory to hold the NAR. The persistent memo does not help: it is keyed by fingerprint, which filesystem paths lack.
- The bulk add cannot take a source whose NAR size is unknown: `LocalStore::addToStore(info, source)` checks `narSize` as well as the object hash (and an asserted NAR hash, when the sender asserted one) (`src/libstore/local-store.cc`), and neither the memo (`sourcePathToHash` stores the hash alone) nor `computeStorePath` yields a size. Streaming a mounted input into the batch would need a third libstore API or a sizing walk.
- Mounted inputs are already deferred: hashed once at mount (`mountInput`, `paths.cc`), copied on demand at the doors that copy, and at the dereferences (`ensureLazyPathCopied`, called from `derivationStrict`, `toFile`, `realiseContext`'s callers, `exec`, `nix eval`, `nix-instantiate`, `installable-value.cc`, `app.cc`). Moving that copy into the flush changes when the same `fetchToStore(Copy)` runs, not how often, and would require a flush after each of those nine sites for the copy to precede the escape; a site missed is a defect the suite would not necessarily see. `path`-type inputs are not even mounted: their fetcher names them by one walk and copies them, when the store lacks the tree, before evaluation sees them (`src/libfetchers/path.cc`, `PathInputScheme::getAccessor`; `01` section 10, *a `path:` input outside the store is named first*).
- Correctness gains nothing: an eager write satisfies (C1) and (C2) trivially, and the specification's "Δ made explicit" does not require Δ to pass through the buffer, only that the implementation be the reference with Δ accounted for. The buffer holds what deferral makes free, objects whose bytes are already in memory.

**The order of copy and emission in `nix eval`.** The reference prints a mounted input's path and copies the input afterwards (`src/nix/eval.cc`, `ensureLazyPathsCopied` after the output statements); once copied the input is in Δ for that command, so a reader of the output can hold the name before the object exists. This is the case the specification's ordering rule names (`01-specification.md` section 3). `nix eval` copies before it emits, in all four output modes: `--raw` and `--json` after producing their bytes and before writing them, `--write-to` per string before `writeFile`, and the default printer after rendering the value to a string and before writing it. `builtins.trace`, `builtins.warn` and the repl's `:p` are left as the reference has them: they never copy, so copying there would add an object to the store the reference does not add, and (C1) forbids it. The check is the (C2) observer with a git input large enough for the copy to take visible time, which distinguishes the two orders (`05-validation.md` section 3, the observer's mounted-input modes).

### 1.6 The naming of sources (libfetchers, libexpr)

**Meaning.** `01-specification.md` section 9.9: every source the evaluator names is named by its object hash under the git method; there is no setting and no second name; an old assertion of a NAR hash is verified by the shim. The mechanism is 1.9's ("The fetchers' and the language's representation"); this section states what stands and names its checks.

**Representation, as it now stands.** `fetchToStore`'s default method is `Git` (`fetch-to-store.hh`, `fetch-to-store.cc`, `methodRequested.value_or(Git)`), and so are `addPath`'s for `builtins.path` and `filterSource` (`primops.cc`; `NixArchive` when the source has references, since the path form with references exists only for that method), `copyPathToStore`'s (`eval.cc`), the `path` fetcher's copy (`path.cc`, `addToStoreFromDump` under `Git`) and the Mercurial fetcher's dirty-checkout copy (`mercurial.cc`); `mountInput` names by `fetchToStore2` in dry run alone (`paths.cc`). ### 1.7 The store's object store (libstore, libfetchers)

**Meaning.** `01-specification.md` section 9.10: the local store keeps its objects' trees as git objects under SHA-256 — blobs, trees, the executable bit on the edge — and a store path is a view of its tree whose regular files are hard links into the object store, one file per (blob, mode). The roots are the column: which root a path has is the object hash in `ValidPaths.hash` (1.9). Unconditional: there is no setting (the `auto-optimise-store` of master is removed, `01` section 10), and the object store is what a local store is.

**Representation.** `GitObjectStore` (`git-object-store.cc`, `.hh`), over `<realStoreDir>/.objects/`: `blobs/<id>` (0444), `blobs-x/<id>` (0555, the twin made only on demand and never by a link across the bit), `trees/<id>` (raw body), `tmp/`. No `roots/`. The directories are made when a writable store is opened (`createDirectories` in `LocalStore`'s constructor) and again at the start of the sweep and of the inode table (`08` K12); the other readers treat their absence as emptiness. Identifiers are SHA-256 in git's object format, computed by libutil's `merkle::blobId`/`merkle::treeId` over the framing, ungated, equal to libgit2's for the same bytes (checked). Two operations put a regular file under the store's care, and they are the whole of optimisation: `link(id, mode, dirFd, name, where, size, repair)` *before* a file is written, when the store holds a sound file for the blob (of the given size, and under repair of the identifier's bytes) — one `linkat`, false when the store lacks it, at the link limit, or when it was swept meanwhile; and `place`, *after* a file is written and canonicalised — replaced by the store's sound file through a temporary link and a rename, entered as the store's file when there is none, left as written at the link or directory limit; it returns the file's inode afterwards, nullopt when left as written (no link-limit out-parameter). Around them: `putBlob` (a symlink's target, from bytes), `putTree`, `putRootTree` (the synthetic tree of an executable or symlink root, through which its blob is reachable), `readTree`, `parseTreeBody`, `blobInodes()` and `sweep`.

**One hasher, one traversal, the visitors.** The hasher is libutil's `HashingVisitor` (`object-hash-sink.hh`), a `NodeVisitor<HashedNode>` over the one traversal `traverse` (`tree-traversal.hh`): a node's result is its entry, its NAR size and, for a directory, the tree body an object store writes; the algorithm is `merkle::hashAlgo` (SHA-256) and nothing else — the hasher has no algorithm parameter, and `checkIngestionAlgorithm` refuses any other algorithm at every creation entry. Two drivers deliver nodes to a visitor: `traverse` over an accessor — the depth bound first, `known` consulted before any read, the names unhacked as `dumpPath` unhacks them, the descent by the on-disk name — and `ObjectHashSink`, the push adapter from the sink protocol (`parseDump`) to the same visitor, on which `known` is never consulted; `objectHashOf(accessor, path, filter, visitor)` runs the first, `objectHashOfNar` the second. Consumers derive from `HashingVisitor` and call its action first: `MemoVisitor` (`fetch-to-store.cc`; 1.6) and the store's five in `optimise-store.cc` — `ObjectStoreVisitor`, which writes each symlink's target as a blob (`putBlob`) and each directory's body as a tree (`putTree`) once the hasher has returned them, regular files being the drivers' business; `LinkingVisitor`, the restore route; `MaterialisingVisitor` over it, the copy from the store's own objects (below); `EnterVisitor`, the on-disk route; `VerifyVisitor`, the verifier's. *A stream being restored:* `LocalStore::restoreThroughObjects` runs `parseDump` → `ObjectHashSink` → `LinkingVisitor`, whose `open` stack holds the `RestoreSink` each directory's callback handed back, seeded with the caller's, so a node is created on the innermost sink under `/name`; `directory` opens `createSubdirectory`'s scope and visits the children inside it, so `directoryDone` (canonicalisation) runs when the scope closes, before the tree is written; `symlink` creates the link, then hashes. A regular file goes to the hasher as its bytes arrive and is held in memory up to `restoreBufferLimit` (one mebibyte; `BufferThenStreamFile`); with the entry in hand the visitor decides: a blob the store holds is linked under the name (`GitObjectStore::link`, one `linkat` of the store's sound file) and never written — the restore sink's `regularFileCreated` does not fire for it; a blob the store lacks is written from memory through the sink's `createRegularFile` and placed (`placeRegularFile` → `GitObjectStore::place`: entered as the store's file, or replaced by the winner's when another writer entered the identifier meanwhile, `08` K3). A file the NAR announces above the limit (`preallocateContents` precedes the bytes), or that overflows without an announcement, is opened at once (`RestoreSink::beginRegularFile`, the two-phase regular file), streamed, finished and placed: the write-then-link cost, paid on large files alone, where the write dominates it. *Why the decision is made before the write.* The question "does the store hold this blob?" needs the blob's identifier, a function of every byte, so it is answerable only when the last byte has been seen; a sink that writes bytes as they arrive has already written the file when the answer comes, and on a hit must undo the write — link the store's file to a temporary name and rename it over the file just written. Measured on APFS, that link and rename cost three and a half times the write they undo, and made a second fetch of a 4000-file tree differing in one file two and a half times slower than a sink that decides first [unverified: measured during the work; the run is not in the tree]; a composition of the two sinks through the generic tee, which writes every file first, was built and measured slower, and this is why. The root's synthetic tree is written after the walk (`putRootTree`). The three ingestions call it — `addToStore(info, source)` from a NAR, and both restores of `addToStoreFromDump`, which every `Store::addToStore` from an accessor reaches by serialising the accessor (`store-api.cc`) — each after its `autoGC()`, so the collection an add triggers cannot sweep the add's own objects (`LocalStoreAutoGCTest`), and register the root as the object hash and the size as `narSize`. *The copy from the store's own objects* (`01` §9.10, *One route*, the second route; `LocalStore::materialise`, `materialiseThroughObjects`, `MaterialisingVisitor`): `fetchToStore2`'s copy, under the git method into a local store for which `materialisesFromObjects()` holds — the one predicate, asked in one place — runs the pull driver over the source accessor with a `LinkingVisitor` beneath and a `known` that answers the root and each directory from the store: the naming's memo (`MemoVisitor::lookup`, passed as the `TreeNamer`) gives the node's entry, and when the store holds the tree body — read and verified against its identifier by `GitObjectStore::readVerifiedTree`, refused with a warning when it does not hash to its name — the subtree is made from the objects alone, `mkdirat` per directory, `GitObjectStore::link` per regular file (one `fstatat` of the blob's file, one `linkat`; the file trusted as K8 trusts a blob's inode, its bytes re-hashed under repair alone since the route has no measure of the file but the store's own), the target read from its blob and checked for a symlink, the canonicalising hooks run on each directory and symlink as `RestoreSink` runs them, and the NAR size summed from the blob files' sizes and the names; a node the memo does not name, or a directory whose objects the store lacks or holds corrupt, is left to the driver, which lists it and hands its files to the `LinkingVisitor` as the one route would — linked when held, written when not — after whatever the failed materialisation made is removed. `known` is asked for the root and for directories and never for a file inside a directory the store lacks, so that a fresh tree costs one memo lookup (a SQLite point query under the cache's encoded key, `encodeAttrs`) per directory and not per file. The on-disk names follow the NAR restorer's case hack on both paths (`CaseHackNames`, one rule shared with `parseDump`: from a tree body the entries are visited in the NAR's order, so a colliding name is numbered as the restorer numbers it). The registration is `addToStoreFromDump`'s spilled route step for step — `autoGC()` before the restore, a locked temporary directory in the store, the path locked, checked valid again, moved into place (`EXDEV` copied and entered by the one walk), fsynced under `fsync-store-paths`, registered with the root's object hash and the walk's NAR size — and the deferred version-1 signature check of `addToStore(info, source)` has no analogue, as it has none in `addToStoreFromDump`. The memo is consulted and never written by this route, so that a first entry pays no upsert per file; the rows are the naming walk's (1.6). *A path already on disk:* `enterIntoObjects` — the walk `nix-store --optimise` (`optimiseStore`), the after-build `enterPath` and the flat-add and `EXDEV`-copy routes of `addToStoreFromDump` make, one walk per built output and per flat add, which hashes and enters in the same pass, under `--repair` entering with `Repair` so that a blob the store holds is re-hashed before a repaired output's file is linked to it — is `objectHashOf` over the written path with `EnterVisitor`: `known` answers a regular file whose inode is a blob's (`blobInodes()`) and which has two links, so it is not read; `regular` asks `placementOf(where)`, the one place the exceptions of `01` §9.10 law 3 are decided (a writable file is left as suspicious; a file this system does not link — `.app/Contents` on macOS, every file on Windows — is left as written), and otherwise makes the parent writable around `placeRegularFile`. `optimiseStore` migrates an older row before entering its path, by the walk `nix store migrate` makes (`walkOldRow`: the object hash and, on a tee of the same bytes, the NAR hash the row asserts, checked before `recordObjectHash` writes), skips a path found modified or missing with the verifier's message, and reports files entered, files linked and rows migrated. *The verifier:* `verifyObjects` is the same on-disk walk with `VerifyVisitor`, expecting every tree, the synthetic root tree, every symlink's blob and the blob of every regular file `placementOf` says the store places. There is no hint route from a named accessor; the git accessor is not consulted for blob identifiers — the copy from the store's objects consults the naming's memo, whose rows a hashing walk wrote. There are no `git::` forwarders over the core; the fetchers call `merkle::` directly. The object store's files are fsynced under `fsync-store-paths`, as the paths' files are. On Windows the object store shares nothing: the `*at` calls the two operations rest on have no counterpart there, so every file is left as written and the verifier expects no blob (by inspection only, `01` section 13).

**The tarball cache.** Opened as a SHA-256 repository (`tarball-cache-v3`; `GitRepo::Options::oidType`, `git_repository_init_ext`), so a tarball's tree identifier is the store's name for it and its blobs' identifiers the store's. Its packs' compression is the per-object decision of `01` section 10 (`packaging/patches/0004-pack-compression-heuristic.patch`, on top of the three patches of NixOS/nix PR 16427; `GitUtilsTest.packsStoreWhatWouldNotShrink`).

**Operations, solved.** A directory the naming names and the store holds: made from its tree body and blob files, nothing read from the source (the second route above). Hit under the limit: `link` — one `linkat` of the store's sound file (of the file's size, and under repair of the identifier's bytes; one that is not is removed as corrupt) under the new name; nothing written. Miss under the limit: written from memory, canonicalised by the restore sink's hooks, `place` enters the file as the store's — or, should another writer have entered the blob meanwhile, replaces it by the winner's file. Over the limit: written as received, then `place` as before, hit or miss. Concurrent entry of the same identifier: `place` tries twice, so the loser links to the winner's entry. At the filesystem's link limit or a full directory index (`EMLINK`, `ENOSPC`, the latter as the old pass tolerated) the file is left as it is; on macOS a file under `.app/Contents` is written and not placed. Collection: `GitObjectStore::sweep` in `collectGarbage` where `.links` was swept — the live roots read from the database as the object hashes of the valid paths (`forEachValidObjectHash`, `gc.cc`); trees unreachable from them, blob files with one link that no reachable tree names (every blob a live tree names is kept, a file's bytes and a symlink's target alike), temporary files older than an hour; each tree body's identifier is verified as the sweep reads it, and a corrupt tree aborts the removal rather than let a wrong body decide what is reachable; no grace (`01` section 9.10); while any row is unmigrated no tree and no blob is removed and the collector says so — and the collector's walk of the store directory skips `.objects` and `.links`. `nix-store --optimise` walks every valid path, enters what an older Nix wrote plainly, links nothing on a store this Nix wrote and says so, and removes the legacy `.links` directory — as every whole-store collection does (`removeLegacyLinks`); neither is done on the local overlay store, whose merged store directory shows the lower store's (`08` K13). Daemon: unchanged, the NAR sink on receipt. `verifyStore --check-contents` hashes every blob file and every tree body against its identifier. The GitHub fetcher parses the tarball cache's tree hash as SHA-256 and treats a row of the SHA-1 cache as absent, as the tarball fetcher does.

**The check order.** `LocalStore::addToStore(info, source)` verifies a received path's content address before its object hash, its asserted NAR hash and its size; the address is what the name asserts, and for a git-addressed path it is the sink's root, so the check reads nothing. All checks remain; the order decides which mismatch is reported when several fail.

**Checks.** `LocalStoreObjectsTest` (libstore-tests), each restore through counting hooks that say how many regular files the restore sink created — the discriminator for the hit path, since inode sharing alone cannot tell a link-before-write from a write-then-link: `restoreThroughObjects` (the composite alone, no pass after it, on a tree two directories deep with the same bytes under both modes, an empty file and a symlink; the same NAR again creating no file; a one-file NAR at the destination itself), `oneChangedFileWritesOneFile`, `restoreThroughObjectsStreamsLargeFiles` (the buffer limit's boundary), `executableFirst`, `repairDoesNotLinkACorruptBlob`, `enterIntoObjectsAndMigrate`, `addToStoreFromDumpUnderTheGitMethod` (the content address is the sink's root and the on-disk walk's), `caseHackSuffixIsNotHashed`, `syntheticRootTreeIsWrittenAndKeepsItsBlob`, the sweep tests, `sweepAndVerifyOnALiveRootWhoseTreeIsMissing`, `sweepTolerantOfAnUnenteredRoot`, `sweepMakesAMissingObjectDirectory`, `verifyExpectsNoBlobForAFileTheStoreDoesNotPlace`, and `LocalStoreAutoGCTest`'s two tests. ### 1.8 Garbage collection

Pre-existing references of a pending object are temp-rooted at enqueue against `EvalState::store` (`addTempRoot`; the daemon deduplicates per connection, `remote-store.cc:751-758`). The pending object itself has nothing on disk. At flush, `LocalStore::addToStore` roots each written path (`local-store.cc:1080`), as eager writes do. ### 1.9 One address (libstore, libfetchers, libexpr, libflake, nix)

**Meaning.** `01-specification.md` section 9.11: a store object's content hash is the git entry of its root under SHA-256, total and injective over store objects; the NAR is a serialisation; the flat hash is read through a shim and never written as a name.

**Representation.** The object hash is a `Hash`: `merkle::objectHash(TreeEntry root)` — the tree id of a directory, the blob id of a plain file, the tree id of `{"." ↦ entry}` for an executable or a symlink — replacing `rootHash`; `UnkeyedValidPathInfo::objectHash` where `narHash` is, `narSize` kept and computed by the same walk (`merkle::nar::{regular,symlink,root}`, from names and sizes; the property `MerkleHash.narSizeEqualsDumpPathLength`). A hasher core in libutil (`merkle-hash.hh`: blob id from size and chunks, tree id from entries, the `name + "/"` key; `merkle::insertEntry` refuses `.` and `..`, so the synthetic root tree is the only tree with a `.` entry and only `syntheticRootTree` makes it), ungated; over it `HashingVisitor` and its two drivers, `traverse` and the push adapter `ObjectHashSink` (a NAR stream or an accessor walk to a root entry and a NAR size, no disk), the store's `LinkingVisitor` (the restore route, deciding before the write; 1.7) and `EnterVisitor` (the on-disk walk, `enterIntoObjects`). `ValidPaths.hash` holds `git:sha256:<hex>` for an object hash and the old `sha256:<hex>` for an unmigrated NAR hash, told apart by prefix before parsing — the prefix test comes first because the old parser raises `UsageError` on an unknown algorithm, not the `BadHash` the read site catches; `nixSchemaVersion` 11. The object store's root record is the column: the sweep reads the object hashes of valid paths (`forEachValidObjectHash`) and treats each as a possible tree; there is no `roots/` directory, and no symlink-root special case. Fingerprint `"2;" + path + ";" + objectHash + ";" + refs`; `WorkerProto::featureObjectHash` (the same string slot on the wire, its meaning negotiated); a serve version; `NarInfo::objectHash` beside `narHash`; JSON version 4. Lock version 8 with `treeHash`; `Input::getTreeHash`; the GitHub fetcher's dormant `treeHash` made the SHA-256 SRI value; no `narHash` attribute on any input. The shim as one function in libfetchers, `narHashOf(settings, Store &, SourcePath tree, Hash treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the existing memoised NAR walk (`fetchToStore2` under `NixArchive`, dry run) with the `treeAddress` pair recorded — called through `assertNarHash` from `Input::getAccessor` (every fetch route, `mountInput`'s included), from `addPath` for a `sha256`, on `fetchTarball`'s route, and directly by `fetchTree` to build the language's lazy `narHash`; in libstore, `narHashOf(Store &, StorePath)` — a walk, `narFromPath` into a `HashSink`, no cache — for an old client on the wire (once per query) and for the path-info JSON formats 1 to 3. A version-1 signature is checked against an `assertedNarHash` when the description carries one, and otherwise through this walk when a caller binds it (`NarHashThunk`: `nix store verify`, `copy-sigs`, and `addToStore`'s tee for a description that asserts none).

**Operations, solved.** Registration computes the object hash where the NAR hash is computed today: the sink's root at the three ingestions, `enterIntoObjects` after a build (so every output has one, input-addressed or not), `objectHashOf` for `computeStorePath` (the one tree walker; the fetchers' memoised naming is `objectHashOf` with `MemoVisitor`, `known` answering from the memo and the actions recording); the NAR hash is computed at registration only where an old sender asserted one — the receiving tee of a copy from an old peer or an old cache, at no cost — and is verified there and never stored. `mountInput` names by `fetchToStore2` alone; the second walk and the lazy attribute's pairing rule go; `narHash` on an input is the shim's lazy attribute. `addPath` and `fetchTarball` with a `sha256`: fetch, then verify by the shim, then record; with a `treeHash`: the fast path is `isValidPath` of the name it determines. Copy: the receiver verifies the object hash from its sink's root and, when the sender is old, the NAR hash from the tee. `verifyStore --check-contents`: the object hash against the root recomputed from the files, by way of the blob identifiers the object store checks already. `nix store migrate`: every unmigrated row filled by the verified walk (`walkOldRow`, `01` section 9.11 *The database*), then re-rendered.

**The column and the type.** Two facts fix the type. First, a path info describes a path in *some* store: for a path the local store holds the object hash is always known, but a substituter's description of a path (a `.narinfo` from an old cache, an old peer's reply) may carry only a NAR hash until the NAR itself arrives. Second, if the daemon kept speaking the old protocol while the column changed, every `QueryPathInfo` from a client would cost a walk to produce the NAR hash it must send; so the worker feature under which the object hash travels is part of the same change. Hence:

- `ObjectHash` (libutil, `object-hash.hh`): a strong type over `Hash` — `static ObjectHash of(const merkle::TreeEntry & root)`, `std::string render() const` giving `git:sha256:<base16>`, `static std::optional<ObjectHash> parse(std::string_view)` (nullopt for anything else, in particular an old `sha256:` row), `==`/`<=>`. A NAR `Hash` cannot be assigned to it by accident; the compiler enumerates the sites.
- `UnkeyedValidPathInfo`: `std::optional<ObjectHash> objectHash` — present for every info the local store returns or accepts for registration (`addValidPath` refuses one without), possibly absent for an info from a substituter or an old peer; `std::optional<Hash> assertedNarHash` — the NAR hash a sender asserted (an old peer on the wire, a `.narinfo`, `--load-db`, JSON before version 4), verified on the receiving tee and never stored; `narSize` as before. The field `narHash` is gone; every former reader is either an `objectHash` reader (content identity), an `assertedNarHash` verifier (receipt), or a call of the shim `narHashOf(store, path)` (a walk producing the NAR hash for an old form).
- The local database: `hash` column holds `objectHash.render()`; an old row's `sha256:` value is recognised at the one read site by `ObjectHash::parse` returning nullopt, and migrated in `queryPathInfoUncached` between two lock scopes, as `verifyStore` does its walk, and never in `queryPathInfoInternal`, which `addSignatures` calls inside a transaction — by `objectHashOf` over the path (`migratePathInfo`) — then written back unless the store is read-only; the migration takes no temp root: a path deleted mid-walk reads as invalid, and the row is left for the next query; `nixSchemaVersion` 11, stated as the deliberate exception to the additive-migration convention.
- Where the object hash is set: the three ingestions from the sink's root; `LocalStore::materialise` from the root the materialising walk computed (1.7, the second route), which is the memo's entry where the store held the tree and the hasher's where it was read; `addToStoreFromDump`'s flat and copy routes by `objectHashOf` over the written path; the builder's outputs by one walk, `enterPath`, where `hashPath(NixArchive)` ran on master, before the `--check` branch: it hashes and enters the object store in the same pass, so a built output and a flat add cost one walk where master's NAR hash and optimise pass cost two, under `--repair` entering with `Repair`; `--load-db`/`--register-validity` by a walk. Verification by recomputation: `verifyStore --check-contents`, `pathContentsGood`, `nix store verify`, `nix-store --verify-path` compare `objectHashOf` with the row; `nix-store --export` and `--import` compute the object hash of the stream with `ObjectHashSink` on the tee and compare or register.
- The forms in this step: fingerprint 2 (`2;<path>;<objectHash.render()>;<refs>`; a version-1 signature verified against `assertedNarHash` when present and otherwise against the NAR hash the caller's `NarHashThunk` supplies by one walk — `ValidPathInfo::checkSignature`, bound by `nix store verify`, `copy-sigs` and `addToStore`'s tee, so a version-1 signature on a locally held path keeps verifying once its row is migrated; `narSize` must be known). Signing produces both where both hashes are known — `ValidPathInfo::sign` signs the version-2 fingerprint and `signV1` the version-1 one (`1;<path>;<NAR hash>;<NAR size>;<refs>`); `nix store sign` calls `sign` only when the info carries an object hash and `signV1` whenever the NAR size is known, the NAR hash asserted by the info (a narinfo's `NarHash:`) or else computed by one walk (`narHashOf(store, path)`), so it works on a cache an older Nix wrote, whose infos have no object hash and get version 1 alone; the binary cache's upload signs both with the cache's keys, its NAR hash from the tee; `Store::signPathInfo`, signing at build under `secret-key-files`, signs version 2 only, no NAR hash existing there — because an old client verifies version 1 alone and counts only the signatures it can verify (master's `checkSignatures`), so a cache carrying version 2 alone was refused under `require-sigs`, and a build-signed path copied into a keyless cache still is until `nix store sign` runs on the cache (`01` section 9.11, *Signatures*). Since one key then has two signatures, `checkSignatures` counts distinct keys. A path an old client verifies is one the daemon can describe to it; a path info that arrives at `LocalStore::addToStore` with neither hash and no content address is refused (the daemon reaches it through the store), since nothing about it can be checked; `WorkerProto::featureObjectHash`, under which the path-info slot carries `objectHash.render()` and without which the daemon sends `narHashOf` and reads the client's string as `assertedNarHash`; a serve-protocol version likewise; `.narinfo` reads `ObjectHash:` into `objectHash` and `NarHash:` into `assertedNarHash`, and the upload writes both, its NAR hash from the tee it already has; path-info JSON version 4 with `objectHash` required and `narHash` optional, versions 1 to 3 written through the shim; `nix hash path --mode git` prints the object hash: for a bare executable or symlink the synthetic tree's id, where master printed the blob's (`01` section 9.11); `nix-store --dump-db` writes the rendering.
- The object store: the synthetic root tree written when entering; the sweep reads the live roots from the column (`forEachValidObjectHash`); there is no `roots/` directory and no root record beside the column: the migration walks the path.

**The fetchers' and the language's representation.** The fetchers and the language stop naming anything by the flat hash; every source is named by its tree hash; old assertions are verified by the shim.

- *No setting.* Every site names by the git method (`fetchToStore`'s default, `addPath`, `copyPathToStore`, `mountInput`, the `path` fetcher's copy and the Mercurial fetcher's dirty-checkout copy); the exceptions and the explicit methods are `01` section 9.9's.
- *`treeHash` on inputs.* `Input::getTreeHash()` reads the attribute `treeHash`, an SRI SHA-256 string, the git tree (object) hash of the input's root — the same value the store's `objectHash` renders, so `Input::computeStorePath` is `makeFixedOutputPathFromCA(name, {Git, SHA256, treeHash})`. Every scheme that allowed `narHash` allows `treeHash` (put it beside `narHash` in each `allowedAttrs`); `isLocked` accepts either; the URL query `treeHash=` is parsed and emitted where `narHash=` is. The GitHub fetcher's dormant `treeHash` (SHA-1 hex behind `#if 0`) becomes this value: the tarball cache is SHA-256, so `TarballInfo::treeHash` is it; a 40-hex value is refused. A fetch's result carries `treeHash` and never `narHash`: `Input::fetchToStore` sets it from the path info's `objectHash`; `mountInput` sets it from the dry-run tree hash; the tarball and file fetchers set it from the cache's tree hash and from the object hash of the flat file.
- *The lock file, version 8.* A locked input's `locked` attributes carry `treeHash`; `narHash` is not written. Reading a version-7 lock: the node's `narHash` is an assertion; `mountInput`, after naming the tree, verifies it through the shim and then replaces it in the input's attributes by the `treeHash` it computed — the one mutation the copy in `checkLocks`'s final branch admits. But `nix flake lock` keeps an unchanged node without fetching it, so a version-7 lock whose inputs are all unchanged is not rewritten, and forcing a rewrite would fetch every input only to name it; the rule is therefore that a node gains `treeHash` when it is next fetched, that a lock is written as version 8 whenever it is written at all, and that a version-8 lock may still carry a node's `narHash` alone — every reader accepts either, and the old-lockfiles test keeps its comparison. `lockfile.cc` reads 5 to 8 and writes 8; `flake.cc` erases `treeHash` where it erased `narHash` after `applySelfAttrs`.
- *The shim, one function in libfetchers:* `Hash narHashOf(const fetchers::Settings &, Store &, const SourcePath & tree, const Hash & treeHash)` — `fetchToStore2`'s dry run under `NixArchive`, the memoised NAR walk, recording the `treeAddress` pair (it keeps no memo of its own); and `void assertNarHash(settings, store, tree, treeHash, asserted, description)` throwing the existing `Error(102, "NAR hash mismatch in input '%s' ...")`. Called from `Input::getAccessor` (`fetchers.cc`, every fetch route — a version-7 lock, `fetchGit { narHash }`, `?narHash=` and `mountInput`'s inputs among them), from `addPath` (a `sha256` on `builtins.path`/`filterSource`), on `fetchTarball`'s route (`fetchTree.cc`), and by `fetchTree`'s `emitTreeAttrs` to build the language's lazy `narHash` thunk from the tree hash. The `treeAddress` memo is read only by the shim's fast paths: a `sha256`/`narHash` assertion that names a tree already present finds it through the memo, else fetches and verifies. No input ever carries a `narHash` attribute again, lazy or not (`attrsToJSON`/`attrsToQuery` force lazy attributes, so one on the input would be walked and written by every lock and URL).
- *The language.* `fetchTree` and `fetchGit` results carry `treeHash`; `narHash` is a lazy attribute `emitTreeAttrs` builds through the shim; `builtins.path { sha256 }`, `fetchTarball { sha256 }`, `fetchTree { narHash }` and `?narHash=` accept the NAR hash (shim) and `treeHash` (the cheap assertion); `nix flake prefetch` prints `treeHash` as `hash` (`01` section 9.9, *The language*).

**Checks.** Totality and injectivity of the object hash as a property over generated trees (`libutil-tests/merkle-hash.cc`, `object-hash.cc`); the case-hack discriminator (`01` section 9.11: a NAR with `Foo` and `foo` through the sink and re-hashed from disk, equal, on macOS; `libutil-tests/object-hash-sink.cc`, `LocalStoreObjectsTest.caseHackSuffixIsNotHashed`); every form's round trip (`libstore-tests/object-hash-*.cc`); the shim's entry points each with a negative control (a wrong old assertion refused: `source-addressing.sh` for `builtins.path { sha256 }`, `filterSource`, `treeHash`, `fetchTarball { sha256 }` and a planted wrong hash in a version-7 lock; `fetchGit.sh` for `fetchGit { narHash }`); the old-peer interop through the reference binary, gated on `NIX_REFERENCE_BIN` (`tests/functional/object-hash.sh`, both directions and both feature states); the cost law measured on Linux (`05-validation.md` section 6: a tarball fetched twice, the second differing in one file; the copy of an edited tree) — no read-counting discriminator exists.

## 2. Risks and open items

- **Destructor flush.** A flush can fail; a destructor cannot throw. Every command flushes explicitly and fails loudly (see the teardown row of 1.2); the destructor's flush is a fallback that logs. A library consumer that neither flushes nor lets the command end normally is the one case where an error could be swallowed; the explicit entry point is the remedy, and its absence is a documented limit, not a silent loss of data.
- **Least sure step.** Inside the kernel: the dereferences that parse a store path from accessor bytes, and the sinks a primop may write to, are held by review and the builtin sweep (every builtin against eager evaluation on pending inputs), not by the type (0.2). Outside it the door is the type and the check.
- **Round trips through a daemon.** The temp root taken at enqueue for each pre-existing reference is one round trip per reference (`RemoteStore::addTempRoot` deduplicates per connection but asks once per new path), and the protocol has no bulk temp-root operation. So a flush is one bulk add plus those roots, not one message; the floor is set by the frozen protocol.
- **Client cache.** `RemoteStore::addToStore` from a stream and `RemoteStore::addMultipleToStore` did not invalidate the client's path-info cache while `addToStoreFromDump` did, so a cached negative answer survived a copy; a defect of master's remote store that any `copyPaths` caller could hit. Fixed in `RemoteStore`; the buffer relies on the store's own invalidation.
- **Repair through the batch add.** `Store::addMultipleToStore(PathsSource&&)` calls `addToStore` only for paths not already valid, so it ignores the repair flag for a valid-but-corrupt object (`src/libstore/store-api.cc`). The buffer cannot repair through its one batch; its flush falls back to a per-object `addToStore` whenever repair is asked, which honours it, exactly as an eager `writeDerivation(_, Repair)` would. Latent from the CLI, since no command sets `EvalState::repair` to `Repair`; `WriteBufferLocalStoreTest.repairRewritesAnObjectTheDatabaseStillCallsValid` pins it.
- **Reuse considered and not taken.** The pending set is a store in the specification's own sense, and the flush is `copyPaths` from it. `DummyStore` cannot yet hold a derivation (it refuses `.drv` names in `addToStoreFromDump` and synthesises reference-free info for them), so making the buffer a `DummyStore` and the flush a `copyPaths` needs a libstore change with its own tests first; the buffer stays a bespoke type until then; recorded as a decision.
- **Two deferred writes, one flush.** Mounted inputs are deferred by master's own mechanism (`mountInput` hashes and mounts, `ensureLazyPathCopied` copies) and the buffer defers the texts; they differ in meaning — a pending text is in Δ unconditionally, a mounted input only once dereferenced, emitted, or named by an object that is written — so a total copy of mounted inputs would write what the reference never writes. The two meet in one place: `flushPendingWrites` copies the mounted inputs the pending objects reference before it writes them (a reference must be valid when its referrer is registered), so `derivationStrict` and `toFile` copy nothing themselves and a pending object's inputs enter the store with it; at the commands' outputs `emit` writes the texts and copies the inputs the provenance names; the dereferences copy what they read (`realisePath`), and the hand-offs to a program or a builder copy what they hand off (`exec`, `realiseString`, the installables, `nix run`'s app), as master does at those points.
- **Memory.** Pending text accumulates between flushes: one top-level closure for the plain printer and `nix-instantiate`, which realise each string as they emit it; the whole serialised value for `nix eval --json` and `--raw`, whose serialisers are pure (about 82 MB against 52 MB eager for 4000 derivations on Linux, about 7 KB per pending object; `05-validation.md` section 6). The buffer bounds this by flushing itself at `deferred-store-writes-max-pending` objects (default 4096; the deferred-minus-eager gap then flat at 30-77 MB out to 64000 derivations on Linux [derived from the tables of `05-validation.md` section 6]), and (C2) holds because those sinks emit nothing until after the final flush. A drain thread would overlap writes with evaluation and is deferred for simplicity.
- **Trust bit.** Equal for everything the buffer holds: derivations and texts carry `ultimate = false` when written eagerly and through the bulk add alike. If the buffer ever holds a built output, which it must not, the bit would differ.
- **Out-of-tree consumers.** `Value::string_view()` is private: an out-of-tree consumer that read `Value` strings directly now goes through `realise`/`emit`, which write first, or through the accessors; a libexpr API change, which the specification does not freeze (`01` section 6).
- **`--eval-store`.** Unchanged: the buffer drains into `EvalState::store`, where master writes.

## 4. Defects of master found by this work

Fixed on the branch and pinned: the ATerm reader promoted `char` to `int`, so a byte 0xFF in a derivation read as `EOF` (`DerivationAtermTest.aByteEqualToEofRoundTrips`); a platform string containing `"` or `\\` was written verbatim and could not be read back (`DerivationAtermTest.platformOutsideTheFormatIsRefused`); the store-directory field of a `.drv` was written verbatim off Windows and unreadable when the directory holds `"` or `\\` — the escape flag's default is the platform, not the directory's characters — and the writer now refuses such a directory under the verbatim mode (`DerivationAtermTest.storeDirOutsideTheVerbatimFormIsRefused`, `WindowsStoreDirTest.unsupportedIsRefusedAtTheWriter`); `nix-prefetch-url --attr` had an inverted condition (`tests/functional/prefetch-url-attr.sh`); `RemoteStore::addToStore` from a stream and `addMultipleToStore` did not invalidate the client's path-info cache while `addToStoreFromDump` did (fixed in `src/libstore/remote-store.cc`; the buffer relies on it and patches nothing). Found and not fixed, master's: `builtins.fetchGit`'s default `exportIgnore = true` makes libgit2 look the attribute up for every file on every copy whether or not the repository declares it.
