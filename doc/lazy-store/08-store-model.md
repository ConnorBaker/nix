# The local store's concurrency and durability model, and the API semantics it rests on

A reference for a maintainer about to touch `src/libstore`. Section 1 states the facts the local store's code keeps, one per sentence, each with its `file:line`; line numbers were taken when the fact was written and drift, so a locator names the function beside it where the line may have moved; where the lazy-store branch's code depends on a fact, the dependency is named beside it. Section 2 is the checklist of API semantics to answer at every call site of the kinds the branch uses. Neither section argues; the arguments are in `01-specification.md` and `04-derivation.md`, and the tests that pin the defects behind these facts are the table of `07-defect-ledger.md`.

## 1. The model

### 1.1 Locks

**The big lock** (`<state>/db/big-lock`).
- A writable store opens it and holds it shared for its life (`local-store.cc:243-261`).
- The lock is taken exclusive only for a schema upgrade, releasing the shared lock first to avoid a promotion deadlock (`local-store.cc:277-283`, `345`, `356`).
- A read-only store takes no lock at all (`local-store.cc:243`, `258`).
- Branch: the schema is 11; a schema-10 store is bumped on first writable open; that version-number bump runs no statement, while `upgradeDBSchema` separately installs the current ingestion-owned layout (`local-store.cc:266-273`, `287-341`, `local-store.hh:29-33`); an older Nix then refuses the store. A read-only open of a schema-10 store is allowed (`local-store.cc:267-273`).

**The database lock** (`_state`, a `Sync<State>`).
- Every SQLite statement runs with `_state` locked; `retrySQLite` retries `SQLITE_BUSY` (`local-store.cc:797-798`, `1041`, `1053-1056`).
- A transaction (`SQLiteTxn`) is opened and committed under one lock scope (`local-store.cc:1187-1190`, `1727-1730`).
- Ordinary hashing, migration and ingestion walks run outside the database lock. The narrow exception is publication-time inode reconciliation: after a write reserves SQLite’s writer, a bulk query finds actual overlapping blob candidates; only a collision walks the completed target’s physical aliases. This helper only uses filesystem operations, never database/index callbacks, provider callbacks or temporary-root registration. It pins and validates donors before replacing aliases, so the reservation excludes GC invalidation and the pin survives concurrent donor replacement. With no collision there is no filesystem pass.
- Branch: `migratedPathInfo` walks the path outside the lock and re-reads the row under the lock before writing, so a row migrated or deleted meanwhile is respected (`walkOldRow`, `migratedPathInfo` and the re-read in `recordObjectHash`, in `local-store.cc`). `addSignatures` migrates first, outside its transaction (`local-store.cc`). `queryPathInfoInternal` never migrates (`local-store.hh`), nor does `queryPathInfoUnmigrated`, the same read under the lock it takes, which the collector uses for its dead set.

**The GC lock** (`<state>/gc.lock`).
- `collectGarbage` holds it exclusive for its whole run (`gc.cc:394-395`).
- `addTempRoot` tries it shared and non-blocking (`gc.cc:105`); when that fails the collector is running and the root is sent over the collector's socket, and the sender waits for the acknowledgement (`gc.cc:107-153`).
- The collector's server thread records each socket root in `tempRoots` and, while the path is being deleted (`pending`), makes the sender wait until the deletion is done (`gc.cc:470-500`, `481-492`; `pending` set at `675` and `738`, reset at `589` and `742`).
- The collector re-checks `tempRoots` immediately before each deletion (`gc.cc:719-744`).
- `verifyStore` takes the GC lock shared and blocking, so it never runs beside a collection (`local-store.cc:1755`).
- Branch: the object-store sweep runs inside the exclusive lock, after the deletions (`gc.cc:864-874`). No branch code takes a temp root on behalf of a query the collector itself makes — the migration takes none (`local-store.cc:895-901`), because the collector reads visited paths' rows — unmigrated, as the database has them (`queryPathInfoUnmigrated`; `topoSortPathsBy`, `gc.cc`), so a dead schema-10 row is deleted without the walk — and the live closure's infos through `computeFSClosure`, and a root registered then would keep a dead path.

**Auxiliary value acquisition and repair** (`LocalStore::readAuxiliary`, `verifyAuxiliary`).
- On success, a single SQLite statement copies all chunks of one ingestion's body under `_state`; ordinary framed hashing and canonical tree parsing follow outside that scope. Returned strings own their bytes. No source, destination or provider callback runs under the database lock.
- Verification enumerates typed-key/ingestion identities, including unreachable cache copies. Repair re-reads and hashes the exact bad incarnation inside a transaction before deleting it. SQLite's deferred read-to-write upgrade either preserves that observation or returns busy; `retrySQLite` rolls back and repeats the whole recheck. A disappeared or now-sound incarnation is not deleted, and diagnostics run after lock release.
- There is no auxiliary namespace lock, valid-root snapshot or per-address link claim. A live ingestion lease protects completed SQL projections through the existing stale rule; a private projection is owned memory, not a globally published object.

**Path locks** (`<realPath>.lock`).
- One path's write is guarded by `PathLocks` on its real path, except from a build hook whose parent holds the lock (`local-store.cc:1292-1304`, `1627`).
- The validity check is repeated under the path lock, because another process may have registered the path meanwhile (`local-store.cc:1305`, `1630`).

**Temporary directories in the store** (`tmp-*`).
- `createTempDirInStore` makes the directory, opens it, and takes an exclusive lock on the descriptor, retrying until the directory both exists and is locked (`createTempDirInStore`, `local-store.cc:1703`).
- The collector deletes a `tmp-*` entry only when it can take that lock itself (`gc.cc:551-558`).
- Branch: `addToStoreFromDump` restores through the object store inside such a directory and then moves it into place (`local-store.cc`); its regular files retain their inodes across the move on the same filesystem; its pending metadata and completed projections have the separate ownership of K16. `LocalStore::materialise` (`optimise-store.cc`) does the same, step for step.

### 1.2 Temporary roots

- Each `LocalStore` handle's temp roots live in a distinct `<state>/temproots/<pid>.<unique>` file, created exclusively on its first root and held write-locked for that handle's lifetime (`createTempRootsFile`). The numeric prefix remains readable by older collectors. Independent handles in one process never replace or unlink each other's root files.
- A root is a path name appended to that file, or, during a collection, a line sent to the collector's socket (`gc.cc:155-158`, `132-138`).
- The collector reads every temproots file after taking the GC lock; a file whose lock it can acquire has no live owning handle and is removed. A creator accepts its locked descriptor only while it remains linked and empty; if a collector removed it before locking, the creator allocates another name. A collector that finds its already-open descriptor unlinked does not remove anything at that old name.
- The file is unlinked when the store object is destroyed. On POSIX, unlink precedes releasing its lock. Destroying one handle releases only its own roots; a command that has exited roots nothing. `temporaryRootsBelongToEachStoreHandle` covers all six two-handle creation/registration interleavings and both destruction orders with actual collections.
- A read-only store creates no temp roots (`gc.cc:86-90`).
- A temp root protects a store path. An ingestion lease is an on-demand locked directory under `.objects/tmp`; it protects completed SQL projections before validity registration and physical replacement/coalescing links. Private rows and auxiliary bytes need only their in-memory owner. Fresh direct publication commits validity and projection together with a NULL hold marker (1.5, K16).
- Branch: writable Text producers call `Store::addTextToStore`, which roots the computed path before checking validity. A valid non-repair referrer protects its recorded closure; a new or repaired write roots each reference before publication. Producer context roots precede mounted copies and closure walks. `storePath` and `appendContext` root admitted writable paths before validity checks, and `appendContext` before arbitrary flag evaluation, including false/empty flags. Read-only Text producers compute addresses without writes or roots. `fetchToStore2` roots cache-hit destinations before validity checks; optimisation, migration and old-peer hash preparation retain their own rooting boundaries.

### 1.3 Between a write and a registration

- Both `LocalStore::registerValidPaths` and `LocalOverlayStore::registerValidPaths` reject a map key unequal to its description's path before registration effects, including lower-store imports (`validatePathInfoKeys`). The database and the full-path memory cache therefore receive the same identity.
- A path is written into its real path or into a temp directory, verified, optionally synced, and registered in one transaction (`addToStore`, `local-store.cc:1265`; `addToStoreFromDump`, `1483`; `registerValidPaths`, `1176`).
- Until `registerValidPaths` commits, the path is invalid; the collector deletes an invalid entry unless a temp root names it (`gc.cc:678`, `819-822`); both ingestions take the root first (`local-store.cc:1290`, `1618`).
- A verification failure after the restore leaves the written files in place as an invalid path, which a later collection removes (`addToStore`, `local-store.cc:1265`: the checks between the restore and `registerValidPath`); two of the checks remove the files themselves — the refusal of a SHA-1 git address (`1377-1378`) and the deferred signature check (`1436-1441`).
- A crash before publication leaves an invalid physical path and loses private pending values. Completed builder output projections may already be committed before validity registration; their lease protects them. After the lease dies, whole-store cleanup removes stale ingestions and cascades both regular and auxiliary rows. Regular lookup still requires a valid named path. Physical path collection retains its existing temp-root rules.
- The database row is durable by SQLite's `synchronous = normal` under `fsync-metadata` (`local-store.cc:557`); the files are durable only under `fsync-store-paths` (1.4).
- Branch: `restoreThroughObjects` writes regular files and stages owned symlink targets/directory bodies while restoring (`ObjectStoreVisitor`, `LinkingVisitor`). Both cases are published only at the completed ingestion boundary. The ingestion's own `autoGC()` remains before restore; the buffered-root route checks existing validity before starting that work.
- `Store` admits descriptions by hash and name, with `MissingName` as the name wildcard (`goodStorePath`, `store-api.cc`; `01` §2.6). Its memory cache records full-path outcomes; the narinfo disk cache records hash outcomes. A wrong-name result can retain the canonical description in the latter, never a false hash miss. Only a null metadata result from a hash-indexed backend establishes that negative. `LocalStore::isValidPathUncached` caches positive validity under the database lock, preserving a fresh description, but caches no negative result; metadata queries retain their full-path negative caching and existing expiry rules. Validity without metadata cannot answer `queryPathInfo`.
- A build hook publishes through another store handle, so its termination is a cache-refresh boundary. Normal build-hook completion and abnormal hook termination clear the parent’s path-info memory cache before subsequent queries. Binary-cache publication updates the shared hash-indexed disk row first, then under the memory-cache lock removes the `MissingName` alias and seeds the actual full path. Seeding last also handles an actual path named `MissingName`; a cached pre-publication absence cannot hide that publication.

### 1.4 Durability points

- Under `fsync-store-paths`, every file of the path is synced and then its parent directory, before registration (`local-store.cc:1448-1450`, `1683-1685`).
- The restore sink starts an asynchronous write-back per file when `startFsync` is set; it waits for none (`fs-sink.cc:264-269`).
- Under `sync-before-registering`, `sync()` runs before every registration (`local-store.cc:1183-1184`).
- Without either setting, nothing makes the files durable before the row.
- Branch: auxiliary metadata follows the existing SQLite metadata transaction durability policy. It has no separate file chmod/fsync/publication sequence. `fsync-store-paths` still controls physical path durability; regular holders retain mtime 1 and exact 0444/0555 modes. Removing metadata files does not weaken the physical path sync boundary.
- Branch: **the full projection stays private until completion.** Workers retain regular rows and auxiliary bodies in one pending typed relation. After joining, they hand `Projection{regular, auxiliary}` to registration or `endIngestion`, including an empty projection. No incremental flush or separate writer connection is introduced.
- Branch: **publication reconciles regular files before making holders visible.** Registration takes the completed projection before the database lock, reconciles regular collisions under the existing writer reservation, then publishes validity and both projections atomically. Retry owns the complete vectors. `endIngestion` also publishes completed builder outputs before their final validity registration: auxiliary bodies are then reusable, but regular donors remain invisible until valid. A shared hold can start its next output without losing the preceding projection.

### 1.5 The object store's invariants

Regular contents live in physical store paths. `Blobs(id,exec,ino,dev,ingestion,name,size)` records candidate holders; `Ingestions(id,path,hold)` gives every completed projection one lifetime. `AuxValues(kind,id,ingestion,chunk,body)` retains directory bodies and symlink targets. Both `Blobs` and `AuxValues` reference `Ingestions` with deletion cascade. Its typed keys admit only Directory/Symlink and full SHA-256 BLOB identifiers. `GitObjectStore::Index` supplies the existing regular operations and an optional `readAuxiliary`; absence of that provider is an ordinary miss. `.objects/tmp` supplies leases and regular coalescing pins, not a second metadata backend.

A complete projection can precede validity registration. Regular donor lookup joins `ValidPaths`; auxiliary lookup needs a committed ingestion and verifies its independent bytes. Each successful reuse stages its body into the receiving ingestion. Path replacement and stale-ingestion deletion therefore cannot erase another surviving ingestion's witness or metadata. Whole-store collection has two ordered phases: overridable bounded legacy/dead-lease cleanup, followed by nonvirtual `sweepStaleBlobRows` for both SQL projections. A surviving lease retains its rows, including after failed cleanup; no override can omit the SQL phase.

Kept by the code:

- K1. *Values are split by their meaning.* Regular rows name physical files; auxiliary rows own canonical metadata bytes. `Hold::addAuxiliary` accepts only Directory/Symlink with full SHA-256 identifiers. The producing visitor establishes body/address correspondence; the committed reader verifies it. No auxiliary byte is published by a filesystem link or written into an old cache file.
- K2. A regular holder is acquired and checked for file kind, 0444/0555 mode, mtime 1, inode, device and available size, with its bytes hashed under repair. Rejection conditionally forgets the observed row, not the valid donor's physical file, then considers the next candidate. The caller writes afresh if no candidate works. Auxiliary corruption is repaired by deleting a rechecked SQL incarnation, separately from physical-path repair.
- K3. Within one ingestion, the first completed file atomically claims `(id, exec)`; a worker whose earlier probe missed links that holder. Every written or reused key records one own candidate, keyed `(id, exec, ingestion)`, so collecting a donor cannot erase a surviving path’s witness. A successful full ingestion atomically replaces that path’s preceding candidate projection and retires its old ingestion rows, including failed named predecessors; an empty regular-file set is a complete projection too. A shared builder hold retains completed `(path, id)` values across outputs; registration consumes those values without recovering completion identities from SQL. Metadata-only registration leaves witnesses untouched. The eight valid/failed-predecessor, empty/nonempty and direct/multioutput cases, followed by two repeated optimisations, check replacement and bounded history (`completedIngestionReplacesThePathsEntireCandidateProjection`). Before publication, a SQLite write reserves the writer and the candidates stay unnamed. A bulk collision query enumerates all registered donors by signed `(device, inode, ingestion)` order, including an already-shared inode. For actual collisions, the filesystem-only helper pins a usable donor, validates canonical metadata and hashes the pinned bytes, and relinks every eligible physical alias of the losing inode. Rejected observations are conditionally forgotten; rewritten candidate rows survive SQL retries in the pending-row vector. A physical alias that successfully linked becomes the representative even if another alias was refused; a key for which pinning or every replacement was refused contributes no new canonical donor. This is a partial map on the already known collision keys, preserving the documented placement exceptions without spreading an exceptional inode to future successful ingestions. Only then are the candidate’s path and validity published. This applies to direct registration, a builder’s named outputs (including a multioutput transaction), and `endIngestion` on already-valid repair/optimisation paths. Existing valid targets are reconciled against committed witnesses before any new candidate is exposed. All 56 insertion/completion schedules check witness availability and physical sharing after each publication; a further 144 combinations cover all four writer routes, three publication boundaries, three regular-root shapes, both publication orders and both repair modes (`everyCandidatePublicationOrderKeepsRegisteredHolders`, `everyWriterReconcilesBeforeEveryPublicationBoundary`). The 12 refusal cases cover pin/full-alias/representative-only refusal, both executable modes and both ingestion-ID orders, then free space and require a third successful ingestion to share the nonexceptional donor (`refusedPublicationDoesNotPromoteAnExceptionalInode`). The same ingestion transaction publishes its complete auxiliary projection; regular reconciliation does not discard auxiliary bytes.
- K4. Auxiliary liveness follows its ingestion. Every recipient retains the metadata it consumed; no global link count or shared address claim stands in for ownership. Regular files are collected with their physical store paths, and stale candidate rows with their ingestions.
- K5. `ValidPaths.hash` remains the root identity. Auxiliary GC does not derive ownership by traversing it, so missing/corrupt roots and unmigrated rows do not block unrelated stale-projection cleanup. Hash migration still does not manufacture an entered projection.
- K6. A successful read copies one body's complete ordered chunk sequence from one snapshot. Chunks are contiguous from zero, each non-final chunk is 1 MiB, and an empty body is one non-NULL empty BLOB. Wrong classes, gaps, short non-final or trailing empty chunks, oversized bodies and wrong framed hashes reject that incarnation; a malformed prefix needs no further chunks; a later signed ingestion ID may supply a sound copy. No prefix and suffix from different incarnations are combined. The state scope ends before ordinary hashing. The shared `parseTreeBody` parser checks canonical mode spelling, ordering and sink admission without a framing copy or re-encoding pass. A held string survives concurrent row deletion; later child reads may still miss.
- K7. The collector's store-directory walk skips `.objects` and `.links`. Whole-store cleanup handles their appropriate contents; specific path deletion does not run that cleanup.
- K8. **The index is the witness, and the link count is not.** A regular-file blob's canonical file is a store path's own, so a holder that no second path shares is at *one* link, and the old statement — every such file at two links or more — is false by design. `EnterVisitor::tryKnown` therefore has no `st_nlink` test: the inode map is only a hint: the current selected holder is validated before a skip, and the path records its own witness, whatever its link count (`EnterVisitor::tryKnown`, `optimise-store.cc`; the `lstat` stays because `readdir`'s `d_ino` can differ from it). The table it consults is one query rather than a walk of `.objects/blobs`: it joins `Blobs`, `Ingestions` and `ValidPaths` and keeps only the first registered candidate in signed `(device, inode, ingestion)` order for each `(id, exec)` (`QueryBlobInodes`, `local-store.cc`; `GitObjectStore::blobInodes`). Only that selected inode is canonical to this shortcut. The physical class precedes the ingestion identity: replacing a path’s complete projection cannot change the selected class, and collecting one donor cannot displace it while a surviving alias retains its own witness. An older store’s noncanonical candidate therefore reaches the hasher and `place`, which selects the same first usable holder and coalesces it; including every candidate here would incorrectly bypass placement. New publication coalesces overlapping ingestions before they become visible. `optimiseCoalescesConcurrentCandidates` enumerates 120 combinations of both executable modes, all six publication orders, all five partitions of three files into inode classes and each possible minimum class; `optimiseKeepsTheCanonicalInodeWhenItsFirstHolderIsCollected` covers collection of a donor after a processed alias retains its witness. A separate relational countercheck enumerates all 4,096 states of three candidates in each executable class, each absent, unnamed, named-invalid or registered; the query selects the first registered physical class independently per mode. A further 1,664 cases enumerate both modes, all 13 ordered partitions of three candidate inodes and all 64 per-mode visibility states, with the other mode present independently; the same cases check complete cursor enumeration without deleting rejected rows. Device and inode coordinates include signed negative values and their minima. Both SQL statements are extracted verbatim from production. **Weaker** as stated, and what replaces it is a witness stronger than the count: the selected row names the canonical inode.
- K9. Executable and symlink roots retain the same synthetic Directory encoding and object hash (`merkle::objectHash`). `putRootTree` stages that body into the owning projection. Ordinary regular/directory roots require no extra synthetic value.
- K10. Directory bodies are produced bottom-up, but only complete ingestion projections are published. GC neither reads these bodies nor requires a whole-closure snapshot. A speculative materialisation owns all acquired bodies and regular rows until successful merge; missing children use the existing private-attempt fallback boundary.
- K11. `placementOf` retains all regular-file exceptions: writable files, unsupported platform paths, Windows, hard-link limits and refusal leave files as written. The existing `failPlaceWithNoSpace` seam remains a regular placement refusal. There is no longer an auxiliary final-link `ENOSPC` soft miss; SQL/allocation/I/O failure is a completion error under the existing transaction protocol. Equality of resource-failure traces with the retired file representation is not claimed.
- K12. Legacy cleanup creates no directory and reads no body. It visits only fixed `blobs`, `blobs-x`, `trees`, their real two-hex shards, flat leaves and known lease contents. Unknown directories remain opaque. POSIX traversal opens no-follow directory descriptors and deletes leaves/empty directories relative to them. Missing or non-directory roots are empty for cleanup. Windows uses the existing portable no-follow classification and nonrecursive removal, without POSIX-equivalent ancestor-race guarantees.
- K13. An overlay owns only upper SQL and upper physical legacy files. `Owned{dir,removed}` selects the upper namespace and notifies after actual deletion; it does not supply a merged-path deleter. No lower cache body is inspected or removed, and no cleanup unlink through the mount can create a whiteout. A separately opened merged lease supplies only lock coordination; a missing view conservatively retains the upper lease. Actual upper removals request the existing remount. Cross-layer regular sharing, direct named materialisation, merged auxiliary verification and `.links` removal remain disabled. Upper regular sharing, physical-path verification and the nonvirtual SQL cleanup remain enabled. Real-overlay oracles must preserve lower files/hashes, merged visibility, upper regular inodes and no whiteouts.
- K14. Schema-10 object-hash migration still checks the asserted NAR hash on the same walk before updating a row; missing/modified paths remain reported as such. One current-layout migration installs the regular-row foreign key and `AuxValues`, preserving eligible rows. Five compatibility markers prevent supported older writers from replaying a rebuild that loses the regular-row cascade. Old read-only databases without `AuxValues` install no provider: reuse misses and auxiliary-availability verification is skipped, while physical hashing and regular-holder checks continue. Existing foreign-key enforcement lets older connections cascade both projections when deleting an ingestion; the retired loose-file protocol is not a parallel reader or a supported concurrent publisher.
- K15. Materialisation uses the shared source traversal and a direct fold of verified canonical directory bodies, symlink targets and regular holders at the original logical path and depth. It asks for named roots and directories, including nested unchanged subtrees, and falls back on an unusable child through the existing private-attempt cleanup. A successful receiver stages every consumed original auxiliary body into its own projection without serialising or hashing it again. The source-known regular shortcut is skipped under repair; a supplied root/directory namer remains callable and regular bytes are checked under repair. `materialisesFromObjects` still gates this route to the supported local non-overlay store; daemon and Windows routes are unchanged.
- K16. Each source add owns a fresh `Hold`. The production `ownRows` user is a speculative directory attempt: it shares its parent’s memoised lease acquisition while retaining a private root, ingestion identity and projection. Batch copies use the existing `Store` dependency scheduler, with no cross-path lease owner or in-memory-source scheduling hint. First demand creates and locks `.objects/tmp/hold-<pid>-<counter>`; concurrent demand synchronizes through the existing memo. `endIngestion` demands the lease before taking the database lock. Regular replacement and coalescing demand it when temporary links are needed, possibly inside the publication transaction. Opening a store and private in-memory staging do not demand the physical namespace; filesystem errors in that unused namespace are deferred until lease acquisition. Fresh direct publication stores a NULL hold marker because validity and projection commit together; existing completed-ingestion markers remain unchanged. The regular and auxiliary key domains use independent synchronized maps, each retaining the first completed value per typed key. Projection order is unspecified. Both output vectors are reserved before extraction, and payload moves are nonthrowing; retry retains the resulting owned values. All workers join before transfer or cleanup. A completed builder projection is published before the hold resets for its next output. Private unfinished bodies are not globally reusable. Lease creation retries if collection removes its name before locking; cleanup never waits for a busy lease. The lock stays held through dead-name removal, including on Windows. Unknown nested occupants and failed removals conservatively retain the lease. All current temporary regular pins belong to the lease and are protected by its lock. Retired flat pins retain the timestamp-in-name age rule; leases are judged by locking, not age. Supported publishers do not rename live lease directories. Overlay lower-name collisions can conservatively retain upper stale rows, but never authorize lower mutation.
- K17. **One bounded pool serves hashing and copying.** `CopyPool` is created only at the first directory with sibling work worth queuing; root memo hits and regular roots allocate none. The machine's width is capped at eight. Only the stateless `AllPaths` filter and an accessor that explicitly permits reordered concurrent traversal can use it; arbitrary filters and unproven accessors remain on the caller thread in depth-first order. Permission is implemented only by final POSIX directory accessors, the built-in allow-list and fixed-membership workdir filter (including their scopes) when the physical accessor permits it, and plain Git accessors without LFS smudging. Workdir membership is fixed; this traversal permission neither freezes its bytes nor supplies a content identity. Git reads remain locked; export-ignore and other unproven wrappers remain serial. Copying additionally requires the caller's explicit permission for its hooks and namer; the public APIs default to serial callbacks, while the two audited production callers opt in. The plain pull hasher and its memo may use the pool; default and caller-supplied visitors and the push driver stay sequential. Only children marked as directories are eligible for queueing, bounded by the extra worker count; the hints are advisory, and a full queue runs inline. The queue reserves that bound once in contiguous storage; workers take the last pending job under the pool mutex without shifting others. Job records borrow only group pointers and child indices. A waiting caller helps only its own child group, filling a removed slot from the back. The joining scope owns the lowest failed child index and its exception, the count of outstanding jobs and one completion condition variable; queued jobs borrow that scope and its callback. Visits complete independently of consuming their results. Hashing and materialisation share the ordered child executor and fold completed values into a private parent tree and optional exact NAR size. With more than one worker, groups with more than one child and at least one directory hint use `CopyPool::ordered` and join before the ordered fold; other groups read and fold each child inline, even when a pool already exists. Failed visits lower the selected index under the pool mutex. A worker releases a displaced or unselected exception outside that mutex before decrementing the outstanding count, then notifies at zero while still locked; inline failure cleanup also occurs outside the mutex. Every accepted job is joined before source and destination scopes expire, including on failure. Unselected exception destruction time and thread are not promised. An inline visit failure stops launch; an asynchronous failure does not. After joining, a reached predicate or admission failure takes priority and consumes nothing. Otherwise the fold consumes only the prefix before the lowest failed visit, then rethrows its exception unless an earlier consume failed. This preserves traversal-order failure selection, with a child’s read before its fold. Test domains cover 144 launch/failure cases (138 reached predicate failures and six preceding inline failures), including multiple admitted failures, 2,072 read/fold outcomes, 32 nested cases and 16 exception-cleanup cases. Joining happens outside exception unwinding so helped jobs still observe interrupts. Tree results and case-hack numbering retain their ordered fold; C++ scopes restore the thread-local current sink and borrowed physical child name, including nested visitors and helped jobs. The shared scheduler copies callback `string_view` names into owned strings alongside dormant visit continuations, keeps one child inline and doubles capacity. Collection finishes before visits start. `Children::canDefer` permits that collection only when callbacks outlive immediate delivery; borrowed push callbacks are consumed immediately. Memo keys belong to each node's continuation; only named cache facts take its mutex. Holder probes use `_state`; the private regular and auxiliary pending sets have independent mutexes. After traversal jobs join, registration takes the completed projection before locking the database; `endIngestion` provides the corresponding completed-output handoff for a shared builder hold. Tests enumerate widths 1–8, permissions, metadata domains, read/fold failures, nested joins and every binding across the memo flush boundary. See [09-performance.md](09-performance.md) for measurements.

Verification and accounting limits:

- X2. `verifyStore --check-contents` still recomputes each valid path's physical object hash and checks eligible regular witnesses. When the provider exists it also checks required auxiliary availability; the global SQL pass verifies every typed-key/ingestion incarnation, including unreachable ones. Writable repair rechecks before deleting and re-enters missing projections; read-only repair reports without writing. A missing derived projection means forgotten reuse information, not by itself changed physical path bytes.
- X3. A specific delete does not run whole-store legacy/stale-projection cleanup. POSIX deletion credits only successfully removed non-directory entries observed at their last link; failed/ENOENT removals add nothing for that entry, while earlier successful child removals retain their estimates. Remaining hard links receive no speculative credit. Open descriptors, concurrent metadata changes and physical allocation prevent an exact immediately freed-space guarantee; Windows retains zero. Deleting auxiliary SQL rows does not promise immediate database-file shrinkage.

### 1.6 The order in which the sinks fire

The NAR parser (`archive.cc:211-341`):
- For a regular file: `createRegularFile(path, f)`, and inside `f`: `isExecutable()` if the entry is executable, then `preallocateContents(size)`, then the bytes (`archive.cc:242-261`, `181-201`).
- For a directory: `createDirectory(path, cb)`, the children delivered inside `cb`, in sorted order (`archive.cc:263-326`).
- For a symlink: `createSymlink(path, target)` (`archive.cc:328-337`).
- A colliding name under `use-case-hack` is renamed with the suffix before it is delivered (`archive.cc:298-317`); a name already carrying the suffix is refused on every platform (`292-294`).

`RestoreSink` (`fs-sink.cc`):
- `createSubdirectory` makes the directory, opens it, hands the callback a fresh `RestoreSink` whose `dstPath` is the directory and whose path is `/`, and runs `directoryDone` when the callback returns (`fs-sink.cc:119-155`).
- `createRegularFile` constructs a stack-owned `RegularFileWriter`, invokes the callback and calls `finish`; the split-lifetime `beginRegularFile[At]` APIs return an owned writer (`fs-sink.cc`); `finish` flushes, runs `regularFileCreated` once, starts write-back when requested and closes the owned descriptor, reporting errors to its caller. Destruction retains best-effort cleanup for an unfinished writer. On POSIX, the resolved parent descriptor and validated final filename suffice for exclusive creation. The directory source accessor likewise opens its canonical basename directly, refusing final symlinks; its subsequent descriptor stat still validates and sizes the file actually opened. A caller that already selected the placement parent reuses that descriptor and validated name for creation. The parent stays alive through the call; the returned writer owns the opened file independently of the parent descriptor.
- The generic `createDirectory(path, cb)` default of the base hands the callback the same sink and the full path (`fs-sink.hh:62-64`); `RestoreSink` hands it a sink of the directory's own under `/` (`fs-sink.cc:119-155`). The two conventions differ; `copyRecursive`'s `Copy` visitor keeps a stack of what the callback handed back, seeded with the caller's sink and destination (`tree-traversal.cc`), so it serves both.

The one traversal and its visitors: `traverse` and `NodeVisitor` (`tree-traversal.hh`), `HashingVisitor` and the push adapter `ObjectHashSink` (`object-hash-sink.hh`). The ordered fold is `dumpPath`'s, regular files follow the sink protocol, and directory scopes outlive every child. After stat, the pull driver calls `node(accessor, from, path, stat, descend)`, with the actual scoped source and its coordinate separate from the destination coordinate: it may return a known summary or synchronously descend once. The continuation carries a memo key without shared handoff state. The push driver never calls `node` and consumes each child's bytes immediately; its adapter closures therefore live on the calling stack and are borrowed through the synchronous visitor calls. Entry names are the tree's own (`unhackName`); node paths retain the accessor's spelling.

Canonical summaries require logical names: `merkle::insertEntry` and the stored-tree parser reject the literal case-hack marker under either policy; canonical Git writers use that same insertion rule. Raw Git writers remain separate. Tar root projection precedes canonical writing (`01` §9.10). The finite tests enumerate four modes and name classes (invalid components, marker positions, ordinary and case-varied spellings), all mode pairs for duplicate names, and requested/unrequested projection against singleton/non-singleton roots; actual tar parsing distinguishes discarded wrappers from retained leaves. The memo test enumerates both initial and later policies, Git/NAR, memory/persistent origins and plain/encoded names. These are test domains, not a validation result. Producer provenance and the stable-input assumption remain prerequisites; the tests do not prove arbitrary imported repositories canonical or concurrent configuration changes coherent.

The store's visitors (`optimise-store.cc`):
- `ObjectStoreVisitor` (`optimise-store.cc`) stages each symlink target and encoded directory body as owned auxiliary metadata after hashing (K16); regular files are the two drivers' business.
- `EnterVisitor`, the on-disk walk (`enterIntoObjects`): `node` tries an inode-map hint only outside repair. A skip requires a currently selected holder matching the file's device, inode, size and canonical metadata, and records this path's own witness (K8), independent of link count. Otherwise it descends, hashes and places the file with its parent temporarily writable; suspicious writable files are left alone.
- `LinkingVisitor` (`optimise-store.cc`), the restore route (`restoreThroughObjects`, synchronous node producer → `ObjectHashSink` → this; NAR callers use `parseDump`, buffered Flat callers emit one regular file): its scoped `Frame` selects the `RestoreSink` each directory's callback handed back, initially the caller's, so a node is created on the current sink under `/name` (`at`); `directory` opens `createSubdirectory`'s scope and visits the children inside it, so `directoryDone` (canonicalisation) runs when the scope closes, before its tree body is staged; `symlink` creates the link then hashes.  A regular file goes to the hasher as it arrives and is held in memory up to `restoreBufferLimit`; when the hasher returns the entry, the visitor decides with it in hand: a blob the store holds is linked (`objects.link`, one `linkat`), nothing written, so `regularFileCreated` does not fire; a miss is written from memory and placed.  A file announced or grown above the limit is opened at once (`BufferThenStreamFile`), streamed, finished and placed.
- `MaterialisingVisitor`, the accessor copy (`materialiseThroughObjects`): `node` first tries a verified immutable regular-file identity, except under repair, then asks `TreeNamer` for the root and directories. A named subtree the store holds is made from verified owned tree bodies, regular-file holders and symlink targets, returning its entry and NAR size without reading below that source node. A recoverable object miss removes the private attempt and calls `descend`; a completed attempt is reconciled with the parent ingestion before returning. `directory` retains the case-hacked disk name around each child, and the shared ordered scheduler joins its scopes (K17). Hooks run for newly written files, directories and symlinks; linking a regular holder fires no `regularFileCreated`.
- `regularFileCreated` fires only for files written, never for files linked (`local-store.hh`, the counting hooks of `LocalStoreObjectsTest`); with `GitObjectStore::link` forced false the four counting assertions fail (`05-validation.md` section 4).

## 2. The semantics checklist

At every call of one of these kinds, the caller writes the assumption as a comment and cites the line that guarantees it. The questions to answer:

**`flock` / `FdLock`.** Who holds which mode now? If the collector holds it exclusive, does my shared attempt fall back to the socket (`gc.cc:107-153`), and do I want a root the running collection honours? Is the lock on this open file description, or on another open of the same file? Does the process that must hold it outlive the operation it protects?

**`linkat` / `link`.** Which errno do I tolerate — `EEXIST`, `EMLINK`, `ENOENT`, `ENOSPC` — and what happens to the file I was about to link in each case? Does the target directory need write permission, and who restores its canonical mode on every exit path, exceptions included? Does the link count I read include the link I am about to make?

**`renameat` over an existing name.** Is the target directory writable? Is the inode I replace still linked elsewhere, or do its bytes vanish? Is the rename within one filesystem (else `EXDEV`, handled at `local-store.cc:1660-1662`, `movePath`)? Is the temporary I rename from removed on every failure?

**`fstatat` / `lstat` / `readdir`.** Do I key a table by `d_ino` or `st_ino`, and does the reader of the table use the same one? Is `st_size` a cheap negative or a proof of identity (it is the former)? Is `st_nlink >= 2` the fact I need? Is the directory being modified while I iterate it? Which of mtime and ctime moves when I link, unlink or chmod?

**`fsync`.** File before link, directory after link; is any metadata changed after the file's fsync? One fsync per file, or `recursiveSync` once? Under which setting?

**`std::filesystem::path::operator/`.** Can the right operand be empty (`"x"/""` is `"x/"`) or absolute (it replaces the left)?

**Containers.** Do I hold a reference or iterator into the element I erase? Do I insert into a map while iterating it?

**`enable_shared_from_this`.** Am I in a constructor, or in a function that may run on a stack object?

**Types as invariants.** Does the token have a user-provided move constructor? Are the members meant to be unreachable `private`, not `protected`? Does the type's constructor do what the type's name promises?

**Destructors and exits.** Does this exit path run destructors — `exec` does not, `_exit` does not? Can the destructor's work fail, and who reports the failure? Is the environment the destructor needs still in place? Local-store factories use `LocalStore::Deleter` to join automatic GC before entering any destructor: a destructor body is too late to protect virtual dispatch from its entry-time vptr writes. Other owners wait for collection inside `autoGC`, even when passed `false`; the completion promise follows all virtual store work. The base destructor still joins any remaining worker tail. The owner is identified through the store's own `weak_from_this`, so unrelated aliasing pointers cannot confer asynchronous lifetime.

**Meson.** Is `--suite` combined with names on one line (the intersection runs)? After a dependency change, does `meson configure build | grep pkg_config_path` show the new path?

**libgit2.** Which layer enforces the rule I rely on — the tree builder (`tree.c:57`), the object writer (`odb.c:1613`), the parser (`tree.c:394`), or the attribute lookup with its flags (`include/git2/attr.h`; `GIT_ATTR_CHECK_INDEX_ONLY` reads the index, where an untracked `.gitattributes` cannot appear, while git itself reads a working directory's attribute files tracked or not; `GIT_ATTR_CHECK_NO_SYSTEM` excludes the system file)? Is `GIT_OPT_ENABLE_STRICT_HASH_VERIFICATION` on, and if not, who verifies what I read?

**Git object formats.** Are the entries ordered as if directory names ended in `/` (`merkle-hash.hh:24-27`)? Does the root carry a mode (it does not)? Does my memo row hold the entry hash or the object hash of a synthetic root, and which does every reader expect?

**Protocols.** Which peer versions and features can be on the other end of this call, in both directions? What does the info carry when the peer is old — `objectHash` absent, so never dereferenced unguarded? Which side pays the shim's walk, and how often?

**Signatures.** Which fingerprint version does each peer verify? Is the NAR hash a version-1 signature needs available where the signature is checked? Does `require-sigs` on the receiver see the info as sent, before anything is stored (`daemon.cc:555-576`, `local-store.cc:1281`)?

**The store directory.** Before adding, renaming or removing anything under it: read the collector's walk (`gc.cc:807-823`), `verifyAllValidPaths` (`local-store.cc:1940`), and every `rmdir`, `ls` and emptiness assertion in `tests/functional`.

**The base class.** Before deriving from or composing over a sink or a store: list every virtual the base calls on child objects (`fs-sink.cc:159-195`), and drive the derived component alone, two levels deep, with a test that fails when the override is removed.
