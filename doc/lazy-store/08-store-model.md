# The local store's concurrency and durability model, and the API semantics it rests on

A reference for a maintainer about to touch `src/libstore`. Section 1 states the facts the local store's code keeps, one per sentence, each with its `file:line`; line numbers were taken when the fact was written and drift, so a locator names the function beside it where the line may have moved; where the lazy-store branch's code depends on a fact, the dependency is named beside it. Section 2 is the checklist of API semantics to answer at every call site of the kinds the branch uses. Neither section argues; the arguments are in `01-specification.md` and `04-derivation.md`, and the tests that pin the defects behind these facts are the table of `07-defect-ledger.md`.

## 1. The model

### 1.1 Locks

**The big lock** (`<state>/db/big-lock`).
- A writable store opens it and holds it shared for its life (`local-store.cc:243-261`).
- The lock is taken exclusive only for a schema upgrade, releasing the shared lock first to avoid a promotion deadlock (`local-store.cc:277-283`, `345`, `356`).
- A read-only store takes no lock at all (`local-store.cc:243`, `258`).
- Branch: the schema is 11; a schema-10 store is bumped on first writable open and runs no statement for it (`local-store.cc:266-273`, `287-341`, `local-store.hh:29-33`); an older Nix then refuses the store. A read-only open of a schema-10 store is allowed (`local-store.cc:267-273`).

**The database lock** (`_state`, a `Sync<State>`).
- Every SQLite statement runs with `_state` locked; `retrySQLite` retries `SQLITE_BUSY` (`local-store.cc:797-798`, `1041`, `1053-1056`).
- A transaction (`SQLiteTxn`) is opened and committed under one lock scope (`local-store.cc:1187-1190`, `1727-1730`).
- Ordinary hashing, migration and ingestion walks run outside the database lock. The narrow exception is publication-time inode reconciliation: after a write reserves SQLite’s writer, a bulk query finds actual overlapping blob candidates; only a collision walks the completed target’s physical aliases. This helper only uses filesystem operations, never database/index callbacks, the auxiliary namespace lock or temporary-root registration. It pins and validates donors before replacing aliases, so the reservation excludes GC invalidation and the pin survives concurrent donor replacement. With no collision there is no filesystem pass.
- Branch: `migratedPathInfo` walks the path outside the lock and re-reads the row under the lock before writing, so a row migrated or deleted meanwhile is respected (`walkOldRow`, `local-store.cc:840-888`; `migratedPathInfo`, `890-925`; the re-read in `recordObjectHash` at `939`). `forEachValidObjectHash` runs under the lock and therefore counts unmigrated rows instead of migrating them (`local-store.cc:1065-1082`). `addSignatures` migrates first, outside its transaction (`local-store.cc:2044-2049`). `queryPathInfoInternal` never migrates (`local-store.hh:590-596`), nor does `queryPathInfoUnmigrated`, the same read under the lock it takes, which the collector uses for its dead set.

**The GC lock** (`<state>/gc.lock`).
- `collectGarbage` holds it exclusive for its whole run (`gc.cc:394-395`).
- `addTempRoot` tries it shared and non-blocking (`gc.cc:105`); when that fails the collector is running and the root is sent over the collector's socket, and the sender waits for the acknowledgement (`gc.cc:107-153`).
- The collector's server thread records each socket root in `tempRoots` and, while the path is being deleted (`pending`), makes the sender wait until the deletion is done (`gc.cc:470-500`, `481-492`; `pending` set at `675` and `738`, reset at `589` and `742`).
- The collector re-checks `tempRoots` immediately before each deletion (`gc.cc:719-744`).
- `verifyStore` takes the GC lock shared and blocking, so it never runs beside a collection (`local-store.cc:1755`).
- Branch: the object-store sweep runs inside the exclusive lock, after the deletions (`gc.cc:864-874`). No branch code takes a temp root on behalf of a query the collector itself makes — the migration takes none (`local-store.cc:895-901`), because the collector reads visited paths' rows — unmigrated, as the database has them (`queryPathInfoUnmigrated`; `topoSortPathsBy`, `gc.cc`), so a dead schema-10 row is deleted without the walk — and the live closure's infos through `computeFSClosure`, and a root registered then would keep a dead path.

**Auxiliary-object lock** (`<state>/object-gc.lock`).
- The auxiliary sweep holds it exclusive from before dead-hold cleanup and the valid-root snapshot through the last removal. Auxiliary publication and acquisition, and an owning hold's cleanup, take it shared (`GitObjectStore::AuxiliaryLock`). The ingestion itself holds no such lock, so a collection can run while its copy is paused.
- Auxiliary repair reserves it exclusively only for a mismatch, reopens and rechecks the current occupant, and removes that occupant only if still corrupt. Initial inspection and all diagnostics are outside the reservation. Reinspection also rederives the pathname's role: a former corrupt shard symlink may now be the real shard directory. Both size and bytes come from one descriptor, closed before diagnostics and removal so Windows does not retain a delete-pending name; the exclusive reservation excludes publication between recheck and removal. This also serializes two verifiers, whose shared whole-store GC locks are compatible.
- These scopes make the live auxiliary-address set stable from its enumeration through removal, and keep an ingestion registered after the root snapshot from releasing its protection during that sweep. A link count alone is insufficient: repair can replace the published inode while a live hold still links its preceding incarnation.
- Shared readers of one object-store instance aggregate on one persistent descriptor; separate instances open independent descriptors for the same file. The lock order is auxiliary namespace before database; registration releases its database lock before its owning hold is destroyed, and hold cleanup joins its writer before acquiring the auxiliary lock.
- The file is in the stable state directory, outside the overlay mount: remounting can replace the merged view's inode while an existing descriptor still names the old inode. Construction and read-only queries create no lock file. The lower overlay store remains subject to its existing no-modification requirement (`src/libstore/local-overlay-store.md`).

**Path locks** (`<realPath>.lock`).
- One path's write is guarded by `PathLocks` on its real path, except from a build hook whose parent holds the lock (`local-store.cc:1292-1304`, `1627`).
- The validity check is repeated under the path lock, because another process may have registered the path meanwhile (`local-store.cc:1305`, `1630`).

**Temporary directories in the store** (`tmp-*`).
- `createTempDirInStore` makes the directory, opens it, and takes an exclusive lock on the descriptor, retrying until the directory both exists and is locked (`createTempDirInStore`, `local-store.cc:1703`).
- The collector deletes a `tmp-*` entry only when it can take that lock itself (`gc.cc:551-558`).
- Branch: `addToStoreFromDump` restores through the object store inside such a directory and then moves it into place (`local-store.cc:1581-1590`, `1660`); the blobs it entered stay linked across the move (same filesystem); the trees and symlink blobs it wrote are protected by its hold, not by this lock (1.5, K16). `LocalStore::materialise` (`optimise-store.cc`) does the same, step for step.

### 1.2 Temporary roots

- Each `LocalStore` handle's temp roots live in a distinct `<state>/temproots/<pid>.<unique>` file, created exclusively on its first root and held write-locked for that handle's lifetime (`createTempRootsFile`). The numeric prefix remains readable by older collectors. Independent handles in one process never replace or unlink each other's root files.
- A root is a path name appended to that file, or, during a collection, a line sent to the collector's socket (`gc.cc:155-158`, `132-138`).
- The collector reads every temproots file after taking the GC lock; a file whose lock it can acquire has no live owning handle and is removed. A creator accepts its locked descriptor only while it remains linked and empty; if a collector removed it before locking, the creator allocates another name. A collector that finds its already-open descriptor unlinked does not remove anything at that old name.
- The file is unlinked when the store object is destroyed. On POSIX, unlink precedes releasing its lock. Destroying one handle releases only its own roots; a command that has exited roots nothing. `temporaryRootsBelongToEachStoreHandle` covers all six two-handle creation/registration interleavings and both destruction orders with actual collections.
- A read-only store creates no temp roots (`gc.cc:86-90`).
- A temp root protects a store path; it protects no object-store object. An ingestion's objects are protected by its hold, a locked directory under `.objects/tmp` with a link per object (1.5, K16), which is to the sweep what a temp root is to the collector.
- Branch: `WriteBuffer::addText` roots the computed path before checking validity. A valid non-repair object needs no pending write or additional reference roots; its root protects its recorded closure. An outstanding write roots each reference outside the pending set at enqueue. `derivationStrict` and `toFile` realise mounted opaque references before that call, including when enqueueing reaches the memory bound; `fetchToStore2` roots before `isValidPath` on a cache hit (`fetch-to-store.cc:292-295`); `optimiseStore` roots each path before walking it (`optimise-store.cc:454`); `nix store migrate` roots before its walk (`store-migrate.cc:60`); the daemon roots before the shim's walk for an old client (`daemon.cc:321-331`).

### 1.3 Between a write and a registration

- A path is written into its real path or into a temp directory, verified, optionally synced, and registered in one transaction (`addToStore`, `local-store.cc:1265`; `addToStoreFromDump`, `1483`; `registerValidPaths`, `1176`).
- Until `registerValidPaths` commits, the path is invalid; the collector deletes an invalid entry unless a temp root names it (`gc.cc:678`, `819-822`); both ingestions take the root first (`local-store.cc:1290`, `1618`).
- A verification failure after the restore leaves the written files in place as an invalid path, which a later collection removes (`addToStore`, `local-store.cc:1265`: the checks between the restore and `registerValidPath`); two of the checks remove the files themselves — the refusal of a SHA-1 git address (`1377-1378`) and the deferred signature check (`1436-1441`).
- A crash before the commit leaves an invalid path and, on the branch, blob files with two links, tree files and symlink blobs linked from a hold whose lock died with the process; the collection removes the path, the sweep removes the hold (unlockable, so dead) and then the blobs (link count 1) and the trees (unreachable, one link). It also leaves index rows against an ingestion that never got its path: `link` is not misled by one, the lookup joining on a path that is not null, and the stale rule removes them after the holds have gone (1.5; `LocalStoreObjectsTest.aCrashBeforeRegistrationLeavesNoRowThatMisleadsLink`).
- The database row is durable by SQLite's `synchronous = normal` under `fsync-metadata` (`local-store.cc:557`); the files are durable only under `fsync-store-paths` (1.4).
- Branch: `restoreThroughObjects` writes blobs (`place`; `putBlob` for a symlink's target) and trees (`putTree`) while restoring, before any registration (`optimise-store.cc`, `LinkingVisitor`); each is held by the caller's hold until the registration (K16), so a concurrent sweep keeps them. The ingestion's own `autoGC()` runs before the restore, not in this window, and on the in-memory route after the validity check, so an add of a valid path runs none (`LocalStoreAutoGCTest`).

### 1.4 Durability points

- Under `fsync-store-paths`, every file of the path is synced and then its parent directory, before registration (`local-store.cc:1448-1450`, `1683-1685`).
- The restore sink starts an asynchronous write-back per file when `startFsync` is set; it waits for none (`fs-sink.cc:264-269`).
- Under `sync-before-registering`, `sync()` runs before every registration (`local-store.cc:1183-1184`).
- Without either setting, nothing makes the files durable before the row.
- Branch: object files are fsynced under the same `fsync-store-paths` flag — the file before it is linked, the directory after (`git-object-store.cc:245-246`, `259-260`; the flag from `local-store.cc:133`). Completed bytes and the exact read-only mode precede the file's fsync (`writeObjectFile`, `git-object-store.cc`). Auxiliary modification time is not part of a represented tree and no auxiliary consumer reads it, so POSIX omits its former canonicalisation. Regular-file holders retain mtime 1; Windows retains its existing combined metadata operation until a permission-only equivalent is provided. The before-fsync check and all 512 permission masks under both modes preserve bytes, readability and durability.
- Branch: **large ingestions add a cache durability point.** Incremental holder batches use the writer's connection with `synchronous = off`; its `Ingestions` row is allocated on first flush, in the same transaction as that batch. These rows are a reconstructible cache. Small ingestions need no separate writer or transaction: their path, ingestion identity and holder rows commit together on the store connection. See [09-performance.md](09-performance.md).
- Branch: **ordinary ingestion registration publishes the path and holders together.** `registerValidPath(info, hold)` joins any incremental writer before taking the database lock, then registers the path, assigns the ingestion its path and inserts remaining holder rows in one transaction. A failed transaction publishes no validity-cache entry. The builder, optimiser and repair callers that use `endIngestion` retain the separate publication step; its temporary loss of sharing is safe because unnamed ingestions are invisible to holder lookup.

### 1.5 The object store's invariants

The object store is `<realStoreDir>/.objects/{blobs,blobs-x,trees,tmp}` (`git-object-store.hh`), made when a writable store opens (`local-store.cc:150`). Each of the three object kinds is sharded 256 ways by the identifier's first byte in hexadecimal, git's own layout: an object file is `<kind>/<xx>/<id>` (`nameUnder`, `git-object-store.cc`), and `tmp` is not sharded.

**Where a regular file's blob is, and where the store's record of it is.** A regular-file blob has no file of the store's own naming: its canonical file is a *store path's own file* — a **holder** — and `blobs` and `blobs-x` hold the symlink-target blobs alone, which no path holds. Where a holder is, is the store's own database, in two tables (`schema.sql`): `Blobs(id, exec, ino, dev, ingestion, name, size)`, keyed `(id, exec, ingestion)` on the identifier and its owning ingestion, and `Ingestions(id, path, hold)`, whose `path` is null until the ingestion registers. The object store reaches them through one indirection it does not own, `GitObjectStore::Index` — `lookup`, `forget`, `inodes` — installed by the `LocalStore` that owns the object store (`blobIndex`, `local-store.cc`); a bare `GitObjectStore` (a test's, an overlay's lower store's) has none and misses every lookup.

**The hold protects rows as it protects objects.** An ingestion's rows are written while its copy runs, before its path exists, so they cannot hang off a foreign key into `ValidPaths` and there is no cascade. What replaces it is a *stale rule*, the discipline the trees and the symlink blobs are already collected by (K4, K16): a row whose ingestion has no path, or whose path is no longer valid, names no holder. Two things judge it. (1) `GitObjectStore::holderOrForget` finds no file at the holder's name, or a file that is not what the row says, and forgets the row; `link` and `place` then write the blob afresh. (2) `LocalStore::sweepStaleBlobRows` removes every such row and its ingestion, in two statements inside one transaction under the GC lock (`local-store.cc`). **A collection's sweep is two halves, and only the first is overridable.** `LocalStore::sweepObjects` (`gc.cc`) is *not* virtual: it calls `sweepObjectStore()`, which is, and then `sweepStaleBlobRows()`, which no override can lose. The order is the one the rows need — the objects' sweep removes the holds of dead ingestions first, so a hold still under `tmp/` is a live ingestion's and its rows are kept exactly as its objects are, the row carrying its hold's name and the rule testing `pathExists(tmp / held)`. A subclass with an object store of its own overrides `sweepObjectStore` alone; `LocalOverlayStore` does, with its upper-layer sweep, and its stale rows go with every collection like any other store's (`LocalStoreObjectsTest.aStoreThatSweepsItsOwnObjectsStillSweepsItsStaleRows`, whose store overrides the virtual half as the overlay does; the overlay's own suite also passes on real overlay mounts; see `09-performance.md`).

Kept by the code:
- K1. *Split by kind, and this is what the holder changed.* A symlink-target blob's file and a tree body are still created from bytes through a temporary file that is linked into place, never written in place (`writeObjectFile`, `git-object-store.cc`). A regular-file blob has no file of the store's own: its canonical file is a store path's own file, canonicalised before the row that names it is written, and the row is what creates the blob (`place`'s miss branch and `enterWritten`, which `addRow` and issue no `linkat` at all). **Weaker for regular files, unchanged for symlink blobs and trees.**
- K2. A store path's file is linked to a **holder** — the blob's canonical file, which is some valid path's own file — only after checking regular-file kind, exact 0444/0555 mode and epoch-plus-one-second timestamp, the row's size against `lstat`, its `ino` and `dev` against the row's, and its bytes too under repair; a holder that fails any of these is **not removed**, because the file belongs to a valid store path and removing it would damage that path. Only the observed candidate row is conditionally forgotten; lookup then tries the remaining registered candidates. If none survives, the caller writes the file afresh and registers another candidate (`holderOrForget`, `git-object-store.cc`, called by `link`, `place` and `VerifyVisitor::regular`). The corrupt file stays where it is; reporting it is `--verify --check-contents`'s job. A symlink-target blob belongs to the object store itself: the auxiliary-object pass in `LocalStore::verifyStore` removes corrupt blobs under repair. **Changed in kind:** strictly safer, since no valid path's file is touched; strictly weaker as a repair, since the bad file stays until `--verify --check-contents --repair` reaches *its* path (`LocalStoreObjectsTest.repairRelinksAFreshFileOverACorruptBlob`, `repairDoesNotLinkACorruptBlob`).
- K3. Within one ingestion, the first completed file atomically claims `(id, exec)`; a worker whose earlier probe missed links that holder. Every written or reused key records one own candidate, keyed `(id, exec, ingestion)`, so collecting a donor cannot erase a surviving path’s witness. A successful full ingestion atomically replaces that path’s preceding candidate projection and retires its old ingestion rows, including failed named predecessors; an empty regular-file set is a complete projection too. A builder recovers the latest completed ingestion using the finite output-path domain and an index on `(path, hold)`. Metadata-only registration leaves witnesses untouched. The eight valid/failed-predecessor, empty/nonempty and direct/multioutput cases, followed by two repeated optimisations, check replacement and bounded history (`completedIngestionReplacesThePathsEntireCandidateProjection`). Before publication, a SQLite write reserves the writer and the candidates stay unnamed. A bulk collision query enumerates all registered donors by signed `(device, inode, ingestion)` order, including an already-shared inode. For actual collisions, the filesystem-only helper pins a usable donor, validates canonical metadata and hashes the pinned bytes, and relinks every eligible physical alias of the losing inode. Rejected observations are conditionally forgotten; rewritten candidate rows survive SQL retries in the pending-row vector. A physical alias that successfully linked becomes the representative even if another alias was refused; a key for which pinning or every replacement was refused contributes no new canonical donor. This is a partial map on the already known collision keys, preserving the documented placement exceptions without spreading an exceptional inode to future successful ingestions. Only then are the candidate’s path and validity published. This applies to direct registration, a builder’s named outputs (including a multioutput transaction), and `endIngestion` on already-valid repair/optimisation paths. Existing valid targets are reconciled against committed witnesses before any new candidate is exposed. All 56 insertion/completion schedules check witness availability and physical sharing after each publication; a further 144 combinations cover all four writer routes, three publication boundaries, three regular-root shapes, both publication orders and both repair modes (`everyCandidatePublicationOrderKeepsRegisteredHolders`, `everyWriterReconcilesBeforeEveryPublicationBoundary`). The 12 refusal cases cover pin/full-alias/representative-only refusal, both executable modes and both ingestion-ID orders, then free space and require a third successful ingestion to share the nonexceptional donor (`refusedPublicationDoesNotPromoteAnExceptionalInode`). Trees and symlink blobs retain their publication protocol.
- K4. A blob file with one link is removed by the sweep unless a reachable tree or a retained hold names its address (`GitObjectStore::sweep`, the blobs pass). **Unchanged in words, narrower in domain:** `blobs` and `blobs-x` now hold the symlink-target blobs alone, so this is the rule for those; a regular-file blob is owned by the path that holds it and is collected with it, by the stale rule above.
- K5. Trees are reachable only from the column: the sweep's roots are the object hashes of the valid paths (`git-object-store.cc:348-353`; `forEachValidObjectHash`); while any row is unmigrated, no tree and no blob is removed (`358`).
- K6. A reachable tree whose occupant is nonregular, whose body does not hash to its name, or whose body does not parse aborts the removal phase (`GitObjectStore::sweep`). Absence is a different state and retains its missing/unentered meaning. Auxiliary readers share a regular-inode opener: reject known nonregular occupants before opening, open the final component without following symlinks and with nonblocking mode on POSIX, then check the opened inode before reading its bytes. The observed size is only an allocation hint for tree and symlink-target bytes, so reads still drain the whole file. Source materialisation falls back on an unusable tree or symlink-target blob; a directory at an auxiliary address remains an error when the fallback publisher cannot hard-link it. These checks concern the final auxiliary entry, not a new restriction on configured ancestor paths. `auxiliaryReadersRejectNonregularOccupants` enumerates seven reader roles against absence, regular files, live/dangling symlinks, FIFOs, sockets, character/block devices and directories (63 cells; unavailable device privileges are reported). FIFO operations run without a writer, under a child-process failure watchdog so the previous blocking implementation cannot hang the suite. The special-file runtime domain is POSIX; the Windows opener is reviewed through its existing no-follow handle semantics.
- K7. The collector's store-directory walk passes over `.objects` and `.links` (`gc.cc:807-822`).
- K8. **The index is the witness, and the link count is not.** A regular-file blob's canonical file is a store path's own, so a holder that no second path shares is at *one* link, and the old statement — every such file at two links or more — is false by design. `EnterVisitor::tryKnown` therefore has no `st_nlink` test: the inode map is only a hint: the current selected holder is validated before a skip, and the path records its own witness, whatever its link count (`EnterVisitor::tryKnown`, `optimise-store.cc`; the `lstat` stays because `readdir`'s `d_ino` can differ from it). The table it consults is one query rather than a walk of `.objects/blobs`: it joins `Blobs`, `Ingestions` and `ValidPaths` and keeps only the first registered candidate in signed `(device, inode, ingestion)` order for each `(id, exec)` (`QueryBlobInodes`, `local-store.cc`; `GitObjectStore::blobInodes`). Only that selected inode is canonical to this shortcut. The physical class precedes the ingestion identity: replacing a path’s complete projection cannot change the selected class, and collecting one donor cannot displace it while a surviving alias retains its own witness. An older store’s noncanonical candidate therefore reaches the hasher and `place`, which selects the same first usable holder and coalesces it; including every candidate here would incorrectly bypass placement. New publication coalesces overlapping ingestions before they become visible. `optimiseCoalescesConcurrentCandidates` enumerates 120 combinations of both executable modes, all six publication orders, all five partitions of three files into inode classes and each possible minimum class; `optimiseKeepsTheCanonicalInodeWhenItsFirstHolderIsCollected` covers collection of a donor after a processed alias retains its witness. A separate relational countercheck enumerates all 4,096 states of three candidates in each executable class, each absent, unnamed, named-invalid or registered; the query selects the first registered physical class independently per mode. A further 1,664 cases enumerate both modes, all 13 ordered partitions of three candidate inodes and all 64 per-mode visibility states, with the other mode present independently; the same cases check complete cursor enumeration without deleting rejected rows. Device and inode coordinates include signed negative values and their minima. Both SQL statements are extracted verbatim from production. **Weaker** as stated, and what replaces it is a witness stronger than the count: the selected row names the canonical inode. For tree bodies and symlink-target blobs, retained holds witness auxiliary addresses independently of their current inode; additional links conservatively retain older representations (K4, K16; `GitObjectStore::sweep`).
- K9. The synthetic root tree of an executable or symlink root is written so that its blob is reachable (`optimise-store.cc:422`, `438`; `merkle-hash.cc:87-98`). **Unchanged in words:** for an executable root the blob reached is now the path's own file, and the sweep's plain-file-root test goes through the index before it falls back to a blob file of the store's own (`GitObjectStore::sweep`, the `!body` branch).
- K10. Trees are written bottom-up, the root last (`ObjectStoreVisitor::directory`; `putRootTree` after the walk), and the sweep removes every unreachable tree in one loop, so a sweep that took a root took every unreachable subtree of it; hence a live root whose object is missing keeps nothing beneath it and does not stop the sweep (`SweepStats::unentered`; `01` §9.10 law 5), while a corrupt tree body does (K6).
- K11. Whether the store places a regular file already on disk — gives it a blob and links it — is decided in one place, `placementOf` (`optimise-store.cc`): a writable file and a file this system does not link (`.app/Contents` on macOS, every file on Windows) are left as written; the on-disk walk skips them and the verifier expects no blob for them. The restore route decides before the file exists and asks `linkableOnThisSystem` directly (its files are never writable, having been canonicalised): two sites, one rule. **Stronger in one respect:** law 3's fourth exception dissolves for a regular file. A placed regular file is no longer linked into a directory of the object store — it *is* the blob's file — so a full directory index cannot leave it unplaced; `ENOSPC` survives for the objects still linked into `<kind>/<xx>/`, a tree body and a symlink-target blob (`writeObjectFile`'s `no_space_on_device` branch, `git-object-store.cc`), and as the condition injected at `place`'s miss branch to drive what an unplaced file costs the verifier (`GitObjectStore::failPlaceWithNoSpace`; `LocalStoreObjectsTest.enospcLeftFileIsReportedNotRepairedForever`). The link limit is untouched and is still law 3's first exception: `EMLINK` linking a holder over a written file leaves that file as written (`place`'s `linkOver`), and `link` answers false on `too_many_links`.
- K12. The sweep and the inode table make the four directories before iterating them (`createDirectories`), so a directory removed after the open does not abort a collection (`LocalStoreObjectsTest.sweepMakesAMissingObjectDirectory`). The 256 shards under each kind are not made there: a shard is made by the first write into it, on the `ENOENT` its link gets (`makeShardOf`, called from `place`, `enterWritten` and `writeObjectFile`), which also remakes one a stray removal took. Every enumeration of a kind goes through one function, `GitObjectStore::eachObjectFile`, which yields both the files in the shard directories and any file lying flat in the kind's own directory -- the layout an earlier, unreleased build of this branch wrote -- so the sweep and the verifier judge a flat file exactly as they judge a sharded one (`LocalStoreObjectsTest.sweepOfAnOwnedPartRemovesOnlyItsFiles`, whose owned part holds one of each). Kind directories must be real directories; a corrupted one is diagnosed without following it. Only real two-hex shard directories are descended. A directory at a valid object identifier is a corrupt leaf in either layout; verification reports it and can remove it only when empty, while the sweep conservatively leaves directories for verification. Unrelated flat directories remain outside the object domain.
- K13. On the local overlay store the merged store directory shows the lower store's `.objects` and `.links` as well, and a write through it lands in the upper layer (an unlink of a lower file is a whiteout, a repair a copy-up). The objects this store owns are the upper layer's, and the collector sweeps those alone (`LocalOverlayStore::sweepObjectStore`; `GitObjectStore::Owned`): the upper layer is enumerated directly, so the lower store's files are never judged; reachability is computed over the merged object store, which is what this store reads, so a tree the lower store holds keeps every blob it names; and an object file whose name the lower store also has goes by an unlink of the upper layer's file, the mount left to be remounted, while one only the upper layer has goes through the mount, which leaves no whiteout there being no lower entry to hide -- `deleteStorePath`'s rule for a store path in both layers, object file for object file. The `.links` removal and the verifier's object checks are still not run (`LocalStore::ownsObjectStore`, false for `LocalOverlayStore`), nor is the materialising copy route taken; the overlay's part follows Linux's merged-mount semantics and is checked by all twelve overlay functional tests on real mounts (`09-performance.md`). **Two things the holder changed here, both weaker, both stated as limits rather than hidden.** (1) *No cross-layer sharing of regular-file blobs.* The index is the *upper* store's own database, and a row is written only by an ingestion of this store (`beginIngestion`, `writeBlobRows`), so a blob that only a lower path holds has no row: this store misses, and writes the file afresh into the upper layer. Before, the lower store's blob file was visible through the merged mount and linking it triggered overlayfs's copy-up — the same bytes in the upper layer either way, but reached by a link and not by a write. Trees and symlink-target blobs are unaffected: reachability is still computed over the merged object store, so a tree the lower store holds keeps every blob it names. (2) *The sweep is unchanged here, and it was nearly not.* The overlay store overrides `sweepObjectStore`, the virtual half of a collection's sweep, and not `sweepObjects`, which is not virtual and which runs the stale-row rule after it (1.5): its stale rows go with every collection as any other store's do. That is a correction, not a decision — while `sweepObjects` was itself virtual the override took the whole method and the overlay's rows were never removed at all, accumulating for ever, a crashed copy's and every collected path's alike. The rows need no narrowing by layer: the index is the upper store's own database and holds no row for a lower path, so the rule reads the same set either way. The overlay suite now also checks real mounts; the decomposition is pinned without one by `LocalStoreObjectsTest.aStoreThatSweepsItsOwnObjectsStillSweepsItsStaleRows`. The sweep's own decomposition -- reachability over the whole object store, removal confined to the part owned -- is pinned by `LocalStoreObjectsTest.sweepOfAnOwnedPartRemovesOnlyItsFiles` and `sweepWritesNothingIntoAnOwnedPart`.
- K14. A schema-10 row's migration checks the NAR hash the row asserts on a tee of the walk that computes the object hash, and writes the column only when they agree (`walkOldRow`); a row whose files are modified or missing is answered as the database has it, and the verifiers report it (`contentMismatch`, `verifyStore`, `nix-store --verify`). A temporary under `.objects/tmp` carries the second of its making in its name and ages by it, since a temporary link's inode is a blob's (`tempPath`); a directory there is a hold (K16), judged by its lock, not its age.
- K16. An ingestion holds every auxiliary address it writes or reuses until registration. A locked directory `.objects/tmp/hold-<pid>-<n>` (`GitObjectStore::Hold`) represents that finite set through link names under exactly `blobs`, `blobs-x` and `trees`: `<kind>/<first-two-hex>/<64-hex-id>`, or `<id>.tmp-<decimal-counter>` for the temporary retained after first publication. Earlier flat `<kind>/<id>` names remain readable. These names denote `(kind, id)`, independently of the old inode's kind, metadata or bytes: repair can remove a corrupt incarnation and publish another while the old entry survives. Only real kind directories and matching two-hex shard directories are descended; a valid claim entry is never descended, even if it is itself a directory. The identifier is exactly 64 lowercase hex digits, optionally followed by `.tmp-` and a nonempty decimal counter. A sharded name must begin with its shard; unrelated hold-root pins and malformed names claim nothing. Under the exclusive auxiliary lock, the sweep removes dead holds first and gathers the addresses of every retained hold, including one whose removal failed. It keeps those addresses independently of link count. Holding a tree keeps that tree alone; descendants are held separately as a materialisation acquires them, and a missing child causes source fallback. Held addresses and the live-root traversal's visited set are separate, so holding a valid root does not suppress traversal of its children. The 36 repair cases enumerate three kinds, three hold-name layouts, owning/`ownRows` handles and reacquisition/no reacquisition; 48 name cases check kind separation, both layouts and valid/invalid temporary suffixes; four cases distinguish held-tree protection from reachable closure (`auxiliaryHoldsKeepTheirAddressesAcrossRepair`, `auxiliaryHoldNamesDenoteExactlyTheirKindAndIdentifier`, `heldTreeAddressesDoNotReplaceReachabilityTraversal`). The inode-kind domain adds regular files, live and dangling symlinks, FIFOs, sockets, character/block devices and directory-shaped claims across all three namespaces and both layouts (48 cells; 12 device-node cells explicitly report unavailable privileges when `mknod` is refused). Nine deterministic nested-verifier cases enumerate three namespaces and absent/sound/corrupt replacements at the initial mismatch diagnostic; six cases keep external files behind kind/shard symlinks untouched, six recognize empty/populated shard directories restored after the initial observation, and twelve diagnose empty/populated directory leaves in both layouts without recursively deleting their contents (`auxiliaryHoldClaimsDoNotDependOnTheOldInodeKind`, `auxiliaryRepairPreservesAConcurrentReplacement`, `auxiliaryVerificationDoesNotFollowNamespaceSymlinks`, `auxiliaryRepairRecognizesARestoredShardDirectory`, `auxiliaryDirectoryLeavesAreDiagnosedInBothLayouts`). A hold is created empty and locked before it receives objects; a sweep that removes it before locking causes construction to retry with a fresh name. A failed removal leaves its surviving claims protected. `EMLINK` or `ENOSPC` refusing a hold says that the object was not held. The writers require a hold argument (`putTree`, `putBlob`, `putRootTree`, and the four ingestion routes), whose owner survives registration. Regular files are protected by their store paths and candidate witnesses instead.

  A protecting directory is shared by strong leases; every path has its own ingestion. `addMultipleToStore` keeps a lease across its batch, and overlapping adds acquire their own leases through a synchronized weak pointer. The final owner releases the directory. `ownRows()` has its own pending index, relative root and ingestion identity, while the three-by-256 shard creation flags belong to the shared directory. Eight direct/batch and completion-order combinations preserve unfinished callers across collection. The hold also carries pending candidate rows, because its lifetime already spans writing through registration; its pending-holder map arbitrates identical regular files within one ingestion, and its directory name witnesses unnamed rows for the stale-row rule.
- K17. **One bounded pool serves hashing and copying.** `CopyPool` is created only at the first directory with sibling work worth queuing; root memo hits and regular roots allocate none. The machine's width is capped at eight. Only the stateless `AllPaths` filter and an accessor that explicitly permits reordered concurrent traversal can use it; arbitrary filters and unproven accessors remain on the caller thread in depth-first order. Permission is implemented only by final POSIX directory accessors, the built-in allow-list and its scopes when both policy and physical accessor permit it, and plain Git accessors without LFS smudging. Git reads remain locked; export-ignore and other unproven wrappers remain serial. Copying additionally requires the caller's explicit permission for its hooks and namer; the public APIs default to serial callbacks, while the two audited production callers opt in. The plain pull hasher and its memo may use the pool; default and caller-supplied visitors and the push driver stay sequential. Only directory children are queued, bounded by the extra worker count; a full queue runs inline. A waiting caller helps only its own child group. Every accepted job is joined before source and destination scopes expire, including on failure. Child reads and result-fold failures are reported in traversal order, a strengthening of the earlier concurrent error behavior. Joining happens outside exception unwinding so helped jobs still observe interrupts. Tree results and case-hack numbering retain their ordered fold; copy jobs seed and restore thread-local sink frames. Memo keys belong to each node's continuation; only named cache facts take its mutex. Holder probes use `_state`; pending rows use 256 lazy shards and the separate writer after 16,384 rows. Registration joins that writer outside the store lock. Tests enumerate widths 1–8, permissions, metadata domains, read/fold failures, nested joins and every binding across the memo flush boundary. See [09-performance.md](09-performance.md) for measurements.
- K15. A path materialised from the store's own objects (`01` §9.10, the second route; `MaterialisingVisitor`, `optimise-store.cc`) is made only from a tree body that hashes to its name (`GitObjectStore::readVerifiedTree`, checked on every read, a corrupt body refused and left for `--verify --check-contents --repair`), from blob files linked as K2 links them (the size unchecked, the route having no other measure of the file; the bytes re-hashed under repair), and from a symlink's blob checked against its identifier; a directory whose objects the store lacks or holds corrupt is removed as far as it was made and read from the source through the one route's visitor. The objects such a copy reads are reachable from the valid paths that entered them (K5), which a collection running beside the copy may delete, so the copy holds each tree body and symlink blob before it reads it (K16; `holdTree`, `holdBlob`) and a missing one falls back. The route is taken under one predicate, `LocalStore::materialisesFromObjects` — a store that owns its object store, not Windows — asked in `fetchToStore2` alone; the daemon, the overlay store and Windows keep the one route.

Not kept, stated:
- X2. `verifyStore --check-contents` checks that every blob and tree file hashes to its name, that every valid path's object hash matches its files, and that the objects a path reaches are present, by the same walk that computes the hash (`verifyObjects`, `VerifyVisitor`), expecting no blob for a file the store does not place (K11). For a regular file it expects a **row** and not a file: `VerifyVisitor::regular` asks `holderOrForget` and reports the file as missing when the index does not know it (`optimise-store.cc`). The bytes are under the verifier's own hands — the file it is walking *is* a file with those bytes — so what the row adds is that the store knows it, which is what a later ingestion needs; a file whose row is missing is a file the store will write again, and that is the defect reported and `--repair` fixes by re-entering the path, which writes the row. The repair says "entered" only when the re-check finds nothing missing. Law 4 is checked per path, and across one interleaving of an ingestion and a collection (K16's test); a path `nix-store --optimise` is entering while a collection runs is counted `unentered` by that sweep, its root live before its trees, and kept whole by its hold.
- X3. A specific delete reclaims no object. The sweep runs on whole-store collections alone (`gc.cc`, `gcDeleteDead`); `nix store delete` sweeps nothing, so a deleted path's objects stay until the next `nix-store --gc`, and its freed-bytes figure counts them as freed (`deletePath`'s two-link credit) — the collector says so. The legacy `.links` directory is removed at every whole-store collection as well (`removeLegacyLinks`).

### 1.6 The order in which the sinks fire

The NAR parser (`archive.cc:211-341`):
- For a regular file: `createRegularFile(path, f)`, and inside `f`: `isExecutable()` if the entry is executable, then `preallocateContents(size)`, then the bytes (`archive.cc:242-261`, `181-201`).
- For a directory: `createDirectory(path, cb)`, the children delivered inside `cb`, in sorted order (`archive.cc:263-326`).
- For a symlink: `createSymlink(path, target)` (`archive.cc:328-337`).
- A colliding name under `use-case-hack` is renamed with the suffix before it is delivered (`archive.cc:298-317`); a name already carrying the suffix is refused on every platform (`292-294`).

`RestoreSink` (`fs-sink.cc`):
- `createSubdirectory` makes the directory, opens it, hands the callback a fresh `RestoreSink` whose `dstPath` is the directory and whose path is `/`, and runs `directoryDone` when the callback returns (`fs-sink.cc:119-155`).
- `createRegularFile` is `beginRegularFile`, the function, `finish` (`fs-sink.cc:267`); `finish` flushes and runs `regularFileCreated` once; the destructor flushes again and starts the write-back (`RegularFileWriter`, `fs-sink.cc:238-266`).
- The generic `createDirectory(path, cb)` default of the base hands the callback the same sink and the full path (`fs-sink.hh:62-64`); `RestoreSink` hands it a sink of the directory's own under `/` (`fs-sink.cc:119-155`). The two conventions differ; `copyRecursive`'s `Copy` visitor keeps a stack of what the callback handed back, seeded with the caller's sink and destination (`tree-traversal.cc`), so it serves both.

The one traversal and its visitors: `traverse` and `NodeVisitor` (`tree-traversal.hh`), `HashingVisitor` and the push adapter `ObjectHashSink` (`object-hash-sink.hh`). The ordered fold is `dumpPath`'s, regular files follow the sink protocol, and directory scopes outlive every child. After stat, the pull driver calls `node(path, stat, descend)`: it may return a known summary or synchronously descend once. The continuation carries a memo key without shared handoff state. The push driver never calls `node` and consumes each child's bytes immediately. Entry names are the tree's own (`unhackName`); node paths retain the accessor's spelling.

The store's visitors (`optimise-store.cc`):
- `ObjectStoreVisitor` (`:178`) writes each symlink's target as a blob and each directory's body as a tree after the hasher returns them, each held by the caller's hold (K16); regular files are the two drivers' business.
- `EnterVisitor`, the on-disk walk (`enterIntoObjects`): `node` tries an inode-map hint only outside repair. A skip requires a currently selected holder matching the file's device, inode, size and canonical metadata, and records this path's own witness (K8), independent of link count. Otherwise it descends, hashes and places the file with its parent temporarily writable; suspicious writable files are left alone.
- `LinkingVisitor` (`:339`), the restore route (`restoreThroughObjects`, `parseDump` → `ObjectHashSink` → this): its `open` stack holds the `RestoreSink` each directory's callback handed back, seeded with the caller's, so a node is created on the innermost sink under `/name` (`at`); `directory` opens `createSubdirectory`'s scope and visits the children inside it, so `directoryDone` (canonicalisation) runs when the scope closes, before the tree is written; `symlink` creates the link then hashes.  A regular file goes to the hasher as it arrives and is held in memory up to `restoreBufferLimit` (`:329`); when the hasher returns the entry, the visitor decides with it in hand: a blob the store holds is linked (`objects.link`, one `linkat`), nothing written, so `regularFileCreated` does not fire; a miss is written from memory and placed.  A file announced or grown above the limit is opened at once (`BufferThenStreamFile`), streamed, finished and placed.
- `MaterialisingVisitor`, the accessor copy (`materialiseThroughObjects`): `node` first tries a verified immutable regular-file identity, except under repair, then asks `TreeNamer` for the root and directories. A named subtree the store holds is made from verified tree bodies, regular-file holders and symlink-target blobs, returning its entry and NAR size without reading below that source node. A recoverable object miss removes the private attempt and calls `descend`; a completed attempt is reconciled with the parent ingestion before returning. `directory` retains the case-hacked disk name around each child, and the shared ordered scheduler joins its scopes (K17). Hooks run for newly written files, directories and symlinks; linking a regular holder fires no `regularFileCreated`.
- `regularFileCreated` fires only for files written, never for files linked (`local-store.hh`, the counting hooks of `LocalStoreObjectsTest`); with `GitObjectStore::link` forced false the four counting assertions fail (`05-validation.md` section 4).

## 2. The semantics checklist

At every call of one of these kinds, the caller writes the assumption as a comment and cites the line that guarantees it. The questions to answer:

**`flock` / `FdLock`.** Who holds which mode now? If the collector holds it exclusive, does my shared attempt fall back to the socket (`gc.cc:107-153`), and do I want a root the running collection honours? Is the lock on this open file description, or on another open of the same file? Does the process that must hold it outlive the operation it protects?

**`linkat` / `link`.** Which errno do I tolerate — `EEXIST`, `EMLINK`, `ENOENT`, `ENOSPC` — and what happens to the file I was about to link in each case? Does the target directory need write permission, and who restores its canonical mode on every exit path, exceptions included? Does the link count I read include the link I am about to make?

**`renameat` over an existing name.** Is the target directory writable? Is the inode I replace still linked elsewhere, or do its bytes vanish? Is the rename within one filesystem (else `EXDEV`, handled at `local-store.cc:1660-1662`, `movePath`)? Is the temporary I rename from removed on every failure?

**`fstatat` / `lstat` / `readdir`.** Do I key a table by `d_ino` or `st_ino`, and does the reader of the table use the same one? Is `st_size` a cheap negative or a proof of identity (it is the former)? Is `st_nlink >= 2` the fact I need? Is the directory being modified while I iterate it? Which of mtime and ctime moves when I link, unlink or chmod?

**`fsync`.** File before link, directory after link; is any metadata changed after the file's fsync? One fsync per file, or `recursiveSync` once? Under which setting?

**`std::filesystem::path::operator/`.** Can the right operand be empty (`"x"/""` is `"x/"`) or absolute (it replaces the left)?

**Containers.** Do I hold a reference or iterator into the element I erase? Do I insert into a map while iterating it?

**`enable_shared_from_this`.** Am I in a constructor, or in a function that may run on a stack object?

**Types as invariants.** Does the token have a user-provided move constructor? Are the members meant to be unreachable `private`, not `protected`? Does the type's constructor do what the type's name promises?

**Destructors and exits.** Does this exit path run destructors — `exec` does not, `_exit` does not? Can the destructor's work fail, and who reports the failure? Is the environment the destructor needs still in place?

**Meson.** Is `--suite` combined with names on one line (the intersection runs)? After a dependency change, does `meson configure build | grep pkg_config_path` show the new path?

**libgit2.** Which layer enforces the rule I rely on — the tree builder (`tree.c:57`), the object writer (`odb.c:1613`), the parser (`tree.c:394`), or the attribute lookup with its flags (`include/git2/attr.h`; `GIT_ATTR_CHECK_INDEX_ONLY` reads the index, where an untracked `.gitattributes` cannot appear, while git itself reads a working directory's attribute files tracked or not; `GIT_ATTR_CHECK_NO_SYSTEM` excludes the system file)? Is `GIT_OPT_ENABLE_STRICT_HASH_VERIFICATION` on, and if not, who verifies what I read?

**Git object formats.** Are the entries ordered as if directory names ended in `/` (`merkle-hash.hh:24-27`)? Does the root carry a mode (it does not)? Does my memo row hold the entry hash or the object hash of a synthetic root, and which does every reader expect?

**Protocols.** Which peer versions and features can be on the other end of this call, in both directions? What does the info carry when the peer is old — `objectHash` absent, so never dereferenced unguarded? Which side pays the shim's walk, and how often?

**Signatures.** Which fingerprint version does each peer verify? Is the NAR hash a version-1 signature needs available where the signature is checked? Does `require-sigs` on the receiver see the info as sent, before anything is stored (`daemon.cc:555-576`, `local-store.cc:1281`)?

**The store directory.** Before adding, renaming or removing anything under it: read the collector's walk (`gc.cc:807-823`), `verifyAllValidPaths` (`local-store.cc:1940`), and every `rmdir`, `ls` and emptiness assertion in `tests/functional`.

**The base class.** Before deriving from or composing over a sink or a store: list every virtual the base calls on child objects (`fs-sink.cc:159-195`), and drive the derived component alone, two levels deep, with a test that fails when the override is removed.
