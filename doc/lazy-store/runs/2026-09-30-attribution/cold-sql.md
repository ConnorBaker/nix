# Pinned cold32 `path:` SQLite statement attribution

Question: What SQLite statement families run behind the extra cold-path local database syscalls? The sealed five-pair benchmark remains the timing authority: f307 versus 8aad cold32 path wall −23.270%, CPU +48.607% (about +1.30 s system and +0.31 s user in its paired resource reduction). This collector run is diagnostic, not a timing comparison.

One fresh-state evaluation used the exact f307 release binary (SHA256 `9c51c263ae7b3f45147180532b8f2ba7b53a2840b86d4039803173ed2fe26661`), fixture, configuration and 32-attribute expression (expression SHA256 `e72731fe38bed1462919c09d624c5fad2e5d9980e311f21a67a9de5b5b4f574a`). It exited 0 in 9.00 instrumented seconds, with load1 0.39→0.93. Full output SHA256 `d1dd4f18ce647e0573b2e52b74c8cd96a08c0b7ca5a05cb2cfc40ebf3daaf440` exactly matches the earlier pinned f307 result. The private database had 3,694 ValidPaths, 56,335 Blobs, 37,121 AuxValues and 3,694 Ingestions, with 4,096-byte pages and 5,250 pages. No source was changed.

The LD_PRELOAD collector intercepts SQLite prepare/step/reset/finalize/exec and libc `fcntl64`/`fcntl`/`pwrite64`/`pwrite`. Counts below are *inside* an interposed `sqlite3_step`, keyed by its unexpanded SQL template and local SQLite connection; reset counts separately establish one `LookupBlob` use per completed query. Every measured `pwrite` (without 64) count was zero.

`LookupBlob` had **56,336 query uses**, each with its own step/reset lifetime. Its 112,682 `fcntl64` calls are **2 per use plus 10** and 72.2% of this run's local SQLite `fcntl64`. This directly identifies the read-lock source route: `GitObjectStore::place` → `LocalStore::blobIndex.lookup` → `SQLiteStmt::Use::step`; the query joins `Blobs`, `Ingestions`, and `ValidPaths`. The prior retained matched FD traces counted local SQLite SHM `fcntl` 43,299→156,044 (+112,745) between 8aad and f307, and their byte-124 read/unlock lock deltas were +56,349/+56,357. The collector's local SQLite `fcntl64` total differs from that earlier f307 SHM total by only **5**; its `LookupBlob` count differs from the *cross-run* delta by **63**. These are separate runs and file/socket classifications, so the small residual is not an exact subtraction proof. A separate 100-miss WAL microcheck reproduced 202 `fcntl64` inside 100 missing-key SELECT steps.

**Write-count cross-run discrepancy:** This collector observed **247,686** `pwrite64` inside local SQLite operations, whereas the earlier f307 `strace` observed **173,455** on local DB WAL plus main DB (166,721 WAL + 6,734 DB). The full outputs and row counts agree, but the write counts do not. The collector's `pwrite` wrapper counted zero calls, and its `pwrite64` wrapper calls the `RTLD_NEXT` libc symbol once, so a `pwrite`→`pwrite64` double count is unsupported. A tiny same-process ptrace/interposer coverage test was attempted but this environment rejected `PTRACE_TRACEME` (`Operation not permitted`). Different instrumentation/scheduling and SQLite page churn are possible explanations, **not established causes**. The table shows only this collector run's SQL-family shares: 66.8% of its local writes inside COMMIT, 31.3% InsertBlob and 1.9% InsertAuxiliary. The collector tags writes by active SQLite connection/statement, not by FD; the earlier FD trace locates local DB WAL/main DB writes, but cannot split them by SQL template. None of these counts assigns causal seconds to the sealed CPU regression.

Evidence: `manifest.json` (exact invocation, configuration, load, hashes), `calls.tsv` (all 236 SQL-operation buckets plus header), `stdout.json`, `stderr`, and `state-retirement-receipt.json` in this directory. ## Source-only follow-up: write discrepancy and lock-removal domain

`pwrite64` double-counting is not supported by the collector source: its wrapper increments one counter then calls the `RTLD_NEXT` `pwrite64` once, and the distinct `pwrite` wrapper recorded zero calls. In this pinned glibc 2.42, `pwrite`/`pwrite64`/`__pwrite64` resolve to the same 32-byte `__libc_pwrite` function at offset `0xdaf40`; disassembly branches to `__syscall_cancel` with syscall number 68. That is a single `pwrite64` syscall route per libc invocation, barring syscall restart details. A same-process ptrace check was unavailable (`PTRACE_TRACEME` denied). The old trace has 166,721 local WAL writes, 6,734 main DB writes, 80 SHM writes and 3 rollback-journal writes: **173,538** local SQLite writes including all targets, versus 247,686 calls tagged to local SQLite by the collector, a **74,148-call** cross-run difference. The old WAL writes split into 85,514 successful 24-byte frame-header writes, 81,204 successful 4,096-byte page writes and 3 successful 32-byte WAL-header writes; its maximum offset was 164,845,376 bytes, close to the configured 40,000-page WAL autocheckpoint span. An additional WAL generation or different page churn under instrumented scheduling could fit the magnitude, but the collector did not record FD or write length per call, so this is **unproved**. The two datasets are different instrumented executions, not a same-run discrepancy.

For eliminating the 112,682 `LookupBlob` lock calls, enumerate the relevant finite outcomes of one regular key at the time of placement:

| State/event | Existing operation | Why an earlier cached/batched answer is insufficient |
|---|---|---|
| Same-ingestion holder exists | `pendingHolder` supplies it before SQLite | Already avoids the SQL query; no remaining lock to remove in this case. |
| A valid published holder exists | Query it, pin/validate its inode and size, then replace the already written file with a hard link | Delaying replacement can retain bytes needed by a later file; that file may hit ENOSPC. For hash-known materialisation, `link` can avoid writing the file entirely. |
| Published candidate is stale, removed, modified or corrupt under repair | Iterate candidates, check the physical inode and optionally hash, forget the bad row | Cached row metadata alone cannot stand for the current file. GC or another writer may change it after prefetch. |
| No candidate exists | Keep this path's private inode/row | A negative cache becomes stale when another process publishes. The current per-file query sees the committed state at that query boundary. |
| Another process publishes/collects during traversal | Per-file query plus physical pin/verification resolves the current candidate; publication later reconciles overlaps | One long read transaction freezes a view for the whole walk and conflicts with the stated no-filesystem-walk-inside-transaction rule. Final reconciliation repairs inode classes but does not restore space or avoid a prior ENOSPC failure. |
| Sharing attempt reaches filesystem link limit or ENOSPC | Leave an exceptional unshared file and do not advertise it as a canonical donor | Whether the attempt succeeds depends on filesystem state *at that operation*, so moving it to the end can change the observed exception. |
| Already-valid path is being optimised/repaired | `endIngestion` reconciles before publishing new rows, while the path's files remain directly observable | Moving the placement decision to publication changes the interval of visible physical inode identity and frees space later. |

Thus no source-only subtraction of the per-file SQLite read transaction is established by this audit. Batching or a persistent read snapshot can remove lock calls, but only by changing when candidate visibility and physical reuse occur; a stronger shared transactional index would be a new representation, not a code simplification. The current `coalesceBlobRows` boundary closes final-publication sharing races but cannot undo a mid-copy ENOSPC caused by deferred reuse. These are obstructions to the proposed shortcut, not a theorem that every conceivable implementation must make two Linux locks per file.
