# Specification: the meaning of sources and store objects, and what lazy materialisation must preserve

This document is the story: what a source and a store object mean, and what evaluator/store implementations must preserve. It states meaning and laws; the mechanism is `04-derivation.md`'s, `05-validation.md` says how the checks are run, and `08-store-model.md` is the local store's model. Section numbers are stable because the code cites them; a gap in the numbering is a section removed. Locators are `file:line` in master at the branch's merge base, or in the libgit2 source where marked; line numbers drift.

## 1. The question

Can evaluation be separated from store mutation so that writes happen later, in bulk, and shared, while everything any observer can see remains exactly what eager Nix shows? To answer that: what does a source accessor mean, which operations on that meaning does Nix use, what must a fingerprint be for the memos to be sound — and what is a store object *one of*, such that its store path is known before its bytes are placed? A **content-addressed value**: one whose name is a function of its meaning (equal name ⇒ equal value), known before materialisation, whose materialisation is a separate, deferrable effect (§2.4).

## 2. Meaning

### 2.1 Trees

The logical value addressed by Git/NAR and materialised in the store is a **tree**: a regular file with bytes and an executable bit, a symlink with a target string, or a directory mapping names to trees. Master already has this as a value type with structural equality and ordering: `fso::VariantT` over `Regular`, `Symlink`, and `DirectoryT<Child>` (`src/libutil/include/nix/util/memory-source-accessor.hh:19-119`). It is exactly the information a NAR serialises; timestamps, ownership, permissions beyond the executable bit, and hard links are not part of it. A directory's entry names are non-empty byte strings other than `.` and `..`, containing no `/`, NUL or literal `~nix~case~hack~` marker, unique and sorted within the directory; `.git` is an ordinary name. The marker belongs to the physical case-collision encoding, not to logical names. The NAR dump writes them verbatim (`src/libutil/archive.cc:131`); the parse validates exactly this, rejecting empty/`.`/`..`/`/`/NUL, the reserved marker and unsorted entries but **not** `.git` (`archive.cc:275-282`).

`SourceAccessor` exposes a representation of the tree. Directory listings and child paths retain its physical spelling, which may contain case-collision markers. Git/NAR folds decode those names under `use-case-hack`; they sort and hash the logical names while reading children by their physical paths. A named view together with that policy determines the logical fold (§8.5).

Reads project this representation: `lstat` gives the node type at a physical path, `readDirectory` its physical entry names, `readFile` the bytes, `readLink` the target, and `pathExists` membership. `resolveSymlinks` uses that same path domain. Three accessor methods are outside the logical value: `getPhysicalPath` is a representation capability, `showPath` is display, and `getLastModified` is input metadata.

A tree is determined by its root: every node is reachable by a listing from the root. An accessor that answers a positive `lstat` for a path no listing reaches does not denote a tree. Section 7.2 says where master has such an accessor and why it does not matter. Directory uniqueness is by logical basename: a directory's slash-suffixed sort key cannot make it distinct from another node with the same name. Decoding an auxiliary tree must reject such duplicates rather than overwrite them. Its body is admissible only when parsing and canonically serialising it reproduces the original bytes: an identifier for another encoding cannot stand in for the canonical tree address. This stored-object requirement does not tighten the generic Git reader.

### 2.2 Partiality and time

- **Partial trees.** A NAR listing with opaque children (`ShallowNarListing`, "not knowing") is a tree with unknown subtrees. Reads force definedness. A name, defined below, always names a total tree.
- **Time.** An accessor over a live filesystem denotes a tree *at a time*. Comparing evaluations fixes their external-input history, including effects deliberately sequenced through `builtins.exec` or a build; it does not make those effects disappear. Where an argument assumes unchanged source bytes, that is a narrower stable-input assumption. `ensureLazyPathCopied` rejects a mounted root whose later copy has a different address (`src/libexpr/paths.cc`); reads that never force that copy need not detect the change.
- **Acquisition.** `mountInput` fixes an expected address, not a snapshot of its accessor. Git's high-level `Input::getAccessor` returns fixed tracked membership with live filesystem bytes: `cachedWorkdirSnapshotsStayImmutableAcrossRenderingAndInvalidation` requires that same returned accessor to observe a later edit, across clean/dirty and gitlink/no-gitlink cases. The `path:` fetcher instead returns an accessor over a registered copy, and raw commit/tarball accessors already denote immutable objects. Under the stable-input assumption these representations agree. Generic fresh-copy tests alone do not forbid a separate fixed value, but freezing Git's returned accessor would contradict its existing test; a later fixed-value boundary at `mountInput` would require an explicit semantic decision and checks. The first hashing walk itself establishes no atomic filesystem snapshot.
- **Growth and replacement.** The evaluator changes its root view when it mounts an input (`EvalState::mountInput`) or adds an allowed prefix. Its lookup cache sits below the growing allow-list, which continues checking admission; it retains positive metadata and link facts but not missing-node answers. A graft is authoritative: even an insert-only input mount can replace an existing node in the physical-store or ambient-host fallback. Missing children under that prefix remain missing; they do not fall through. Explicit mounted descendants require directory ancestors: a blocking ambient file or symlink is replaced by a synthetic directory, and its old descendant view is hidden. `mountInput` therefore invalidates the root view's observations immediately after mounting; the allow-list wrapper delegates this invalidation. Repeating a mount at the same mount point keeps the first mount. Positive metadata and link observations remain cached until refresh; file contents and directory listings still reach the child. A content-addressed mount pathname alone does not establish immutable bytes for an arbitrary raw host occupant (section 8.4).
- **Evaluation epochs.** Source-tree observations and evaluated Nix values have different lifetimes. An input graft refreshes the accessor metadata/naming cache; it does not clear `evalFile`'s parse/evaluate-once memo, cached import resolution or search-path resolution. A previously imported file and unchanged modules depending on its value retain that value until the evaluator's explicit reset boundary. Fresh reads and imports not already memoized use the current tree. Resetting all evaluator caches at a mount would repeat evaluation effects and input acquisition, and selectively clearing one prefix would still not recompute transitive values. This is the existing evaluator contract, not a new source snapshot.
- **Cached naming observations.** The evaluator retains positive metadata, link targets, supplied identities and decisions to supply none. It forwards file reads and directory listings: retaining metadata does not freeze bytes. A present identity remains subject to its producer’s complete-tree naming contract; metadata retention supplies no additional content guarantee. No identity says nothing about node existence and promises no bytes, so unnamed worktrees still require their byte observations. Invalidation discards the old observations after the child finishes invalidating, including exceptional completion; a nested or in-flight observation cannot repopulate the refreshed view with an old fact. This boundary does not name a mutable input or discharge its later materialisation check.
- **Completed copy requests.** An unfiltered, unasserted, reference-free evaluator copy is identified by its resolved source accessor/path, ingestion method and output name. Repeating that request can return its earlier successful result even after a sequenced mutation or admission growth, as the branch base's operation memo does. This is a past operation result, not a claim about current source bytes: another name, method, source, filter or hash assertion must not inherit it. A prior dry run answers only another dry run; a completed copy answers either mode, and a requested copy must root and validate its destination before reuse. Repair bypasses this memo and does not populate it. Mounting or explicitly resetting retires these requests after source invalidation completes, including throws; operations begun in the retired generation cannot populate the new one. This refresh rule corrects the base's broader lifetime. Raw fetches and the mounted-root materialisation check remain independent.

### 2.3 Trees versus store objects

A source **store object** is a tree together with a name, a set of references, and an ingestion method; its store path is a function of the name, the hash of the tree under that method, and the references. References and method live at the object level, not the tree level.

### 2.4 One address, and the serialisation

A tree's address is its **object hash**: the git identifier of its root under SHA-256 — a directory hashing its sorted `(mode, name, child-hash)` entries, a leaf its bytes (`git.cc dumpTree`, `src/libutil/git.cc:138-160`; on the branch `merkle::objectHash`, §9.11 for the three non-directory roots). The store path is a function of that hash together with the object's name and references (`makeFixedOutputPath(name, {method, hash, references})`, `store-dir-config.hh:81`; §2.3): the *path* addresses the object, the object hash addresses the *tree*, and the hash can never stand in for a path even in principle, since it lacks name and references. The address is **compositional**: it is built from the addresses of the subtrees, so a subtree's hash is O(1) once known and a filter/union/graft's is O(the structure it cuts), which is why §8 names subtrees by it. That compositional structure is what gives subtree names at all — a name for a subtree is a name the address already contains.

The NAR is the tree's canonical depth-first **serialisation** (`archive.cc`), the transport of a copy and the form a store hands a reader. Parsing and serialisation round-trip between trees and canonical NAR bytes. Its hash `SHA256(NAR)`, the *flat* hash, and the object hash are distinct total functions of the tree, not mutually invertible encodings. Conversion uses the tree or a recorded pair computed from that tree; it does not invert either digest. Content-address reasoning assumes no relevant collisions in object hashes, NAR hashes or store-path derivation; fixed-length digests are not injective over all inputs. The flat hash is *not* compositional: SHA-256 is Merkle–Damgård, so a subtree sits at a context-dependent offset (BY-REASONING), and the structure of §2.1 is absent from it, so every operation that needs the structure must recover it. New source identities do not use it: it is computed on demand for compatibility (§9.11).

The compositional encoding is name-agnostic: `git.cc` writes and reads any entry name verbatim (`:138-160` dump, `:48-93` parse), so every tree — `.git` included — has an address. The one place in libgit2 that rejects `.git` is the `git_treebuilder` convenience API, a write-path check (`GIT_PATH_REJECT_DOT_GIT`, libgit2's `src/libgit2/tree.c:57-61,488,781-795`); the raw object write (`odb.c:1613`) and the parser (`tree.c:394-441`) validate no names, and `git.cc` never uses the treebuilder, so the encoding's totality is not limited by it. The genuine subtree-naming asymmetries are *fetch-time* (LFS, export-ignore, submodules; §8.3), not a limit of the encoding.

### 2.5 Where the executable bit lives

The executable bit is *in* the leaf: a regular file is *(bytes, exec-bit)* (§2.1), so equal bytes with a different bit are different leaves, different trees, different store paths, and must stay distinct. A git-style representation puts the mode on the *edge* and the blob is bare bytes, so identical bytes are one blob whatever the edge's mode; the two are isomorphic and differ only in **dedup granularity** — the blob layer shares by content, the meaning (and any materialised inode, which carries the mode) splits by *(content, mode)*. The object store of §9.10 keeps that rule: regular files share registered store-path holders indexed by (blob, mode), not separate files under `.objects`, and a link is never made across the bit (`GitObjectStore`, `git-object-store.hh`); master's `.links` pool respected it by hashing each file's NAR, which includes the exec marker (`optimise-store.cc:150-160`). The bit on the edge leaves a **bare root** with no edge to carry it, so the address of §2.4 gives such a root a synthetic one: an executable file or a symlink at the root is addressed as the one-entry tree `{"." ↦ (mode, blob)}`, a directory or a plain file by git's own identifier (`merkle::objectHash`; §9.11). Only a singleton `.` entry with executable or symlink mode is a synthetic root wrapper; auxiliary decoding rejects every other dot-entry shape. No real directory has an entry named `.`, so the root encoding distinguishes these cases: subject to §2.4's collision assumption, the same bytes as a plain file, an executable and a symlink have three addresses. Nothing is conflated: the bit rides the root's entry into the address and the `blob`/`blob-executable` mode onto the edge of any tree; sharing happens only where it is invisible.

### 2.6 The store, a command, and Δ

Nothing here is new; it is what Nix means today, made explicit.

- A **store** S is a finite map from `StorePath` to (file-system object, path info) that is closed under references, together with a build-trace map from `DrvOutput` to `StorePath` and a set of permanent roots. Reference closure is enforced by the database: `Refs.reference` carries `on delete restrict`, and a reference must be valid at registration.
- **Path identity.** A registration map's key equals its description's path. A query accepts a description only when both hash part and name match, except that `Store::MissingName` requests the canonical name for that hash. A hash-indexed cache may retain that canonical description after a wrong-name request; rejecting one full path does not establish absence of its hash. A validity observation alone supplies no path description.
- A store object is **content-addressed** when its path is a function of its name, its content, and its references. Every object evaluation adds is: a `.drv` is text-addressed over its ATerm and references; a source is addressed under the git method over its name and its object hash (§2.4), or — when it has references, which the git path form does not admit — under the NAR method over its name, its NAR hash and its references (§9.9). A build output of an input-addressed derivation is not: its path is a function of the derivation, and its content is whatever the builder produced.
- **Evaluating a command** c against S, under a fixed external-input history, denotes the pair (v, Δc): the command's result and the finite set of store objects, build-trace entries, and permanent roots the reference implementation adds while running c to completion. External inputs are the filesystem, the network, the substituters, the environment, the clock, and the outputs and effects of any program `builtins.exec` runs; evaluation is deterministic given their history. Building is not: the outputs of an input-addressed derivation depend on the builder, so for a command that builds, the reference denotes a *set* of possible pairs, one per run, and (v, Δc) below means any member of it. For a command that only evaluates, the set has one member.
- S + Δc is the union of the two maps. It is well defined because the reference never re-adds a path already valid in S, and two objects at one path in Δc are one object: evaluation's objects are content-addressed, and a build produces each output at most once per run. The references of Δc lie in S + Δc. An already-valid object has no outstanding write unless repair was requested. Its validity does not discharge observations of external inputs: a mounted source used as a reference must still agree with the name assigned to it, even when the referrer already exists.
- **The reference implementation** is master at the commit the rewrite branches from (its merge base), not an older fully eager Nix. Master already defers the byte copy of flake inputs and prints their store paths without copying them, by design (release note "Sources are copied to the store more lazily", `doc/manual/source/release-notes/rl-2.35.md:5-29`; `src/nix/flake.cc:222-225`). Such paths are not in Δc, and (C2) below does not constrain them. Conversely Δc does contain every `builtins.path` source, every `toFile`, and every instantiated `.drv`, because master writes those at evaluation time; for them laziness can reorder and batch the writes but not omit them.

### 2.7 Checks

What discharges the claims of this section. The NAR node set and name domain: `archive.cc:131` (dump, names verbatim) and `:275-282` (parse, rejecting empty/`.`/`..`/`/`/NUL and unsorted entries, not `.git`); `narMaxName = 255` (`archive.cc:215`) against libgit2's `UINT16_MAX` parse limit (`tree.c:423`), so no length gap. The encoding's name-agnosticism: `git.cc:48-93` (parse) and `:138-160` (dump); libgit2 validates names only in the treebuilder (`tree.c:57-61,488,781-795`), not in the raw write (`odb.c:1613`), the parser (`tree.c:394-441`) or strict object validation (`object.c:604`); the branch's tree sink writes trees raw (`GitDirectorySinkImpl`, `git-utils.cc`; `merkle::serialiseTree`), so a tarball carrying a `.git` entry unpacks where the reference fails (`GitUtilsTest.sinkWritesEveryNarName`). The canonical serialisation round trip of §2.4: byte-exact over real store objects, `maxToCheck = 300` per machine, in runs gated by `NIX_TEST_REAL_STORE=1` since the test opens the machine's own store (`GitUtilsTest.storeObjectsRoundTripThroughAGitTree`, `realStorePathsRoundTripThroughAGitTree`, `src/libfetchers-tests/git-utils.cc`), and for `.git` and the name domain directly (`GitTest.tree_encoding_round_trips_dot_git`, `GitTest.nar_accepts_dot_git_and_rejects_dot_names`, `src/libutil-tests/git.cc`). The exec bit's dedup granularity (§2.5): `GitObjectStore`'s mode-separated regular-holder index (§9.10), `tests/functional/object-store.sh`.

## 3. Correctness

An **escape** of a path p is any event after which an agent that reads the store's representation directly, rather than through the evaluator, could dereference p. The representation is read directly by the filesystem, the database, the daemon, builders, other processes, and any reader of the process's output. Instances include: p written to stdout, stderr, or any file (lock files, GC root symlinks); p passed to a Builder or across the daemon protocol; p embedded in the contents of another store object; p returned through the C API as a plain string; p's string context discarded. The list is a derivation aid, not the definition; a missed instance is a violation of (C2), detected by the test below. The eval cache is not an escape: its reader re-validates every cached path against the store and re-evaluates on a miss (`src/libexpr/eval-cache.cc:640-641`), so it is a memo, not an observer.

An implementation of evaluation is correct iff for every command c, every initial store S, and fixed external-input history:

**(C1) Final state on success.** Subject to the explicit semantic corrections in section 5, if the reference can complete c successfully, the implementation completes c successfully with a result v and a final store S + Δc that some run of the reference could also have produced, **up to the renaming the address induces**: the reference names a source by its NAR hash and the implementation by its object hash (§2.4, §9.11), so every source's path differs, and with it the path of everything built from one. Two stores are equal up to the renaming when they hold the same objects — the same bytes once the hash part of every embedded store path is masked, the same content-addressedness, the same reference graph by name — under a name-preserving renaming of paths. For a command that does not build, this is equality with the reference's one outcome; for a command that touches no source it is row-for-row equality. `registrationTime` is excluded from the comparison; it is a wall-clock value today. Temporary roots are excluded; they are process lifetime.

**(C1') Failure.** Subject to those same corrections, if the reference fails c, the implementation fails c with the same error class and message text modulo diagnostics, and leaves a store that is closed under references. The partial set of objects written before the failure is not specified: the reference's partial writes are an accident of evaluation order, and pinning them would forbid every reordering the freedoms below permit.

What the differential check of `05-validation.md` compares: the exit status and the store snapshots, with standard output recorded and reported but not part of the verdict, and standard error not compared at all, because both carry paths, timings and version strings that differ run to run. The judgement is the **renaming view** (`snapshot.py renamed`, `renamed-content.py`, and its strict form, which digests build outputs' bytes too; `tests/functional/differential/README.md`): the loose and strict snapshot views differ on every row of a store the branch wrote, since the `ValidPaths.hash` column the snapshot dumps is rendered `git:sha256:<hex>` by the branch and `sha256:<hex>` by the reference, and they read nothing where a source is renamed. Error classes and message texts are compared where a test script greps for them itself (`05-validation.md` section 3). The builtin sweep of `04` section 1.2 compares message texts directly, in-process.

**(C2) Escape.** Whenever a path p in Δc escapes before c completes, the object named p is already in the store. This holds on success and on failure alike, so an error message that names a path names an object that exists.

Ordering. Master's own printers write to stdout first and force deferred copies afterwards, within the same command (`src/nix/eval.cc:113-126`, `src/nix/nix-instantiate/nix-instantiate.cc:76-98`). (C2) as stated is stricter: the object must be in the store when the bytes leave, so a reader on the other end of a pipe never sees a name before its object. The implementation therefore completes required mounted copies before emitting, buffering output when necessary. Text producers publish eagerly. This is a deliberate tightening relative to master; it changes no final state and no output.

The conditions are checkable without knowledge of the implementation:

- (C1) is a differential test: run c under the reference and under the implementation from the same S and the same external-input history, then compare `queryAllValidPaths`, each `queryPathInfo` minus `registrationTime`, realisations, permanent roots, and the command's outputs — up to the renaming, by the renaming view. The existing functional suite supplies the commands. The test is sound where the reference is deterministic; running the reference against itself first identifies the commands where it is not, and those are compared modulo output contents or listed as exclusions.
- (C2) is a differential test per observation: for any command that emits paths, dereference each emitted path from a second process in both modes and compare.
- (C1') is checked by the same runs on the failing cases of the suite, comparing error class and reference closure.

These tests replace boundary enumeration. A boundary the implementation forgot shows up as a failure on some command, not as an audit gap.

**What (C2) requires, and what it does not.** A returned text-created store path must already name its published object, except in read-only evaluation. This can be satisfied directly by eager publication at the two text producers; it does not require deferred writes, typed strings or an inventory of flush fences. Mounted input materialization is different: copy only where the reference copies, and complete that copy before the corresponding external output. A diagnostic or ordinary string getter must not copy an otherwise unused mount, because that would add an object forbidden by C1. Context dropping does not undo a text write. Real build/output rewriting and mounted-source checks remain separate effects. Section 4 permits reordering but does not mandate it; `04-derivation.md` describes the shared eager Text publisher.

## 4. Freedoms

Everything below is open to the implementation, and this is where performance lives.

- **When** each object in Δc is written: any time before the earliest escape of its path, or before completion.
- **Grouping**: any partition of Δc into batches, in any order consistent with references.
- **Concurrency**: writes may overlap evaluation.
- **Naming**: a path may be computed at any time before it is needed. The hashing walk may be memoised under any key that determines the tree: a git tree OID for an unmodified tree; a tree OID together with the prefix-closed accepted set for a filtered tree. The soundness condition on a memo key is exactly "equal key implies equal tree" (hence equal NAR and equal object hash); a key that ignores something the tree depends on, such as LFS attributes resolved from outside a subtree, is not a key. Section 8 derives the keys.
- **Byte placement**: bytes may reach the store by copy, hardlink, or reflink from any source with identical content, provided the registered hash is measured from the bytes registered.

## 5. Intended differences from master's implementation

The reference is master's documented meaning where it is documented and master's behaviour otherwise. Where the two disagree, the meaning wins, and the departure is listed here so that the differential check can exclude exactly it. The following are explicit corrections to the reference for (C1) and (C1'), not claims of observational equivalence to its implementation:

- **A mount lists at its parent.** Master's mounted accessor resolves any path to the nearest mount and lists an ancestor of a mount point from the underlying accessor alone, with a FIXME acknowledging the missing entries (`src/libutil/mounted-source-accessor.cc:27, 48-52`). Under the tree meaning a graft's parent lists the grafted name and missing ancestors are directories. Master's own release note for lazy trees commits to that meaning: "The evaluator continues to behave as if the copy was performed" (`doc/manual/source/release-notes/rl-2.35.md:5-29`). The observable consequence is in impure evaluation, where `builtins.readDir` of the store directory lists inputs that are mounted but not yet copied, which is what eager Nix showed. Master cannot list the store directory in impure evaluation at all: the store accessor's root listing throws "path '/' is not a valid store path" (`src/libstore/local-fs-store.cc:58-63, 107-110`, the root being special-cased only in `maybeLstat`), and the union propagates the error; the departure is therefore from an error to a listing, and the listing agrees with the meaning.

- **The directories leading to a mount point exist.** The same tree meaning, seen in pure evaluation. Once a store path is allowed, the allow list also allows its ancestors (`src/libutil/canon-path.cc:126-146`), and those ancestors are directories of the evaluation root: `builtins.pathExists /nix` is true and `builtins.readDir /.` lists `nix`, where master answered false and an empty set while `builtins.pathExists /nix/store` was already true. Master's own unit test marks its answer with a FIXME (`src/libexpr-tests/eval.cc`, `PureEvalTest.pathExists`); the test pins the tree's answer.

- **The store directory lists in pure evaluation too.** The same root cause as the first entry, seen under the allow list: `builtins.readDir /nix/store` in pure evaluation returned an error on master and returns the allowed entries on the branch. The local filesystem accessor makes one `queryVisibleValidPaths` request per listing and filters the physical entries by that set. An overlay combines lower and upper visible validity here; `queryAllValidPaths` remains the upper database's ownership query.

- **A fetched input owns its mounted prefix.** A fresh read of a fetched input's `outPath` projects that fetched tree, including its complete child domain. A raw ambient occupant at that pathname is not another part of the input. With a relocated store, a fetched `default.nix` containing `42` and an unregistered ambient file containing `7` previously made an uncached `import` return `7` while the opaque input reference copied `42`. The authoritative graft makes both observations use the input; a host-only extra child stays absent. This can change results and errors in impure evaluation. It does not require host validity or infer equal bytes from the pathname, and it preserves the original host/store fallback outside the graft and the ancestors needed to construct it, including physical-store imports with a relocated selected store. A blocking file or symlink at a proper ancestor is promoted to a directory; siblings survive only through directory ancestry, so the old symlink target cannot leak into the new tree. The release note's source-I/O and `outPath` contracts support this correction (`doc/manual/source/release-notes/rl-2.35.md:9-24`).

- **Shell metadata belongs to the execution store.** After realizing its installables, `nix shell` reads package `bin` links and propagated-package metadata from the store whose paths it executes. A distinct evaluation store or its input/host view cannot supply those bytes. The reference instead reads the evaluator's store accessor; with `--eval-store` selecting a different store, an opaque package present only in the execution store can fail with `InvalidPath`. Reading the execution store corrects this independently of input-graft authority.

- **Completed requests refresh with their source view.** Mounting an input or explicitly resetting source observations retires earlier completed copy requests (section 2.2), including when child invalidation throws. The base's broader memo lifetime can return a result from before that refresh. Repair bypasses this operation memo and does not replace an ordinary request's historical result. These rules govern operation reuse; they do not turn live filesystem bytes into immutable source identities.

The general union still has its own top-down shadowing law (section 7.1), including on the evaluator's unmounted fallback. Making explicit input grafts authoritative does not give a union permission to ignore a contributor or forward an unsound name.

## 6. Excluded, and unchanged by decision

- **Elision**: skipping any object the reference would write on success. Excluded by (C1).
- **The store path's form**, `makeFixedOutputPath(name, {method, hash, references})`, and the **string-context variants** visible to library consumers. The *method* under which the evaluator names a source is a parameter of that form that master already carries (`FileIngestionMethod::Git`); it is the git method for every source, with no setting (section 9.9).
- **Changes to the Nix language** beyond the attributes section 9.11 lists and the tree-view corrections in section 5: every builtin returns on the same inputs what it returns today, `treeHash` is added where a tree is named or asserted, and `narHash` stays as a lazily computed attribute. Slicing, length, matching, and hashing builtins must neither throw nor return a different string because a name was deferred.
- **Dry-run**: `nix build --dry-run` keeps master's behaviour and writes the derivations it classifies; they are in Δc. "Dry-run writes nothing" is a change of meaning for one flag and is not part of this work.

**What is not frozen.** The Store interface, the daemon and serve protocols and the on-disk formats — the database, `.narinfo`, the lock file, the path-info JSON — changed as section 9.11 says: the store's content hash is the object hash, old flat hashes are accepted and verified through a shim and never written as a name, and (C1) is equality up to the renaming the address induces (section 3). The path form and the context variants above are what remains frozen.

## 7. The operations

Four operations on trees account for every accessor combinator on master. Each is defined pointwise on paths, total on total trees where its precondition holds, and monotone on partial ones.

### 7.1 Definitions

- **subtree(T, p)**: the tree at p. Master's `SourcePath` offset. Where p passes through a symlink, the node at p is whatever `lstat` semantics give: the symlink is a leaf, not its target. Its adjoint, the tree that has T at p and nothing elsewhere, is a graft onto the empty tree, not a fifth operation.

- **filter(T, S)** for a **prefix-closed** set S of paths containing the root: the tree with exactly those entries of T whose paths lie in S. Prefix-closure makes the result a tree in the sense of 2.1: every kept entry's ancestors are kept, and a kept directory is kept even if every entry under it is dropped. A predicate f over paths induces S_f = { p : every prefix of p other than the root satisfies f }, the set reached by a top-down walk that prunes at the first rejection. That is what `dumpPath` does with a path filter: the filter is consulted once per directory entry and the walk descends only into accepted entries (`src/libutil/archive.cc:102-108`), so a rejected directory's descendants are never asked about. Composition is intersection: filter(filter(T, S1), S2) = filter(T, S1 ∩ S2), and the intersection of prefix-closed sets is prefix-closed. A representation that keeps only the roots of kept subtrees and fuses two filters by intersecting those roots is unsound: the roots are not the prefix-closed sets. Masking by a set W is filter by the prefix-closed complement of W.

- **union(T1, T2)**: defined top-down, as an overlay filesystem is. At the root, and at every path where both have a directory, the result is a directory whose entries are the merge of both listings, T1 winning name collisions; at a path where the first tree that has a node has a non-directory, the result is that node, and nothing below it exists whatever T2 contains there. A pointwise reading ("T1's node where defined, else T2's") is wrong exactly there: it would let T2's `f/z` exist under T1's file `f`, and the result would not be a tree. Master's `Union`. Master's implementation is pointwise: `maybeLstat` and `readFile` take the first child that has the path, so a file in the first child does not hide the second child's subtree, and `readDirectory` calls every child whose `lstat` succeeds and therefore throws on a directory-versus-file collision (`src/libutil/union-source-accessor.cc:21-59`).

- **graft(T, p, U)**: the tree that has U at p, authoritatively. Recursively, `graft(T, root, U) = U`; for a nonempty path `name/rest`, let D be T if T is a directory and the empty directory otherwise, then replace D's `name` child by `graft(D[name], rest, U)`, treating an absent child as empty. Thus existing directory siblings survive, but a blocking file or symlink becomes a directory and contributes no old descendants. A miss under p never falls through to T. A finite set of mounts applies this rule in ancestor-before-descendant order; repeating one mount point keeps its first binding. This total law covers a relocated store whose *logical* parents are files or symlinks even though its *physical* store has valid directory parents. The earlier precondition excluding those logical configurations was unjustified. Master's `Mounted` is the representation; the branch implements the total graft. Fall-through belongs to union.

Derived: overlay(base, entries, whiteouts) = union(filter(workdir, entries), filter(base, complement of whiteouts)). Not an operation: caching is the identity with metadata.

#### 7.1.1 More than two union layers

For an ordered list of layers, the first node at each path decides its type. If it is a directory, every layer's directory there contributes children; later non-directories there are hidden. Thus an empty directory `A/d`, a file or symlink `B/d`, and a directory containing `C/d/x` yield a union containing `d/x`. Testing each earlier layer independently for an ancestor blocker is wrong: `A/d` already hides `B/d`. The implementation checks ancestors from nearest to farthest, retaining only layers earlier than the first directory observed at each ancestor. That directory's own shallower ancestors are directories, so later layers cannot block them. For two layers this makes the same probes as the ordinary ancestor check.

This ordered operation is not associative: `union(union(A, B), C)` retains `d/x` in the example, while `union(A, union(B, C))` loses it. A list of layers must not be regrouped arbitrarily. `UnionSourceAccessor.everySmallTreeAndNamingCombinationThroughThreeLayers` checks all 18,279 combinations of zero through three layers and naming masks over the 13 valid trees of depth at most two with one permitted child name per depth and absent, plain, executable, symlink, or empty-directory outcomes. Its independent recursive directory merge checks complete membership, types, bytes, listings, and name soundness; the explicit three-layer witness and two-layer probe-order test pin the original failure and the unchanged common route.

### 7.2 Where master's accessors are these operations, and where they are not quite

- `FilteringSourceAccessor` implements `filter` for reachable reads: a listing omits rejected entries (`filtering-source-accessor.cc:38-47`) and `maybeLstat` answers nothing for a rejected path (`:27-30`). It does not check ancestors, so for a predicate that is not prefix-closed it answers positively for a path no listing reaches, which is not a tree. Both producers on master supply prefix-closed sets: the allow list accepts a path when it equals, is an ancestor of, or lies under an allowed prefix (`src/libutil/canon-path.cc:126-146`), and the git working-tree accessor passes the tracked files as prefixes plus the root as the one exact path (`git-utils.cc:1410-1417`). A predicate-based filter such as `builtins.filterSource` reaches the store through `dumpPath`, which prunes (`archive.cc:102-108`), so it denotes filter by S_f. The rewrite's fixed-set filtering accessor (`04-derivation.md` section 1.4) computes S_f by the same pruning walk, so its accessor and its NAR agree.

- `LocalStoreAccessor` is the on-disk store directory restricted to entries whose first component parses as a store path (`src/libstore/local-fs-store.cc:79-93`), further filtered by validity when `requireValidPath` is set (`:52-55`). On master it is not quite a tree: its root exists (`maybeLstat` special-cases it) but cannot be listed, since `readDirectory` requires a store object at every path including the root (`:58-63, 107-110`). The design makes the root listing the set of store objects, valid ones when validity is required, which is what `maybeLstat` already answers entry by entry. In pure evaluation it is `filter(disk, valid)`; in impure evaluation the validity filter is off (`eval.cc:274`, passing `settings.pureEval`), and the leaf is the disk directory as it is. Master's own comment says why: an invalid path in the upper layer of the impure union would throw instead of falling through (`eval.cc:255-273`).

- A git accessor with submodules mounted is a graft of submodule trees over the base tree; a git accessor with export-ignore or LFS smudging is a different tree, not a subtree (section 8.3).

- **The evaluation root as a term.** Let the pure base be `graft(empty, storeDir, filter(disk, valid))`, and the impure base be `union(host, graft(empty, storeDir, disk))`. In either mode, `storeFS` is that base with each explicitly fetched input grafted at its computed store path; `rootFS` is `cache(storeFS)`, enclosed by the growing allow-list in pure or restricted evaluation. Distinct input paths do not nest; repeating a path keeps its first mount. `allow(A, ·)` is filter by the growing prefix-closed set A; `cache` is the identity. Thus fresh reads and names under an input prefix belong to its accessor; away from the graft and its promoted ancestors the impure view retains the original general union. A symlink resolved outside an input returns to that same outer view and access policy.

## 8. Names

### 8.1 Definition and law

A **fingerprint** is a partial function from total trees to names with one law: if two trees have names and the names are equal, the trees are equal, hence their NARs are equal at every path. Master's per-path query `getFingerprint(path)` returning a pair of a path and a name is the naming query for the pair (tree, path), which determines the subtree (`src/libutil/include/nix/util/source-accessor.hh:216-235`).

A content-derived name identifies the complete rendered view. A Git object identifier supplies this identity for an immutable raw tree; a registered store object supplies it through its object hash. The path fetcher assigns its whole-view fingerprint only to the already copied store object, not the original mutable directory. A live Git workdir supplies no revision-derived fingerprint: status may omit comparisons or normalize unequal filesystem bytes. The interface still permits an explicit whole-view assertion, whose producer must ensure the view remains the tree named; later verification cannot justify returning a wrong memo result before it runs.

### 8.2 The rules, derived

Once the operations are fixed, the naming rule for each is forced. Where a rule can be coarser or finer, the coarser is still sound; the finer shares more. The rules below apply to the general case, including the evaluator’s unmounted impure fallback (8.4).

- **subtree(T, p) at q**: if the leaf names subtrees, the leaf's name for the subtree at p/q; otherwise the pair (name of T, p/q). A vanilla Git accessor names supported subtrees by object kind and identifier, declining noncanonical raw entry modes. A NAR-backed or store-path-backed tree names only its root, by hash, and rebases. This single rule is the cross-revision sharing property.
- **filter(T, S) at q**: the pair (name of T at q, canonical form of S restricted to the paths below q). The NAR of the filtered subtree at q depends only on the kept entries below q, so nothing else belongs in the name. The set is data, computed by a pruning walk over directory listings and file types, without file contents. That walk is not free: master fuses it with the dump, so on a cold memo the filtered source costs the metadata walk *and* the dump where master paid the dump alone, and on a warm memo it costs the metadata walk where master paid the dump. Naming by the predicate's identity is rejected: a closure pointer or a lambda's position is not canonical across processes. For a git tree, a synthetic object identifier of the filtered tree is an alternative name that normalises the key without avoiding the cold walk.
- **union(T1, T2) at q**: if q is defined in T1 and is not a directory present in both, T1's name at q; if q is undefined in T1, T2's name at q; if q is a directory in both, the pair of both names at q, or no name if either lacks one. Master's rule, the first child with any name regardless of where the path lives (`union-source-accessor.cc:94-104`), is unsound: a child’s named subtree must equal the whole rendered union, including its domain, before that name can be forwarded. Section 8.4 applies this obligation to the evaluator.
- **graft(T, p, U) at q**: under p, U's name at the relative path. At a proper ancestor of p, name the composite from the base tree at q and the relative graft bindings; if required ancestry discarded that base, use an explicit empty base instead. Every contributing tree must supply its name, otherwise decline. Off the graft's branch, a node below a promoted nondirectory ancestor is absent and supplies no name; elsewhere use T's name at q. For multiple mounts apply the same ancestor-before-descendant interpretation. Master returns T's name alone at ancestors (`mounted-source-accessor.cc:106-112`), which cannot name a subtree changed by a graft.
- **identity**: pass through.

All names share one flat string space. Composite names are JSON arrays beginning `[` (`["filter", ...]`, `["graft-v2", ...]`, `["union", ...]`); Git leaf names begin `git-object-v2:`, content-named leaves begin `nar:`, and input-level names begin their scheme and a colon (`git:`, `path:`, `tarball:`). These prefixes separate producer families; they do not prove soundness within a family.

An entry-derived Git name is admitted only for canonical raw modes `0040000`, `0100644`, `0100755`, `0120000` and `0160000`; other raw modes supply no name. Normalized mode must not select the identity: raw `0160100` can normalize to executable while retaining gitlink behavior, so sharing its blob identifier with canonical `0100755` must not let a memo bypass the former's failing file read. The `git-object-v2:` namespace applies to all Git object names, including roots and empty-directory gitlinks. Retiring every v1 name also prevents reuse of legacy parent answers that may have incorporated an unsound child hit; correcting leaf admission alone would not invalidate those parent memos. The implementation changes the namespace rather than deleting persistent rows or adding cache state.

### 8.3 Consequences

- **Attribute-dependent accessors.** An accessor that smudges LFS pointers or applies export-ignore does not denote a subtree of a vanilla tree; it denotes a different tree, a function of the tree and of attributes resolved from the repository root. Its subtrees have no context-free name, so a subtree name must include the attribute context or be withheld. This is why master's tree-hash memo, written only for tarball roots (`src/libfetchers/git-utils.cc:831-844`; `tarball.cc:512`), is safe, and why a subtree key that ignores the attribute context is not.
- **Submodules.** With submodules mounted, the graft rule names a path above a mount point as (base subtree identifier, the mount points beneath, the submodule identifiers), which is precise. Without mounting, a submodule entry renders as an empty directory (`git-utils.cc:963-965`), which the subtree identifier determines.
- **Input-addressed outputs.** Their store pathname is not a content name. A valid registered output can nevertheless be named by its recorded object hash and a relative subpath; an accessor that does not establish validity must decline this identity. Two stores can hold different realizations at the same input-addressed pathname.

### 8.4 Fetched inputs are grafted above the impure fallback

An explicit fetched-input binding supplies both its accessor and the store path computed from the tree it denotes. Under that prefix, fresh tree reads and names belong to that accessor: this is `graft`, not `union`. The binding does not prove that a raw host occupant has the same bytes, does not turn a mutable worktree into a snapshot, and does not make the pathname a fingerprint. An unnamed input remains unnamed, and `ensureLazyPathCopied` still observes its current bytes and rejects a changed address. Registration and physical presence in the selected store are separate from this selection; ordinary copying still treats an already-valid destination according to the store's no-repair contract.

Outside explicit input mounts and their promoted ancestors the evaluator retains `union(host, store view)`, with the host first. A sibling below a promoted file or symlink has no fallback node; an ordinary directory sibling retains its old view. Synthetic ancestor views have no whole-subtree physical-path capability, and a name for the displaced file or symlink cannot be forwarded as their identity. This is required for imports from an ambient physical store while using a relocated store (`tests/functional/chroot-store.sh`, regression #11503). Both an arbitrary raw host entry and an impure physical-store entry lack a content identity. The general union rule remains: a selected single subtree may forward its child's name; a merged directory requires both contributing names. Agreement on common entries cannot prove equality of complete child domains. The removed `ChildrenAgree` policy remains unsound and is not reintroduced.

This is the explicit result/error correction listed in section 5. Preserving the old host-first selection *inside* an input would preserve the import/copy disagreement, rather than the fetched-input meaning. The implementation uses the existing mounted accessor above the unchanged fallback; it neither probes the host to justify an input's identity nor creates a second naming policy.

### 8.5 Two caveats about what a name is relative to

Names name trees under a fixed interpretation of their representation. The runtime `use-case-hack` policy changes directory-name decoding, so both the in-process address memo and persistent `sourcePathToHash` keys include it for Git and NAR folds. Flat and Text read only root bytes and keep policy-independent keys. Older recursive memo rows without that argument are misses. On case-insensitive filesystems such as macOS's default, physical case-collision suffixes decode to the logical names; a raw listing is not that logical tree. This does not require rereading a producer's established canonical entry merely because a different decoding policy makes its physical witness unreadable: the known value and the availability of a byte witness are separate facts.

### 8.6 The checks

The per-operator laws collapse to one property and a few identities, and the tests are theirs. *Soundness:* over generated `MemorySourceAccessor` trees and terms of the four operations with a content-naming leaf, prefix-closed filter sets and grafts over directory or absent ancestors, equal names imply equal NARs at every path, union names are compared against both child views as well as the merged view, with all 144 combinations of six node cases and named/unnamed children enumerated (`SourceAccessorNaming.equalNamesImplyEqualTrees`, `unionNamesAreSoundAcrossChildrenAndMergedView`, `unionNamesAcrossEveryNodeAndNamingCase`; `FetchToStore.prop_filtered_names_are_sound`). *Sharing:* equal subtrees under a naming leaf yield equal names (`GitUtilsTest.namesFollowTheTreeObjects`, `GitUtils.prop_sharedSubtreesNameAndRenderAlike`). *Identities:* a filtered dump equals the dump with the filter (`FetchToStore.prop_wrapped_dump_equals_filtered_dump`); the top-down union and its names (`UnionSourceAccessor.overlaySemantics`, `fingerprints`); the graft's listing and names (`MountedSourceAccessor.graftIsATree`, `mountOverExistingEntryIsListedOnce`, `mountingTwiceKeepsTheFirst`). *Reference agreement:* the listed differences from master (section 5) are checked against their stated tree meaning; elsewhere the condition remains reference agreement (`tests/functional/mounted-inputs-listed.sh`, `PureEvalTest.pathExists`). `EvalStateTest.mountInputInvalidatesPreviouslyObservedStoreNodes` enumerates 180 combinations of selected-store/ambient-store/relocated-host occupants, impure/restricted/pure modes, five old node kinds including absence, and four fetched root kinds. It checks pre-mount observations, cache invalidation, complete mounted bytes/listings and first-mount retention. `mountedReadsAndCopiesUseTheSameInputDespitePhysicalOccupants` checks twelve registration/presence/location cases, imports, subtree copies, unchanged no-repair behavior and later source-change rejection. `mountedInputsPreserveFallbackBoundariesAndSymlinkEscapes` checks unmounted ancestor hiding, restricted symlink escape and legal nested grafts. `mountedInputsPromoteEveryLogicalAncestorKind` adds thirty combinations of two proper-ancestor positions, five old node kinds and three admission modes, checking directory construction, hidden symlink targets, surviving directory siblings, capabilities and uncached imports. The import/search epoch regression separately preserves already-computed values until explicit reset.

## 9. The naming of sources, the object store, and the one address

### 9.9 The naming of sources

**Meaning.** Every source the evaluator names is named by its object hash (§2.4) under the git content-address method: the store path is `makeFixedOutputPath(name, {Git, objectHash, {}})`. There is no setting and no second name. A store object is still a content-addressed value (§1); a source's path is a function of its name and its tree, and the tree's address is git's.

**The doors.** The sources the evaluator names, each on the git method: `fetchToStore`'s default (`src/libfetchers/fetch-to-store.cc`, `methodRequested.value_or(Git)`; `fetch-to-store.hh` says so), through which mounted inputs (`EvalState::mountInput`, `paths.cc`, a dry run that names the tree), `copyPathToStore` (`eval.cc`, the coercion of a path value) and the installables and flake commands pass; `builtins.path` and `builtins.filterSource` with the default `recursive = true` (`addPath`, `primops.cc`); the `path` fetcher's own copy (`path.cc`: the tree named first by one walk — `objectHashOf` over the filesystem, since a filesystem path has no fingerprint for the memo — and `addToStoreFromDump` under `Git` only when the store lacks the path; the memo then seeded from the object hash the store holds); and the dirty-checkout route of the Mercurial fetcher (`mercurial.cc`, `store.addToStore(..., Git, ...)` with the tracked-files filter).

**The exceptions, each derived from a form rather than chosen.** These keep the NAR method: a source with **references** — the path form with references exists only for the NAR method (`makeType("source", references)`, `store-dir-config.cc`; every other method refuses them), so `addPath` with a non-empty reference set switches to `NixArchive` (`primops.cc`, the comment beside it) and refuses a `treeHash` assertion, since no tree name exists for it; the **committed-revision Mercurial route** (`mercurial.cc`, `store.addToStore(name, {accessor})` on `Store::addToStore`'s default, `NixArchive`); **profiles** (`src/nix/profile.cc`, `FileIngestionMethod::NixArchive`); **`make-content-addressed`** (`src/libstore/make-content-addressed.cc`, the same); and the **explicit methods**, which are the format's content-address methods and not a naming of sources — `builtins.path { recursive = false; }` (the flat file), `nix store add --mode`, and fixed-output derivations in `recursive`/`flat` mode, whose `outputHashMode` and the hashes nixpkgs records under it are untouched. No experimental feature gates the git method, `outputHashMode = "git"` on a derivation, or the reading of git object streams (section 10); a configuration that still names `git-hashing` gets a stabilisation warning.

**Why.** The evaluator's filesystem work is naming and transforming the trees it fetched (§7); under the flat address it cost O(content) whenever the memo was cold, because a subtree's flat hash depends on its position (§2.4); under the object hash a subtree's name is O(1) once known, a filter, union or graft's is O(the structure it cuts) (§8.2), and a git-backed tree's is the identifier git already holds. The bytes that reach the store are the same trees, serialised as NARs on the way (§9.10).

**The memo's rule, and its limit.** A canonical SHA-256 entry supplied by a producer that preserves the canonical encoding already names the node and needs no memo translation. A SHA-256 Git repository alone does not establish this: raw modes, gitlinks and content-changing views may render another tree. For names requiring translation, the tree hash is computed subtree by subtree, and each independently named subtree the accessor names — a git object by its identifier, a filtered subtree by the inner name and the admitted set below it, a grafted subtree by the names of its parts (§8.2) — is looked up in the memo before it is hashed and recorded after, under the key form of the NAR memo with the method `git`. A fingerprint for an entire view, rather than its individual objects, is cached at each requested subtree root; merely visiting its descendants does not eagerly persist a row for each. Such rows cannot survive a change of the view's fingerprint, while independently named Git objects can. A missing row always means computing that subtree, never omitting an object from the store. The hash a row holds is the node's *entry* hash — a blob id or a tree id — for the root of a naming as for a child, since one key has two readers: the naming of a tree reads its root's row and derives the address from the root's mode, and the parent's walk reads the same row as the child's entry. Every seeding of a row from a store object's object hash writes the entry hash, which for a bare executable or symlink root is the blob id and not the synthetic tree's id — such a root, whose blob id is not a function of its object hash, is not seeded and is hashed at its next naming; a row holding the object hash instead would give the parent of an executable file named alone a wrong tree hash (`GitUtilsTest.memoRowsHoldEntryHashesForBareExecutableAndSymlinkRoots` for an executable file and a symlink at a repository's top level; `FetchToStoreTest.prop_memoRowIsTheEntryHashForEveryRootKind` over generated trees whose root kind is drawn, every node of each named alone and its row checked against the walk's entry, and every directory then named again with its children answered from those rows). Two consequences of the meaning. A filter decides a directory's entries, so while one is in force no directory's name is used or recorded, only a file's, whose blob is the same under any filter. And a tree without a name — a plain directory — is hashed whole. A working checkout has no revision-derived content identity. Git status determines tracked membership and change metadata, but its comparisons can ignore changed bytes (`assume-unchanged` and `skip-worktree`), normalize line endings, or consult attributes from outside the working tree. Both clean and dirty working checkouts are therefore read from the filesystem and named from the rendered tree. The input records an absent fingerprint even when it reports a revision as metadata. Commit views with export-ignore or LFS likewise decline a whole-view revision fingerprint because their rendering consults external attributes; a commit view whose export-ignore filter is proved unnecessary can expose its inner immutable Git identities. The export-ignore filter that `builtins.fetchGit` applies by default (`exportIgnore = true`) hides the names beneath it, since the exported tree is not the commit's; it is omitted only for a commit view with the conservative absence proof below. Worktree views keep the requested native wrapper even when it currently hides nothing. Neither naming is conditional on a setting. The fetcher cache is opened lazily and its absence is a miss, since naming a source needs no cache. The functions and the tests that hold each sentence here are named in `04` section 1.6.

**Native export-ignore semantics and conservative commit-filter omission.** The filter decides what a *tree* exports, so its attributes are the tree's own and the repository's, never those of some other tree the same repository happens to hold. For a commit — `builtins.fetchGit { url; rev; }`, a flake input — the tree is the commit's, and the sources are, in precedence order: `$GIT_DIR/info/attributes`; the commit's own `.gitattributes` blob in each directory from the path's up to the root; `core.attributesFile`, or the user's `attributes` on libgit2's XDG search path only when that key is absent (a present null/empty value selects no file and suppresses that fallback); and, for macro definitions only, since `GIT_ATTR_CHECK_NO_SYSTEM` excludes its rules, the system's `gitattributes`, as also the working directory's root `.gitattributes`, which libgit2 parses for macros whatever the flags (`attr.c`, `attr_setup`). That is what `git archive <rev>` reads: it unpacks the tree being archived into its in-core index and reads attributes from the index alone (git's `archive.c`, `unpack_trees` with `index_only`, then `git_attr_set_direction(GIT_ATTR_INDEX)`), and `--worktree-attributes` is what asks for the checkout's files instead. For a working directory — `builtins.fetchGit` of a local path with no `rev` — the tree named is the working tree, so its own `.gitattributes` belong to it, committed or not; the accessor asks with `GIT_ATTR_CHECK_INDEX_ONLY | GIT_ATTR_CHECK_NO_SYSTEM`, whose per-directory source is the index's entry (section 13 records what that leaves out). The filter's answer is libgit2's (`GitExportIgnoreSourceAccessor`, `git-utils.cc`), and libgit2 answers from a fixed list of sources chosen by the flags' low bits (`attr.c`: `attr_setup`, `attr_decide_sources`, `collect_attr_files`): `GIT_ATTR_CHECK_FILE_THEN_INDEX` (0) reads the working directory's file then the index's entry, `GIT_ATTR_CHECK_INDEX_ONLY` (2) the index's alone, and there is no value that reads neither. So the commit lookup runs against a private handle on the same repository, sharing its object database and carrying an empty in-memory index, with `GIT_ATTR_CHECK_INDEX_ONLY | GIT_ATTR_CHECK_INCLUDE_COMMIT | GIT_ATTR_CHECK_NO_SYSTEM`: the per-directory sources are then an index that names nothing and the commit's blob. For immutable commit views, `GitRepoImpl::getAccessor` may omit the wrapper only when no applicable source contains the literal bytes `export-ignore`. Comments, longer names and bytes after NUL conservatively retain native filtering. User-defined macros cannot introduce this attribute without those bytes in a definition; libgit2's built-in `binary` macro does not define it. Only the immutable tree fact is memoized, under the fresh `treeContainsAttribute` domain; old `treeMentionsAttribute` rows are not reused. External sources are checked for every view. Only `~/` expands in `core.attributesFile`; bare `~` and `~name` remain literal, and relative files are anchored at the worktree when present. Unresolved configuration/path selection and selected-file read failure retain the filter; ambiguous search-path spellings are not used to prove absence. Worktree views always retain the requested native wrapper because the shared repository may cache attribute sources or macros that a fresh scan no longer represents. This can add native checks for `exportIgnore = true` worktrees without effective rules; `exportIgnore = false` still skips the wrapper. No current performance result is claimed. The earlier implementation's nixpkgs experiment in `05` section 6 reported 37 298 `newfstatat` reduced to 170, matching its `exportIgnore = false` control; that measurement is historical and does not validate this proof or its cost. The pins: `GitUtilsTest.exportIgnoreFilterIsLeftOutWhenNoSourceNamesIt` (commit omission without attribute bytes, and native worktree rendering), `GitUtilsTest.exportIgnoreDeclaredAnywhereKeepsTheFilter` (each source of a commit alone keeps the filter and hides what libgit2 hides), `GitUtilsTest.committedRevIgnoresTheWorkdirsUncommittedGitattributes` (an untracked `.gitattributes` in every directory below the root, and a staged one, withdraw nothing from a commit), `GitUtilsTest.committedRevHonoursInfoAttributes`, `GitUtilsTest.workdirExportIgnoreSources`, `GitUtilsTest.exportIgnoreWrapperPassesNamesThroughWhenItHidesNothing`, `tests/functional/fetchGit.sh`; the mutations, `05` section 4.

**The shim: old assertions of the flat hash.** An assertion of a NAR hash — `?narHash=` in a flake reference, `fetchGit { narHash }`, `fetchTree { narHash }`, `builtins.path { sha256 }`, `fetchTarball { sha256 }`, a node's `narHash` in a version-5-to-7 lock — is accepted and verified, never used as a name. One function verifies them all: `assertNarHash` (`fetch-to-store.cc`). The `treeAddress` memo answers first when it already pairs the asserted NAR hash with the tree's object hash; otherwise `narHashOf` runs — `fetchToStore2` under `NixArchive` in dry run, which is the existing memoised NAR walk — and the pair is recorded only for a *named* tree, since then both hashes came from the memo of one name and a tree changing between two walks cannot leave a wrong row behind. It is called at `Input::getAccessor` (`fetchers.cc`), which every fetch route passes — `nix flake prefetch`, the registry, the tarball fetcher, and `mountInput` (`paths.cc`), which verifies nothing of its own, since it reaches the tree through `Input::getAccessor` — at `addPath` (`primops.cc`) and on `fetchTarball`'s route (`fetchTree.cc`); a wrong assertion throws the existing `NAR hash mismatch in input` error, exit 102. A consequence stated: a `sha256` pin finds a present tree without a fetch only once a pinned fetch has verified it, because an unpinned fetch computes no NAR hash and so records no pair (`tarball.sh` forces the lazy `narHash` first). `builtins.path` and `fetchTarball` accept `treeHash`, the assertion that costs nothing: the fast path is `isValidPath` of the name it determines, and a locked input is substituted under that name alone (`getAccessorUnchecked`, one candidate; the flat candidate went with the loops).

**The lock file and the input.** An input carries `treeHash`, an SRI SHA-256 string, the object hash of its root (`Input::getTreeHash`; `Input::computeStorePath` is `makeFixedOutputPathFromCA(name, {Git, SHA256, treeHash})`); every scheme that allowed `narHash` allows `treeHash`, in the URL query too, and `isLocked` accepts either. No input carries a `narHash` attribute past verification, lazy or not — serialising an input's attributes forces lazy ones (`attrsToJSON`, `attrsToQuery`), so a lazy `narHash` on the input would be walked and written by every lock, URL and diagnostic: `mountInput` and `Input::getAccessor` replace it by the `treeHash` they computed, the one mutation `checkLocks`' final branch admits. `flake.lock` is version 8 and does not write `narHash` (`lockfile.cc`); versions 5 to 7 are read, a node's `narHash` being the assertion above, verified by one walk when that input is next fetched and replaced by `treeHash`. A lock is written as version 8 whenever it is written at all; a lock whose inputs are all unchanged is not rewritten, since `nix flake lock` keeps an unchanged node without fetching it; so a version-8 lock may still carry a node's `narHash` alone, and every reader accepts either (`LockFile.version8AcceptsANodeWithOnlyANarHash`). An older Nix refuses a lock with `treeHash` or version 8; accepted (section 10).

**The language.** `fetchTree` and `fetchGit` results carry `treeHash` and a lazily computed `narHash` — a thunk that runs `narHashOf` when a program forces it (`emitTreeAttrs`, `fetchTree.cc`), so an expression that reads it still evaluates and one that does not never pays the walk. `fetchTarball` returns a path string, as before (`allowAndSetStorePathString`). `fetchMercurial` returns neither hash (`fetchMercurial.cc`). `nix flake prefetch` prints the tree hash as `hash`.

**The algorithm.** SHA-256, decided (section 10): a store path is a name substitution trusts, and SHA-1's collision resistance is broken. A SHA-1 repository's objects therefore have no SHA-256 identifiers until read; the tree is hashed once per object and memoised under its SHA-1 name thereafter, which is the memo above. The git content-address method admits no other algorithm anywhere it *creates* an object, a name or a derivation output — `checkIngestionAlgorithm` (`src/libutil/include/nix/util/file-content-address.hh`) at each of the eight creation entries, which `LocalStoreObjectsTest.gitMethodRefusesSha1AtEveryCreationEntry` and `git-hashing/simple-sha1.sh` enumerate — and the hasher has no algorithm parameter; what *reads* a description an older Nix made under SHA-1 tolerates it (section 10, the derived decision on old data). Equality with git is pinned under SHA-256: `ObjectHashSink.sha256_identifiers_are_gits` against the ids `git` gives in `simple-sha256.sh`, `GitUtilsTest.sha256IdentifiersAgreeWithLibgit2` against libgit2's SHA-256 object database, and `MerkleHash.blobHeaderAndIncrementalHasher` against git's ids of the empty blob and tree.

**Costs stated.** Naming a source is one walk under the git method where master paid one under the NAR method; a source whose tree is memoised costs its lookups. An old assertion costs one NAR walk on first sight, memoised for a named tree. A tree in a SHA-256 object database — the tarball cache (§9.10) — carries the store's identifiers already.

(3) `tests/functional/git-hashing/source-addressing.sh`, the one-address test: every door names by git's own SHA-256 tree hash; a `sha256` verified by the shim and refused when wrong; `treeHash` finding a present tree from a dead URL; a fresh lock at version 8 with `treeHash` and no `narHash`; a hand-written version-7 lock evaluating, refused with a planted wrong hash, and rewritten at version 8 by `nix flake update`; substitution pinned by `treeHash`. (4) `tests/functional/flakes/old-lockfiles.sh`: a version-7 lock whose inputs are unchanged is left byte-identical by `nix flake lock`. ### 9.10 The store's object store: git objects under SHA-256

**Meaning.** A store object's tree (§2.1) is encoded as Git blobs and trees under SHA-256 (§2.4). The executable bit belongs to the leaf's meaning and to the encoded edge: equal bytes under regular and executable modes have the same blob hash but require different physical files. An entered store path is a view of this tree. Eligible equal regular files share a canonical physical holder in a valid store path; directory bodies and symlink targets are immutable metadata retained by owning ingestions. `ValidPaths.hash` remains the path's root identity, with unchanged references and the protocols of §9.11. Neither a second root table nor a loose-object pathname defines that identity.

**Laws.**

1. *Encoding round trip.* Materialising the objects of any admitted tree gives that tree; hashing the result gives the same root entry and object hash, including executable and symlink synthetic roots. Canonical names, modes, Git ordering, case-hack stripping and NAR framing retain their existing rules.
2. *Route independence.* NAR restoration, accessor copying, entering an existing physical path and materialisation from held objects produce the same object hash, bytes and NAR. The last route applies at every named directory, including an unchanged nested subtree of an edited checkout; it is not restricted to complete store-path roots. Missing usable objects send the private subtree attempt back to its source traversal.
3. *Sharing.* Entered regular files with one inode have the same bytes and executable bit. Eligible files with equal bytes and bit share an inode. The exceptions remain the filesystem's link limit, files under `.app/Contents` on macOS, writable files left unplaced, placement refusal including the existing `ENOSPC` seam, unsupported hard links and paths not yet entered. Windows shares no regular files. Every successful reuse records the recipient's own witness, so collecting the donor does not erase a surviving path's candidate. Concurrent publication reconciles inode classes before exposing new candidates; it does not add an overlap exception.
4. *Presence after entry.* A successful complete ingestion retains all directory bodies, symlink targets and eligible regular-holder witnesses needed by its tree, including synthetic roots and reused subtrees. Regular presence means a valid registered holder with the required mode, not a second copy of its bytes. Auxiliary presence means a complete owned byte value indexed by its typed SHA-256 address. Reuse checks that body against its framed hash and canonically parses a tree. Migrating an old hash row or loading metadata alone does not enter these derived values; verification reports missing availability and optimisation or repair rebuilds it from the path. A read-only old database without the auxiliary table can only miss this cache and still verifies physical path contents.
5. *Collection and ownership.* Private unfinished projections are owned by their ingestion. Completed projections are attached to `Ingestions`, and live leases protect completed-but-not-yet-valid outputs. Whole-store collection removes stale ingestions after dead-lease cleanup; both regular and auxiliary rows cascade with their ingestion. Each recipient retains every auxiliary body it consumed, so removing the donor cannot remove the recipient's copy. Regular files remain owned by their physical store paths. Collection needs no metadata graph walk: a missing or corrupt tree cannot hide a row's ingestion owner or block unrelated stale-row cleanup. A later child acquisition can miss after collection; an acquired body is an owned string and survives deletion of its SQL row. There is no promise of one snapshot for an entire recursive closure.

**Ingestion writes only what the store lacks.** A regular file at or below the existing buffering limit can be hashed before any destination write. A usable holder is linked and `regularFileCreated` does not fire; a miss writes the retained bytes once. Larger files stream to the destination and may subsequently be replaced by a holder. Metadata staging does not change this regular-file contract (`04` §1.7).

**Representation and operations.**

- *Identifiers.* SHA-256 in git's object format, as libgit2 2.0 computes them for the fetchers' caches (SHA-256 object databases are first-class there) and as the store computes them for its own files, which links no libgit2 (`merkle::blobId`, `merkle::treeId`); the two are checked equal. The build takes libgit2 2.0.0-rc.1 with the changes of NixOS/nix PR 16427 (section 10 has the inventory).
- *The tarball cache is canonical SHA-256.* Its directory is `tarball-cache-v4` (`git-utils.cc`): v3 accepted reserved logical names and therefore cannot establish the provenance required by `getKnownEntry`. The canonical writer uses the same checked name insertion as the stored-tree parser; ordinary raw Git writing retains its wider domain. Tarball and archive fetchers remove their single enclosing directory before canonical writing, so a discarded wrapper's name is unrestricted while every retained component obeys §2.1. Existing path normalization, last-entry and hard-link resolution precede that projection; symlink target bytes are unchanged.
- *One ingestion projection.* `Blobs` retains regular holder candidates, keyed by identifier, executable bit and ingestion. `AuxValues(kind,id,ingestion,chunk,body)` retains Directory or Symlink values, keyed by full 32-byte SHA-256 identifiers and owning ingestion. `Ingestions` supplies the common path/lease lifetime. One typed pending map holds both cases; after all workers join, `takeProjection()` transfers owned regular rows and auxiliary bodies for transaction retry. There is no auxiliary file publication or second pending cache.
- *Complete values.* SQL bodies use contiguous 1 MiB chunks from ordinal zero, with every non-final chunk full. An empty body is one non-NULL empty BLOB. A reader rejects malformed sequences and wrong framed hashes, and tries another ingestion's copy without mixing their chunks. One statement snapshot supplies each complete body; the state lock ends before ordinary hashing, callbacks or fallback. The shared tree-body parser checks canonical mode spelling, ordering and sink admission separately from framed hash verification; no re-encoding pass is required (`08` K6).
- *Publication.* `endIngestion` publishes a completed builder output and both projections in one transaction, retaining its path/id completion value while the shared hold starts its next output. Registration consumes those completions without recovering their identities from SQL. Direct registration publishes the completed projection with validity; regular coalescing still precedes holder visibility. Retry retains the complete owned projection, including rewritten regular representatives. Auxiliary reads may use committed ingestion values before validity registration because they verify independent bytes; regular donors still require `ValidPaths`. Failed private subtree attempts publish nothing. A successful reuse stages its bodies into the receiving ingestion.
- *One route.* Accessor and NAR drivers use the same hashing/restore visitors. `MaterialisingVisitor` can answer the root and each named directory through `ObjectAccessor` and `CachedVisitor` on the common traversal, preserving its enclosing logical path and depth without reading below that source node. It creates directories and symlinks and links eligible files, retaining the same NAR size, case-hack numbering and hooks. On a recoverable miss it removes the private attempt before descending through the source. Once a successful attempt's projection begins merging into its parent, a merge error aborts; it cannot turn into source fallback. Immutable regular producer identities may avoid a source read outside repair. Repair bypasses that shortcut; a supplied root/directory namer can still be called, with acquired regular bytes checked under repair. Production fetch-layer repair policy separately controls memo use. Working-directory accessors read current filesystem bytes; clean Git status does not establish immutable byte identity. The named route is enabled only for the local non-overlay store on supported POSIX systems; daemon and Windows paths keep their existing routes.
- *Traversal lifetime.* Hashing and copying share the bounded ordered scheduler of `08` K17. Parallel traversal needs the accessor/filter permissions and, for copying, explicit callback/namer permission. Every accepted child joins before its directory scope ends. The ordered fold determines tree bytes, NAR size and case-hack numbering; a listing's type hints do not determine the result. No SQL transaction spans source or destination callbacks.
- *Checks before registration.* Received content address, object hash, asserted NAR hash and size retain their existing order. Physical path syncing and canonical regular-file metadata are unchanged. SQL auxiliary values follow the existing metadata transaction durability policy; they have no separate per-body file mode or fsync protocol.
- *Collection.* `LocalStore::sweepObjects` first calls the overridable `sweepObjectStore` for bounded legacy-cache/dead-lease cleanup, then unconditionally calls `sweepStaleBlobRows` for both projections. A busy or unsuccessfully removed lease conservatively retains its ingestion; no grace period substitutes for a live lease. The legacy cleanup reads no object body, follows no graph and creates no namespace. It descends only known kinds/shards and removes leaves or empty known directories, never recursively deleting an unknown directory. POSIX deletion is descriptor-relative and no-follow. Windows retains its portable operations, with no claim of equivalent ancestor-race protection.
- *Overlay authority.* SQL rows belong to the upper store's database. Legacy cleanup selects the physical upper `.objects` root and never deletes through the merged view, probes lower objects or creates whiteouts. A merged lease descriptor supplies only lock coordination; a missing view conservatively retains the upper lease. Actual upper removals request the existing remount. Cross-layer regular sharing, named object materialisation, merged auxiliary verification and `.links` removal remain disabled. Physical path verification and upper regular sharing retain their existing behavior.
- *Compatibility.* Schema version 11 installs the current ingestion-owned layout in one migration, retaining eligible rows while adding the regular-row foreign key and `AuxValues`. Five earlier migration markers prevent supported older writers from replaying a rebuild that would remove that foreign key. Older read-only databases without `AuxValues` install no auxiliary provider and miss normally. Older connections' ingestion deletion cascades the derived table through foreign keys. Legacy loose bodies are a retired cache, not a parallel read backend; optimisation rebuilds metadata from valid physical paths. Concurrent old binaries publishing the retired file protocol are not supported by this cleanup. There is no new daemon operation or lower-database provider.

**Limits and obligations.** Unfinished ingestions no longer expose auxiliary bodies globally; completed-output publication preserves sharing before final builder validity registration. This changes optional early cache hits, source callback/read traces and resource-failure points, not just storage syntax. The complete pending metadata and per-ingestion SQL copies consume memory and database pages; fewer filesystem publications alone does not establish lower CPU, RSS or wall time. Cached traversal also rebuilds, serializes and hashes a directory summary after parsing its verified table, and hashes verified symlink bytes again; that added work is unmeasured. Allocation failure, SQLite limits, interruption and I/O errors retain the normal transaction/exception boundaries, but equality with the former auxiliary file's `ENOSPC` soft-miss trace is not established. The general C1/C1′ obligations in §3 remain obligations; a representation proof is not a runtime or universal failure-trace result. Read-only repair reports corruption without writing. Writable repair rechecks an exact bad incarnation transactionally before deleting it, retaining a sound concurrent replacement; diagnostics run after releasing the database lock.

**Checks induced by the meaning.** Retain the independent Git identifier and NAR round-trip oracles, all four root modes, nested/case-hacked trees, every ingestion route, regular inode/metadata/refusal laws, unchanged-subtree zero-source-read checks, repair and missing/corrupt-donor fallback. SQL-specific checks must distinguish empty from absent values, exact/partial multi-chunk bodies, malformed storage classes and ordinals, alternative corrupt/sound incarnations, signed ingestion boundaries, publication retry, multiple builder outputs, reuse followed by donor collection, old read-only stores and failed private attempts. GC tests must retain live/dead lease and creation-window cases, stale rows after an overridden cleanup, and real-overlay lower physical data/merged visibility/no-whiteout assertions. Retired file-count, fsync and graph-counter assertions require new representation oracles; prior passing runs do not validate the replacement. Historical commands and discriminating controls remain in `05-validation.md` and `07-defect-ledger.md`; current executed gates and measurements belong in `09-performance.md`.

### 9.11 One address: the compositional hash as the store's content hash

**The direction.** One address, not two parallel naming functions: consolidating and simplifying the implementation cannot be done by building out parallel implementations, so the store's content hash is the tree hash itself; existing hashes are invalidated, with a compat shim that reads them; the direction is git's.

**Meaning.** A store object has one content hash, its *object hash*: the git identifier of its root under SHA-256 — the tree id of a directory, the blob id of a plain file, and for an executable file or a symlink the tree id of the one-entry tree `{"." ↦ (mode, blob)}` (`merkle::objectHash`, libutil). It is a plain `Hash`, rendered `git:sha256:<hex>` (`ObjectHash::render`, `object-hash.hh`), and it is kept in one place, `ValidPaths.hash`; there is no root record beside it. It is total over store objects — a directory, a plain file, an executable file, a symlink — and distinguishes root encodings under §2.4's collision assumption: object types are in git's header, the two synthetic roots differ in mode, and no real directory has an entry named `.` (the NAR parser refuses it, `CanonPath` asserts it away, and a directory walk never yields it); the partiality of the bare root under git's blob id is dissolved rather than refused. A plain-file root keeps its blob id because master already names single-file sources by it, so a uniform "every root is a tree" definition would have renamed them. The synthetic body is retained in the ingestion's auxiliary projection; its encoding preserves the root mode without making GC depend on graph traversal. For a directory or plain-file root it is git's own identifier. Section 2.4's address is this one; the NAR is a *serialisation* of a tree (`nix-store --dump`, the transport of a copy), and the NAR hash a derived quantity, a function of the tree that is computed by one walk when something old asks for it and is never the name of anything new. Every law of sections 8, 9.9 and 9.10 is stated over this address.

*The names the hash is over.* The object hash is a function of the tree (§2.1), so it is over the tree's own entry names, not over whatever a filesystem made of them. This is not idle: on macOS the NAR restorer renames case-colliding entries as it writes them (`archive.cc`, `useCaseHack`, default on for Apple; the suffix appended before the child is parsed), and `dumpPath` removes the suffix again when it serialises (`unhackedEntries`). A hash computed from the stream sees the tree's names; one computed by walking the written path sees the filesystem's, unless the walk unhacks as `dumpPath` does. Master's `git::dump` reads the directory raw, so its git address of a case-colliding tree on macOS is already not git's, and the import's verification of such a git-addressed path would fail there. Under this section every on-disk computation of the object hash — the after-build walk, `verifyStore`, `nix hash path` over a store path — goes through the same unhacking the serialiser uses, and the check is a tree with `Foo` and `foo` restored through the sink and re-hashed from disk, the two hashes equal (route independence, §9.10 law 2, on the one platform where it can fail). The converse hazard is closed at the parser: a NAR whose entry name already carries the case-hack suffix would unhack to a name the tree never had, so the NAR parser refuses such a name on every platform, not only where the hack is in force — its second collision check, for a hacked name colliding with a name already present, stays, since an upper-case spelling of the suffix reaches it (`NarTest.hackedNameCollidingWithAnUpperCaseSuffixEntryIsRefused`); the four cells of the setting against the two directions — the dump refusing such an on-disk name with the hack off, stripping it with the hack on so that no suffix is ever emitted and the bytes are the tree's own, and the parser refusing it under either setting — are driven together by `NarTest.caseHackSuffixRefusedAndNeverEmittedOnEveryPlatform` — and the serialiser refuses an on-disk name carrying the suffix when the hack is off, since nothing would then strip it; the tree's name domain (§2.1) excludes the suffix.

**The forms, amended.** Each of the forms section 6 froze, with what it carries now, what it carries under this section, and the shim, which is read-side only: the system accepts an old assertion and verifies it, and never *names* anything by the flat hash again.

- *The path's name.* Sources are named `fixed:git:sha256:<id>` as master's git method already names them, for every root kind — a non-directory root by the id of its synthetic tree, no mode word in any rendering (decision (b)). There is no `nar` value and no setting; the `treeAddress` memo is the shim's, not a naming device. Master's explicit methods remain for what asks for them by name — `nix store add --mode nar`, `builtins.path { recursive = false; }`, fixed-output derivations in `recursive` or `flat` mode — because those are the format's content-address methods, not a second naming of sources. Sources with references keep the NAR path form (section 9.9; a `.drv`, a `builtins.toFile` and a `nix-env` manifest carry references in the text form, and were never trees) until the git form admits references, which section 10 leaves open.
- *The database.* `ValidPaths.hash` holds the object hash, rendered `git:sha256:<hex>`; schema version 11, so that an older Nix refuses the store. The object store's root and this column are one fact, kept once, in the database (there is no `roots/` directory; auxiliary lifetime follows ingestion ownership, §9.10). `narSize` stays: it is the serialisation's length, a function of the tree computable from names and sizes alone, and the transfer framing needs it; it is computed in the same walk as the object hash, from names and sizes alone (`merkle::nar::{regular,symlink,root}`, `merkle-hash.hh`; the property `MerkleHash.narSizeEqualsDumpPathLength`), because a zero size is refused by the copy's size check, by the daemon's framing of an incoming NAR, by the serve protocol and by the output-size checks. Existing rows hold NAR hashes, rendered `sha256:<hex>`, and are told apart by their prefix (`ObjectHash::parse`; every reader of a description's content hash takes the two renderings where its own form puts them, enumerated by `ObjectHashLocalStore.everyPathInfoReaderAcceptsBothColumnRenderings` over the eight: one field carrying either rendering for the row and the `--dump-db` record, two fields each admissible alone for the JSON versions, the narinfo and the two protocols under their feature, one field that is always a NAR hash for the two protocols to an older peer); they are the shim's domain: such a row's object hash is filled by one walk of the path on first query (`queryPathInfoUncached`, the old value kept as the info's `assertedNarHash`; written back unless the store is read-only), by `nix store migrate` or by `nix-store --optimise`, after which the row is new. The walk hashes the NAR on a tee of the same bytes and checks it against the row's assertion before anything is written (`walkOldRow`, as `--load-db` checks a registration): a path whose files no longer hash to it is not migrated — the row is answered as the database has it, and the verifiers report "was modified" through the NAR hash as master's did — and a row whose files are gone is answered from the database and left to `nix-store --verify`, which removes it. Unmigrated identities do not block stale-ingestion cleanup; migration alone does not build auxiliary projections (§9.10).
- *Signatures.* Fingerprint version 2: `2;<path>;<object hash>;<references>`. **Both fingerprints are signed where both hashes are known**: `nix store sign` signs version 2 whenever the path's description carries an object hash and version 1 — over `1;<path>;<NAR hash>;<NAR size>;<references>` — whenever the NAR size is known, the NAR hash asserted by the description or computed by one walk of the path; so it works on any store, a cache an older Nix wrote included, whose narinfos carry `NarHash:` alone and get version 1. The binary cache's upload signs both with the cache's own keys, its NAR hash coming from the upload stream. An older client verifies version 1 alone and counts only the signatures it can verify, so it accepts what either of these signs. Signing at build (`secret-key-files` on the local store) is version 2 only: no NAR hash exists there and a walk per output is not paid. Two consequences stated. A path signed at build and copied with `nix copy --to` into a cache that has no key of its own carries its version-2 signature unchanged, and an older client under `require-sigs` refuses it; the remedy is `nix store sign --store <cache> --key-file <key> --all` on the cache, which adds version 1 (`--all` enumerates a `file://` cache; for another cache, name the paths). And a version-1 signature is verified against the path's NAR hash: the one asserted for it — received from an older cache or peer, or an old row not yet migrated — or, for a locally held path whose row holds the object hash alone, the one a walk of the path gives (`ValidPathInfo::checkSignature` takes it as a `NarHashThunk`; `nix store verify` and `copy-sigs` bind one walk per path, `addToStore` its receiving tee — section 10, *a version-1 signature is checked on the stream*). So a version-1 signature made before the upgrade keeps verifying once the row is migrated, `nix store copy-sigs` establishes identity with an older cache's `NarHash:` through the walked hash and copies its version-1 signatures, and `nix store verify --substituter` checks them; the walk is the cost, paid at most once per path and only when such a signature by a trusted key is met. Content-addressed paths need no signature, as now. Which fingerprint versions a description admits is a function of the two hashes it carries, and that function is one place (`ValidPathInfo::signOverEveryFingerprint`, which `nix store sign` calls and nothing else computes): the four combinations are enumerated by `ObjectHashPathInfo.everyDescriptionKindCanBeSigned`, three signable and the fourth — neither hash, so nothing verifiable — refused, with the walk paid for the one shape that needs it. Older clients read a cache written by this Nix unchanged only when the cache signs at upload or was signed by `nix store sign`; for build-signed paths copied into a keyless cache they do not, and the release note says so.
- *The daemon and serve protocols.* A worker feature (`object-hash`, `WorkerProto::featureObjectHash`) under which path info carries the object hash and any asserted NAR hash; serve protocol version 2.9 with the same rule. To a client without the feature the daemon supplies the NAR hash by one walk of the path **per query** (`daemon.cc`, `withNarHashForOldClient`); there is no cache, so the cost falls on the old client, at every query of every path. A path info that reaches `LocalStore::addToStore` with neither hash and no content address describes nothing checkable and is refused (the daemon reaches it through the store).
- *Binary caches.* `.narinfo` gains `ObjectHash:`; `NarHash:` and `NarSize:` are still written, because an upload streams the NAR and hashing it costs nothing (`binary-cache-store.cc`, the tee); and a cache that signs at upload carries a signature over each fingerprint version (the *Signatures* bullet), which is what lets an old client consume it unchanged — the hash field alone does not, since an old client under `require-sigs` verifies version-1 signatures only. A cache with no key of its own carries whatever signatures the copied path had: version 2 alone for a path signed at build, which an old client under `require-sigs` refuses until `nix store sign` is run on the cache (the *Signatures* bullet names the command). Receiving from an old cache, the store verifies the NAR hash on the stream, which also costs nothing, and computes the object hash from the sink's root, which it already does. The per-user narinfo disk cache gains the object hash's column and so changes name (`binary-cache-v9.sqlite`, `nar-info-disk-cache.cc`): every user's cache of narinfo lookups goes cold once and the `v8` file is left, as the tarball cache's was (§9.10, *Limits*). A new client copying to an old cache writes both hash fields. So the hash shim is free in both directions and needs no switch; the signature side needs a key at the upload or a `nix store sign` afterwards, and a cache signed by a build before the dual signing carries version 2 alone until then.
- *The lock file.* Version 8: a locked input carries `treeHash` (the object hash as an SRI string), and `narHash` is not written. Versions 5 to 7 are read: a node's `narHash` is an assertion, verified by one NAR walk of the fetched tree when that input is next fetched, the pair recorded in the `treeAddress` memo, which is the shim's memo and nothing else, and replaced by `treeHash`. A lock is written as version 8 whenever it is written at all; a lock whose inputs are all unchanged is not rewritten, since `nix flake lock` keeps an unchanged node without fetching it; so a version-8 lock may still carry a node's `narHash` alone, and every reader accepts either (§9.9). Older Nix refuses a lock with `treeHash` or version 8 — accepted (section 10).
- *The language.* `fetchTree` and `fetchGit` return `treeHash` and a lazily computed `narHash`, a thunk that walks the tree when a program forces it, so an expression that reads it still evaluates; `fetchTarball` returns a path string, as before; `fetchMercurial` returns neither hash. `builtins.path { sha256 }`, `fetchTarball { sha256 }`, `fetchGit { narHash }`, `fetchTree { narHash }` and the `narHash` URL query accept a NAR hash under the shim, verified by a walk after the fetch, and `builtins.path`, `fetchTarball`, `fetchTree` and flake references accept `treeHash` (a new attribute) as the assertion that costs nothing. The `narHash` inputs in nixpkgs and in the wild keep working, slower by one walk on first sight; nothing in nixpkgs needs to change for this section, and `outputHashMode = "recursive"` is untouched: it is a derivation's assertion checked once per build, not the store's memo.
- *JSON and text.* Path-info JSON version 4 with `objectHash` required and `narHash` optional; `nix hash path` prints the object hash under a mode that names it; `nix-store --dump-db` writes the object hash and `--load-db` reads both: a record carrying the object hash is registered as written, and a record an older Nix wrote is walked once — the object hash the row needs, and the NAR hash and size the record asserts checked on the same tee (`walkOldRecord`, `nix-store.cc`; one read of every byte of a restored store, paid once) — a record whose path does not hash to it reported with both hashes and not registered, the rest registered, the exit status non-zero: per record, as `nix store migrate` reports. *Consequences stated:* master trusted a `--load-db` record and the walk is the cost of verifying it; a bad record loses its own path and no other; an older Nix cannot read a dump this Nix writes; and the values a builder sees in `exportReferencesGraph` under structured attributes are this hash and size (`doc/manual/rl-next/one-address.md`).

**(C1) restated.** The reference writes the same objects up to the bijection of names the new address induces, and the differential's judgement for every source and everything downstream of one is the renaming view (`snapshot.py renamed`, `renamed-content.py`, and the strict view; section 3 states it). Row-for-row equality remains the judgement for everything the address does not touch: derivations from store-path literals, `toFile`, fixed-output builds, the daemon's behaviour — judged by the renaming view too in practice, since the loose view differs on every row of a store the branch wrote (the column's rendering changed, section 3).

**The cost property, restated as a law.** Where stable subtree names identify the source's rendered view (§2.2 and §9.9), naming a tree the memo already knows costs its lookups; naming a tree differing in one file hashes that blob and its ancestors without walking the other named subtrees. The object address introduces no flat hash pass over the new tree. A raw working directory supplies no such names, so establishing its current value still reads its filesystem contents; Git status cannot discharge that observation. A tarball cache identifies the objects as it unpacks them, which is the compositional hashing itself. Copying a named tree into the store still creates its filesystem entries (§9.10).

**The decisions of this section.** (a) The `nar` value goes, not stays as a switch: a switch would be the parallel naming the direction refuses; the shim is acceptance of old assertions, not a second name. (b) The object hash is the root *entry*, mode included — the mode carried inside the synthetic one-entry tree for a bare executable or symlink, so that the content address is `fixed:git:sha256:<id>` for every root kind, no rendering, protocol field, `ContentAddress` or column learns a mode word, git's identifier is the address wherever git has one, and the three bare roots stay three objects. (c) The lock file is version 8 with `treeHash`, `narHash` not written; version 7 read through the shim. (d) `narinfo` publishes both hashes (free); the protocols negotiate; JSON version 4. (e) `outputHashMode = "recursive"` and every hash nixpkgs records under it are untouched. (f) The shim is on by default and has no switch to turn on, only a `nix store migrate` to finish; what may be wanted switchable is *refusal* of old assertions, a strict mode, which is cheap to add and is not assumed.

## 10. Decisions

Each decision with its reason and its consequence. A decision marked *derived* follows from the meaning, from a check or from a measurement; the others were taken and are recorded with their reason. Superseded decisions are not listed; where the reason for rejecting an alternative is part of a decision's reason, the alternative is named there. The open decisions are section 13.

**The frame.**

- **Preserve the store path's form and the string-context variants; upstreamability is a hard goal** (section 6). As first taken this decision also froze the Store interface, the daemon and serve protocols and the on-disk formats; the one-address decision below reopened those (section 9.11), and the path form and the context variants are what remains frozen.
- **No elision:** the store after any successful command equals the reference implementation's, up to the renaming the address induces (section 3, C1). Every text producer retains its write even if its result is discarded.
- **Correctness first, then simplicity, then performance.** Quoted performance numbers come from Linux; macOS gives direction only (`05-validation.md` section 6).
- **A memo row's rule says what it means, not when it is written** (section 9.9). The naming walk holds the rows it names and hands them to the cache in batches, each batch one transaction, because a row per commit was 15 of the 38 syscalls a file a first entry paid (`05-validation.md` section 6). *Consequence:* a batch lost to a crash, or to an exception in the walk, costs the next walk exactly the work this one did and nothing else — which is the whole of what a memo promises. *derived*
- **Dry-run keeps master's behaviour** (section 6): "dry-run writes nothing" is a change of meaning for one flag and is not part of this work.
- **(C2) requires materialization before emission** (section 3). *Reason:* a reader on the other end of a pipe must never see a name before its object. *Consequence:* `nix eval` and `nix-instantiate` copy the mounted inputs they print before printing; the observer's mounted-input modes read present on the branch and absent on master.
- **Ordinary bytes, explicit mounted-output ordering:** text producers publish before returning; command sinks complete required mounted copies before delivering bytes. Ordinary rendering and C getters carry no text-flush effect (`04` §§1.1–1.2).
- **The tree semantics for grafts:** mounts list at their parent and missing ancestors are synthesised as directories, and fetched inputs own their complete prefix above the ambient fallback, recorded as explicit corrections in section 5 and justified by master's release note for lazy trees. *Consequence:* observable in impure evaluation (`builtins.readDir` of the store directory lists mounted inputs not yet copied; master errored) and in pure evaluation (the store directory's ancestors exist once a store path is allowed; master said `/nix` did not exist while `/nix/store` did); `tests/functional/mounted-inputs-listed.sh` and `PureEvalTest.pathExists` pin it.
- **One eager Text publication route, no deferral setting.** `Store::addTextToStore` owns the shared destination/root/validity/reference/publication sequence used by `writeDerivation` and `toFile`. The evaluator write buffer, thresholds, destructor flushes and temporal string/exec tokens are removed. The earlier unconditional-deferral decision was a mechanism choice, not a consequence of C1 or C2. Mounted-input deferral and real realization boundaries remain.
- **Represent current obligations, not historical events.** Arena ownership and build/mount context remain meaningful state. A token recording a past flush cannot prove that later evaluation created no writes. Eager Text publication removes that obligation at its source; tests check real store and output effects instead of retaining no-op wrappers or textual call-site enforcement (`04` §§0–1.2).
- **Reference protection belongs to actual use and publication.** Root a text destination before checking validity; on a write or repair protect its references before backend GC. A valid referrer protects its recorded closure. Protect actual evaluator inputs before mounted-copy/closure work and existing context admission before nested writes, while read-only evaluation and unselected source-filter candidates gain no publication roots. `appendContext` roots each parsed writable key before validating availability and evaluating its flags, including false/empty flags, because either operation can race or trigger GC. The temporary root remains on failure and is excluded from C1/C1′ store comparisons; this narrowly extends the existing all-key validation lifetime.
- *Derived:* the Builder is an escape; no store view or decorator (`04-derivation.md` section 1.1).
- *Derived:* an explicit fetched-input prefix uses the graft naming rule; its unmounted impure fallback uses the general union’s three-case rule. A raw host occupant is not proved equal to an input by the store pathname (section 8.4).
- *Derived:* `filter` takes a prefix-closed set; a predicate induces one by the pruning walk (section 7.1).
- *Derived:* the union is defined top-down, as an overlay is; a pointwise definition is not a tree at a file-versus-directory collision (section 7.1). The earlier child shadows later subtrees at and below a non-directory; this applies to the unmounted impure fallback too, where host and relocated stores need not agree at every pathname.
- *Derived:* the naming query already exists; the graft naming rule is replaced by the derived one (section 8.2). The combined directory-listing callback and known-entry capability extend the accessor interface; the superseded scoped-only listing overload is removed.
- *Derived:* the vanilla git leaf names subtrees by object identifier, which turns master's existing `sourcePathToHash` memo into the subtree memo with no new domain; attribute-dependent variants decline names that omit their rendering context (sections 8.2 and 8.3).
- *Derived:* the filtering accessor names itself from its prefix-closed accepted set, and `fetchToStore` stops treating a filter as uncacheable (`fetch-to-store.cc:64-65` on master).
- *Derived:* mounts add and never replace; allow prefixes are added and never withdrawn (section 2.2).
- *Found:* master cannot list the store directory in impure evaluation (the store accessor's root throws); the branch makes it listable, so the intended difference is from an error to the meaning's listing (section 5; `tests/functional/mounted-inputs-listed.sh`).

**The naming of sources and the one address.**

- **Every source is named by its object hash under the git method, with no setting** (section 9.9). *Reason:* the evaluator's filesystem work is naming and transforming fetched trees, which the compositional address makes proportional to the change; a setting choosing between two naming functions would be the parallel implementation the direction below refuses. *Derived from the renaming check:* a `sha256` given to `builtins.path` or `fetchTarball` asserts the NAR hash rather than naming the flat address, and the pinned fast paths find a present tree through the previously recorded hash correspondence of section 2.4, so a pinned fetch after an unpinned one adds nothing, as on master. *Consequence:* every source's path and everything built from one changes; a binary cache holding a source under its earlier path does not serve it under the new one (the release's blast radius, `doc/manual/rl-next/one-address.md`).
- **SHA-256** (section 9.9, "The algorithm"). *Reason:* a store path is a name substitution trusts, and SHA-1's collision resistance is broken. *Consequence:* a SHA-1 repository's objects have no SHA-256 identifiers until read; the tree is hashed once per object and memoised under its SHA-1 name thereafter.
- **Sources with references keep the NAR path form** (section 9.9), since the path form with references exists only for that method; whether the git form should admit references is open (section 13).
- **The `export-ignore` filter's attributes are the named tree's** (section 9.9). For a commit, per-directory rules come from the commit's `.gitattributes`, not the checkout's files or repository index. Repository/external sources and the worktree root's macro definitions still apply as described in section 9.9. *Reason:* uncommitted per-directory rules must not override the selected commit's rules; this does not erase the explicitly admitted external attribute inputs. *Mechanism:* `attr_decide_sources` offers no flag that selects no per-directory source and no way to make libgit2's index absent, so the commit lookup runs against a private handle on the same repository — its object database shared, an empty in-memory index in place of the repository's — under `GIT_ATTR_CHECK_INDEX_ONLY | GIT_ATTR_CHECK_INCLUDE_COMMIT | GIT_ATTR_CHECK_NO_SYSTEM`. *Consequences:* uncommitted or staged per-directory rules no longer override a committed revision's rules (`doc/manual/rl-next/fetchgit-attributes-from-the-tree.md`), while the admitted macro/external sources remain. The 37 298-versus-170 `newfstatat` result in `05-validation.md` section 6 belongs to the earlier implementation, not the current absence proof. Worktrees retain native `GIT_ATTR_CHECK_INDEX_ONLY` filtering whenever requested; its source limitations remain in section 13.
- **One address: the store's content hash is the object hash; old flat hashes are read through a shim and never written as a name** (section 9.11). *Reason:* consolidating and simplifying the implementation cannot be done by building out parallel implementations, and the store's hash should be the tree's; the shim is acceptance of old assertions, not a second name. The decisions of section 9.11: (a) the `nar` value goes, not stays as a switch; (b) the object hash is the root entry with its mode inside a synthetic tree for a bare executable or symlink, rendered `fixed:git:sha256:<id>` for every root kind; (c) the lock file is version 8 with `treeHash`, `narHash` not written, versions 5 to 7 read through the shim; (d) the narinfo publishes both hashes, the protocols negotiate, JSON version 4; (e) `outputHashMode = "recursive"` and every hash nixpkgs records under it are untouched; (f) the shim is on by default and has no switch to turn on, only `nix store migrate` to finish. *Consequences:* (C1) becomes equality up to renaming for everything downstream of a source; the database schema is 11 and an older Nix refuses the store; an older Nix refuses a lock with `treeHash` or version 8; an older client pays one walk per query for the NAR hash it must be sent; a version-1 signature on a locally held path whose row is migrated is verified by one walk of the path (the derived entry below, *a version-1 signature is checked on the stream*).
- **The git method is stable.** The `git-hashing` experimental feature is removed, with a stabilisation notice in the settings' documentation; `outputHashMode = "git"` on a derivation and the readers of git object streams are ungated. *Reason:* a method that names every store object and every source cannot be optional. Read as stable, not as a change of the fixed-output default: `outputHashMode` still defaults to `flat`.
- **The git method is SHA-256 only.** Refused, with one message naming the remedy (`nix hash path --mode git`), at every entry that creates a git-addressed object, name or derivation output: instantiation of a fixed, floating or impure derivation with `outputHashMode = "git"` and another algorithm (`primops.cc`), `nix store add --mode git --hash-algo sha1` and its dry run, `nix hash path --mode git --algo sha1`, the daemon's `addToStoreFromDump`, a binary cache's upload, the import of a description under the SHA-1 form, and the build of a derivation that names the form (`checkIngestionAlgorithm`, `src/libutil/include/nix/util/file-content-address.hh`). The hasher's algorithm parameter is gone, for the structural fact: no algorithm can be passed to the hasher, so "the git method is SHA-256" is a property of the types and not of eight guards' agreement. *Derived — old data:* what **reads** a description an older Nix made under the SHA-1 form tolerates it: `ContentAddress::parse` and the derivation readers accept `git:sha1`, and `makeFixedOutputPath` still names the form. *Reason:* the collector calls `queryPathInfo` on every path it visits (`gc.cc`, `topoSortPaths`), whose row reader parses the `ca` column (`local-store.cc`, `queryPathInfoUncached`), and under `ca-derivations` it reads every derivation it visits (`store-api.cc`, `queryPartialDerivationOutputMap` → `readInvalidDerivation`, whose fixed-output check computes the path with `makeFixedOutputPath`); `nix-store --verify` reads every row likewise; a refusal in either reader would stop `nix-collect-garbage` and `nix-store --verify` on a store holding one such row or derivation. Pinned by `ContentAddress.sha1GitFormIsReadable`, `DerivationAtermTest.sha1GitFixedOutputReads`, `LocalStoreObjectsTest.sha1GitRowIsReadVerifiedAndCollected` and `git-hashing/simple-sha1.sh`'s planted-row block, each shown to fail under the rejected parser-refusal design by mutation (`05-validation.md` section 4). *Consequences:* a path an older Nix made under the form stays valid, is verified by its object hash, collected, exported and imported (`--export | --import` asserts no content address) and shown by `nix path-info`; it cannot be copied into a **local** store of this Nix (`nix copy`, substitution), whose check of the address it cannot pass, with the remedy in the message; a binary cache accepts it and a local store of this Nix then refuses it at substitution; a `.drv` naming the form is read and shown and refused when built. Recorded in `doc/manual/rl-next/one-address.md`.
- *Derived, confirmed:* **older peers need `git-hashing` for git-named sources.** Master parses `fixed:git:` only under its `git-hashing` experimental feature (master's `src/libstore/content-address.cc`, the `Xp::GitHashing` check in the parser), reached from the worker-protocol reader, the narinfo parser and the daemon's `AddToStore`; the branch names every source that way. So a released Nix refuses a new daemon's or a new cache's description of a source, and a new client's `builtins.path`/`fetchTree`/`path:` input to an old daemon, with `experimental Nix feature 'git-hashing' is disabled; add '--extra-experimental-features git-hashing' to enable it` — confirmed by run against a binary built from master in all three directions. Nothing in new code changes an old binary; the decision, taken, is to accept: operators of mixed fleets set `extra-experimental-features = git-hashing` on the older side; the exact requirement and message in the release note (`one-address.md`, *Older peers and git-named sources*), and pin both directions in `tests/functional/object-hash.sh`, without the feature and with it. The alternative — naming sources under the NAR method again for compatibility — is the second naming this section refuses (section 13).
- **The memo's rows are written in key order, into a page cache large enough to hold a walk's own.** A memo key is a content address -- a Git node's fingerprint is that node's own object id (`GitSourceAccessor::getFingerprint`) -- so a naming walk's probes and inserts are scattered over the whole of its part of the index, and a batch inserted as it arrives dirties every leaf it touches until its commit. *Consequence:* a first entry of 40 000 files wrote 42 126 pages where the rows are eight megabytes; sorted, and with sixteen megabytes of page cache, it writes fewer than 20 000 and reads one page a file less (`05-validation.md` section 6). *Rejected alternative:* one range query per fingerprint at the walk's start, which the design asked for and which is not possible here -- the walk's nodes share no key prefix, each being named by its own object id with the path always the root, so a range over a fingerprint selects the one row the point query already selects.

**The object store.**

- **The store's object store: git objects under SHA-256** (§9.10). One encoding identifies tree metadata and regular contents. The executable bit remains on the encoded edge, with different physical inodes for the two regular modes. Indexed holders supply sharing; ingestion-owned SQL supplies auxiliary bytes. The tarball cache uses the same canonical identifiers. Neither the old NAR-keyed `.links` table nor an auxiliary pathname is a second content identity.
- **libgit2 2.0.0-rc.1 with the changes of NixOS/nix PR 16427:** strict hash verification off on reads, no delta search when unpacking into the tarball cache, the `pack.window`/`bigFileThreshold` configuration fix, and the zlib-ng patch. *Consequence:* a blob read from a fetcher's object database is not re-hashed by libgit2, so whoever enters it verifies it (section 9.10, law 1).
- **No compression setting: the pack builder decides per object.** Whether zlib bails out early on incompressible content was checked: it does not — deflate at any level above 0 runs its match finder over every byte and only afterwards emits a stored block for what did not shrink (`deflate.c`, `configuration_table` and `deflate()`'s dispatch; `trees.c`, `_tr_flush_block`'s `stored_len + 4 <= opt_lenb`; zlib-ng's `deflate_quick`/`deflate_medium` are faster implementations of the same contract), so incompressible input costs the full work and saves nothing. libgit2 compresses every pack object through one `git_zstream` it resets per object (`pack-objects.c`, `write_object`), so the decision can be made per object and cheaply. The fourth patch (`packaging/patches/0004-pack-compression-heuristic.patch`): before each object is written, 4096 bytes of it, in eight 512-byte slices spread from its start to its end, are deflated at zlib's fastest level through a second stream kept for the purpose; the object is deflated at zlib's default when the sample shrinks by 5 % or more and stored (level 0) otherwise; an object no longer than the sample is always deflated, since the probe would cost as much as the deflation it decides and deflate's stored-block fallback bounds the loss to a few bytes. *Rejected alternative:* a fetcher setting supplying a compression level, measured: nothing gained and two and a half times the unpacking time for incompressible content against a 60 % smaller cache for source text [unverified: measured during the work; the run is not in the tree] — and there should be no settings. Checked by `GitUtilsTest.packsStoreWhatWouldNotShrink` (a 4 MB pseudo-random blob is written with the level-0 zlib header and within 1 % of its size; a 4 MB text blob with the default header and under half).
- **The object store is unconditional, and the decision comes before the write.** `auto-optimise-store` has no meaning: every local store enters every path, and `nix-store --optimise` remains as the migration of an older store's paths and the removal of `.links`. *Reason:* sharing identical files is what a local store is, not a mode; and a measured slowdown of the write-then-link discipline — which decides after the bytes are on disk and must undo a write on every hit, three and a half times the write on APFS [unverified: measured during the work; the run is not in the tree] — had no reason to be paid: the store's composite decides before the write (section 9.10; the mechanism, its limit and its measurement are `04-derivation.md` section 1.7).
- *Derived:* **`auto-optimise-store` is accepted and ignored with one warning**, from `nix.conf` and the command line (`RemovedSetting`), for `true` alone — `false`, which the build hook hands its child for every setting, is silent — and once per top-level process: the hook child, which re-reads the configuration in `initNix()`, warns nothing (`Settings::configurationDiagnosedByParent`, set by `main.cc` before the configuration is loaded; every other `nix` process is its own top-level process from the user's view). *Reason:* the release note promises a warning, and a flag that had become an error broke it; the second warning of a `nix-build` was located by run in the child's own configuration read, not in the hand-off. *Where it appears* follows the repository's convention (`excludedFromFullSerialisation`, as `DeprecatedWarnSetting` has it): out of `nix config show`'s key=value dump, which is the effective configuration; in the JSON, which is the registry the manual's settings page is generated from; and by name. Pinned by `tests/functional/optimise-store.sh`.
- **Both fingerprints are signed where both hashes are known** (section 9.11, *Signatures*): `nix store sign` signs version 2 whenever the description carries an object hash and version 1 whenever the NAR size is known, the NAR hash asserted or computed by one walk; the binary cache's upload signs both; signing at build is version 2 only. *Reason:* an older client verifies version 1 alone and counts only the signatures it can verify, so a cache carrying version 2 alone was refused under `require-sigs`. *Consequence:* a build-signed path copied into a keyless cache carries version 2 alone until `nix store sign` runs on the cache; the release note says so.
- *Derived:* **a version-1 signature is checked on the stream when the description asserts no NAR hash.** `addToStore(info, source)` restores such a path, hashes it on the tee and makes the same check with the stream's hash in the assertion's place, removing the path when it fails; nothing is registered before the check. `nix store verify` and `copy-sigs` walk a path once for a trusted key's version-1 signature that version 2 does not verify. *Reason:* without it every path substituted from a NAR-hash-only cache is untrusted once stored, and `nix copy` of it to a `require-sigs` daemon is refused. *Stated cost:* untrusted bytes reach the disk before the refusal; the path's files are removed at once (`deletePath`, `local-store.cc`), and the blobs and trees the restore entered stay in `.objects` until the next whole-store collection sweeps them.
- **Whole-store collections clean legacy namespaces and stale projections.** A specific delete removes its selected physical paths and validity records without running those cleanup phases. Regular-file reclamation follows surviving links; later SQL row removal has no immediate database-file-shrink guarantee. The collector skips `.objects` and `.links` in its ordinary directory walk and handles them through their owned cleanup paths.
- **`max-free` uses estimated successfully removed last-link bytes.** POSIX `deletePath` adds a non-directory entry's observed size only after successful unlink and only when its observed link count was one. A second link can belong to another live store path, so it receives no speculative credit. An ENOENT or other unlink failure adds nothing for that entry; earlier successful removals retain their estimates. This aligns the stopping threshold with surviving regular holders, but open descriptors, concurrent changes, sparse/compressed allocation and non-regular entries prevent an exact immediate-disk-space guarantee. Windows retains its zero-byte estimate. Auxiliary SQL page reclamation is not included as a per-body file estimate.
- *Derived:* **collection follows ingestion ownership, not auxiliary reachability** (§9.10 law 5). A missing, corrupt or unmigrated tree identity cannot block stale SQL projection cleanup. The collector removes dead leases first; a surviving lease conservatively retains its ingestion. Physical store-path collection and reference closure remain the authority for valid paths.
- *Derived:* **the ingestion's `autoGC()` runs before the restore**, master's order (`local-store.cc`); between the restore and the registration, inside the window, the first add that triggered `min-free` swept its own trees. Not a race but a call order. And after the validity check where one precedes the restore: the in-memory route of `addToStoreFromDump` knows the path's name before it writes, so an add whose path is valid already runs no collection (`LocalStoreAutoGCTest.inMemoryAddOfAValidPathRunsNoCollection`); the spilled route learns the name from the restored tree and pays the check whatever the outcome.
- *Derived:* **a complete projection has one owner and one publication boundary** (§9.10; `08` K16). Workers retain regular witnesses and auxiliary bytes privately, then transactionally publish them under one ingestion. A locked lease protects completed outputs before validity registration and remains shared by strong `ownRows` views. No lifetime-wide database or namespace lock spans traversal; the collector never waits for an active lease. Optional globally visible auxiliary hits before completion are not preserved.
- *Derived:* **the collector removes a legacy `.links` directory at every whole-store collection.** Master unlinked its dead entries every collection; one deleter, `removeLegacyLinks`, for the collection and for `--optimise`; every entry is a hard link to a file a store path also links or a dead one, so nothing is lost.
- *Derived:* **`nix-store --optimise` writes an older row's object hash and reports what it entered.** An older row is migrated by the verified walk first (`walkOldRow`, the entry below) and the path then entered by the on-disk walk; `recordObjectHash` is the one write, shared with `migratedPathInfo`; a report of all zeros is a no-op, and a migration says how many files it entered and rows it wrote.
- *Derived:* **a schema-10 row's migration checks the NAR hash the row asserts, and never writes the column from bytes that fail it** (section 9.11, *The database*). The question first: what must every reader see when the bytes do not hash to the row's assertion? Master returned the row on every query and left the corruption to `--verify --check-contents`, `nix store verify` and `--verify-path`; the collector queries every path it visits, so a query must not throw; and an info with `assertedNarHash` and no object hash is the shape every reader already handles (a schema-10 row before its first query, an old peer's description). So: the walk hashes the NAR on a tee (`walkOldRow`, as `--load-db` checks a registration) and on a mismatch writes nothing; the row is answered as the database has it; the verifiers report "was modified" through the NAR hash with master's remedy; `nix store migrate` counts the path failed naming both hashes; `nix-store --optimise` migrates an older row by the same verified walk before entering it (an older path read twice there, once to migrate and once to enter; a row this Nix wrote is read once) and does not enter a modified one. Writing the walk's hash would bless the corruption for every later check.
- *Derived:* **a schema-10 row whose files are gone is answered from the database and belongs to `nix-store --verify`.** The row is valid and its files are missing — the state master's `--verify` (without `--check-contents`) finds and removes ("disappeared, removing from database"), and master answered every query from the row. So the migration returns the row as read when the directory is absent or a file of it is (`ENOENT`) while the row is valid; `nix store migrate` and `--optimise` report it naming `nix-store --verify`; a row that is gone is still `InvalidPath`, the collector's doing. The collector's `unmigrated` note names both commands that migrate rows and the verifier for what they cannot.
- *Derived:* **the collector reads a dead row without migrating it.** The collector's dead set needs a row's references (`topoSortPaths`) and, under `keep-derivations`, an output's deriver — row fields both — so it reads those rows as the database has them (`queryPathInfoUnmigrated`, `topoSortPathsBy`, `gc.cc`) and a schema-10 row on its way to deletion is not walked first; the live rows its closure reaches are still migrated by `computeFSClosure`'s queries, which is right, since they are kept. *Reason:* the migration reads and hashes every byte of the path (`walkOldRow`), so the first collection of an upgraded or `--load-db` store paid a walk of its whole garbage before deleting it (800 MB dead path: 0.71 s against 0.15 s, `05-validation.md` section 6). *Consequence:* none to the laws — the row is deleted; a dead path the serialising walk would refuse (an unsupported file type) is now deleted where the collection failed before. Pinned by `LocalStoreObjectsTest.deadSchema10RowIsDeletedWithoutAWalk`.
- *Derived:* **a `path:` input outside the store is named first and copied only when the store lacks the tree.** `PathInputScheme::getAccessor` (`path.cc`) hashes the tree by one walk (`objectHashOf` over the filesystem accessor; a filesystem path has no fingerprint, so no memo answers and every byte is read, `04` section 1.5), takes a root on the name and copies — the dump, the restore, the links — only when `isValidPath` says the store lacks it. *Reason:* master and the branch dumped and restored a `path:` input on every evaluation whenever the path was not itself a valid `-source` store path — the local-development pattern `inputs.x.url = "path:../x"`, and a flake evaluated as `path:<dir>`; the copy of an unchanged tree was the whole of that cost. *Consequence:* a miss pays the naming walk and the copy, two reads of the tree; the window between the naming and the copy is every `builtins.path`'s (a tree edited meanwhile is copied as it then is, and the add computes the address from what it writes); `lastModified` is the same tracked walk's mtime as the dump's. Pinned by `tests/functional/flakes/path-input-copies-once.sh`; the release note is `doc/manual/rl-next/path-input-copies-once.md`.
- *Derived:* **a temporary under `.objects/tmp` ages by the second in its name**, since regular pin links share an inode whose change time later links can advance. A hold directory is judged by its lock, not its age. Regular placement refusal, including the existing injected `ENOSPC` case, still leaves an unindexed file that verification reports and repair retries; auxiliary SQL publication is a separate resource boundary.
- *Derived:* **the local overlay store mutates only its own layer** (§9.10; `08` K13). Upper SQL owns both projections. Legacy-cache cleanup selects the physical upper namespace and sends only an after-removal notification to request remount; the merged namespace is used solely for lease locking, never deletion. Lower physical data and merged visibility must survive without whiteouts. The nonvirtual stale-row phase runs after the overridable cleanup. Cross-layer regular sharing, direct named materialisation, merged auxiliary verification and `.links` removal remain disabled; enabling any requires its own authority proof and real-mount tests.
- **Every held named subtree can be materialised from store values** (§9.10, *One route*). `fetchToStore2` consults the root and directories, not just complete store-path roots: a known directory uses verified owned metadata and regular holders, while an unusable child causes the existing private-attempt source fallback. Each successful receiver retains its own complete projection. The resulting object hash, NAR, physical sharing, hooks and case-hack spelling retain the same contracts; regular bytes are checked under repair. Named reuse stays within the memo's stated input window and requires actual destination availability. Creating directory entries and acquiring regular holders still visits the tree; this is not O(change) filesystem materialisation. Daemon, overlay and Windows routes stay unchanged. Historical route timings remain in `05`; the current empirical comparison is `09`.
- **Hashing and copying share a bounded ordered pool** (section 9.10, *One route*; `CopyPool`, `thread-pool.cc`; `08` K17). Eligible directory children run on workers and results are folded in traversal order. Accessor, filter and callback permissions determine eligibility; the output does not depend on the pool width. The following measurements describe the earlier copy-only scheduler. *Reason:* the first entry of a new tree is the operation the object store does not make cheaper, and after everything else had been taken out of it the remainder was the kernel work of creating and linking the files — 0.66 to 0.72 s for 40 000 files on the measurement's filesystem, of which 0.19 to 0.21 s is the `linkat` that the sharing *is*. That work is per directory and ext4 serialises it per directory, so it parallelises across directories and nowhere else (the previous entry's floor, and the one before it, which measured that within a directory it buys nothing). *Measurement* (`05-validation.md` section 6): the first entry of 40 000 files falls from 1.51–1.69 s to 0.83–0.95 s, against master with sharing off at 1.37–1.49 s and master with sharing on at 1.73–1.95 s — **below master with sharing off by about two fifths**, over six trials in two orders. At 4 000 files the four are within the machine's noise (0.15–0.19 against 0.18–0.22, 0.20–0.24, 0.22–0.23). The syscalls are the same work on other threads: 21.78 a file against 21.72 sequential, 27.11 for master with sharing off and 36.11 with it on; the system time rises from 1.18–1.20 s to 1.62–1.95 s while the wall time halves, which is what overlapping kernel work looks like. *The source constraint:* `GitSourceAccessor` holds its repository lock throughout a blob read, including the sink callback; libgit2 does not generally permit concurrent access to one repository handle. The scheduler does not clone handles or remove that lock. POSIX accessors that explicitly permit independent traversal can overlap their reads and hashing. Plain pull hashing and the memo now use the same scheduler as copying; default or caller-supplied visitors and NAR push traversal remain sequential. *What is kept:* the set of files, their bytes, modes, link counts, the tree body, the NAR size and the case hack's numbering, all pinned against the one-thread copy on generated trees and on a wide fixed tree, from an in-memory source and from the filesystem (`LocalStoreObjectsTest.parallelCopyIsTheSequentialCopy`, `prop_parallel_copy_is_the_sequential_copy`). *Traversal contract:* pull child visits may be retained only until their directory returns; every accepted worker is joined before its source and destination scopes expire. Push child visits consume the stream immediately. Entry types from listings remain advisory. *No setting:* the width is the machine's processor count capped at eight, with lazy pool creation and tests across widths one through eight. The named-facts mutex protects memo access; each node's continuation retains its own key, so concurrent siblings share no handoff state (`08` K17 and §1.6).
- **Auxiliary values are ingestion-owned database metadata.** The full typed key and complete chunk sequence define a value; a file path or link count does not. The private pending relation retains the first completed value per typed key; new metadata has no filesystem publication. Retired flat/sharded auxiliary cache leaves are cleaned in a fixed-depth namespace without reading their bodies. Historical filesystem-sharding measurements in `05-validation.md` describe that former representation, not the cost of this SQL replacement.
- **A regular-file blob's canonical file is a store path's own, and the store indexes it** (section 9.10, *Where the objects live*). A regular file is no longer linked into `.objects`: a store path's own file is the blob's *holder*, recorded through `Blobs` and `Ingestions`. First entry writes each file once; later paths share eligible holders. Each path retains its own candidate for a reused blob, so collecting the donor does not erase the recipient's witness. A completed ingestion replaces that path's previous projection, including an empty projection; its rows remain private until the completed-path boundary, with reconciliation before holder visibility. Law 4 therefore uses the index; repair forgets a corrupt candidate without removing a valid path's file (K2); the index, rather than link count, witnesses a holder (K8); and local overlay stores retain no cross-layer sharing of regular-file blobs (K13). The holder, separate-writer and probe-ablation experiments in `05-validation.md` section 6 and `06-holder-index.md` describe their earlier implementations. Their timings, claims of no measurable index cost and database-size results do not establish the cost of the current per-path candidate representation or its completed-path publication. Current measurements belong in `09-performance.md`.
- **A written file is entered as its blob on the walk's own thread.** *The `linkat` this decision is about is gone* — `enterWritten` now takes the file's inode and records a row, the file itself being the blob's holder (the entry above) — and the decision survives as the placement of that work: it is done on the walk's own thread, not handed to another. What follows was measured when the link was still there. The `linkat` that gave a written file its blob (`GitObjectStore::enterWritten`) is the kernel time the store pays for sharing and a store without sharing does not; it was moved to a thread of its own, measured and moved back. *Measurement* (`05-validation.md` section 6): on the measurement's filesystem writing 40 000 small files costs 0.41 s and writing and linking them 0.60 s, and writing on one thread while another links costs 0.45 s — but in the walk it is *slower*, 1.48 s against 1.39 with the link in place and 1.32 to 1.53 s of system time against 0.92 to 1.02, because the walk's thread does the reading, the hashing and the memo between its writes, so the two streams of metadata work contend rather than overlap. Handing the files over one at a time is worse still: a wake, a sleep and an answer a file is 117 891 `futex` calls and 45 % of the entry's syscall time, more than the link it moves. *Rejected with it, each measured:* a bounded pool over a directory's regular-file siblings, which buys nothing, ext4 serialising creation in a directory (0.45 s at one thread, 0.43 at four); several threads linking into the flat blobs directory, which is slower than one (1.09 s at eight). The one arrangement that took the link further is the blobs directory sharded and the walk parallel across directories, 0.68 s down to 0.23; both halves are taken in the two entries above.
- **Windows is by inspection only:** the object store shares no regular-file contents there, since the `*at` calls the two operations rest on have no counterpart; no Windows build or run has checked it (section 13).

## 13. Open, and outside this specification

This section separates remaining choices from enforced semantic limits and historical cost measurements. Section 10 records the decisions already taken; current validation and performance measurements are in `09-performance.md`.

- **The local overlay store's remaining object-store operations.** The current upper-only cleanup and SQL ownership do not authorize reads from a lower auxiliary provider, cross-layer holder reuse or named materialisation. `.links` removal and merged auxiliary verification stay disabled. Any extension must separately preserve lower physical data, merged visibility, copy-up/whiteout behavior and lease coordination; previous overlay test results establish only their tested revision (`09-performance.md`).
- **Sources with references** stay on the NAR path form, since the path form with references exists only for that method (sections 9.9 and 9.11; the store's column still holds the object hash for such a path, only its *name* is the NAR form). Admitting references under the git method would be a new type string no released Nix parses — a wire and format change every peer and cache would have to learn before such a path could be copied to it — for one rule instead of two in `primops.cc` and a `treeHash` assertion on a rare kind of source. *Recommendation:* leave it; revisit only as its own specification step with both protocol directions tested.
- **A working-directory view is not identified by Git status.** The removed shortcut read files reported clean from HEAD and named them with HEAD's identities. That changed the tree when Git deliberately suppressed a comparison or a clean filter equated different bytes. The filesystem now supplies both the bytes and the name; status supplies membership and metadata. The earlier measurements in `05` section 6 describe a rejected implementation, not a valid speedup. The finite regression domains and the current measurements are in `09-performance.md`.
- **A copy proportional to the change, not to the tree.** An immutable view with independently named subtrees can materialise a held directory from the store's own objects (section 9.10, *One route*). This still visits its files to acquire and validate their holders and link them into the destination. A raw working-directory view has no revision-derived name: its current filesystem bytes must first be observed. The earlier clean-HEAD shortcut cannot justify skipping that work. Even when subtree names are available, materialisation stays proportional to the number of files, in `linkat`. O(change) needs the unchanged *directories* shared, which hard links cannot do: a directory clone where the filesystem offers one is platform-specific and a copy-on-write of bytes, not a sharing of the tree, so the invariant "every regular file is the object store's file" would need restating per filesystem; a store whose path is a view of objects changes what a store path *is* for every observer, builders included. Both are outside this specification. *Recommendation:* accept the remaining constant; a finer fallback than the named subtree (one file re-read from the accessor where one blob is missing, rather than the subtree) is the small step left inside the route, not taken since only a corrupt or swept object reaches it.
- **The working-directory accessor's `export-ignore` sources.** The tree that `builtins.fetchGit` of a local path with no `rev` names is the working tree, so a `.gitattributes` on disk belongs to it whether or not it is tracked (section 9.9). The accessor asks libgit2 with `GIT_ATTR_CHECK_INDEX_ONLY`, whose per-directory source is the index's entry, so a `.gitattributes` present only in the working directory below the root does not reach the lookup — master's reading, kept here and pinned by `GitUtilsTest.workdirExportIgnoreSources` rather than left to chance. Changing that accessor to `GIT_ATTR_CHECK_FILE_THEN_INDEX` would change what an existing dirty-checkout fetch exports; this step retains native `INDEX_ONLY` lookup and removes the fresh-scan omission proof instead. *Recommendation:* take it as its own step, with the release note that behaviour change deserves.
- **Windows**, where the object store shares no regular-file contents, by inspection only — no Windows build or run has checked it (section 9.10).
- **The cost property.** Stable immutable subtree names can avoid rehashing unchanged contents; materialisation still creates destination directory entries and acquires regular holders. Raw worktrees remain filesystem views. Historical clean-HEAD measurements do not establish this property for them. The exact current revision, all workload cases, regressions and CPU/RSS limits are in `09-performance.md`; no universal lower-wall claim follows from this specification.
- **The first entry of a new tree** was the operation the object store did not make cheaper, and it is measured with the rest (`05-validation.md` section 6); what follows is the historical account of that implementation, not the current branch-base performance result (`09-performance.md`). It costs two walks of the tree — the naming, which the store path must have before the tree can be mounted, and the copy, which cannot be answered from objects that do not yet exist — as master's does, plus one `linkat` a file into `.objects/blobs`, which is the sharing itself. After the memo's rows were batched into one commit and then written in key order into a page cache large enough to hold them, the blob's file named once as a string and entered by that one `linkat`, and the memo's names and keys built without a temporary, it is a fifth below master with sharing on and about a sixteenth above master with sharing off, and issues five fewer syscalls a file than master with sharing off and fourteen fewer than master with sharing on. **What remains is the `linkat` and nothing else, and it was measured rather than reasoned about**: on the same filesystem, creating 40 000 small files costs 0.41 s and creating and linking them 0.60 s, while the whole first entry is 0.08 s above master's — so on everything that is not the sharing the branch is already the cheaper of the two. Closing the last sixteenth meant walking the copy from several threads across directories, with the object store's layout sharded so that the threads do not queue on one directory (the two entries above); that implementation was measured below master with sharing off by about two fifths. What is left and not taken is writing the objects during the naming walk, which runs for every mounted input, copied or not, so it would write a whole unused input into `.objects`; and not sharing at all, which is what a store path is here. Entering a written file's blob on a thread of its own was built and measured and is slower, above. *Recommendation:* accept the remaining constant; it buys what master with sharing on pays two and a half times over.
