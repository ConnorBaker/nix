# Specification: the meaning of sources and store objects, and what lazy materialisation must preserve

This document is the story: what a source and a store object mean, and what an evaluator that defers store writes must preserve. It states meaning and laws; the mechanism is `04-derivation.md`'s, `05-validation.md` says how the checks are run, and `08-store-model.md` is the local store's model. Section numbers are stable because the code cites them; a gap in the numbering is a section removed. Locators are `file:line` in master at the branch's merge base, or in the libgit2 source where marked; line numbers drift.

## 1. The question

Can evaluation be separated from store mutation so that writes happen later, in bulk, and shared, while everything any observer can see remains exactly what eager Nix shows? To answer that: what does a source accessor mean, which operations on that meaning does Nix use, what must a fingerprint be for the memos to be sound — and what is a store object *one of*, such that its store path is known before its bytes are placed? A **content-addressed value**: one whose name is a function of its meaning (equal name ⇒ equal value), known before materialisation, whose materialisation is a separate, deferrable effect (§2.4).

## 2. Meaning

### 2.1 Trees

A source accessor denotes a **tree**: a regular file with bytes and an executable bit, a symlink with a target string, or a directory mapping names to trees. Master already has this as a value type with structural equality and ordering: `fso::VariantT` over `Regular`, `Symlink`, and `DirectoryT<Child>` (`src/libutil/include/nix/util/memory-source-accessor.hh:19-119`). It is exactly the information a NAR serialises; timestamps, ownership, permissions beyond the executable bit, and hard links are not part of it. A directory's entry names are non-empty byte strings other than `.` and `..`, containing no `/` and no NUL, unique and sorted within the directory; `.git` is an ordinary name. The NAR dump writes them verbatim (`src/libutil/archive.cc:131`); the parse validates exactly this, rejecting empty/`.`/`..`/`/`/NUL and unsorted entries but **not** `.git` (`archive.cc:275-282`).

Every read is a projection of the tree: `lstat` gives the node type at a path, `readDirectory` the names under a directory, `readFile` the bytes, `readLink` the target, `pathExists` membership. `resolveSymlinks` is a function of the whole tree and a path, not a read. Three accessor methods are outside the meaning: `getPhysicalPath` is a capability of the representation, `showPath` is display, and `getLastModified` is input metadata carried beside the tree.

A tree is determined by its root: every node is reachable by a listing from the root. An accessor that answers a positive `lstat` for a path no listing reaches does not denote a tree. Section 7.2 says where master has such an accessor and why it does not matter.

### 2.2 Partiality and time

- **Partial trees.** A NAR listing with opaque children (`ShallowNarListing`, "not knowing") is a tree with unknown subtrees. Reads force definedness. A name, defined below, always names a total tree.
- **Time.** An accessor over a live filesystem denotes a tree *at a time*. The specification fixes external inputs for the duration of a command; where that assumption fails, master detects it at materialisation and errors (`src/libexpr/paths.cc:46-52`).
- **Growth.** The evaluator's root accessor changes during evaluation in exactly two ways, both additive: a graft is added when an input is discovered (`paths.cc:77`, `emplace` only at `src/libutil/mounted-source-accessor.cc:93-96`), and an allow prefix is added when a path becomes readable in pure or restricted mode (`src/libexpr/eval.cc:405-408`, `insert` only at `src/libfetchers/filtering-source-accessor.cc:98-101`). Its denotation is therefore a sequence of trees ordered by information: a later tree extends an earlier one. That monotonicity is what makes the evaluator's lookup cache sound, and the cache is built for it: it stores positive `lstat` and `readLink` answers and never negatives (`src/libutil/caching-source-accessor.cc:30-42, 67-76`). A graft that *replaces*, or an allow prefix that is withdrawn, would break the order, because a fact already handed out could become false; mounts therefore add and never replace, and allow prefixes are added and never withdrawn. A graft is authoritative, so in general a graft over a path where the base tree was defined withdraws facts too; for the terms the evaluator builds it cannot: under the store directory the graft's parent is the store leaf, which has nothing at an uncopied path, and under the coherent union of section 8.4 both children agree wherever both are defined, so a positive answer is never withdrawn.

### 2.3 Trees versus store objects

A source **store object** is a tree together with a name, a set of references, and an ingestion method; its store path is a function of the name, the hash of the tree under that method, and the references. References and method live at the object level, not the tree level.

### 2.4 One address, and the serialisation

A tree's address is its **object hash**: the git identifier of its root under SHA-256 — a directory hashing its sorted `(mode, name, child-hash)` entries, a leaf its bytes (`git.cc dumpTree`, `src/libutil/git.cc:138-160`; on the branch `merkle::objectHash`, §9.11 for the three non-directory roots). The store path is a function of that hash together with the object's name and references (`makeFixedOutputPath(name, {method, hash, references})`, `store-dir-config.hh:81`; §2.3): the *path* addresses the object, the object hash addresses the *tree*, and the hash can never stand in for a path even in principle, since it lacks name and references. The address is **compositional**: it is built from the addresses of the subtrees, so a subtree's hash is O(1) once known and a filter/union/graft's is O(the structure it cuts), which is why §8 names subtrees by it. That compositional structure is what gives subtree names at all — a name for a subtree is a name the address already contains.

The NAR is the tree's canonical depth-first **serialisation** (`archive.cc`), the transport of a copy and the form a store hands a reader. Its hash `SHA256(NAR)`, the *flat* hash, is a second total function of the tree, related to the object hash by a total bijection — parse a NAR to a tree and hash it, or read a tree and serialise it, and you return to the start — but it is *not* compositional: SHA-256 is Merkle–Damgård, so a subtree sits at a context-dependent offset (BY-REASONING), and the structure of §2.1 is absent from it, so every operation that needs the structure must recover it. It names nothing: it is computed by one walk when an old form asks for it and never stored (§9.11).

The compositional encoding is name-agnostic: `git.cc` writes and reads any entry name verbatim (`:138-160` dump, `:48-93` parse), so every tree — `.git` included — has an address. The one place in libgit2 that rejects `.git` is the `git_treebuilder` convenience API, a write-path check (`GIT_PATH_REJECT_DOT_GIT`, libgit2's `src/libgit2/tree.c:57-61,488,781-795`); the raw object write (`odb.c:1613`) and the parser (`tree.c:394-441`) validate no names, and `git.cc` never uses the treebuilder, so the encoding's totality is not limited by it. The genuine subtree-naming asymmetries are *fetch-time* (LFS, export-ignore, submodules; §8.3), not a limit of the encoding.

### 2.5 Where the executable bit lives

The executable bit is *in* the leaf: a regular file is *(bytes, exec-bit)* (§2.1), so equal bytes with a different bit are different leaves, different trees, different store paths, and must stay distinct. A git-style representation puts the mode on the *edge* and the blob is bare bytes, so identical bytes are one blob whatever the edge's mode; the two are isomorphic and differ only in **dedup granularity** — the blob layer shares by content, the meaning (and any materialised inode, which carries the mode) splits by *(content, mode)*. The object store of §9.10 keeps that rule: one file per (blob, mode), `blobs/<id>` and `blobs-x/<id>`, and a link never made across the bit (`GitObjectStore`, `git-object-store.hh`); master's `.links` pool respected it by hashing each file's NAR, which includes the exec marker (`optimise-store.cc:150-160`). The bit on the edge leaves a **bare root** with no edge to carry it, so the address of §2.4 gives such a root a synthetic one: an executable file or a symlink at the root is addressed as the one-entry tree `{"." ↦ (mode, blob)}`, a directory or a plain file by git's own identifier (`merkle::objectHash`; §9.11). No real directory has an entry named `.`, so the address stays injective: the same bytes as a plain file, an executable and a symlink are three addresses. Nothing is conflated: the bit rides the root's entry into the address and the `blob`/`blob-executable` mode onto the edge of any tree; sharing happens only where it is invisible.

### 2.6 The store, a command, and Δ

Nothing here is new; it is what Nix means today, made explicit.

- A **store** S is a finite map from `StorePath` to (file-system object, path info) that is closed under references, together with a build-trace map from `DrvOutput` to `StorePath` and a set of permanent roots. Reference closure is enforced by the database: `Refs.reference` carries `on delete restrict`, and a reference must be valid at registration.
- A store object is **content-addressed** when its path is a function of its name, its content, and its references. Every object evaluation adds is: a `.drv` is text-addressed over its ATerm and references; a source is addressed under the git method over its name and its object hash (§2.4), or — when it has references, which the git path form does not admit — under the NAR method over its name, its NAR hash and its references (§9.9). A build output of an input-addressed derivation is not: its path is a function of the derivation, and its content is whatever the builder produced.
- **Evaluating a command** c against S, under fixed external inputs, denotes the pair (v, Δc): the command's result and the finite set of store objects, build-trace entries, and permanent roots the reference implementation adds while running c to completion. External inputs are the filesystem, the network, the substituters, the environment, the clock, and the outputs of any program `builtins.exec` runs; evaluation is deterministic given them. Building is not: the outputs of an input-addressed derivation depend on the builder, so for a command that builds, the reference denotes a *set* of possible pairs, one per run, and (v, Δc) below means any member of it. For a command that only evaluates, the set has one member.
- S + Δc is the union of the two maps. It is well defined because the reference never re-adds a path already valid in S, and two objects at one path in Δc are one object: evaluation's objects are content-addressed, and a build produces each output at most once per run. The references of Δc lie in S + Δc.
- **The reference implementation** is master at the commit the rewrite branches from (its merge base), not an older fully eager Nix. Master already defers the byte copy of flake inputs and prints their store paths without copying them, by design (release note "Sources are copied to the store more lazily", `doc/manual/source/release-notes/rl-2.35.md:5-29`; `src/nix/flake.cc:222-225`). Such paths are not in Δc, and (C2) below does not constrain them. Conversely Δc does contain every `builtins.path` source, every `toFile`, and every instantiated `.drv`, because master writes those at evaluation time; for them laziness can reorder and batch the writes but not omit them.

### 2.7 Checks

What discharges the claims of this section. The NAR node set and name domain: `archive.cc:131` (dump, names verbatim) and `:275-282` (parse, rejecting empty/`.`/`..`/`/`/NUL and unsorted entries, not `.git`); `narMaxName = 255` (`archive.cc:215`) against libgit2's `UINT16_MAX` parse limit (`tree.c:423`), so no length gap. The encoding's name-agnosticism: `git.cc:48-93` (parse) and `:138-160` (dump); libgit2 validates names only in the treebuilder (`tree.c:57-61,488,781-795`), not in the raw write (`odb.c:1613`), the parser (`tree.c:394-441`) or strict object validation (`object.c:604`); the branch's tree sink writes trees raw (`GitDirectorySinkImpl`, `git-utils.cc`; `merkle::serialiseTree`), so a tarball carrying a `.git` entry unpacks where the reference fails (`GitUtilsTest.sinkWritesEveryNarName`). ## 3. Correctness

An **escape** of a path p is any event after which an agent that reads the store's representation directly, rather than through the evaluator, could dereference p. The representation is read directly by the filesystem, the database, the daemon, builders, other processes, and any reader of the process's output. Instances include: p written to stdout, stderr, or any file (lock files, GC root symlinks); p passed to a Builder or across the daemon protocol; p embedded in the contents of another store object; p returned through the C API as a plain string; p's string context discarded. The list is a derivation aid, not the definition; a missed instance is a violation of (C2), detected by the test below. The eval cache is not an escape: its reader re-validates every cached path against the store and re-evaluates on a miss (`src/libexpr/eval-cache.cc:640-641`), so it is a memo, not an observer.

An implementation of evaluation is correct iff for every command c, every initial store S, and fixed external inputs:

**(C1) Final state on success.** If the reference can complete c successfully, the implementation completes c successfully with a result v and a final store S + Δc that some run of the reference could also have produced, **up to the renaming the address induces**: the reference names a source by its NAR hash and the implementation by its object hash (§2.4, §9.11), so every source's path differs, and with it the path of everything built from one. Two stores are equal up to the renaming when they hold the same objects — the same bytes once the hash part of every embedded store path is masked, the same content-addressedness, the same reference graph by name — under a name-preserving renaming of paths. For a command that does not build, this is equality with the reference's one outcome; for a command that touches no source it is row-for-row equality. `registrationTime` is excluded from the comparison; it is a wall-clock value today. Temporary roots are excluded; they are process lifetime.

**(C1') Failure.** If the reference fails c, the implementation fails c with the same error class and message text modulo diagnostics, and leaves a store that is closed under references. The partial set of objects written before the failure is not specified: the reference's partial writes are an accident of evaluation order, and pinning them would forbid every reordering the freedoms below permit.

What the differential check of `05-validation.md` compares: the exit status and the store snapshots, with standard output recorded and reported but not part of the verdict, and standard error not compared at all, because both carry paths, timings and version strings that differ run to run. The judgement is the **renaming view** (`snapshot.py renamed`, `renamed-content.py`, and its strict form, which digests build outputs' bytes too; `tests/functional/differential/README.md`): the loose and strict snapshot views differ on every row of a store the branch wrote, since the `ValidPaths.hash` column the snapshot dumps is rendered `git:sha256:<hex>` by the branch and `sha256:<hex>` by the reference, and they read nothing where a source is renamed. Error classes and message texts are compared where a test script greps for them itself (`05-validation.md` section 3). The builtin sweep of `04` section 1.2 compares message texts directly, in-process.

**(C2) Escape.** Whenever a path p in Δc escapes before c completes, the object named p is already in the store. This holds on success and on failure alike, so an error message that names a path names an object that exists.

Ordering. Master's own printers write to stdout first and force deferred copies afterwards, within the same command (`src/nix/eval.cc:113-126`, `src/nix/nix-instantiate/nix-instantiate.cc:76-98`). (C2) as stated is stricter: the object must be in the store when the bytes leave, so a reader on the other end of a pipe never sees a name before its object. The rewrite therefore flushes before emitting, or buffers output. This is a deliberate tightening relative to master; it changes no final state and no output.

The conditions are checkable without knowledge of the implementation:

- (C1) is a differential test: run c under the reference and under the implementation from the same S and the same external inputs, then compare `queryAllValidPaths`, each `queryPathInfo` minus `registrationTime`, realisations, permanent roots, and the command's outputs — up to the renaming, by the renaming view. The existing functional suite supplies the commands. The test is sound where the reference is deterministic; running the reference against itself first identifies the commands where it is not, and those are compared modulo output contents or listed as exclusions.
- (C2) is a differential test per observation: for any command that emits paths, dereference each emitted path from a second process in both modes and compare.
- (C1') is checked by the same runs on the failing cases of the suite, comparing error class and reference closure.

These tests replace boundary enumeration. A boundary the implementation forgot shows up as a failure on some command, not as an audit gap.

**What (C2) forces on an implementation.** A string value denotes a text together with its provenance, the store paths it depends on, which the evaluator already carries as the string's context. An escape, by the definition above, is text crossing the evaluator's boundary separated from its provenance. So (C2) is satisfied by construction, rather than by an inventory of sites, exactly when there is **one** operation that separates text from provenance and it discharges the obligation first: `realise(v)` writes every pending object and copies every mounted input named in `prov(v)`, then yields the bare text; and the only way to construct a string with less provenance than its inputs is `realise` re-wrapped with empty context, so `unsafeDiscardStringContext`, `getContext`, `match` and `split` are instances of one rule, not four cases. A `StorePath` is text without provenance by its type, so it is obtainable from a value only through `realise`. Embedding a pending path in another pending object is not an escape: the obligation transfers into the new object's references and is discharged in flush order. Two refinements follow from the conditions rather than from the mechanism. First, the write of pending texts at `realise` may be *total* — every pending object, whatever `prov(v)` says — because every pending text is in Δc regardless (section 4, *when*), and totality is what closes the one case provenance cannot see: a context-free literal, read from a file or typed, that happens to name a pending path. Second, the copy of mounted inputs must remain *provenance-driven* and confined to the exits at which the reference copies — the commands' outputs, not diagnostics such as `trace`, `warn` or the repl — because a mounted input is in Δc only where the reference copies it, and copying elsewhere would write what the reference never writes, violating (C1). So the door has two exits, told apart by the conditions: one that writes the pending texts, and one that also copies the mounts. The freedom left to the implementation is only *where the door is*: on the accessor that yields text, or on the sinks that emit it. `04-derivation.md` section 0.1 chooses.

## 4. Freedoms

Everything below is open to the implementation, and this is where performance lives.

- **When** each object in Δc is written: any time before the earliest escape of its path, or before completion.
- **Grouping**: any partition of Δc into batches, in any order consistent with references.
- **Concurrency**: writes may overlap evaluation.
- **Naming**: a path may be computed at any time before it is needed. The hashing walk may be memoised under any key that determines the tree: a git tree OID for an unmodified tree; a tree OID together with the prefix-closed accepted set for a filtered tree. The soundness condition on a memo key is exactly "equal key implies equal tree" (hence equal NAR and equal object hash); a key that ignores something the tree depends on, such as LFS attributes resolved from outside a subtree, is not a key. Section 8 derives the keys.
- **Byte placement**: bytes may reach the store by copy, hardlink, or reflink from any source with identical content, provided the registered hash is measured from the bytes registered.

## 5. Intended differences from master's implementation

The reference is master's documented meaning where it is documented and master's behaviour otherwise. Where the two disagree, the meaning wins, and the departure is listed here so that the differential check can exclude exactly it. One intended difference of meaning — the tree semantics for grafts and mounts (section 10) — with three observable consequences:

- **A mount lists at its parent.** Master's mounted accessor resolves any path to the nearest mount and lists an ancestor of a mount point from the underlying accessor alone, with a FIXME acknowledging the missing entries (`src/libutil/mounted-source-accessor.cc:27, 48-52`). Under the tree meaning a graft's parent lists the grafted name and missing ancestors are directories. Master's own release note for lazy trees commits to that meaning: "The evaluator continues to behave as if the copy was performed" (`doc/manual/source/release-notes/rl-2.35.md:5-29`). The observable consequence is in impure evaluation, where `builtins.readDir` of the store directory lists inputs that are mounted but not yet copied, which is what eager Nix showed. Master cannot list the store directory in impure evaluation at all: the store accessor's root listing throws "path '/' is not a valid store path" (`src/libstore/local-fs-store.cc:58-63, 107-110`, the root being special-cased only in `maybeLstat`), and the union propagates the error; the departure is therefore from an error to a listing, and the listing agrees with the meaning.

- **The directories leading to a mount point exist.** The same tree meaning, seen in pure evaluation. Once a store path is allowed, the allow list also allows its ancestors (`src/libutil/canon-path.cc:126-146`), and those ancestors are directories of the evaluation root: `builtins.pathExists /nix` is true and `builtins.readDir /.` lists `nix`, where master answered false and an empty set while `builtins.pathExists /nix/store` was already true. Master's own unit test marks its answer with a FIXME (`src/libexpr-tests/eval.cc`, `PureEvalTest.pathExists`); the test pins the tree's answer.

- **The store directory lists in pure evaluation too.** The same root cause as the first entry, seen under the allow list: `builtins.readDir /nix/store` in pure evaluation returned an error on master and returns the allowed entries on the branch. The listing asks the store once for all valid paths (`Store::queryAllValidPaths`, one round trip through a daemon) and filters the directory's entries by it, so the cost is bounded through a daemon.

A related alignment is not listed because it is unobservable on master: the union accessor's directory listing throws where an earlier child has a directory and a later child has a file at the same path (`src/libutil/union-source-accessor.cc:43-59`); the meaning says the earlier child shadows, and master's only union, the impure evaluation root, cannot produce the collision when the on-disk store is a valid content-addressed store (section 8.4).

## 6. Excluded, and unchanged by decision

- **Elision**: skipping any object the reference would write on success. Excluded by (C1).
- **The store path's form**, `makeFixedOutputPath(name, {method, hash, references})`, and the **string-context variants** visible to library consumers. The *method* under which the evaluator names a source is a parameter of that form that master already carries (`FileIngestionMethod::Git`); it is the git method for every source, with no setting (section 9.9).
- **Changes to the Nix language** beyond the attributes section 9.11 lists: every builtin returns on the same inputs what it returns today, `treeHash` is added where a tree is named or asserted, and `narHash` stays as a lazily computed attribute. Slicing, length, matching, and hashing builtins must neither throw nor return a different string because a name was deferred.
- **Dry-run**: `nix build --dry-run` keeps master's behaviour and writes the derivations it classifies; they are in Δc. "Dry-run writes nothing" is a change of meaning for one flag and is not part of this work.

**What is not frozen.** The Store interface, the daemon and serve protocols and the on-disk formats — the database, `.narinfo`, the lock file, the path-info JSON — changed as section 9.11 says: the store's content hash is the object hash, old flat hashes are accepted and verified through a shim and never written as a name, and (C1) is equality up to the renaming the address induces (section 3). The path form and the context variants above are what remains frozen.

## 7. The operations

Four operations on trees account for every accessor combinator on master. Each is defined pointwise on paths, total on total trees where its precondition holds, and monotone on partial ones.

### 7.1 Definitions

- **subtree(T, p)**: the tree at p. Master's `SourcePath` offset. Where p passes through a symlink, the node at p is whatever `lstat` semantics give: the symlink is a leaf, not its target. Its adjoint, the tree that has T at p and nothing elsewhere, is a graft onto the empty tree, not a fifth operation.

- **filter(T, S)** for a **prefix-closed** set S of paths containing the root: the tree with exactly those entries of T whose paths lie in S. Prefix-closure makes the result a tree in the sense of 2.1: every kept entry's ancestors are kept, and a kept directory is kept even if every entry under it is dropped. A predicate f over paths induces S_f = { p : every prefix of p other than the root satisfies f }, the set reached by a top-down walk that prunes at the first rejection. That is what `dumpPath` does with a path filter: the filter is consulted once per directory entry and the walk descends only into accepted entries (`src/libutil/archive.cc:102-108`), so a rejected directory's descendants are never asked about. Composition is intersection: filter(filter(T, S1), S2) = filter(T, S1 ∩ S2), and the intersection of prefix-closed sets is prefix-closed. A representation that keeps only the roots of kept subtrees and fuses two filters by intersecting those roots is unsound: the roots are not the prefix-closed sets. Masking by a set W is filter by the prefix-closed complement of W.

- **union(T1, T2)**: defined top-down, as an overlay filesystem is. At the root, and at every path where both have a directory, the result is a directory whose entries are the merge of both listings, T1 winning name collisions; at a path where the first tree that has a node has a non-directory, the result is that node, and nothing below it exists whatever T2 contains there. A pointwise reading ("T1's node where defined, else T2's") is wrong exactly there: it would let T2's `f/z` exist under T1's file `f`, and the result would not be a tree. Master's `Union`. Master's implementation is pointwise: `maybeLstat` and `readFile` take the first child that has the path, so a file in the first child does not hide the second child's subtree, and `readDirectory` calls every child whose `lstat` succeeds and therefore throws on a directory-versus-file collision (`src/libutil/union-source-accessor.cc:21-59`).

- **graft(T, p, U)**: the tree that has U at p and T elsewhere, authoritatively: a miss under p is a miss and never falls through to T. Precondition: every proper ancestor of p is a directory in T or absent from T; absent ancestors become directories. Where an ancestor is a file or a symlink the operation is undefined, and no producer on master violates this: the evaluator grafts at the store directory and at store paths under it (`eval.cc:254-274`; `paths.cc:77`), and the git fetcher grafts submodules at gitlink entries, which render as directories (`src/libfetchers/git.cc:981-986, 1043-1047`; `git-utils.cc:963-965`). Master's `Mounted`. A mount is a graft and not a union of stripped trees: fall-through belongs to union.

Derived: overlay(base, entries, whiteouts) = union(filter(workdir, entries), filter(base, complement of whiteouts)). Not an operation: caching is the identity with metadata.

### 7.2 Where master's accessors are these operations, and where they are not quite

- `FilteringSourceAccessor` implements `filter` for reachable reads: a listing omits rejected entries (`filtering-source-accessor.cc:38-47`) and `maybeLstat` answers nothing for a rejected path (`:27-30`). It does not check ancestors, so for a predicate that is not prefix-closed it answers positively for a path no listing reaches, which is not a tree. Both producers on master supply prefix-closed sets: the allow list accepts a path when it equals, is an ancestor of, or lies under an allowed prefix (`src/libutil/canon-path.cc:126-146`), and the git working-tree accessor passes the tracked files as prefixes plus the root as the one exact path (`git-utils.cc:1410-1417`). A predicate-based filter such as `builtins.filterSource` reaches the store through `dumpPath`, which prunes (`archive.cc:102-108`), so it denotes filter by S_f. The rewrite's fixed-set filtering accessor (`04-derivation.md` section 1.4) computes S_f by the same pruning walk, so its accessor and its NAR agree.

- `LocalStoreAccessor` is the on-disk store directory restricted to entries whose first component parses as a store path (`src/libstore/local-fs-store.cc:79-93`), further filtered by validity when `requireValidPath` is set (`:52-55`). On master it is not quite a tree: its root exists (`maybeLstat` special-cases it) but cannot be listed, since `readDirectory` requires a store object at every path including the root (`:58-63, 107-110`). The design makes the root listing the set of store objects, valid ones when validity is required, which is what `maybeLstat` already answers entry by entry. In pure evaluation it is `filter(disk, valid)`; in impure evaluation the validity filter is off (`eval.cc:274`, passing `settings.pureEval`), and the leaf is the disk directory as it is. Master's own comment says why: an invalid path in the upper layer of the impure union would throw instead of falling through (`eval.cc:255-273`).

- A git accessor with submodules mounted is a graft of submodule trees over the base tree; a git accessor with export-ignore or LFS smudging is a different tree, not a subtree (section 8.3).

- **The evaluation root as a term.** Reading `eval.cc`: storeFS = graft(empty, storeDir, store leaf) ⊕ the input grafts `mountInput` adds during evaluation, the store leaf being `filter(disk, valid)` in pure evaluation and `disk` in impure evaluation; pure evaluation: rootFS = allow(A, cache(storeFS)); impure evaluation: rootFS = allow-if-restricted(A, cache(union_c(host, storeFS))), with union_c the coherent union of section 8.4 (`UnionCoherence::ChildrenAgree`). `allow(A, ·)` is filter by the growing prefix-closed set A; `cache` is the identity. Every read the evaluator performs is a projection of that term's tree, and every name it can compute follows from section 8 applied to the term.

## 8. Names

### 8.1 Definition and law

A **fingerprint** is a partial function from total trees to names with one law: if two trees have names and the names are equal, the trees are equal, hence their NARs are equal at every path. Master's per-path query `getFingerprint(path)` returning a pair of a path and a name is the naming query for the pair (tree, path), which determines the subtree (`src/libutil/include/nix/util/source-accessor.hh:216-235`).

Names are **proofs** for content-addressed leaves and **assertions** for mutable ones. A git object identifier or a NAR hash names a tree by its content, so the law holds by construction. A name assigned to a directory on disk, such as `path:<narHash>` at `src/libfetchers/path.cc:169` or the dirty-workdir suffix over the dirty files' bytes at `src/libfetchers/git.cc:1122-1138`, is an assertion about a snapshot; the tree can change afterwards while the name persists. The memo consumer therefore verifies at materialisation, which master does and the rewrite keeps.

### 8.2 The rules, derived

Once the operations are fixed, the naming rule for each is forced. Where a rule can be coarser or finer, the coarser is still sound; the finer shares more. The rules below are the finest sound ones for the general case; 8.4 gives the one specialisation the evaluator needs.

- **subtree(T, p) at q**: if the leaf names subtrees, the leaf's name for the subtree at p/q; otherwise the pair (name of T, p/q). A vanilla git tree names every subtree by its object identifier. A NAR-backed or store-path-backed tree names only its root, by hash, and rebases. This single rule is the cross-revision sharing property.
- **filter(T, S) at q**: the pair (name of T at q, canonical form of S restricted to the paths below q). The NAR of the filtered subtree at q depends only on the kept entries below q, so nothing else belongs in the name. The set is data, computed by a pruning walk over directory listings and file types, without file contents. That walk is not free: master fuses it with the dump, so on a cold memo the filtered source costs the metadata walk *and* the dump where master paid the dump alone, and on a warm memo it costs the metadata walk where master paid the dump. Naming by the predicate's identity is rejected: a closure pointer or a lambda's position is not canonical across processes. For a git tree, a synthetic object identifier of the filtered tree is an alternative name that normalises the key without avoiding the cold walk.
- **union(T1, T2) at q**: if q is defined in T1 and is not a directory present in both, T1's name at q; if q is undefined in T1, T2's name at q; if q is a directory in both, the pair of both names at q, or no name if either lacks one. Master's rule, the first child with any name regardless of where the path lives (`union-source-accessor.cc:94-104`), is unsound in general; 8.4 says why it is nevertheless right for the one union master builds.
- **graft(T, p, U) at q**: under p, U's name at the relative path; at a proper ancestor of p, the tuple (T's name at q, the mount points below q relative to q, their grafts' names), or no name if any of these is missing; elsewhere T's name at q. Master returns T's name alone at ancestors (`mounted-source-accessor.cc:106-112`), unsound whenever T is named, safe today only because the store root has none.
- **identity**: pass through.

All names share one flat string space, and their disjointness — which a collision would turn into a cache hit returning a store path whose bytes were never written — rests on prefixes rather than on structure: the composite names are JSON arrays beginning `[` (`["filter", ...]`, `["graft", ...]`, `["union", ...]`), the git leaf names begin `git-object-v1:`, the content-named leaf's begin `nar:`, and the input-level names begin a scheme and a colon (`git:`, `path:`, `tarball:`), none of which is `git-object-v1` or renders as `[`. No reachable collision exists [by reading of the producers; no test pins it]; the structural remedy, were a future scheme to threaten it, is the Merkle-node vocabulary of `merkle-files.hh` in place of the hand-rolled JSON.

### 8.3 Consequences

- **Attribute-dependent accessors.** An accessor that smudges LFS pointers or applies export-ignore does not denote a subtree of a vanilla tree; it denotes a different tree, a function of the tree and of attributes resolved from the repository root. Its subtrees have no context-free name, so a subtree name must include the attribute context or be withheld. This is why master's tree-hash memo, written only for tarball roots (`src/libfetchers/git-utils.cc:831-844`; `tarball.cc:512`), is safe, and why a subtree key that ignores the attribute context is not.
- **Submodules.** With submodules mounted, the graft rule names a path above a mount point as (base subtree identifier, the mount points beneath, the submodule identifiers), which is precise. Without mounting, a submodule entry renders as an empty directory (`git-utils.cc:963-965`), which the subtree identifier determines.
- **Input-addressed outputs.** A store path that is a build output is not a content name, so a source taken from inside one has no cheap name and must be walked. Consistent with the law; master does the same.

### 8.4 The impure evaluation root is a coherent union

Master builds exactly one union, the impure evaluation root, `union(host, storeFS)` with the host filesystem first (`eval.cc:286-287`; no other producer, by grep of `makeUnionSourceAccessor`). Under the general rule of 8.2 that union names almost nothing: the host is never named, and wherever the host is defined the host's name wins. In particular a flake input that is both mounted at its store path and already copied to disk is defined in the host, so it would get no name, and the persistent memo lookup in `fetchToStore2` (`src/libfetchers/fetch-to-store.cc:64-69`) would miss where master hits today. That is a caching regression with no soundness gain, so the general rule is the wrong rule for this term.

The right rule follows from what the two children are. The second child is the store directory as the store presents it, with inputs grafted at store paths computed from their own content hashes (`paths.cc:73-77`). The first child is the same directory as the disk presents it. Wherever both are defined at a store path, they are defined at the same content-addressed name, so either the two trees agree there or the store is corrupt; master reads through this union on the same assumption. Call a union whose children agree wherever both are defined a **coherent union**. Its tree is the plain union, and its naming rule is: the name of whichever child has one, because on the region where both are defined, a name for one child's subtree is a name for the other's. That is master's first-child-with-a-name rule (`union-source-accessor.cc:98-102`), now with the precondition that makes it sound written down, and it is the rule the rewrite keeps for this one accessor. The general union keeps the three-case rule.

The precondition is checkable and is already the specification's assumption: the store directory on disk is a valid content-addressed store. The one way to violate it, an object on disk under a store path that is not the object named by that path, is a corrupt store, outside every condition the specification states.

### 8.5 Two caveats about what a name is relative to

Names name trees under a fixed tree-to-NAR mapping. That mapping has a version, and the persistent memo file is versioned with it; a change to NAR canonicalisation would invalidate the memo, not the law. And on case-insensitive filesystems such as macOS's default, master stores files under case-hack suffixes and strips them when dumping (`archive.cc:86-99`), so the tree that is named is the logical tree after the strip, not the directory listing on disk.

### 8.6 The checks

The per-operator laws collapse to one property and a few identities, and the tests are theirs. *Soundness:* over generated `MemorySourceAccessor` trees and terms of the four operations with a content-naming leaf, prefix-closed filter sets and grafts satisfying the precondition, equal names imply equal NARs at every path, the coherent union's rule holds for children that agree and the general rule refuses a name where they differ (`SourceAccessorNaming.equalNamesImplyEqualTrees`, `coherentUnionNamesByTheFirstChildAndStaysSound`; `FetchToStore.prop_filtered_names_are_sound`). *Sharing:* equal subtrees under a naming leaf yield equal names (`GitUtilsTest.namesFollowTheTreeObjects`, `GitUtils.prop_sharedSubtreesNameAndRenderAlike`). *Identities:* a filtered dump equals the dump with the filter (`FetchToStore.prop_wrapped_dump_equals_filtered_dump`); the top-down union and its names (`UnionSourceAccessor.overlaySemantics`, `fingerprints`); the graft's listing and names (`MountedSourceAccessor.graftIsATree`, `mountOverExistingEntryIsListedOnce`, `mountingTwiceKeepsTheFirst`). *Reference agreement:* the one listed difference from master (section 5) is checked against master's behaviour, since the condition is agreement with the reference except where section 5 says otherwise (`tests/functional/mounted-inputs-listed.sh`, `PureEvalTest.pathExists`).

## 9. The naming of sources, the object store, and the one address

### 9.9 The naming of sources

**Meaning.** Every source the evaluator names is named by its object hash (§2.4) under the git content-address method: the store path is `makeFixedOutputPath(name, {Git, objectHash, {}})`. There is no setting and no second name. A store object is still a content-addressed value (§1); a source's path is a function of its name and its tree, and the tree's address is git's.

**The doors.** The sources the evaluator names, each on the git method: `fetchToStore`'s default (`src/libfetchers/fetch-to-store.cc`, `methodRequested.value_or(Git)`; `fetch-to-store.hh` says so), through which mounted inputs (`EvalState::mountInput`, `paths.cc`, a dry run that names the tree), `copyPathToStore` (`eval.cc`, the coercion of a path value) and the installables and flake commands pass; `builtins.path` and `builtins.filterSource` with the default `recursive = true` (`addPath`, `primops.cc`); the `path` fetcher's own copy (`path.cc`: the tree named first by one walk — `objectHashOf` over the filesystem, since a filesystem path has no fingerprint for the memo — and `addToStoreFromDump` under `Git` only when the store lacks the path; the memo then seeded from the object hash the store holds); and the dirty-checkout route of the Mercurial fetcher (`mercurial.cc`, `store.addToStore(..., Git, ...)` with the tracked-files filter).

**The exceptions, each derived from a form rather than chosen.** These keep the NAR method: a source with **references** — the path form with references exists only for the NAR method (`makeType("source", references)`, `store-dir-config.cc`; every other method refuses them), so `addPath` with a non-empty reference set switches to `NixArchive` (`primops.cc`, the comment beside it) and refuses a `treeHash` assertion, since no tree name exists for it; the **committed-revision Mercurial route** (`mercurial.cc`, `store.addToStore(name, {accessor})` on `Store::addToStore`'s default, `NixArchive`); **profiles** (`src/nix/profile.cc`, `FileIngestionMethod::NixArchive`); **`make-content-addressed`** (`src/libstore/make-content-addressed.cc`, the same); and the **explicit methods**, which are the format's content-address methods and not a naming of sources — `builtins.path { recursive = false; }` (the flat file), `nix store add --mode`, and fixed-output derivations in `recursive`/`flat` mode, whose `outputHashMode` and the hashes nixpkgs records under it are untouched. No experimental feature gates the git method, `outputHashMode = "git"` on a derivation, or the reading of git object streams (section 10); a configuration that still names `git-hashing` gets a stabilisation warning.

**Why.** The evaluator's filesystem work is naming and transforming the trees it fetched (§7); under the flat address it cost O(content) whenever the memo was cold, because a subtree's flat hash depends on its position (§2.4); under the object hash a subtree's name is O(1) once known, a filter, union or graft's is O(the structure it cuts) (§8.2), and a git-backed tree's is the identifier git already holds. The bytes that reach the store are the same trees, serialised as NARs on the way (§9.10).

**The memo's rule, and its limit.** The tree hash is computed subtree by subtree, and each subtree the accessor names — a git object by its identifier, a filtered subtree by the inner name and the admitted set below it, a grafted subtree by the names of its parts (§8.2) — is looked up in the memo before it is hashed and recorded after, under the key form of the NAR memo with the method `git`. The hash a row holds is the node's *entry* hash — a blob id or a tree id — for the root of a naming as for a child, since one key has two readers: the naming of a tree reads its root's row and derives the address from the root's mode, and the parent's walk reads the same row as the child's entry. Every seeding of a row from a store object's object hash writes the entry hash, which for a bare executable or symlink root is the blob id and not the synthetic tree's id — such a root, whose blob id is not a function of its object hash, is not seeded and is hashed at its next naming; a row holding the object hash instead would give the parent of an executable file named alone a wrong tree hash (`GitUtilsTest.memoRowsHoldEntryHashesForBareExecutableAndSymlinkRoots`). Two consequences of the meaning. A filter decides a directory's entries, so while one is in force no directory's name is used or recorded, only a file's, whose blob is the same under any filter. And a tree without a name — a plain directory — is hashed whole. A dirty checkout is named in two ways: the whole tree by a hash over its changed files, and each clean subtree — no modified, added or deleted file at or below it — by the commit's object at that path, the same name the clean commit's accessor gives, so the memo rows written when the commit was named answer for it and an edit costs its blobs and their ancestors. That naming asserts that a clean file's bytes and mode are its blob's, which the repository's status says only when no content filter can apply and modes and symlinks are honoured; the checkout is named that way only when `core.autocrlf`, `core.filemode`, `core.symlinks` and every attributes file the repository can see allow it, and otherwise the tree is hashed whole. The export-ignore filter that `builtins.fetchGit` applies by default (`exportIgnore = true`) hides the names beneath it, since the exported tree is not the commit's; when it would hide nothing it is left out altogether (the next paragraph). Neither naming is conditional on a setting. The fetcher cache is opened lazily and its absence is a miss, since naming a source needs no cache. The functions and the tests that hold each sentence here are named in `04` section 1.6.

**The export-ignore filter is the identity when the repository declares nothing.** The filter's answer for a path is libgit2's: `git_attr_get_ext` with `GIT_ATTR_CHECK_INCLUDE_COMMIT | GIT_ATTR_CHECK_NO_SYSTEM` for a commit, `git_attr_get` with `GIT_ATTR_CHECK_INDEX_ONLY | GIT_ATTR_CHECK_NO_SYSTEM` for a working directory (`GitExportIgnoreSourceAccessor`, `git-utils.cc`), and libgit2 answers from a fixed list of sources (`attr.c`: `attr_setup`, `attr_decide_sources`, `collect_attr_files`). In precedence order: `info/attributes`; for each directory from the path's up to the root — in a repository with a working directory the file `<dir>/.gitattributes` there, tracked or not, then the index's entry of that name, then the commit's blob, since the flags' low bits are `GIT_ATTR_CHECK_FILE_THEN_INDEX` (0); for the working-directory accessor the index's entry alone; `core.attributesFile`, or the user's `attributes` on libgit2's XDG search path when it is unset; and, for macro definitions only, since the flag excludes its rules, the system's `gitattributes`, as also the working directory's root `.gitattributes`. Each working-directory file costs a `stat` per path component per lookup, and no session spans lookups (`attr_file.c`, `git_attr_file__out_of_date`): on the nixpkgs checkout of `05` section 6 the filter was 360 000 syscalls of a 0.5 s evaluation. When no source in that list assigns `export-ignore` — set, unset or valued, or through a macro — the filter admits every path and is the identity on the tree, so `GitRepo::getAccessor` returns the inner accessor: the same object, the same names, no lookup. The decision is one walk of the commit's tree reading its `.gitattributes` blobs, whose answer, a function of the commit, is kept in the fetcher cache (`treeMentionsAttribute`; `exportIgnoreHidesNothing`, `git.cc`), plus the sources outside the tree, read each time (`attributesOutsideTheTreeMention`): the files above, the index's `.gitattributes` entries and, for a commit read from a checkout, one `stat` of `<dir>/.gitattributes` per directory of the tree, since libgit2 would read those; a bare repository — the cache clone of a remote URL — has none. A mention counts however negated or valued and wherever it stands, so the decision errs only towards keeping the filter, whose answers are then libgit2's as before. The pins: `GitUtilsTest.exportIgnoreFilterIsLeftOutWhenNoSourceNamesIt` (the accessor's type, and the name and path, equal with and without the filter), `GitUtilsTest.exportIgnoreDeclaredAnywhereKeepsTheFilter` (each source alone keeps the filter and hides what libgit2 hides, libgit2's reading of an uncommitted `.gitattributes` for a commit pinned as it is), `GitUtilsTest.exportIgnoreWrapperPassesNamesThroughWhenItHidesNothing`, `tests/functional/fetchGit.sh`; the mutation, `05` section 4.

**The shim: old assertions of the flat hash.** An assertion of a NAR hash — `?narHash=` in a flake reference, `fetchGit { narHash }`, `fetchTree { narHash }`, `builtins.path { sha256 }`, `fetchTarball { sha256 }`, a node's `narHash` in a version-5-to-7 lock — is accepted and verified, never used as a name. One function verifies them all: `assertNarHash` (`fetch-to-store.cc`). The `treeAddress` memo answers first when it already pairs the asserted NAR hash with the tree's object hash; otherwise `narHashOf` runs — `fetchToStore2` under `NixArchive` in dry run, which is the existing memoised NAR walk — and the pair is recorded only for a *named* tree, since then both hashes came from the memo of one name and a tree changing between two walks cannot leave a wrong row behind. It is called at `Input::getAccessor` (`fetchers.cc`), which every fetch route passes — `nix flake prefetch`, the registry, the tarball fetcher, and `mountInput` (`paths.cc`), which verifies nothing of its own, since it reaches the tree through `Input::getAccessor` — at `addPath` (`primops.cc`) and on `fetchTarball`'s route (`fetchTree.cc`); a wrong assertion throws the existing `NAR hash mismatch in input` error, exit 102. A consequence stated: a `sha256` pin finds a present tree without a fetch only once a pinned fetch has verified it, because an unpinned fetch computes no NAR hash and so records no pair (`tarball.sh` forces the lazy `narHash` first). `builtins.path` and `fetchTarball` accept `treeHash`, the assertion that costs nothing: the fast path is `isValidPath` of the name it determines, and a locked input is substituted under that name alone (`getAccessorUnchecked`, one candidate; the flat candidate went with the loops).

**The lock file and the input.** An input carries `treeHash`, an SRI SHA-256 string, the object hash of its root (`Input::getTreeHash`; `Input::computeStorePath` is `makeFixedOutputPathFromCA(name, {Git, SHA256, treeHash})`); every scheme that allowed `narHash` allows `treeHash`, in the URL query too, and `isLocked` accepts either. No input carries a `narHash` attribute past verification, lazy or not — serialising an input's attributes forces lazy ones (`attrsToJSON`, `attrsToQuery`), so a lazy `narHash` on the input would be walked and written by every lock, URL and diagnostic: `mountInput` and `Input::getAccessor` replace it by the `treeHash` they computed, the one mutation `checkLocks`' final branch admits. `flake.lock` is version 8 and does not write `narHash` (`lockfile.cc`); versions 5 to 7 are read, a node's `narHash` being the assertion above, verified by one walk when that input is next fetched and replaced by `treeHash`. A lock is written as version 8 whenever it is written at all; a lock whose inputs are all unchanged is not rewritten, since `nix flake lock` keeps an unchanged node without fetching it; so a version-8 lock may still carry a node's `narHash` alone, and every reader accepts either (`LockFile.version8AcceptsANodeWithOnlyANarHash`). An older Nix refuses a lock with `treeHash` or version 8; accepted (section 10).

**The language.** `fetchTree` and `fetchGit` results carry `treeHash` and a lazily computed `narHash` — a thunk that runs `narHashOf` when a program forces it (`emitTreeAttrs`, `fetchTree.cc`), so an expression that reads it still evaluates and one that does not never pays the walk. `fetchTarball` returns a path string, as before (`allowAndSetStorePathString`). `fetchMercurial` returns neither hash (`fetchMercurial.cc`). `nix flake prefetch` prints the tree hash as `hash`.

**The algorithm.** SHA-256, decided (section 10): a store path is a name substitution trusts, and SHA-1's collision resistance is broken. A SHA-1 repository's objects therefore have no SHA-256 identifiers until read; the tree is hashed once per object and memoised under its SHA-1 name thereafter, which is the memo above. The git content-address method admits no other algorithm anywhere it *creates* an object, a name or a derivation output — `checkIngestionAlgorithm` (`src/libutil/include/nix/util/file-content-address.hh`) at each of the eight creation entries, which `LocalStoreObjectsTest.gitMethodRefusesSha1AtEveryCreationEntry` and `git-hashing/simple-sha1.sh` enumerate — and the hasher has no algorithm parameter; what *reads* a description an older Nix made under SHA-1 tolerates it (section 10, the derived decision on old data). Equality with git is pinned under SHA-256: `ObjectHashSink.sha256_identifiers_are_gits` against the ids `git` gives in `simple-sha256.sh`, `GitUtilsTest.sha256IdentifiersAgreeWithLibgit2` against libgit2's SHA-256 object database, and `MerkleHash.blobHeaderAndIncrementalHasher` against git's ids of the empty blob and tree.

**Costs stated.** Naming a source is one walk under the git method where master paid one under the NAR method; a source whose tree is memoised costs its lookups. An old assertion costs one NAR walk on first sight, memoised for a named tree. A tree in a SHA-256 object database — the tarball cache (§9.10) — carries the store's identifiers already.

**The checks the meaning induces.** (1) The law and the bijection (§2.7, §8.6). (2) Equality with git: the object hash equals `git rev-parse`'s and `git hash-object`'s where git can hash SHA-256 (`tests/functional/git-hashing/simple-sha256.sh`, `source-addressing.sh`, `bare-root.sh`). (3) `tests/functional/git-hashing/source-addressing.sh`, the one-address test: every door names by git's own SHA-256 tree hash; a `sha256` verified by the shim and refused when wrong; `treeHash` finding a present tree from a dead URL; a fresh lock at version 8 with `treeHash` and no `narHash`; a hand-written version-7 lock evaluating, refused with a planted wrong hash, and rewritten at version 8 by `nix flake update`; substitution pinned by `treeHash`. (4) `tests/functional/flakes/old-lockfiles.sh`: a version-7 lock whose inputs are unchanged is left byte-identical by `nix flake lock`. (5) Unit: `FetchToStoreTest.gitSubtreeMemoRespectsFilters`, `FetchToStoreTest.aBareRootIsAddressedByTheObjectHash`, `GitUtilsTest.workdirNamesCleanSubtreesByTheCommit`, `GitUtilsTest.exportIgnoreWrapperPassesNamesThroughWhenItHidesNothing`, `GitUtilsTest.exportIgnoreFilterIsLeftOutWhenNoSourceNamesIt`, `GitUtilsTest.exportIgnoreDeclaredAnywhereKeepsTheFilter`, `GitUtilsTest.narHashOfIsTheMemoisedShim`, `LockFile.version7IsReadWithItsNarHashAsAnAssertion`, `LockFile.version8RoundTripsWithTreeHash`. (6) Against the reference: the differential under the renaming views (section 3; `05-validation.md` section 3). (7) The cost property, measured on Linux, not asserted (`05-validation.md` section 6).

### 9.10 The store's object store: git objects under SHA-256

**Meaning.** A store object's tree (§2.1) is encoded as git objects: one blob for each distinct byte string, one tree for each directory, a tree's entries being (name, mode, object) with the mode one of regular, executable, symlink, directory, and the object identifiers SHA-256 in git's object format — the address of §2.4. The meaning keeps the executable bit in the leaf (§2.5: a regular file is *(bytes, bit)*); the encoding puts it on the edge, so the same bytes under the two modes are one blob and two leaves. The local store keeps the objects of every store object it *enters* — its object store — and an entered store path on disk is a *view* of its tree: its directories made, its symlinks made, and each regular file a hard link to the object store's file for that (blob, mode). There is one such file per (blob, mode) in use and never one for both modes: an inode carries a mode, so the two leaves of §2.5 are two files, the same bytes twice, and a link is never made across the bit. **The roots are the column**: which root a store path has is the object hash in `ValidPaths.hash` (§9.11), the one place that fact is kept; the object store holds no record of its own. The store object's name is its object hash's; the NAR is its serialisation (§2.4); the references are unchanged; the database and the protocols changed as §9.11 says.

**Laws.** (1) *Encoding round trip:* for every tree *t* of §2.1, materialising the objects of *t* gives *t*, and the objects of the materialised path are those of *t*; the root object's identifier is `merkle::objectHash` of *t*'s root. (2) *Route independence:* the object hash and the objects of a path are a function of its tree alone, over the four routes that exist — the NAR stream (`ObjectHashSink` behind `parseDump`), the accessor walk (`objectHashOf` over `copyRecursive`), the on-disk walk (`objectHashOf` over a written path, `enterIntoObjects`), and the materialisation from the store's own objects (`materialiseThroughObjects`, *One route* below), which makes the subtrees the store holds from their tree bodies and reads the rest through the accessor walk — the last three reading the tree's own names through the case-hack strip the serialiser uses (§9.11), and the path a route makes dumping to the same NAR as any other's. (3) *Sharing:* two regular files of entered paths with one inode have the same bytes and the same bit, always; two with the same bytes and bit have one inode, except a file the store cannot link (the filesystem's link limit, macOS's `.app/Contents`, a file the store found writable, and a file `place` could not enter for `ENOSPC` on a full directory index — the fourth, which leaves no mark on the file, so `placementOf` cannot know it: the verifier reports such a file as missing and `--repair` tries again; unverifiable without a full directory index) and a path not entered (a path an older Nix wrote plainly, before `nix-store --optimise`). (4) *The store's relation to its paths:* the database is the truth; for every valid path whose row carries its object hash, every object that hash reaches — every tree on the way and every blob a reached tree names, except the blob of a regular file the store does not place (law 3's exceptions: `placementOf`, `optimise-store.cc`) — is present in the object store when the path was entered, and the view is the tree the hash names; the object store may hold more (an ingestion in progress) and holds nothing for a path never entered. A tree body is verified against its identifier when it is read to materialise a path, as it is when the sweep reads it. The law is false by design for a row migrated by the walk or by `--load-db` (an older Nix wrote the path; nothing was entered) and for a path whose objects a concurrent collection took between its restore and its registration (the window of `08-store-model.md` section 1.5, X1); `--verify --check-contents` reports each such path (`verifyObjects`, one walk hashing and checking) and `--repair` or `nix-store --optimise` enters it. The ingestion's own `min-free` collection runs before the restore; inside the window it would make the law false deterministically (`LocalStoreAutoGCTest`). (5) *Collection:* after the collector deletes paths, the sweep reads the live roots from the column and removes every tree no live root reaches and every blob file with one link that no reachable tree names; a blob a live tree names is kept whether or not any path links it. A live root whose object the store lacks — the two cases of law 4 — keeps nothing beneath it and does not stop the sweep: trees are written bottom-up and swept as a set, and a path's regular-file blobs are held by its own links, so what such a root could have kept is orphaned trees an interrupted repair or `ENOSPC` left and its symlink-target blobs, all re-entered by `--optimise` and read by nothing; the collector reports their number and names `nix-store --optimise`. A row not yet migrated is a root the sweep cannot see, so while any remains the sweep removes nothing and says so. A corrupt tree body stops the removal phase, because it hides what is reachable; `--verify --check-contents --repair` removes and re-enters it. The alternative — abandoning the removal phase on a missing live root — would be the steady state of every upgraded, `--load-db` and `min-free` store and reclaim nothing (section 10). Checks (1), (2) and (4) below are these laws' checks; (3) and (5) are checked in their single-path forms (`LocalStoreObjectsTest`: `sweepAndVerifyOnALiveRootWhoseTreeIsMissing`, `sweepTolerantOfAnUnenteredRoot`, `verifyExpectsNoBlobForAFileTheStoreDoesNotPlace`; `object-hash.sh`'s upgraded-store block) and stated as the invariants the code keeps; the concurrent interleaving of law 5 is unchecked (`05-validation.md` section 7).

**Why.** One blob store where master had three substrates — the fetcher caches' git object databases, the `.links` table under its own key, and the NAR's flat name. A source fetched into a SHA-256 object database carries the store's own identifiers, so its name is known before a byte is copied; the path's object hash is computed from the stream as it is restored. The optimisation pass, `.links` and the setting that switched it on dissolve: the object store is what a local store is.

**Ingestion writes only what the store lacks.** For every regular file under a stated limit (`04` section 1.7 states it), an ingestion that meets a blob the store already holds links the store's file and writes nothing; a blob the store lacks is written once and becomes the store's. The decision is made *before* the write, and it can be: the identifier is a function of every byte, so the question "does the store hold this blob?" is answerable exactly when the last byte has been seen, and a file under the limit can be held until then. Above the limit the file is written as received and then replaced by the store's file when the store held it, the cost falling where the write dominates it. This is the property; the composite that keeps it, and the measurement that showed the write-then-link discipline slower, are mechanism and are in `04` section 1.7.

**What follows from the meaning, and what is decided.**
- *Identifiers.* SHA-256 in git's object format, as libgit2 2.0 computes them for the fetchers' caches (SHA-256 object databases are first-class there) and as the store computes them for its own files, which links no libgit2 (`merkle::blobId`, `merkle::treeId`); the two are checked equal. The build takes libgit2 2.0.0-rc.1 with the changes of NixOS/nix PR 16427 (section 10 has the inventory).
- *The tarball cache is SHA-256.* A tarball's tree identifier is then the store's name for it and its blobs' identifiers the store's; the cache directory is `tarball-cache-v3` (`git-utils.cc`), since its rows and objects are not those of the SHA-1 cache.
- *Where the objects live.* Under the store directory as `.objects/`: `blobs/<id>` (0444) and `blobs-x/<id>` (0555), one file per blob under each mode in use; `trees/<id>`, a tree's raw body; `tmp/`, files not yet linked into place (`git-object-store.hh`). No `roots/` — the column is the root — and no `.links`: the legacy directory is removed by `nix-store --optimise` and by every whole-store collection (`removeLegacyLinks`, one deleter), and the collector's walk of the store directory passes over both names (`gc.cc`). The directories are made when a writable store is opened and again at the start of the sweep and of the inode table (`createDirectories`); the other readers treat their absence (a store an older Nix made and this one opened read-only) as emptiness. On the local overlay store the merged store directory shows the lower store's `.objects` and `.links` too, so none of this is done there (section 10). The symlink's target is a blob too, kept for the encoding's completeness (law 1) and linked by nothing.
- *One route.* Every add from an accessor is one NAR dump into `addToStoreFromDump` (`Store::addToStore`, `store-api.cc`), and every NAR — received from a substituter or the daemon, or made by the store from an accessor — is restored through the store's composite (`04` section 1.7), which yields the root and the NAR size (`restoreThroughObjects`). A flat file (`--mode flat`, a fixed-output file) and a build output are entered by one on-disk walk after they are written (`enterPath`, which hashes and enters in the same pass, one walk per built output and per flat add; `enterIntoObjects` beneath it), as migration enters them. There is no route from a fetcher cache's raw objects, no hint from an accessor, no buffered link-before-write; and there is one materialisation from the store's own objects (section 10, 2026-09-17): a tree the store already holds — each directory's body in `trees/`, each blob's file in `blobs/` — is made on disk from those objects by `mkdirat`, `linkat` and `symlinkat`, without serialising the source, and only a subtree the store lacks is read from the accessor; law 2 holds over this route too, checked by dumping the path back, and a tree body is verified against its identifier when it is read to materialise a path (law 4). The route is `LocalStore::materialise`, taken by `fetchToStore2`'s copy under the git method for a local store that owns its object store (`materialisesFromObjects`; never through the daemon, never on the overlay store, never on Windows), and what it materialises is what the naming's memo names — a directory's row, consulted for the root and for directories and never for a file inside a directory the store lacks, so that a fresh tree costs the route one lookup per directory — and the store holds; everything else is read and restored through the composite as before. Per unchanged regular file it costs one `fstatat` of the blob's file and one `linkat`: no read, no hash, no attribute lookup. The blob's file is trusted as the on-disk walk trusts an inode that is a blob's (`08` K8), its bytes re-hashed under `--repair` alone (K2); a missing or corrupt object sends the subtree the naming named back to the accessor, bounded by one read of it. The window between the naming and the copy is the memo's own (§2.2): what the memo names and the store holds is copied as named. The copy stays proportional to the number of files, in `linkat`; the measurement is `05-validation.md` section 6.
- *The content address is checked first.* A path received with a content address is verified against it before its asserted NAR hash and size (`LocalStore::addToStore(info, source)`): the address is what the path's name asserts, and for a git-addressed path it is the root the sink computed while restoring; then the object hash the sender gave, then the NAR hash it asserted, if any (through the store's composite, `04` section 1.7), then the size. Nothing is admitted that was not before.
- *No setting.* The object store is the local store's representation, unconditionally: `auto-optimise-store` is removed (section 10); a configuration or command line that still gives it, or its flag, is accepted and ignored with one warning saying why when it is set to `true`; `false` asks for nothing and is silent (the build hook hands its child `false` for every setting; the hook child, which re-reads the configuration, warns nothing, so the warning is once per top-level process). The setting is absent from `nix config show`'s key=value dump and present in its JSON and by name, as a deprecated setting is. Files identical in bytes and bit share their storage in every local store. `nix-store --optimise` remains as the migration of paths an older Nix wrote: every valid path is walked and entered — a path entered before costs its directory walk and no more, since its files' inodes are already blobs' — and the legacy `.links` is removed; on a store this Nix wrote it links nothing and says so; the wire operation is unchanged.
- *Collection.* After the collector deletes paths, `GitObjectStore::sweep` reads the live roots from the database — the object hash of every valid path (`forEachValidObjectHash`, `gc.cc`) — and removes every tree no live root reaches, every blob file that no reachable tree names and that nothing but the store links (a blob a live tree names is kept whatever its link count, a symlink's target and a file's bytes alike), and every temporary file older than an hour. No grace: an ingestion racing a *concurrent* collector (another process's `nix-store --gc`, the builder's asynchronous `autoGC(false)`) can lose its trees and its symlink-target blobs in that same sweep; its regular-file blobs are held by its own links. What that costs: law 4 is false for that path until `--optimise` or `--repair` enters it, `--verify --check-contents` reports it, and every later collection reports it and sweeps on — nothing else, since the tolerant rule of law 5 above. The ingestion's own synchronous `autoGC()` is not a race: it runs before the restore (run between the restore and the registration it would sweep the add's own trees whenever `min-free` triggered it; `LocalStoreAutoGCTest`). A row not yet migrated to the object hash is a root the sweep cannot see, so **while any remains the sweep removes no tree and no blob** and says so, naming `nix store migrate`. A grace by modification time protects nothing (every object file's mtime is canonical) and a grace by change time is advanced by the collector's own unlinks; and the collector's walk of the store directory passes over `.objects` by name, as it passes over `.links`, since it deletes every other entry that is not a store path.

**Limits, stated, and costs accepted.** The tarball cache changed name, so every user's cache of tarballs went cold once: tarballs are unpacked once more. The documented layout `/nix/store/.links` and the verifier's check of it are gone: the verifier checks the object store's blobs and trees against their identifiers (`verifyStore --check-contents`), and `nix-store --optimise` and every whole-store collection remove `.links`. A regular file over the composite's limit whose blob the store holds is written and then replaced by a link; under it a duplicate is linked and not written (above; the limit is `04` section 1.7's). The protocol carries whole NARs, so a copy through the daemon still reads every file on the client side and the daemon hashes every file it receives, writing only what it lacks. Directories cannot be hard-linked, so trees share in the object store and not on disk. The per-user caches keep a compressed copy of what the store holds uncompressed. A blob at the filesystem's link limit is left as written; on macOS files under `.app/Contents` are left as written, as optimisation skipped them. There is no way to run a local store without the object store; a filesystem that cannot hard-link leaves every file as written and shares nothing, and on Windows the object store shares nothing (section 10; the port is by inspection only, section 13).

**The checks the meaning induces.** (1) Identifiers and the round trip (law 1): a blob and a tree hashed by the store equal what a SHA-256 libgit2 object database returns on writing them (`GitUtilsTest.sha256IdentifiersAgreeWithLibgit2`) and what `git hash-object` and `git rev-parse` give (`bare-root.sh`, `source-addressing.sh`); the identifier equals `nix hash path --mode git`'s (`object-store.sh`); a tree materialised from the store dumps back byte for byte. (2) Route independence (law 2): the same tree through the NAR sink, the accessor walk and the on-disk walk gives one object hash, including the `Foo`/`foo` tree under the case hack (`ObjectHashSink` tests in libutil-tests; `LocalStoreObjectsTest.caseHackSuffixIsNotHashed`). (3) Collection (law 5): a sweep with every path valid removes nothing — including a blob a live tree names that no path links (the sweep test that plants such an unlinked file); with none valid it removes the trees, then the blobs nothing names or links, a blob going with the trees that named it; with an unmigrated row it removes neither (the sweep tests of `LocalStoreObjectsTest`, libstore-tests, which plant a root the enumeration cannot give). (4) The sink alone, no pass after it, on a tree two directories deep (`LocalStoreObjectsTest.restoreThroughObjects`, `restoreThroughObjectsStreamsLargeFiles`, `executableFirst`, `repairDoesNotLinkACorruptBlob`, `enterIntoObjectsAndMigrate`, `addToStoreFromDumpUnderTheGitMethod`, `syntheticRootTreeIsWrittenAndKeepsItsBlob`): every file a link into the object store, the trees present, the tree dumping back byte for byte; and the property above — writes only what the store lacks — by the counting hooks, which say how many regular files each restore created (`oneChangedFileWritesOneFile`: three, then exactly one; the `filesCreated` assertions of the other restores: four then none, three then two for the large files, none then one under repair), shown to discriminate by forcing the link to fail. (5) Functional: `tests/functional/object-store.sh` (a tree added twice shares every inode; the same bytes executable and not are two inodes; the identifier equals `nix hash path --mode git`'s; a path deleted and collected frees its blobs and trees and no others; `nix-store --optimise` removes a planted `.links` and links nothing on a store this Nix wrote; substitution from a binary cache comes back through the object store), `optimise-store.sh` (master's test made true: built outputs share as they are registered, `--optimise` links nothing), `git-hashing/object-store-fetch.sh` (a tarball fetched: its name the tree's identifier, its files links, a second tarball differing in one file writing one blob). (6) The differential under the renaming views (section 3). (7) The cost, measured on Linux (`05-validation.md` section 6): the copy of an edited tree, and a tarball's second materialisation.

### 9.11 One address: the compositional hash as the store's content hash

**The direction.** One address, not two parallel naming functions: consolidating and simplifying the implementation cannot be done by building out parallel implementations, so the store's content hash is the tree hash itself; existing hashes are invalidated, with a compat shim that reads them; the direction is git's.

**Meaning.** A store object has one content hash, its *object hash*: the git identifier of its root under SHA-256 — the tree id of a directory, the blob id of a plain file, and for an executable file or a symlink the tree id of the one-entry tree `{"." ↦ (mode, blob)}` (`merkle::objectHash`, libutil). It is a plain `Hash`, rendered `git:sha256:<hex>` (`ObjectHash::render`, `object-hash.hh`), and it is kept in one place, `ValidPaths.hash`; there is no root record beside it. It is total over store objects — a directory, a plain file, an executable file, a symlink — and injective: object types are in git's header, the two synthetic roots differ in mode, and no real directory has an entry named `.` (the NAR parser refuses it, `CanonPath` asserts it away, and a directory walk never yields it); the partiality of the bare root under git's blob id is dissolved rather than refused. A plain-file root keeps its blob id because master already names single-file sources by it, so a uniform "every root is a tree" definition would have renamed them. The synthetic tree is written to the object store like any tree, so the sweep reaches an executable's or a symlink's blob through it. For a directory or plain-file root it is git's own identifier. Section 2.4's address is this one; the NAR is a *serialisation* of a tree (`nix-store --dump`, the transport of a copy), and the NAR hash a derived quantity, a function of the tree that is computed by one walk when something old asks for it and is never the name of anything new. Every law of sections 8, 9.9 and 9.10 is stated over this address.

*The names the hash is over.* The object hash is a function of the tree (§2.1), so it is over the tree's own entry names, not over whatever a filesystem made of them. This is not idle: on macOS the NAR restorer renames case-colliding entries as it writes them (`archive.cc`, `useCaseHack`, default on for Apple; the suffix appended before the child is parsed), and `dumpPath` removes the suffix again when it serialises (`unhackedEntries`). A hash computed from the stream sees the tree's names; one computed by walking the written path sees the filesystem's, unless the walk unhacks as `dumpPath` does. Master's `git::dump` reads the directory raw, so its git address of a case-colliding tree on macOS is already not git's, and the import's verification of such a git-addressed path would fail there. Under this section every on-disk computation of the object hash — the after-build walk, `verifyStore`, `nix hash path` over a store path — goes through the same unhacking the serialiser uses, and the check is a tree with `Foo` and `foo` restored through the sink and re-hashed from disk, the two hashes equal (route independence, §9.10 law 2, on the one platform where it can fail). The converse hazard is closed at the parser: a NAR whose entry name already carries the case-hack suffix would unhack to a name the tree never had, so the NAR parser refuses such a name on every platform, not only where the hack is in force — its second collision check, for a hacked name colliding with a name already present, stays, since an upper-case spelling of the suffix reaches it (`NarTest.hackedNameCollidingWithAnUpperCaseSuffixEntryIsRefused`) — and the serialiser refuses an on-disk name carrying the suffix when the hack is off, since nothing would then strip it; the tree's name domain (§2.1) excludes the suffix.

**The forms, amended.** Each of the forms section 6 froze, with what it carries now, what it carries under this section, and the shim, which is read-side only: the system accepts an old assertion and verifies it, and never *names* anything by the flat hash again.

- *The path's name.* Sources are named `fixed:git:sha256:<id>` as master's git method already names them, for every root kind — a non-directory root by the id of its synthetic tree, no mode word in any rendering (decision (b)). There is no `nar` value and no setting; the `treeAddress` memo is the shim's, not a naming device. Master's explicit methods remain for what asks for them by name — `nix store add --mode nar`, `builtins.path { recursive = false; }`, fixed-output derivations in `recursive` or `flat` mode — because those are the format's content-address methods, not a second naming of sources. Sources with references keep the flat path form (section 9.9) until the git form admits references, which section 10 leaves open.
- *The database.* `ValidPaths.hash` holds the object hash, rendered `git:sha256:<hex>`; schema version 11, so that an older Nix refuses the store. The object store's root and this column are one fact, kept once, in the database (there is no `roots/` directory; the sweep reads the column, §9.10). `narSize` stays: it is the serialisation's length, a function of the tree computable from names and sizes alone, and the transfer framing needs it; it is computed in the same walk as the object hash, from names and sizes alone (`merkle::nar::{regular,symlink,root}`, `merkle-hash.hh`; the property `MerkleHash.narSizeEqualsDumpPathLength`), because a zero size is refused by the copy's size check, by the daemon's framing of an incoming NAR, by the serve protocol and by the output-size checks. Existing rows hold NAR hashes, rendered `sha256:<hex>`, and are told apart by their prefix (`ObjectHash::parse`); they are the shim's domain: such a row's object hash is filled by one walk of the path on first query (`queryPathInfoUncached`, the old value kept as the info's `assertedNarHash`; written back unless the store is read-only), by `nix store migrate` or by `nix-store --optimise`, after which the row is new. The walk hashes the NAR on a tee of the same bytes and checks it against the row's assertion before anything is written (`walkOldRow`, as `--load-db` checks a registration): a path whose files no longer hash to it is not migrated — the row is answered as the database has it, and the verifiers report "was modified" through the NAR hash as master's did — and a row whose files are gone is answered from the database and left to `nix-store --verify`, which removes it. Until every row is migrated the collector sweeps no object-store tree or blob (§9.10).
- *Signatures.* Fingerprint version 2: `2;<path>;<object hash>;<references>`. **Both fingerprints are signed where both hashes are known**: `nix store sign` signs version 2 whenever the path's description carries an object hash and version 1 — over `1;<path>;<NAR hash>;<NAR size>;<references>` — whenever the NAR size is known, the NAR hash asserted by the description or computed by one walk of the path; so it works on any store, a cache an older Nix wrote included, whose narinfos carry `NarHash:` alone and get version 1. The binary cache's upload signs both with the cache's own keys, its NAR hash coming from the upload stream. An older client verifies version 1 alone and counts only the signatures it can verify, so it accepts what either of these signs. Signing at build (`secret-key-files` on the local store) is version 2 only: no NAR hash exists there and a walk per output is not paid. Two consequences stated. A path signed at build and copied with `nix copy --to` into a cache that has no key of its own carries its version-2 signature unchanged, and an older client under `require-sigs` refuses it; the remedy is `nix store sign --store <cache> --key-file <key> --all` on the cache, which adds version 1 (`--all` enumerates a `file://` cache; for another cache, name the paths). And a version-1 signature is verified against the path's NAR hash: the one asserted for it — received from an older cache or peer, or an old row not yet migrated — or, for a locally held path whose row holds the object hash alone, the one a walk of the path gives (`ValidPathInfo::checkSignature` takes it as a `NarHashThunk`; `nix store verify` and `copy-sigs` bind one walk per path, `addToStore` its receiving tee — section 10, *a version-1 signature is checked on the stream*). So a version-1 signature made before the upgrade keeps verifying once the row is migrated, `nix store copy-sigs` establishes identity with an older cache's `NarHash:` through the walked hash and copies its version-1 signatures, and `nix store verify --substituter` checks them; the walk is the cost, paid at most once per path and only when such a signature by a trusted key is met. Content-addressed paths need no signature, as now. Older clients read a cache written by this Nix unchanged only when the cache signs at upload or was signed by `nix store sign`; for build-signed paths copied into a keyless cache they do not, and the release note says so.
- *The daemon and serve protocols.* A worker feature (`object-hash`, `WorkerProto::featureObjectHash`) under which path info carries the object hash and any asserted NAR hash; serve protocol version 2.9 with the same rule. To a client without the feature the daemon supplies the NAR hash by one walk of the path **per query** (`daemon.cc`, `withNarHashForOldClient`); there is no cache, so the cost falls on the old client, at every query of every path. A path info that reaches `LocalStore::addToStore` with neither hash and no content address describes nothing checkable and is refused (the daemon reaches it through the store).
- *Binary caches.* `.narinfo` gains `ObjectHash:`; `NarHash:` and `NarSize:` are still written, because an upload streams the NAR and hashing it costs nothing (`binary-cache-store.cc`, the tee); and a cache that signs at upload carries a signature over each fingerprint version (the *Signatures* bullet), which is what lets an old client consume it unchanged — the hash field alone does not, since an old client under `require-sigs` verifies version-1 signatures only. A cache with no key of its own carries whatever signatures the copied path had: version 2 alone for a path signed at build, which an old client under `require-sigs` refuses until `nix store sign` is run on the cache (the *Signatures* bullet names the command). Receiving from an old cache, the store verifies the NAR hash on the stream, which also costs nothing, and computes the object hash from the sink's root, which it already does. The per-user narinfo disk cache gains the object hash's column and so changes name (`binary-cache-v9.sqlite`, `nar-info-disk-cache.cc`): every user's cache of narinfo lookups goes cold once and the `v8` file is left, as the tarball cache's was (§9.10, *Limits*). A new client copying to an old cache writes both hash fields. So the hash shim is free in both directions and needs no switch; the signature side needs a key at the upload or a `nix store sign` afterwards, and a cache signed by a build before the dual signing carries version 2 alone until then.
- *The lock file.* Version 8: a locked input carries `treeHash` (the object hash as an SRI string), and `narHash` is not written. Versions 5 to 7 are read: a node's `narHash` is an assertion, verified by one NAR walk of the fetched tree when that input is next fetched, the pair recorded in the `treeAddress` memo, which is the shim's memo and nothing else, and replaced by `treeHash`. A lock is written as version 8 whenever it is written at all; a lock whose inputs are all unchanged is not rewritten, since `nix flake lock` keeps an unchanged node without fetching it; so a version-8 lock may still carry a node's `narHash` alone, and every reader accepts either (§9.9). Older Nix refuses a lock with `treeHash` or version 8 — accepted (section 10).
- *The language.* `fetchTree` and `fetchGit` return `treeHash` and a lazily computed `narHash`, a thunk that walks the tree when a program forces it, so an expression that reads it still evaluates; `fetchTarball` returns a path string, as before; `fetchMercurial` returns neither hash. `builtins.path { sha256 }`, `fetchTarball { sha256 }`, `fetchGit { narHash }`, `fetchTree { narHash }` and the `narHash` URL query accept a NAR hash under the shim, verified by a walk after the fetch, and `builtins.path`, `fetchTarball`, `fetchTree` and flake references accept `treeHash` (a new attribute) as the assertion that costs nothing. The `narHash` inputs in nixpkgs and in the wild keep working, slower by one walk on first sight; nothing in nixpkgs needs to change for this section, and `outputHashMode = "recursive"` is untouched: it is a derivation's assertion checked once per build, not the store's memo.
- *JSON and text.* Path-info JSON version 4 with `objectHash` required and `narHash` optional; `nix hash path` prints the object hash under a mode that names it; `nix-store --dump-db` writes the object hash and `--load-db` reads both: a record carrying the object hash is registered as written, and a record an older Nix wrote is walked once — the object hash the row needs, and the NAR hash and size the record asserts checked on the same tee (`walkOldRecord`, `nix-store.cc`; one read of every byte of a restored store, paid once) — a record whose path does not hash to it reported with both hashes and not registered, the rest registered, the exit status non-zero: per record, as `nix store migrate` reports. *Consequences stated:* master trusted a `--load-db` record and the walk is the cost of verifying it; a bad record loses its own path and no other; an older Nix cannot read a dump this Nix writes; and the values a builder sees in `exportReferencesGraph` under structured attributes are this hash and size (`doc/manual/rl-next/one-address.md`).

**(C1) restated.** The reference writes the same objects up to the bijection of names the new address induces, and the differential's judgement for every source and everything downstream of one is the renaming view (`snapshot.py renamed`, `renamed-content.py`, and the strict view; section 3 states it). Row-for-row equality remains the judgement for everything the address does not touch: derivations from store-path literals, `toFile`, fixed-output builds, the daemon's behaviour — judged by the renaming view too in practice, since the loose view differs on every row of a store the branch wrote (the column's rendering changed, section 3).

**The cost property, restated as a law.** A fetch of a tree the store already holds under a name costs the memo's lookups; a fetch of a tree differing in one file costs that file's blob and the trees on its path to the root, and no walk of the rest, on every machine, cold or warm — because no form any longer asserts a flat hash of the new tree. The one remaining full pass over content is the cache's own identification of what it unpacks (libgit2 hashing the objects it writes), which is the compositional hashing itself, done once.

**The decisions of this section.** (a) The `nar` value goes, not stays as a switch: a switch would be the parallel naming the direction refuses; the shim is acceptance of old assertions, not a second name. (b) The object hash is the root *entry*, mode included — the mode carried inside the synthetic one-entry tree for a bare executable or symlink, so that the content address is `fixed:git:sha256:<id>` for every root kind, no rendering, protocol field, `ContentAddress` or column learns a mode word, git's identifier is the address wherever git has one, and the three bare roots stay three objects. (c) The lock file is version 8 with `treeHash`, `narHash` not written; version 7 read through the shim. (d) `narinfo` publishes both hashes (free); the protocols negotiate; JSON version 4. (e) `outputHashMode = "recursive"` and every hash nixpkgs records under it are untouched. (f) The shim is on by default and has no switch to turn on, only a `nix store migrate` to finish; what may be wanted switchable is *refusal* of old assertions, a strict mode, which is cheap to add and is not assumed.

## 10. Decisions

Each decision with its reason and its consequence. A decision marked *derived* follows from the meaning, from a check or from a measurement; the others were taken and are recorded with their reason. Superseded decisions are not listed; where the reason for rejecting an alternative is part of a decision's reason, the alternative is named there. The open decisions are section 13.

**The frame.**

- **Preserve the store path's form and the string-context variants; upstreamability is a hard goal** (section 6). As first taken this decision also froze the Store interface, the daemon and serve protocols and the on-disk formats; the one-address decision below reopened those (section 9.11), and the path form and the context variants are what remains frozen.
- **No elision:** the store after any command equals the reference implementation's, up to the renaming the address induces (section 3, (C1)). *Consequence:* deferral reorders and batches writes and never omits one.
- **Correctness first, then simplicity, then performance.** Quoted performance numbers come from Linux; macOS gives direction only (`05-validation.md` section 6).
- **Dry-run keeps master's behaviour** (section 6): "dry-run writes nothing" is a change of meaning for one flag and is not part of this work.
- **(C2) is tightened to flush before emission** (section 3). *Reason:* a reader on the other end of a pipe must never see a name before its object. *Consequence:* `nix eval` and `nix-instantiate` copy the mounted inputs they print before printing; the observer's mounted-input modes read present on the branch and absent on master.
- **Typed sinks:** flush inside the eliminators of `Value`, total flush, output sinks accept realised bytes only (`04-derivation.md` sections 1.1 and 1.2).
- **The tree semantics for grafts:** mounts list at their parent and missing ancestors are synthesised as directories, recorded in section 5 as the one intended difference from master's implementation and justified by master's own release note for lazy trees. *Consequence:* observable in impure evaluation (`builtins.readDir` of the store directory lists mounted inputs not yet copied; master errored) and in pure evaluation (the store directory's ancestors exist once a store path is allowed; master said `/nix` did not exist while `/nix/store` did); `tests/functional/mounted-inputs-listed.sh` and `PureEvalTest.pathExists` pin it.
- **Deferral is unconditional.** The boolean setting of the staged rollout was removed once the differential had established (C1); the only setting is `deferred-store-writes-max-pending`, the memory bound (`04-derivation.md` section 2, *Memory*). *Reason:* a second, eager write path beside the buffer is a parallel implementation.
- **Correct by construction, not by convention.** A rule that only a reader's care keeps is a way to diverge from the meaning. Where the language can hold a boundary — the compiler on a type's representation, a move-only token an operation must present — it holds it; where it cannot, a check that runs without judgment holds it, and each check is shown to fail on a planted violation before it counts. What neither reaches is stated as such. This is the ruling behind the doors, the kernel, the C boundary, the exec token and the check script (`04-derivation.md` sections 0.1 and 1.2).
- **Two write rules, each from its premise.** A door writes the whole buffer, because a text's provenance may be incomplete — the context-free case — so nothing less is known to suffice. A dereference writes the buffer when the object dereferenced is pending, because the object needed is known; when it is written already, nothing is written. Dropping a string's provenance inside the evaluator writes nothing, since the text cannot leave or be dereferenced without meeting one of the two rules. *Derived* by ablation (`05-validation.md` section 4) from what the earlier per-builtin flushes had rested on: the context law, which the total write at the doors superseded.
- *Derived:* the Builder is an escape; no store view or decorator (`04-derivation.md` section 1.1).
- *Derived:* the impure evaluation root is a coherent union and keeps master's naming rule under a stated precondition; the general union uses the three-case rule (section 8.4).
- *Derived:* `filter` takes a prefix-closed set; a predicate induces one by the pruning walk (section 7.1).
- *Derived:* the union is defined top-down, as an overlay is; a pointwise definition is not a tree at a file-versus-directory collision (section 7.1). The collision is aligned with the meaning silently — the earlier child shadows where master throws — unobservable on master's only union under the coherence precondition of 8.4.
- *Derived:* the accessor interface is unchanged; the naming query already exists. The graft naming rule is replaced by the derived one (section 8.2).
- *Derived:* the vanilla git leaf names subtrees by object identifier, which turns master's existing `sourcePathToHash` memo into the subtree memo with no new domain; attribute-dependent variants keep the input-level name (sections 8.2 and 9.3).
- *Derived:* the filtering accessor names itself from its prefix-closed accepted set, and `fetchToStore` stops treating a filter as uncacheable (`fetch-to-store.cc:64-65` on master).
- *Derived:* mounts add and never replace; allow prefixes are added and never withdrawn (section 2.2).
- *Found:* master cannot list the store directory in impure evaluation (the store accessor's root throws); the branch makes it listable, so the intended difference is from an error to the meaning's listing (section 5; `tests/functional/mounted-inputs-listed.sh`).

**The naming of sources and the one address.**

- **Every source is named by its object hash under the git method, with no setting** (section 9.9). *Reason:* the evaluator's filesystem work is naming and transforming fetched trees, which the compositional address makes proportional to the change; a setting choosing between two naming functions would be the parallel implementation the direction below refuses. *Derived from the renaming check:* a `sha256` given to `builtins.path` or `fetchTarball` asserts the NAR hash rather than naming the flat address, and the pinned fast paths find a present tree through the memoised bijection of section 2.4, so a pinned fetch after an unpinned one adds nothing, as on master. *Consequence:* every source's path and everything built from one changes; a binary cache holding a source under its earlier path does not serve it under the new one (the release's blast radius, `doc/manual/rl-next/one-address.md`).
- **SHA-256** (section 9.9, "The algorithm"). *Reason:* a store path is a name substitution trusts, and SHA-1's collision resistance is broken. *Consequence:* a SHA-1 repository's objects have no SHA-256 identifiers until read; the tree is hashed once per object and memoised under its SHA-1 name thereafter.
- **Sources with references keep the NAR path form** (section 9.9), since the path form with references exists only for that method; whether the git form should admit references is open (section 13).
- **One address: the store's content hash is the object hash; old flat hashes are read through a shim and never written as a name** (section 9.11). *Reason:* consolidating and simplifying the implementation cannot be done by building out parallel implementations, and the store's hash should be the tree's; the shim is acceptance of old assertions, not a second name. The decisions of section 9.11: (a) the `nar` value goes, not stays as a switch; (b) the object hash is the root entry with its mode inside a synthetic tree for a bare executable or symlink, rendered `fixed:git:sha256:<id>` for every root kind; (c) the lock file is version 8 with `treeHash`, `narHash` not written, versions 5 to 7 read through the shim; (d) the narinfo publishes both hashes, the protocols negotiate, JSON version 4; (e) `outputHashMode = "recursive"` and every hash nixpkgs records under it are untouched; (f) the shim is on by default and has no switch to turn on, only `nix store migrate` to finish. *Consequences:* (C1) becomes equality up to renaming for everything downstream of a source; the database schema is 11 and an older Nix refuses the store; an older Nix refuses a lock with `treeHash` or version 8; an older client pays one walk per query for the NAR hash it must be sent; a version-1 signature on a locally held path whose row is migrated is verified by one walk of the path (the derived entry below, *a version-1 signature is checked on the stream*).
- **The git method is stable.** The `git-hashing` experimental feature is removed, with a stabilisation notice in the settings' documentation; `outputHashMode = "git"` on a derivation and the readers of git object streams are ungated. *Reason:* a method that names every store object and every source cannot be optional. Read as stable, not as a change of the fixed-output default: `outputHashMode` still defaults to `flat`.
- **The git method is SHA-256 only.** Refused, with one message naming the remedy (`nix hash path --mode git`), at every entry that creates a git-addressed object, name or derivation output: instantiation of a fixed, floating or impure derivation with `outputHashMode = "git"` and another algorithm (`primops.cc`), `nix store add --mode git --hash-algo sha1` and its dry run, `nix hash path --mode git --algo sha1`, the daemon's `addToStoreFromDump`, a binary cache's upload, the import of a description under the SHA-1 form, and the build of a derivation that names the form (`checkIngestionAlgorithm`, `src/libutil/include/nix/util/file-content-address.hh`). The hasher's algorithm parameter is gone, for the structural fact: no algorithm can be passed to the hasher, so "the git method is SHA-256" is a property of the types and not of eight guards' agreement. *Derived — old data:* what **reads** a description an older Nix made under the SHA-1 form tolerates it: `ContentAddress::parse` and the derivation readers accept `git:sha1`, and `makeFixedOutputPath` still names the form. *Reason:* the collector calls `queryPathInfo` on every path it visits (`gc.cc`, `topoSortPaths`), whose row reader parses the `ca` column (`local-store.cc`, `queryPathInfoUncached`), and under `ca-derivations` it reads every derivation it visits (`store-api.cc`, `queryPartialDerivationOutputMap` → `readInvalidDerivation`, whose fixed-output check computes the path with `makeFixedOutputPath`); `nix-store --verify` reads every row likewise; a refusal in either reader would stop `nix-collect-garbage` and `nix-store --verify` on a store holding one such row or derivation. Pinned by `ContentAddress.sha1GitFormIsReadable`, `DerivationAtermTest.sha1GitFixedOutputReads`, `LocalStoreObjectsTest.sha1GitRowIsReadVerifiedAndCollected` and `git-hashing/simple-sha1.sh`'s planted-row block, each shown to fail under the rejected parser-refusal design by mutation (`05-validation.md` section 4). *Consequences:* a path an older Nix made under the form stays valid, is verified by its object hash, collected, exported and imported (`--export | --import` asserts no content address) and shown by `nix path-info`; it cannot be copied into a **local** store of this Nix (`nix copy`, substitution), whose check of the address it cannot pass, with the remedy in the message; a binary cache accepts it and a local store of this Nix then refuses it at substitution; a `.drv` naming the form is read and shown and refused when built. Recorded in `doc/manual/rl-next/one-address.md`.
- *Derived, awaiting confirmation:* **older peers need `git-hashing` for git-named sources.** Master parses `fixed:git:` only under its `git-hashing` experimental feature (master's `src/libstore/content-address.cc`, the `Xp::GitHashing` check in the parser), reached from the worker-protocol reader, the narinfo parser and the daemon's `AddToStore`; the branch names every source that way. So a released Nix refuses a new daemon's or a new cache's description of a source, and a new client's `builtins.path`/`fetchTree`/`path:` input to an old daemon, with `experimental Nix feature 'git-hashing' is disabled; add '--extra-experimental-features git-hashing' to enable it` — confirmed by run against a binary built from master in all three directions. Nothing in new code changes an old binary; the decision is to accept, state the exact requirement and message in the release note (`one-address.md`, *Older peers and git-named sources*), and pin both directions in `tests/functional/object-hash.sh`, without the feature and with it. The alternative — naming sources under the NAR method again for compatibility — is the second naming this section refuses (section 13).

**The object store.**

- **The store's object store: git objects under SHA-256** (section 9.10). One blob store; libgit2's SHA-256 object format; the executable bit on the edge, two leaves that differ in it never sharing an inode; `.links` and the optimisation pass dissolve into the object store; the tarball cache becomes SHA-256 so that fetched trees carry the store's identifiers. *Rejected alternative:* the existing `.links` table consulted at ingestion under its old key, the NAR hash of the one-file tree; section 9.10 ("Why a table under the old key was considered first, and why it was wrong") says why its grounds did not hold.
- **libgit2 2.0.0-rc.1 with the changes of NixOS/nix PR 16427:** strict hash verification off on reads, no delta search when unpacking into the tarball cache, the `pack.window`/`bigFileThreshold` configuration fix, and the zlib-ng patch. *Consequence:* a blob read from a fetcher's object database is not re-hashed by libgit2, so whoever enters it verifies it (section 9.10, law 1).
- **No compression setting: the pack builder decides per object.** Whether zlib bails out early on incompressible content was checked: it does not — deflate at any level above 0 runs its match finder over every byte and only afterwards emits a stored block for what did not shrink (`deflate.c`, `configuration_table` and `deflate()`'s dispatch; `trees.c`, `_tr_flush_block`'s `stored_len + 4 <= opt_lenb`; zlib-ng's `deflate_quick`/`deflate_medium` are faster implementations of the same contract), so incompressible input costs the full work and saves nothing. libgit2 compresses every pack object through one `git_zstream` it resets per object (`pack-objects.c`, `write_object`), so the decision can be made per object and cheaply. The fourth patch (`packaging/patches/0004-pack-compression-heuristic.patch`): before each object is written, 4096 bytes of it, in eight 512-byte slices spread from its start to its end, are deflated at zlib's fastest level through a second stream kept for the purpose; the object is deflated at zlib's default when the sample shrinks by 5 % or more and stored (level 0) otherwise; an object no longer than the sample is always deflated, since the probe would cost as much as the deflation it decides and deflate's stored-block fallback bounds the loss to a few bytes. *Rejected alternative:* a fetcher setting supplying a compression level, measured: nothing gained and two and a half times the unpacking time for incompressible content against a 60 % smaller cache for source text [unverified: measured during the work; the run is not in the tree] — and there should be no settings. Checked by `GitUtilsTest.packsStoreWhatWouldNotShrink` (a 4 MB pseudo-random blob is written with the level-0 zlib header and within 1 % of its size; a 4 MB text blob with the default header and under half).
- **The object store is unconditional, and the decision comes before the write.** `auto-optimise-store` has no meaning: every local store enters every path, and `nix-store --optimise` remains as the migration of an older store's paths and the removal of `.links`. *Reason:* sharing identical files is what a local store is, not a mode; and a measured slowdown of the write-then-link discipline — which decides after the bytes are on disk and must undo a write on every hit, three and a half times the write on APFS [unverified: measured during the work; the run is not in the tree] — had no reason to be paid: the store's composite decides before the write (section 9.10; the mechanism, its limit and its measurement are `04-derivation.md` section 1.7).
- *Derived:* **`auto-optimise-store` is accepted and ignored with one warning**, from `nix.conf` and the command line (`RemovedSetting`), for `true` alone — `false`, which the build hook hands its child for every setting, is silent — and once per top-level process: the hook child, which re-reads the configuration in `initNix()`, warns nothing (`Settings::configurationDiagnosedByParent`, set by `main.cc` before the configuration is loaded; every other `nix` process is its own top-level process from the user's view). *Reason:* the release note promises a warning, and a flag that had become an error broke it; the second warning of a `nix-build` was located by run in the child's own configuration read, not in the hand-off. *Where it appears* follows the repository's convention (`excludedFromFullSerialisation`, as `DeprecatedWarnSetting` has it): out of `nix config show`'s key=value dump, which is the effective configuration; in the JSON, which is the registry the manual's settings page is generated from; and by name. Pinned by `tests/functional/optimise-store.sh`.
- **Both fingerprints are signed where both hashes are known** (section 9.11, *Signatures*): `nix store sign` signs version 2 whenever the description carries an object hash and version 1 whenever the NAR size is known, the NAR hash asserted or computed by one walk; the binary cache's upload signs both; signing at build is version 2 only. *Reason:* an older client verifies version 1 alone and counts only the signatures it can verify, so a cache carrying version 2 alone was refused under `require-sigs`. *Consequence:* a build-signed path copied into a keyless cache carries version 2 alone until `nix store sign` runs on the cache; the release note says so.
- *Derived:* **a version-1 signature is checked on the stream when the description asserts no NAR hash.** `addToStore(info, source)` restores such a path, hashes it on the tee and makes the same check with the stream's hash in the assertion's place, removing the path when it fails; nothing is registered before the check. `nix store verify` and `copy-sigs` walk a path once for a trusted key's version-1 signature that version 2 does not verify. *Reason:* without it every path substituted from a NAR-hash-only cache is untrusted once stored, and `nix copy` of it to a `require-sigs` daemon is refused. *Stated cost:* untrusted bytes reach the disk before the refusal; the path's files are removed at once (`deletePath`, `local-store.cc`), and the blobs and trees the restore entered stay in `.objects` until the next whole-store collection sweeps them.
- **The object store is swept on whole-store collections only.** `nix store delete` removes the path; its objects are reclaimed at the next `nix-store --gc`, and the collector says so. *Reason:* the sweep is O(store) and every specific delete paid it.
- **`max-free` counts the bytes a deletion frees on the disk.** Under the unconditional object store every regular file of a store path is one of at least two links, so a path whose files are shared with other live paths frees nothing when it is deleted, and the collector's limit (`max-free`, `--max-freed`) is crossed later than an unshared store would cross it; the blobs are reclaimed at the next whole-store sweep. Found by `gc-auto.sh` on Linux: three copies of one script went in one round where one was meant to remain. *Derived, not chosen:* `deletePath` credits a file at one or two links (`src/libutil/unix/file-system.cc`), which is the physical truth; a logical accounting that credits a shared file on every deletion would overstate, and is rejected. *Consequence:* `nix store delete` says that the bytes it counts as freed and the object store still holds are reclaimed at the next `nix-store --gc` (a conditional-credit alternative was measured at about sixteen lines and not taken).
- *Derived:* **a live root without an object keeps nothing beneath it and does not stop the sweep** (section 9.10, law 5). *Rejected alternative:* abandoning the removal phase on a missing live root, as a corrupt tree does — the semantics, re-derived and checked by run, showed that rule to be the steady state of every upgraded, `--load-db` and `min-free` store, reclaiming nothing from `.objects` until an operator's `--optimise`. What tolerating could lose was enumerated case by case before the code: trees are written bottom-up and swept as a set, regular-file blobs are held by their paths' links, and the orphans — symlink-target blobs, subtrees an interrupted repair or `ENOSPC` left — are re-entered by `--optimise` and read by nothing. The corrupt-tree gate stands. The sweep counts valid paths without an object apart from the trees a present tree names, and says "object", since a plain file's is a blob.
- *Derived:* **the ingestion's `autoGC()` runs before the restore**, master's order (`local-store.cc`); between the restore and the registration, inside the window, the first add that triggered `min-free` swept its own trees. Not a race but a call order. And after the validity check where one precedes the restore: the in-memory route of `addToStoreFromDump` knows the path's name before it writes, so an add whose path is valid already runs no collection (`LocalStoreAutoGCTest.inMemoryAddOfAValidPathRunsNoCollection`); the spilled route learns the name from the restored tree and pays the check whatever the outcome.
- *Derived:* **the collector removes a legacy `.links` directory at every whole-store collection.** Master unlinked its dead entries every collection; one deleter, `removeLegacyLinks`, for the collection and for `--optimise`; every entry is a hard link to a file a store path also links or a dead one, so nothing is lost.
- *Derived:* **`nix-store --optimise` writes an older row's object hash and reports what it entered.** An older row is migrated by the verified walk first (`walkOldRow`, the entry below) and the path then entered by the on-disk walk; `recordObjectHash` is the one write, shared with `migratedPathInfo`; a report of all zeros is a no-op, and a migration says how many files it entered and rows it wrote.
- *Derived:* **a schema-10 row's migration checks the NAR hash the row asserts, and never writes the column from bytes that fail it** (section 9.11, *The database*). The question first: what must every reader see when the bytes do not hash to the row's assertion? Master returned the row on every query and left the corruption to `--verify --check-contents`, `nix store verify` and `--verify-path`; the collector queries every path it visits, so a query must not throw; and an info with `assertedNarHash` and no object hash is the shape every reader already handles (a schema-10 row before its first query, an old peer's description). So: the walk hashes the NAR on a tee (`walkOldRow`, as `--load-db` checks a registration) and on a mismatch writes nothing; the row is answered as the database has it; the verifiers report "was modified" through the NAR hash with master's remedy; `nix store migrate` counts the path failed naming both hashes; `nix-store --optimise` migrates an older row by the same verified walk before entering it (an older path read twice there, once to migrate and once to enter; a row this Nix wrote is read once) and does not enter a modified one. Writing the walk's hash would bless the corruption for every later check.
- *Derived:* **a schema-10 row whose files are gone is answered from the database and belongs to `nix-store --verify`.** The row is valid and its files are missing — the state master's `--verify` (without `--check-contents`) finds and removes ("disappeared, removing from database"), and master answered every query from the row. So the migration returns the row as read when the directory is absent or a file of it is (`ENOENT`) while the row is valid; `nix store migrate` and `--optimise` report it naming `nix-store --verify`; a row that is gone is still `InvalidPath`, the collector's doing. The collector's `unmigrated` note names both commands that migrate rows and the verifier for what they cannot.
- *Derived:* **the collector reads a dead row without migrating it.** The collector's dead set needs a row's references (`topoSortPaths`) and, under `keep-derivations`, an output's deriver — row fields both — so it reads those rows as the database has them (`queryPathInfoUnmigrated`, `topoSortPathsBy`, `gc.cc`) and a schema-10 row on its way to deletion is not walked first; the live rows its closure reaches are still migrated by `computeFSClosure`'s queries, which is right, since they are kept. *Reason:* the migration reads and hashes every byte of the path (`walkOldRow`), so the first collection of an upgraded or `--load-db` store paid a walk of its whole garbage before deleting it (800 MB dead path: 0.71 s against 0.15 s, `05-validation.md` section 6). *Consequence:* none to the laws — the row is deleted; a dead path the serialising walk would refuse (an unsupported file type) is now deleted where the collection failed before. Pinned by `LocalStoreObjectsTest.deadSchema10RowIsDeletedWithoutAWalk`.
- *Derived:* **a `path:` input outside the store is named first and copied only when the store lacks the tree.** `PathInputScheme::getAccessor` (`path.cc`) hashes the tree by one walk (`objectHashOf` over the filesystem accessor; a filesystem path has no fingerprint, so no memo answers and every byte is read, `04` section 1.5), takes a root on the name and copies — the dump, the restore, the links — only when `isValidPath` says the store lacks it. *Reason:* master and the branch dumped and restored a `path:` input on every evaluation whenever the path was not itself a valid `-source` store path — the local-development pattern `inputs.x.url = "path:../x"`, and a flake evaluated as `path:<dir>`; the copy of an unchanged tree was the whole of that cost. *Consequence:* a miss pays the naming walk and the copy, two reads of the tree; the window between the naming and the copy is every `builtins.path`'s (a tree edited meanwhile is copied as it then is, and the add computes the address from what it writes); `lastModified` is the same tracked walk's mtime as the dump's. Pinned by `tests/functional/flakes/path-input-copies-once.sh`; the release note is `doc/manual/rl-next/path-input-copies-once.md`.
- *Derived:* **a temporary under `.objects/tmp` ages by the second in its name**, since a temporary link's inode is a blob's, whose change time every later link advances; the temporary pass runs before the blob pass so the blob a stale link pinned goes in the same sweep. *Stated:* law 3's fourth exception — a file `place` could not enter for `ENOSPC` on a full directory index, handled as the first (`EMLINK`, the link limit) is — leaves no mark, so the verifier reports it and `--repair` tries again; unverifiable without a full directory index.
- *Derived:* **the local overlay store's object store is not its own** (by reading, Linux's). Its store directory is a merged mount, so `.objects` and `.links` under it show the lower store's too, and every write through it lands in the upper layer — an unlink of a lower file a whiteout, a repair a copy-up. The overlay's contract (a read-only, shared lower) requires the object-store operations to apply to the upper layer alone or not run; they do not run (`LocalStore::ownsObjectStore`, false for the overlay: no sweep, no `.links` removal, no object check or repair; the object hash still recomputed and compared). *Cost stated:* the upper layer's own objects are not reclaimed until a sweep over the upper layer alone is built — owed with the `local-overlay-store` suite (`05-validation.md` section 7).
- **The copy of a tree the store holds is made from the store's own objects** (section 9.10, *One route*; 2026-09-17). `fetchToStore2`'s copy, under the git method and into a local store that owns its object store, materialises every directory the naming's memo names and the store holds from its tree body and blob files — `mkdirat`, `linkat`, `symlinkat` — and reads from the accessor only a subtree the store lacks (`LocalStore::materialise`, `MaterialisingVisitor`). *Reason:* the one route paid a dump, a parse, a SHA-256 and libgit2's attribute lookup per unchanged file to reach a decision — "does the store hold this blob?" — that the store's tree bodies already answer; the naming is proportional to the change and the copy was not (section 13, as it stood). *What is kept:* every law of 9.10 — law 2 gains the route, checked by dumping the path back; law 3 by construction, each file the blob's link; law 4 by verifying each tree body on read; law 5 untouched — and every invariant of `08` (K15 states the new one). *What is trusted:* a blob's file as K8 trusts an inode that is a blob's, re-hashed under `--repair` alone (the route has no measure of the file but the store's own); the memo's answers, within the memo's own window. *Consequences:* the copy stays proportional to the number of files, in `linkat`, with a smaller constant (`05` section 6); a fresh tree pays one memo lookup and one `stat` per directory the one route did not; a file inside a directory the store lacks is read as before; the daemon, the overlay store and Windows keep the one route (`materialisesFromObjects`, the one predicate). *Derived:* proportional to the change would still need shared directory entries, which no in-scope filesystem gives without changing what a store path is on disk (section 13).
- **Windows is by inspection only:** the object store shares nothing there, since the `*at` calls the two operations rest on have no counterpart; no Windows build or run has checked it (section 13).

## 13. Open, and outside this specification

Each item: what the code does today, what closing it would take, and the recommendation the work leaves. Nothing here is built. Everything else in section 10 is decided and is not reopened by this list.

- **The concurrent window X1** (`08-store-model.md` section 1.5). A collector in another process — another process's `nix-store --gc`, the builder's asynchronous `autoGC(false)` — can take an in-flight ingestion's trees and symlink-target blobs between its restore and its registration, and `nix-store --optimise`, which takes no GC lock, has the same window for the trees it writes; the path is then registered naming a tree the store lacks, reported by every collection and by `--verify --check-contents`, and re-entered by `--optimise` (section 9.10, law 4's second false-by-design case; law 5 sweeps on). Closing it exactly — a shared/exclusive lock on `.objects`, held shared from an ingestion's first object write to its registration and exclusive by the sweep, about thirty lines [estimated] — would make the sweep wait on in-flight ingestions and stall new ones for its duration; a change-time grace on tree files is the grace section 9.10 excludes. *Recommendation:* leave it accepted and stated, since the tolerant sweep made the consequence a report line and one re-entry; the interleaving test that would pin the consequence under the race is owed (`05-validation.md` section 7).
- **Older peers and git-named sources.** An older Nix parses `fixed:git:` only under its `git-hashing` experimental feature, and every source this Nix adds is named under that method (section 9.9), so an older client reading such a path's description from a new daemon or from a cache this Nix wrote, and an older daemon receiving one from a new client, refuse it with `experimental Nix feature 'git-hashing' is disabled` unless the older side sets the feature; pinned in both directions, without the feature and with it, by `tests/functional/object-hash.sh`. Nothing in new code changes what an older binary accepts; operators of mixed fleets set `extra-experimental-features = git-hashing` on the older side, and the release note (`doc/manual/rl-next/one-address.md`) states the requirement and the message. The only alternative is naming sources under the NAR method again for the transition, the second naming section 9.11 refuses. *Recommendation:* accept; it is the release's blast radius, already stated for the store paths themselves.
- **Sources with references** stay on the NAR path form, since the path form with references exists only for that method (sections 9.9 and 9.11; the store's column still holds the object hash for such a path, only its *name* is the NAR form). Admitting references under the git method would be a new type string no released Nix parses — a wire and format change every peer and cache would have to learn before such a path could be copied to it — for one rule instead of two in `primops.cc` and a `treeHash` assertion on a rare kind of source. *Recommendation:* leave it; revisit only as its own specification step with both protocol directions tested.
- **A copy proportional to the change, not to the tree.** The copy of an edited checkout is now made from the store's own objects for every directory the store holds (section 9.10, *One route*; section 10, 2026-09-17): per unchanged file an `fstatat` and a `linkat`, nothing read or hashed, the constant of `05-validation.md` section 6. It stays proportional to the number of files, in `linkat`. O(change) needs the unchanged *directories* shared, which hard links cannot do: a directory clone where the filesystem offers one is platform-specific and a copy-on-write of bytes, not a sharing of the tree, so the invariant "every regular file is the object store's file" would need restating per filesystem; a store whose path is a view of objects changes what a store path *is* for every observer, builders included. Both are outside this specification. *Recommendation:* accept the remaining constant; a finer fallback than the named subtree (one file re-read from the accessor where one blob is missing, rather than the subtree) is the small step left inside the route, not taken since only a corrupt or swept object reaches it.
