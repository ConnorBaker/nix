# Preserving identities and reducing ingestion work

The measured runtime is `5d323262ac0075a5037bba7e4f0061c273182bd3`. Its complete optimized comparison against branch base `8aad447f0bace6be413963e897ad690247ad6aa2` passes all 156 outputs and eighteen complete store comparisons. All nine separate wall medians and median paired ratios are lower, with 72/75 faster pairs, but CPU medians rise in three cases and RSS in six. The direct comparison against a989 has 39/75 faster wall pairs, four higher median paired wall ratios and four higher CPU and RSS medians. These mixed results establish no overall improvement over a989. Profiles and syscall evidence retain their recorded revision boundaries; the 5d syscall diagnostic below does not establish a reduction in kernel work.

The pinned input is Nixpkgs `6aefcda9401be8acc2b74244fb3b37520ea1f0a8`, on aarch64 Linux. The [driver](runs/nixpkgs-evaluation.py) records commands, binaries, environment, resources and every sample. Cold means fresh private stores and fetcher caches, with warm operating-system caches; GitHub cold timings include network access. Before timing, every local source node is checked against the pinned raw Git tree for bytes, executable bits, symlink targets and complete membership. Git status flags and attribute-normalized comparisons cannot substitute for that check.

## Implementation and semantic boundaries

The question is whether evaluations can produce the same abstract store and results with less work. The [specification](01-specification.md), [derivation](04-derivation.md) and [store model](08-store-model.md) define that meaning. The [design guidance](/home/connorbaker/ExtPackages/denotational-design/reasoning-and-design-guidance.md) requires each representation change to preserve its operations, including failures, effects and ownership. The tests below can reject an implementation; they are not a formal proof.

| Boundary | Required meaning and resulting implementation |
| --- | --- |
| Canonical object → accessor | `getKnownEntry` supplies the SHA-256 entry and mode of the rendered object. The canonical tarball writer supplies this fact; arbitrary SHA-256 Git repositories do not, because raw modes, gitlinks and transformations can render another tree. Executable and symlink store roots retain their synthetic wrapper. Registered content hashes can name store views; input-addressed paths and unregistered views cannot. Repair bypasses known entries and naming caches. |
| Git metadata → live files | The libgit2 patch skips ignore rules only for tracked-only diffs, retaining traversal, stat/content comparisons, attributes, modes and conflicts. A clean status or reported revision does not name raw worktree bytes: index flags can suppress comparisons and attributes can normalize content. Worktrees remain filesystem sources. Export-ignore and LFS views decline revision-only names because external attributes affect them. |
| Immutable metadata → ownership | Git listings retain their parsed tree and borrow sibling entries. Optional sizes do not require packed-object header reads before lookup or read; reads still announce size. Workdir accessors retain existing immutable tracked membership while reading live bytes. Repository-owned locking encloses attribute lookup/interpretation, including status; accessor state precedes this lock, while network and raw immutable-object reads remain outside it. |
| Source name → cached address | The description key contains current view fingerprint, canonical relative path, address method, logical store directory, output name and recursive decoding policy. Its hash/path value claims no destination presence and retains neither accessor nor store. Unnamed views bypass it. Whole-view memo entries retire with that name; independently named Git objects permit recursive reuse. Every copy roots and checks its requested destination. |
| Accessor cache → observations | Optional fingerprints, positive metadata and links are cached within one generation; reads and listings remain live. Missing names differ from missing nodes. Invalidation replaces the generation after child invalidation, even when it throws, so in-flight observations cannot repopulate the successor. Admission growth and accessor identity do not establish byte identity. |
| Fetched input → namespace | A fetched input owns its mounted prefix. Outside explicit grafts, the impure host/store union remains fallback. Descendant bindings imply directory ancestors, replacing absent or nondirectory ancestors without leaking displaced symlink targets. Structural queries need no discarded fallback observations; unchanged subtrees delegate directly. Names use `graft-v2`. Existing imported values/search results keep their evaluation epoch until explicit reset; shell package metadata comes from the execution store. |
| Composite view → callbacks | A forwarded operation retains its selected child, and any policy/cache/layer state used during or after callbacks. Compound stat, directory, symlink-resolution and dump operations retain their shared owner. Stack-scoped views remain borrowed only within their callback. Allow-list naming unlocks after monotone admission; mounted invalidation snapshots owned children before calling them, so reentrant new mounts belong to the next invalidation. No new content cache is introduced. |
| Mutable path → ingestion | An empty store permits one hash-and-materialise traversal without spooling/replay. A populated store first names the source so a valid destination can avoid staging. On a miss, ingestion names the bytes actually copied; a prior observation does not freeze them. Final validity remains checked under the ordinary destination lock, including after concurrent registration. |
| Regular file → destination | A producer-supplied immutable blob identity permits holder lookup before reading and direct streaming on a miss, with complete size framing checked. Otherwise bytes are hashed. A complete bounded root buffer supplies its address before staging; only a miss or repair needs a hold and temporary file. A fresh writer accepts an already complete bounded buffer directly, without another buffering layer; callbacks still observe complete bytes and canonical metadata. A spill starts ordinary staging when bytes must be written. Small resident streams use one dependency worker; external/unknown streams retain parallelism. Flat/text and NAR checks hash incoming bytes rather than rereading files. |
| Directory → ordered work | Parallelism requires source permission, the stateless `AllPaths` filter and separate callback permission. Otherwise traversal and filter effects remain depth-first on the caller. One bounded pool keeps singletons inline, falls back inline when full, and helps only its own child jobs while joining. Every accepted child finishes before its directory/accessor/sink scope ends, including on error. |
| Copy scope → representation | C++ scopes save/restore only the current sink and optional physical name. Deferred visits borrow shared directory context; a child owns one physical spelling and retains its logical prefix length. Each copy group borrows its enclosing callback and retains indexed failures. It joins accepted visits before folding their completed values in traversal order; visits and their results must not depend on that fold. Incremental and one-shot object hashing use the supported SHA-256 algorithm without unused generic buffering. Parents retain only each child's entry and optional NAR size; encoded directory bodies end at hashing/publication. Known child spellings extend their canonical parent directly. Owned logical names move into the tree after their visits. The push adapter borrows callbacks from live directory calls, preserving both their address during recursion and their state across siblings. |
| Pending text → completed obligation | A rooted valid object discharges an ordinary write; repair and later repair upgrades remain pending. Both producers still verify mounted opaque references before enqueueing, including before automatic threshold flush. Successful flush requires every pending write to succeed; keep-going cannot let absent paths escape. Text addresses include references. Valid objects need no retained body/reference-order scan; blob hashing occurs only for writes. |
| Completed files → pending holders | The first completed canonical file claims the object/mode key atomically; another worker that previously missed must link to that winner. Rows remain private in lazily allocated shards until each path completes. One set owns the first completed row and projects its active identifier bytes and executable bit; no second encoded key or queue is retained. Hash tags and inactive bytes remain data in that first row. The compiled tests enumerate all 65 hash lengths, 64 byte positions and 256 byte values, with mode/tag factors checked separately. |
| Ingestion → publication | Direct registration inserts the complete pending projection with validity. `endIngestion` hands off completed builder outputs or publishes already-valid repair/optimisation paths. There is no background writer or incremental flush. `Blobs` uses its complete `(id, exec, ingestion)` key without an additional rowid; the migration preserves all seven columns, including invisible candidates. SQLite's writer reservation encloses reconciliation before candidate visibility. Completed outputs retain separate ingestion identities under one hold; overlapping writers own strong leases. |
| Store description → caches | A full-path description must match its key. A hash-indexed cache can admit matching-hash canonical metadata even when a requested name differs, but an exact-path miss proves no hash-wide absence. Only a missing binary-cache `hash.narinfo` supplies that negative. Binary validity reads/parses metadata; corruption propagates. Local/overlay registration rejects mismatched keys before effects. Validity publication follows commit; remote completion and binary alias publication invalidate stale observations. |
| Evaluator arena → owners | Arena expressions borrow sources retained once by the arena. Parse thunks use that arena; cached failed values borrow evaluator-owned exceptions, while escaped C++ exceptions retain independent source positions. Growing parser containers use the existing owned pool; parse failure and discarded merges release storage. Optional inherited-source storage is allocated only when present, and migrated before nonthrowing replacement. No GC-timing workaround is needed to close stores. |
| Auxiliary object → lifetime | An already-held object needs no temporary-name allocation; a newly published temporary remains its protecting link in the locked hold, including across repair replacement. Auxiliary directories are created only when used, with 256 identifier shards. Exact permissions precede optional fsync; unobservable auxiliary timestamps need no update, while regular holders remain canonical. Views share one lease owning the hold directory, descriptor, lock reference and shard flags; their pending rows and ingestion identities remain separate. POSIX hold-side operations use that descriptor, and the last view cleans up under namespace exclusion; dead holds use general cleanup. Fresh names are claimed exclusively, including after PID reuse. |
| Auxiliary namespace → collection | Publication/acquisition and final hold release take the shared namespace lock; sweep holds its exclusive lock from snapshot through deletion. This protects replacement inodes and newer registrations. Extending that lock across an entire ingestion or general store GC would prevent required progress. One file per auxiliary tree remains; no packed-tree representation is claimed. |
| SQLite connection → WAL locks | Filesystem detection opens no independent shared-memory descriptor in the parent. Only ZFS invokes the syncing helper. Closing such a descriptor cancels that process's POSIX locks on the inode, allowing another connection to truncate a still-mapped WAL index. The primary connection uses its existing `_state` mutex without a second connection mutex. |

A reusable regular holder must have canonical permissions (`0444` or `0555`), mtime `1s + 0ns`, and matching device, inode and size; repair also checks bytes. Content equality alone is insufficient because a hard link propagates physical metadata. Invalid candidates are forgotten without modifying store-path files. A refused link must not promote an exceptional donor.

Reuse records the recipient's own witness, so collecting a donor cannot erase it. Complete re-ingestion replaces the path's entire previous projection, including an empty projection. Candidate selection orders physical inode classes before ingestion identities. Collision reconciliation performs the necessary physical alias walk before publication; candidate metadata cannot replace that sharing law. A speculative directory's rows stay isolated until it succeeds; merge errors after publication abort and join the whole copy, rather than rolling back exposed claims and falling back.

## Completed request reuse and holder selection

A completed request is an operation-history fact, not a content fingerprint. The evaluator key contains resolved source path/accessor, method and output name. Filtered, asserted, reference-bearing and repair requests bypass it; reused copies still root/check their destination. Mounting or explicit reset replaces the generation, including exceptional invalidation. It supplies no new identity to mutable accessors.

This distinction is externally checked. A rejected generic regular-entry cache returned stale `AAA` after `builtins.exec` synchronously changed a same-sized source to `BBB` and a second copy used another name. Branch base returned `BBB`. The [rejected candidate](/home/connorbaker/Benchmarks/nix-performance-fixes/rejected-regular-entry-cache-e470a5169/ANALYSIS.md) and [restored public counterexample](/home/connorbaker/Benchmarks/nix-performance-fixes/evaluator-request-counterexample-restored-e470a5169/README.md) retain exact source/binary/output evidence. Successful prior reads and callback-generation guards did not establish the missing cross-operation identity.

Holder lookup independently folds the least eligible signed `(device, inode, ingestion)` cursor from SQLite rows, preserving the exact relation and cursor order without another index/cache. The pinned query plan drops from 69 to 51 VM operations and avoids opening a sorter on a miss. Combined source phases and performance bundles do not isolate the fold's elapsed benefit.

## Remaining cost, measured separately

Auxiliary bodies remain necessary: sweep follows tree edges, materialisation reads names/modes/identifiers, and verification reports missing trees. Root hashes and regular-holder rows cannot recover adjacency, empty directories or symlink targets. The [source-only representation analysis](/home/connorbaker/Benchmarks/nix-performance-fixes/auxiliary-representation-e77d0c12e/README.md) distinguishes this required body/claim relation from the current file-per-body layout (manifest `2987a955007fe287b1aaa1d2dc7b6dd26aa4a64ad6190cc6dcef1a93c4ff62cc`). Auxiliary inodes have no regular-holder sharing law; changing their layout would still have to preserve publication, repair, live claims, collection, read-only/legacy and overlay behavior, including the existing filesystem-facing API. No replacement is designed or proved. A hold-wide namespace shared lock remains rejected: [addMultipleToStore](../../src/libstore/local-store.cc) can retain its hold while a child waits for synchronous `autoGC`, whose [sweep](../../src/libstore/git-object-store.cc) needs the conflicting namespace lock.

The [6739 database-boundary review](/home/connorbaker/Benchmarks/nix-performance-fixes/auxiliary-database-boundary-6739a4955/README.md) identifies why the existing registration transaction is insufficient: completed auxiliary bodies can be reused before any containing path is valid, and live claims also protect acquisitions and repair replacements. Overlay GC consumes merged tree bodies even though overlay materialisation is disabled. SQLite can represent the relation, but changing only pending regular rows would lose these operations. These are source-derived schedules, not executed countertests; no replacement or speedup is established.

The warm `git+file:` comparison includes a correctness difference in naming. Branch base 8aad names a clean worktree by its reported revision and a dirty one by HEAD plus only status-reported changed/deleted paths, permitting persistent hash reuse. Both versions' accessors read filesystem bytes. Current [Git acquisition](../../src/libfetchers/git.cc) declines that identity: assume-unchanged/skip-worktree flags can suppress comparisons, clean filters can normalize unequal bytes, and mode/case policies and tracked-prefix replacements do not prove the rendered tree equals HEAD. Status supplies membership/dirtiness; its cached stats or filtered Git OIDs cannot supply the raw SHA-256 fold. Explicit commit accessors can reuse immutable object names when transformations preserve their meaning. The benchmark's external raw-tree census validates its fixture, not a production frozen-worktree guarantee.

The initial fold follows the current address representation: the tested URI asserts neither revision nor content hash; [mountInput](../../src/libexpr/paths.cc) names the rendered root, and `getFlake` reparses there before imports through `sourceInfo.outPath`. Public paths/contexts, `treeHash`, locks and later materialisation must agree. Omitting the fold locally changes observations; avoiding it requires a lawful separation of source-relative evaluation from the eventual address. This explains an obligation relative to base's cache assumption, not an impossibility theorem about warm Git CPU performance. The repository-open deletion measured in 3fed removes a separate acquisition; it does not remove this raw-tree naming obligation.
